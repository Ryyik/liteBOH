## 🔴 L1 也是误诊：超时层 2026-05 就下沉了

用户选了「L1 请求超时下沉」开工，调研第一步就推翻了前提。

**`src/utils/supabase-client.js:53` 的 `timeoutFetch`** 通过 `createClient({ global: { fetch } })`

报告原文的判据是 `grep "withTaskTimeout" src/` 只命中 2 个 ⇒ 推断「其余页面全没超时」。
**但超时不在页面层，在 client 层** —— 这个 grep 从方向上就找错地方了。

实测（`docs/demos/request-timeout-audit.mjs`，390×844，route 挂起 `/rest/v1/**` + `/rpc/**`）：

| 页面 | 时间线 |
| --- | --- |
| `/shop` | 0.8s→8.1s 骨架 18 → **8.7s 归零**，落静态兜底内容 |
| `/lotteries` | 骨架 15 → **7.5s 落错误态**（`--mode=abort`，等价超时已触发） |

原文说「4s 快照时全部停在骨架」—— **4s < 8s/15s 超时，当然还在骨架**。
⚠️ **通用教训：量超时行为时，观察窗口必须长于超时本身**，否则量到的是「还没到点」，
会被误读成「永不超时」。这类错误结论最有欺骗性 —— 截图、数字都真，只有推断错。

### 剩下两个真的打磨点（P3，加起来一天）

1. **抽奖页等待偏长**：`rpc` 是 POST ⇒ 吃 15s 写超时，失败后还走

   读路径的 RPC 应该按读超时算。
2. **`/shop` 静默降级**：8.7s 后显示静态兜底内容，**不提示「数据可能不是最新」**。

另有一个未查明项：`--mode=abort` 下错误态 7.5s 才落，期间发了 9 个请求（hang 模式下 3 个）⇒

`CommunityLotteries` 的 `nowTimer`（每秒 tick）与 `loadPityStatus` 两条线入手。

## 🔴 P3 抽奖项：尝试后**主动回滚**（别重试这条路）

目标：让超时可被上层识别，好让 `getCommunityLotteries` 跳过静态 fallback（省一次 8s）。

试了两版，两版都把 `/shop` 弄坏：

| 做法 | `/shop` 落点 | 请求数 |
| --- | --- | --- |
| 基线 | **8.8s** | 3 |
| `controller.abort(new DOMException(..., 'TimeoutError'))` | 13s+ 不落 | 5 |
| abort 保持裸调、在 catch 里抛自定义 `TimeoutError` | 13s+ 不落 | 5 |

⇒ **supabase-js 靠 `error.name === 'AbortError'` 判定「不重试」**。一旦把错误换成
`TimeoutError`，它按可重试处理 ⇒ 请求数翻倍、页面迟迟不落。省 8 秒不值得动这层，放弃。

⚠️ 通用教训：**改请求层的错误类型/abort 语义前，必须先做「改前改后」双跑对照**
（`git stash` 是最省事的办法）。只看「改后能跑」会漏掉「请求数变多」这种静默回归 ——
页面最终也能出结果，只是慢了一截，肉眼和单测都抓不到。

## 图库↔我 切换：底栏重播 + 白板 三根因（3160b30b）

用户连报两单：① 切图库「闪白 + 底栏刷新了一下」；② 点「我」整块空白。
用伪造 supabase 本地会话（`sb-<ref>-auth-token` + mock profiles 接口）走真点击流复现，
**伪 pinia 注入过不了 requiresLogin 守卫**（守卫 await initLoginState 会用真会话覆盖）——
以后测受保护路由的切换流直接走 localStorage 会话这条线。

三个根因 / 修法：
1. 底栏三处各自挂载 ⇒ 每次切换重播 760ms 滑入。会话级闩锁「只播一次」。
   ⚠️ 闩锁挂 window：dev 下 UserSpaceBottomNav 被相对路径与 @ 别名解析成
   **两个模块实例**，模块级变量各记各的（插桩实测）。
2. ProfileHomePanel 异步 chunk 无 loadingComponent ⇒ 首次进我页白板。
   新增 ProfileHomeSkeleton + delay:0；Cloud+ 空闲预热我页三件套。
3. **dev 大头**：样式就绪门 `areApplied()` 只认 `link[rel=stylesheet]`，
   而 vite dev 动态 CSS 是 `<style data-vite-dev-id>` ⇒ dev 判活恒 false，
   每次冷进我页白板 1s（90ms→1.2s 实测）。guard 加 `devStyleIds` 选项后 90ms 放行。
   prod 走 link 判活不受影响。

⚠️ 通用教训：这类「分段 tab 在、内容白板」先量
`getComputedStyle(host).visibility` 和 rows 数，一分钟定位；
「每页各自挂同一组件 + 组件内有 mount 动画」是重播感的标准成因。
