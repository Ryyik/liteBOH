## 自审发现并修掉的两个隐患（2026-11-01 下午）

### 隐患 1：`manualChunks` 用 `endsWith('.vue')` 只拆走了 JS，CSS 仍留在首屏
- **症状**：三个岛（ShareIsland / ContentDetailIsland / NotificationSuggestIsland）的 JS 已进路由 chunk，
  但 `share-island`(27 处) / `cdi-`(66 处) 仍留在首屏的 `ui-components.css` 里 —— 白拆一半。
- **根因**：SFC 的**样式子模块** id 是 `X.vue?vue&type=style&index=0&scoped=…&lang.css`，
  `id.endsWith('/UnifiedNavbar/X.vue')` **匹配不到它**，于是落到下一条通配规则被塞回 `ui-components`。
  `GlobalSearchIsland` 当时用的是 `includes('…X.vue')` 才侥幸正确。
- **修法**：统一改成正则 `/\/UnifiedNavbar\/(A|B|C|D)\.vue/`，脚本与样式子模块都命中。
- **验收**：`share-island` → `ForumMain-*.css`、`cdi-` → 路由 CSS、`gs-bar` → 搜索岛 CSS；
  首屏 245 → **242 KB**（ui-components.css 9923→7310B gz，ui-components.js 反涨 309B）。
- 🔴 **通用教训**：`manualChunks` 里按 SFC 路径匹配时，**永远用 `includes` / 正则，不要用 `endsWith('.vue')`**。
  拆完必须验证**CSS 归属**，不能只看首屏 JS 体积 —— JS 走了 CSS 没走是静默的。

### 隐患 2：切回标签页自动强刷会丢未提交内容
- **场景**：用户打完字 → 点了别处（滚动/切预览）→ `document.activeElement` 回到 `body`
  → 切走 ≥30s 再回来 → `forceCleanAndReload` 强刷 ⇒ 内容凭空消失。
  原护栏 `isTypingInForm(document.activeElement)` 只看焦点，**这种场景完全失效**。
- **修法**（`version-checker.js`）：模块级 `dirtyEditables = new WeakSet()`，
  在 `document` 上**捕获阶段**监听 `input`，只对**文本型**输入（text-like input / textarea /
  contenteditable）标记「有内容」。`blockedBy` 扩成 `typing | media | editing` 三态。
- **为什么用 input 事件而不是比 `defaultValue`**：`v-model` 程序化回填**不触发** input 事件，
  所以不会把「页面本来就有内容」误判成用户输入；比 `el.value !== el.defaultValue` 精确得多
  （后者对任何 v-model 预填表单恒为脏）。
- **为什么只收文本型**：select / checkbox 的「值」不代表未提交内容，收进来会让列表页
  一碰筛选就永久禁用自动更新。
- **测试**：`tests/unit/version-checker-auto-apply-guard.test.js`（6 例，含 3 条对照）。
  反向证明做过：注释掉 `hasUnsavedEditableContent()` 后恰好那条用例变红（`dispatchEvent` 0 次）。

### 顺带加固：弱网不主动预取
- `useGlobalSearch.js` 新增 `isSlowOrMeteredConnection()`（`saveData` / `slow-2g` / `2g`），
  只拦**空闲预取**；悬停 / 聚焦触发的 `prefetchSearchPanel` 不拦（强意图信号）。

## 后台「独立控制台页」孤岛：四个页面统一套 AdminConsoleShell（2026-11-01 中午）

### 三条实现坑（都写进了 AdminConsoleShell.vue 注释）
1. **token 作用域**：侧栏宽度/配色/间距全部来自 `.data-management-page` 下定义的

   ⚠️ base.css 里还有一批**不带作用域前缀的裸类**（`.back-btn` / `.publish-btn` /
   `.refresh-btn` / `.dm-header` …），引之前 grep 过四个页面确认都没用这些类名，
   否则会把 DataManagement 的头部样式漏进控制台页。
2. **`--dm-nav-height` 必须归零**：那组变量的 64px 是给「带 AdminHeader 的
   data-management」用的；四个控制台页 `hideNavbar: true`、页内无固定头，
   沿用 64px 会让侧栏顶部凭空空出一条。
3. **背景别写死**：壳刻意不设 `background`，让 base.css 的淡光晕底露出来
   （侧栏液态玻璃才有东西可透）；写死 `var(--background)` 会把页面压成纯白。

这四个页面的媒体查询原本按**视口**写。加了常驻侧栏后可用宽度 = 视口 - 260，
不改会让中间列在过渡区间被挤扁。已补偿：`.gc-body` 900→1160、`.afc-body` 1180→1440
（原值 + 260）。HeroConsole / ShopConsole 是纵向列表，无断点，不受影响。
**以后给任何页面加常驻侧栏，都要回头把这些页面的断点统一 +260。**

### 修好的两个真缺陷

1. **即时模式下同一发件人窗口内第 2 条及以后的动作被静默丢弃**（`boh_enqueue_follow_mail`）

     别人新评论、自己刚发的评论都不再出现，`comment_count` 却涨了（「2 条评论」只看得到 1 条）。

     `post-api.js` 两条列表路径写 `replies_snapshot_count`；`ForumMain` 写入后刷新改 `{ force: true }`。

## 关注邮件定稿：两种投递方式（站长 19:32 拍板）

站长确认「同一个人频繁动作不邮件」是原设计（2026102801 ④），但指出旧实现把「其余动作」直接丢了。
定稿两种模式，前端文案同步改：

| 模式 | `follow_mail_digest` | 行为 |
|---|---|---|
| **及时与摘要**（默认） | false | 窗口内首条**立刻发**；其余动作**不丢**，进 `delivery='digest'`、`due_at=窗口末` 的「摘要尾巴」，窗口结束时汇总成一封 ⇒ 每窗口最多 2 封 |
| **减少干扰** | true | 窗口内全部动作只发一封，窗口结束才送达（旧聚合语义不变） |

### 实现（`2026110102_follow_mail_instant_then_digest_tail.sql`，已推线上）
- 键结构：head = `收件人:发件人:w<bucket>`、tail = 同键 + `:t`，仍靠 `UNIQUE(dedupe_key)` 保幂等，**表结构不动**。
- `v_window_end = to_timestamp(((bucket+1)*window*60)::double precision)`，tail 的 `due_at` 就是它。
- ⚠️ 两个刻意的取舍：① head 还是 `pending`（EF 正在读那几百毫秒）时到达的动作**一律走尾巴**，不追加进 head
  —— 追加会和 EF 的读取竞争，产生「账本里有、邮件里没有」；② 尾巴延迟 = 窗口长度 + cron ≤5 分钟。
- 演练（事务内 rollback，4 个动作）：默认模式 2 行（instant 1 条 + digest 尾巴含 2 条 extra）；
  减少干扰模式 1 行（digest，extra 3）—— 后者证明老语义没被改坏。
- `2026110101`（每条各一封）被本迁移取代，保留在历史里，别删。
