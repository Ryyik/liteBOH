## 云上咖啡店（/anniversary-cafe）审计 —— 只出方案，未改代码

用户反馈「拥挤 / 玩不好 / 操作感差 / 设计不好」。用 Playwright 跑真页面取几何 +
`node -e` 核算数值，结论是**玩法内核塌陷**而不是美术问题。方案落 `plans/026-anniversary-cafe-redesign.md`。

### 实测到的三条硬结论

1. **11 个制作步骤退化成同一条规则**：`processProgress` 0→100 涨进金色区。
   hold / toggle / gesture(water×3, steam, pour) / tap(×4) 只是输入方式不同，
   `tap` 类点够次数直接 `completeStep(96,...)` = 无技巧空间。
2. **猫的救场是最优解**（奖励结构反了）：
   摸猫 320ms 冷却 +1、逗猫 +2 → 攒 8 点最快 1.28s → 救场 0.35s = **2.9s/杯**；
   认真做 4-5 步 ≈ **17s/杯**。且 `resolveSuccess` 里 catAssist 品质硬编码 82（比满分 96 低，
   但时间成本只 1/6），`totalQuality` 还照记 ⇒ `getAnniversaryCafeStars` 的三星门槛
   （`served>=8 && avg>=85`）纯靠刷猫就能过。
3. **竖屏面板占屏 59.7%**（390×844 下 7→311px 共 504px），
   但**零重叠零溢出**（探针 `overlaps:[]` `overflow:[]`）⇒ 拥挤是设计算出来的，不是 bug。
   机器占位被压到 `grid-template-columns: 128px 1fr`，`font-size` 出现 7px。

其它实测：操作窗口 455–636ms（无分级）；`targetBounds` 的 shrink(≤-10) 会被
磨豆机满级 bonus(+8.4) 反超 ⇒ 越熟练越难但升级能把难度买回来；耐心 0.62%/s 太慢几乎不构成压力。

### 反证式验证抓到 9 个真 bug（都不是测试写错）
1. **rAF 只给 swirl/trace 起了循环** —— oscillate/staged/texture/layer 从不推进，
   读数条恒 0%，但 commitStep 拿未推进的 state 判定却「完成」。
   端到端症状：1c 通过而 1b 转红的自相矛盾。⇒ 所有按住型机制都必须起 rAF。
2. **`.gesture-capture` 定位祖先是 `.machine-deck`**（当时没有 position）⇒ 落到页面左上角
   （y=9），**盖住订单条导致点不到切单**。加 `position: relative` 修。
   ⚠️ 同类病：absolute 元素的定位祖先要显式确认，别假设。
3. **排气阀写在 `<svg>` 里** ⇒ 浏览器不渲染 SVG 内的 HTML 按钮（尺寸恒 0、Playwright 报

4. **投料投够数不提交** —— `doseOnce` 最后一次设 status='holding' 等提交，

5. **采样型坐标未做正方形归一化** —— 事件来自 504×132 的捕获层而引导线在 1:1 的 SVG 里，

6. **`anyStepInProgress` 只看 holding** ⇒ 开局没人按按钮时摸猫可用，P0-4① 反白嫖形同虚设。

7. **萃取排气窗 [34,62] 与金区 [58,88] 只重叠 4 点** ⇒「排气」与「拿 perfect」时间上互斥。

8. **研磨 riseRate 46/s 穿越窗口只要 0.70s，而 holdRequired=1.0s** ⇒ 玩家**物理上不可能**

### 实测踩出的平台硬坑（都是花真金白银的时间换的）
1. **deploy 端点 `slug` 是 query 参数**：`POST /functions/deploy?slug=<name>`。
   不传 → server 生成 **UUID slug** → `/functions/v1/<name>` 永远 404，pg_cron 怎么发都打不到函数。
   multipart 字段名是 `file`（单数）+ `metadata`（JSON 串）；纯 JSON body 报 "Invalid multipart boundary"。
   filename 用**相对项目根**路径（`supabase/functions/...`），_shared 子目录才能落对位置。
2. **`/secrets` GET 读回值 ≠ EF env 注入值**（SUPABASE_SERVICE_ROLE_KEY：got=70783c62… want=sb_secre…，
   新 API key 体系切换期）⇒ 平台 secret 不能当调用方鉴权凭证比对。
   改用 ops 脚本生成的专用 token（MAIL_KEEPALIVE_TOKEN），单值源 = cron 命令文本。
3. **pg_cron→pg_net→EF 链路上自定义 header（x-keepalive-token）到不了函数**（EF 读到空），
   只有 Authorization 头能穿 ⇒ token 走 `Authorization: Bearer <token>`。
4. **论坛周报 cron（job 11）的 app.settings.* GUC 从未配置**（pg_db_role_setting 无记录），
   它每周都在发空 Bearer——若周报函数内也校验 Bearer，等于从未成功过。待另行修复。
5. `cron.job_run_details` **没有 jobname 列**（jobname 只在 cron.job 上），联查要 join。
6. `net.http_response` 在 Management API 只读/非只读会话都打不开（42809），EF 日志端点旧路径全废
   ⇒ **云端代触发**（一次性 pg_cron job + 底账表回读）是 supabase.co 被本机阻断时唯一可用的端到端验证法。
7. 本机 → `*.supabase.co` 间歇性全断（ip4/ipv6/代理皆 000），`api.supabase.com` 始终通 —— 部署/查询走 Management API 不受影响。

## 追加修复：两处「有概率」bug（用户实测报障，非探针能抓的那类）

### ① `Cannot read properties of undefined (reading 'target')`

`createStepState(null)` 在**一杯做完最后一步**时被调用（`currentStepId` 变 null，
视图仍用它渲染装置台），而 `STEP_DEFINITIONS[null].target` 直接抛错，
被全局错误边界捕获 ⇒ **出杯那一瞬间整页渲染报错**。

修：`createStepState` 对未知/null stepId 返回中性 `{kind:'serve', status:'settled'}`。
反证：撤掉兜底立刻重现同一报错与堆栈（`at Proxy.createStepState`）。

⚠️ 这类「只在终态出现的空指针」**单测极难覆盖**（要跑完整流程才触发），
必须靠端到端探针 + 「把修复撤掉确认重现」来抓。

### ② 「有概率出现长按没反应」—— 三个缺陷叠加

用户报的是"有概率"，实测定位到三个独立缺陷，任一都会导致该症状：

1. **`applyStepResult` 失败也推进步骤**（`stepIndex: order.stepIndex + 1` 无条件）
   ⇒ 玩家按坏了却被静默送到下一步，而反馈还写着「下一步：xxx」，
   按钮/进度条却还在原地 ⇒ 观感就是「按钮失灵」。
   修：fail 时 `stepIndex` 不变、不累加品质/档位、反馈写「这一步要重做」**且不含「下一步」**。
2. **`stepStates` 是全局单例**（`{[stepId]: state}`），三单共用一份
   ⇒ A 单的 `status:'failed'` 污染 B 单，而 `canInteract()` 见到 failed 直接 return false
   ⇒ **切单后长按真的完全没有任何反应**（连 holding 都不出现）。
   修：改成**按订单隔离** `{[orderId]: {[stepId]: state}}`，
   `removeOrder` 时一并清理，`pointer` 里带 `orderId` 供 frameLoop/move/up 用。
3. **失败后 `failed` 状态残留**，即使不切单也回不到 idle。
   修：失败 900ms 后直接删掉该步状态（而不是改字段），下次 `ensureStepState` 重建干净的。

**「有概率」的来源**：取决于「哪一单先失败」+「玩家有没有切单」+「有没有等自动复位」。

⚠️ 教训：**共享可变状态没按实体隔离，是这类"偶发串味"bug 的通用根因**。
游戏里多单并行、每单各自有进度/失败态时，状态容器必须以**实体 id 为第一层key**。

### 探针自身的两处判据错误（也记下来）
- `doneCount` 在「整单做完→ 订单被移除」时会被重置成 0 ⇒ 出现 `2 → 0` 的假失败。
  改用 `activeStepIndex`，并把「订单消失」也计为终点证据。
- 场景之间互相污染（`switchToKind` 把所有单都做掉了）⇒ 后面场景拿不到 kind。
  用 `window.__cafeDebug.forceDrink()` 直接指定配方 + 每场景独立开页。

新增：`tests/unit/cafe-round.test.js`(9)，咖啡店单测合计 **45条全绿**。
探针加场景 6.5（6 条断言）专门盯「失败后还能重按 + 切单切回后还能长按」。

## BOHAI 侧栏与快捷跳转条两处修正（2026-10-08 下午续）

### ① 侧栏「新对话 / 搜索条」超出
用户报「新对话和搜索的条有超出」。根因是**一类通用缺陷**：桌面档
`.boh-sidebar > * { min-width: var(--boh-sidebar-w) }`（本意是「收起态裁切、内容不挤压」）
算的是元素**自身**宽度、**不含水平外距** ⇒ 自带 `margin: 0 12px` 的两个块各宽出 24px，
被侧栏的 `overflow: hidden` 从右边裁断（实测 1440×900：侧栏 right=368，两元素 right=380）。
修法：这两个块单独 `min-width: calc(var(--boh-sidebar-w) - 24px)`。

⚠️ **通用坑**：给「所有直接子元素」统一下 `width/min-width` 时，必须意识到子元素可能自带 margin
—— 宽度约束和 margin 是**相加**的，不是包含关系的。

护栏：`probe-bohai-shell` 新增「侧栏子元素不水平溢出」（对**所有**直接子元素取最大右溢出，
任何一条再冒头都会红）；`bohai-quick-sidebar.test.js` 加源码侧断言。

### ② 快捷对话跳转条改成「常态一个条 / hover 才显示消息」
用户口径：「侧边改成 hover 才显示消息，普通就是一个条」——**不是**会话侧栏，
是消息流右下那排 `.boh-jump` 跳转条（每条用户消息一根竖条 + 摘要文字）。
改法：`.boh-jump-label` 常态 `max-width: 0; opacity: 0`（**`max-width` 才可过渡**，
`display:none` / `width:auto` 都不行），`.boh-jump:hover / :focus-within` 展开到 140px；
`.boh-jump-item` 常态去掉胶囊底（`transparent`），hover 才恢复浅灰。
另加 `@media (hover: none)` 让触屏常驻摘要 —— 判据用 `hover: none` 而非宽度断点，
因为平板横屏（≥1024）也可能是触屏。
实测：常态 navW=25px（只剩 3 根竖条）→ hover 148px + label 宽 123 + 底 rgb(245,245,245)。

⚠️ **差点走错方向**：用户说「侧边」，我第一反应是会话侧栏（还专门问了确认，他回「不是，是快捷对话跳转」）。
教训：用户口中的**方位词（侧边 / 旁边）要结合同句里的名词一起读** —— 这里的关键词是「消息」，
指向的是消息流里的跳转条，而不是装了会话列表的侧栏。

### ③ 跳转条二次调整（用户给了目标图）
上一版是「3×12 竖条 + hover 时各项各自浅灰胶囊」；用户给图后改成：

- **mark 改扁横条** `16×3`（原 `3×12` 竖条）；

  不再在单项上画药丸；`padding: 6px` 与圆角**常态就占位**，hover 只补底色 + 投影
  ⇒ 切换时没有几何跳变，只有一层底色淡入；

## BOH AI 联网搜索状态（纯文本活动行 · 2026-10-08 晚）

用户三轮口径收敛：① 实时显示网页标题 + 轮换 + 默认折叠；② 黑点只在模型思考/回复时显示，
搜索期不显示；③ 参考 Grok 活动列表 → **纯文本行**，检索期「网页搜索」四字配流动光效，
不要卡片框，点行展开标题清单。

### 实现
- **数据真源** `useWebSearchLifecycle`：新增 `webSearchResults`（{title,url}≤8 条）。
  搜索是**单请求一次性返回**（Tavily → 免费代理，无增量流）⇒「实时」的可达口径 =
  结果到达即填充；每轮 `runWebSearch` 开始先清空（否则关联网那轮显示旧标题）。
  引擎 sendMessage 开头也清一次（双保险）。
- **展示** `BohChatStream`：`.boh-search-row` 纯文本行（图标 + 行文字 + chevron）。
  行文字 = 检索在途「网页搜索」（`.is-shimmer` 流光：linear-gradient + background-clip:text，
  亮/底走 text-1/text-3 令牌，时长复用 --boh-dur-bob）→ 结果到达后轮换标题（2.4s，
  `:key` 重挂放淡入动画）。展开清单 = 纯文本行（编号+标题+域名，可点出原文）。
  面板可见窗口挂**整轮 isLoading**（只挂 webSearchActive 的话，标题出现的瞬间面板就消失）。
- **黑点分相** `showThinkingDot`：`(isThinking||isLoading) && !webSearchActive && last`。
  ⚠️ `communitySearchActive` **不进门控**——它从检索开始挂到整轮结束，进门控会让社区类
  问题黑点全灭（探针 A4 抓到）。操作行改挂 `isGenerationBusy`（忙时隐藏，避免流式期黑点+操作行同屏）。
  isThinking 从发送保持到首个可见 token（含搜索期），所以不能只看它。

### 探针 probe-bohai-search-status.mjs（9 条，含两个环境级坑）
1. **伪造登录要全程保活**：auth store 的会话同步（auth.ts:776）由 supabase 监听器驱动，
   沙箱网络黑洞让回调迟到数秒 ⇒「注入-复核两次」仍被盖回 false（消息根本没发出去）。
   修法：400ms 定时补注（只在 false 时翻 true，不重复触发引擎 watcher）。
2. **模式表必须 mock 合法清单**：`sendMessage` 在 runtimeAvailableModels 为空时**静默中止**
   （等 8s 只留 warn）—— 把 `**/rest/v1/rpc/**` 全兜 [] 会让消息不进流；沙箱里 supabase
   间歇性通，偶发成功极易误判已修复。修法：同一 handler 里对 list_public_bohai_modes
   返回合法行（mode_id/model_id/display_name 缺一整条被丢）。
3. 断言：A2 搜索在途无黑点+默认折叠+「网页搜索」；A3 结果到达行变标题；A4 思考期黑点出现；
   A5/A6 展开清单往返；A7 完成后面板退场+黑点消失；A8 零 pageerror。

单测：bohai-web-search-lifecycle.test.js（5 条：到达即填/轮前清空/失败复位/reset/上限 8 条）；
bohai-quick-sidebar 守卫同步改版（shimmer 契约替代滑动进度条契约）。
实测：verify 绿、probe 9/9、单测 23/23。
