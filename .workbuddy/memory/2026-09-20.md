### 反解产物算路由成本的技巧（关键）
`app-*.js` 里有 `const __vite__mapDeps=(i,m=...,d=(m.f||(m.f=[...])))` —— 把这个文件名数组扒出来，

## 追加：`image-compression-timeout.test.js` 偶发失败 —— 已定位根因并修复

之前只报了「偶发」，瑞一颗追问「这个是啥」，于是挖到底。**结论：不是「偶发测试」，是 1 个 bug + 1 条级联假失败。**

### 根因
- `flushRealLoop()` 用 **固定 5 次 `setImmediate`** 放行事件循环。而 `setImmediate` 属事件循环 **check 阶段**，可能**早于**动态 `import()` 的真实 I/O 回调（模块图解析 / fs 读）完成。
- 单文件跑 5 个 tick 够用；**整套件 100+ 文件并行、机器繁忙时就不够** → 用例 2 的 `expect(calls).toBe(1)` 拿到 **0** 而抛错。
- **级联**：用例 2 在 `await pending` **之前**就抛了 → 那个 promise 永远没被 await，它后续的「降级主线程」调用落进了**用例 3**（在用例 3 的 `mockReset()` 之后）→ 用例 3 报 `expected 2, got 3`。用例 3 是受害者。

### 实验验证（决定性）
把 `flushRealLoop` 的 5 改成 1 复制成临时文件跑 → **复现出与整套件完全相同的两条失败**：
`用例2: expected "spy" to be called 1 times, but got 0 times` / `用例3: expected "spy" to be called 2 times, but got 3 times`。因果链确认。

### 修复（`tests/unit/image-compression-timeout.test.js`）
1. 删掉 `flushRealLoop`，改为 `waitUntil(predicate, describe, timeoutMs=5000)` —— **条件 + 真实时间上限**，与机器负载无关：
   - 用例 2：等 `mocks.compressionFn.mock.calls.length >= 1`；
   - 用例 4/5：等 `vi.getTimerCount() >= 1`（假定时器数量可观测，比猜 tick 数可靠）。
2. `afterEach` 改成 async，先 `await setImmediate` 放行一轮再 `vi.useRealTimers()` —— 吸收上一用例可能残留的续体，**彻底切断级联**。

### 验收（含反证，证明没有把测试改成「等到通过为止」）
- 单文件连跑 **6/6** 绿；完整套件连跑 **4/4** 绿（修复前 2 次挂 1 次）。
- **反证 A**：把 worker 压缩超时去掉 → 用例 2 以 `Test timed out in 5000ms` 转红，**且只有 1 个用例失败**（改前会级联成 2 个，反证了级联已消除）。
- **反证 B**：把 `libURL` 回退为 `undefined` → 用例 1 转红（`expected 'undefined' to be 'string'`）。
- 反证后 `src/utils/image-compression.js` 与备份逐字节一致、`git diff` 为空（未污染业务源码）。

## 追加：页面/分区切换流畅度（「APP 级体验」）

目标：切来切去要「点下去就出来」。

### 根因：`boundaryKey` 挂在 `route.fullPath` 上 → 每次同页改 query 都重建整棵页面树
App.vue 里 `watch(() => route.fullPath, () => boundaryKey.value += 1)`，而 `boundaryKey` 是包住整个 RouterView 的 `GlobalErrorBoundary` 的 `:key`。UserSpace 切分区正是「同 path 改 query」→ 边界连同整棵树销毁重建 → `UserSpaceMain`（1.2 万行 + 5 个面板）每次切换全部重挂载、所有 onMounted 取数重跑，**路由级 KeepAlive 也因此失效**。
**修法**：`route.fullPath` → `route.path`（换页面才重置边界，同页改参数不动树）。原意「一次崩溃不污染后续页面」完整保留。

### 实测（UserSpace 分区切换）
| 指标 | 修复前 | 修复后 |
|---|---|---|
| 「切回来」平均 / 最慢 | 44ms / 63–75ms | **19ms / 29ms** |
| 每次切回的数据请求 | **14–28 个** | **0 个** |
| `community` 逐层节点身份 | shell/tab-page/panel 全重建 | **三层全部复用** |

### 测量方法（可复用，见 `scripts/probes/probe-userspace-switch.mjs`）
- 分区入口选择器是 `.userspace-rail [data-tab]`（横屏左栏）/ `.userspace-bottom-nav`（窄屏）。
- **逐层节点身份**是定位「重建发生在哪一层」的关键：把 `.user-space-page` → `.tab-page` → 面板根依次存进 `window.__probeNodes`，离开再回来比对。若只用「面板根」单层比对，会误判成面板问题而错过真正原因。
- 抓「每次切换打了哪些接口」用 `page.on('request')` 按 path 聚合，一眼看出重复取数。

### 过渡动画（用户明确要求「优雅」）—— 本轮未落地，原因是硬的
尝试给路由加 `<Transition name="route-enter">`（只做 enter 不做 leave，避免 out-in 硬加等待）。结果：**两种独立探测（MutationObserver + rAF 采样）都确认过渡类名从未被加上**，且无告警（生产构建会剥掉 Vue 的开发告警，所以「没告警」不能当依据）。已排除的假设：
- 不是编译问题：产物 JS 里确实是 `Transition{name:"route-enter",mode:"out-in"}` 包住路由组件。
- 不是 `out-in` 死锁：新页面正常出现（页面内容确实换上了）。
- 换成最简形态（无 KeepAlive、无 key、单 Transition）**同样不触发**。
- 外层 `<Suspense>` 是可疑点（其 fallback 按 App.vue 自己的注释「实测永远不会 pending」= 死重量），但移除它的实验因模板手术出错未完成。

### ⚠️ 自我修正：上一轮「收窄 Realtime 发布表可省 70% DB 时间」是错的

- **错在哪**：看到 `pg_stat_statements` 前三名（Realtime WAL 轮询 `realtime.list_changes`）占 `total_exec_time` 73.9%，就直接推「收窄发布表能省这么多」。**占比是相对值，且轮询成本 ≠ 解码量。**
- **实测推翻**：已发布 4 张表（posts/likes/comments/notifications）**135 天累计变更只有 2,367 条（≈17 条/天）**，而轮询 4,723,970 次 → **99.95% 的空转**，开销是轮询固定成本（WAL 顺序扫描 + 每次重算 `pub` CTE 里的 `::regclass` 目录查找），与发布表宽度基本无关。
- **量级换算**：23,567s ÷ 135 天 ≈ **175 秒 CPU/天**，且跑在 Realtime 自己的连接上，不阻塞用户请求。
- **机制仍然成立**（不是纯过滤）：`realtime.list_changes` 定义里把 publication 表列表拼成 wal2json 的 `add-tables` 参数**下推给逻辑解码插件**。→ **「机制有效」和「收益显著」是两件事，必须分开陈述。**
- **订阅面结案**：全仓 `postgres_changes` 只有 2 处且都在 `notifications`；`notifications-api.js:451 subscribeToNotifications` 是**死代码**（全仓仅定义处 1 次出现，未经 auth.js 再导出）；唯一活消费者是 `Messages/index.vue:1104`。`supabase/functions`、`public`、`cloudflare`、`android-twa`、`scripts` 全无引用 → **移除 posts/likes/comments 零功能影响**。
- **真正能动那 73.9% 的唯一杠杆是整项目关闭 Realtime**（消息中心实时推送 → 退回 60s 轮询兜底，`UnifiedNavbar/index.vue:1100` 已有）。属产品决策。

### 新踩的坑
- **`pg_logical_slot_peek_changes` 被拒**：`42501 Only roles with the REPLICATION attribute may use replication slots`。Management API 角色没 REPLICATION 权限，**没法做「解码面宽度 vs 耗时」的因果实验**。
- ⛔ **绝对不要改用 `pg_logical_slot_get_changes` 绕过权限去试**——它会消费并推进槽，会真实抢走正在运行的 Realtime 服务的变更、导致线上实时通知静默丢消息。做不了就在报告里写明「用 X 做替代推断，非直接测量」。
- Supabase Realtime 的复制槽是**按需创建/销毁**的：同一会话里前后两次查 `pg_replication_slots`，一次有 2 个 active 槽、一次为空。→ 不存在「槽滞后把 WAL 堆积撑爆磁盘」的风险，别写成风险项。

## 追加：「立即更新」点了不刷新 —— PWA 版本更新链路修复

### 根因（端到端复现证实）
`forceCleanAndReload` 最多等 **1.8s** 让新 SW 接管，超时仍无条件导航。而新 SW 要下载完整新预缓存才能激活（远超 1.8s），于是导航被**旧 SW** 的 `NavigationRoute(createHandlerBoundToURL('index.html'))` 拦截 → 用**旧预缓存**的 index.html 应答；`?__boh_update` 查询串只能绕 HTTP/CDN 缓存、**绕不过 SW 预缓存**（workbox 查清单时会剥掉查询参数）。页面重载了但字节级还是旧版本；且 sessionStorage 目标 buildId 让启动自检认为「该目标已尝试过」→ 只把同一个弹窗再弹出来 → 用户看到「点了没反应」。

### 修复（`src/utils/version-checker.js` + `PWAUpdateToast/index.vue`）
- 接管等待窗口 1.8s → **10s**；先 `update()`，**无 installing/waiting（当前 SW 已最新）直接导航**，有则等 `controllerchange`；整链路与超时对跑（防 update() 挂起卡死）。
- 超时走兜底 `dismantleServiceWorkers()`：**先清空 Cache Storage**（旧 SW 即使继续拦截，预缓存未命中 → workbox 回落网络 fetch → 照样拿新 index.html），`unregister()` 发起后只等 **1s 宽限**就导航。
- PWAUpdateToast 点「立即更新」后弹灵动岛「正在更新…」（等接管最长 10s 期间给可见反馈）。

### 两个实测结论（探针抓到，值钱）
1. **Chrome 在有 SW 正在安装时 `unregister()` 的 promise 拖到安装结束才 resolve**（几十秒级）→ 绝不能 `await unregister()` 到底；真正保命的是 `caches.delete`。
2. 生产构建 logger 只出 **warn+error**（`info` 全静默）→ 页面侧探针想看 `info` 级面包屑要用 `console.warn` 直注。

### 验收（scripts/probes/probe-version-update-click.mjs，真实点击全链路）
- **复现**（旧 dist 构建 + `--static-delay-ms 3000` 拖慢安装）：点击 → 落地 buildId 仍是旧构建 = BUG 证实。
- **验证**（修复后 dist-check）：场景 A（安装快，接管后导航）与场景 B（4s/资源拖慢 → 10s 超时 → 清缓存兜底导航）落地均为新构建、无重复弹窗。
- 单测：version-checker 9 条（新增「unregister 挂起时导航仍须发生」「接管成功不注销」）；全量 **118 文件 / 1925 通过**；eslint 0 error。
- 探针坑：`waitForSelector('meta…')` 默认等 visible，meta 永不可见 → 必须 `state:'attached'`；static-delay 不能误伤旧目录首屏（只对新目录的 `/static/` 加延迟）。
