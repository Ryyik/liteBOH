### 用户后续要求「图案丰富一点」→ 静态装饰版（第二版）

用户先问「邮件能不能用动画」，随后自己收回：「不用动画，做精致一点的普通 HTML」。
**邮件动画的结论（以后别再重新调研）**：`@keyframes`/`animation` 只有 Apple Mail 稳，
Gmail 网页部分、Gmail App 与 Outlook（Word 引擎）直接剥；`<svg>`/`<video>` 被 Gmail 剥；
**唯一跨客户端可靠的是 Animated GIF**（Outlook 桌面版只播首帧）。本仓版式建立在
「全部 inline style」上（Gmail 连 `<style>` 都不保证留），所以模板里**永久禁用动画**，
单测 `expect(html).not.toContain('animation'|'@keyframes'|'<style')` 已锁死。

第二版加了四样，全部静态、零外链图（`not.toContain('<img')` 也锁了）：
① 顶部 6px 四色渐变彩带 —— **必须同时写 `background-color`**，Outlook 不认

- `users` 和 `points` **都是 `profiles` 表**。单条删除两者都走
  `admin_delete_user_account`（删 profile + auth.users，带 `CANNOT_DELETE_SELF`）；
  批量删除却只判 `tabId === 'users'`，`points` 落到裸 `delete from profiles`。
- 后果：`profiles` 上 78 个外键、绝大多数 `ON DELETE CASCADE` ⇒ 一次批量就把该用户
  帖子/评论/积分流水/云盘/相册/订单全清空，**auth.users 那行留着** ⇒ 用户还能登录、
  后台再也查不到人，`handle_new_user` 只在注册时跑，不重建 ⇒ 只能连库手工补。
- 更尖锐：裸删绕过了 RPC 的 `CANNOT_DELETE_SELF`。管理员在积分 tab 全选（含自己）
  会删掉自己的 profile，而 `current_user_is_admin()` 依赖 profiles ⇒ **把自己锁在后台外**。
- 顺带修：旧批量删 users 第一条例外就跳出 for，前面删掉的真删了却报「批量删除失败」、
  不清选中、不刷新 ⇒ 部分成功被报成全失败。

修法（纯前端，不动数据库）：
- `useDataAdminMutations.js` 新增 `ACCOUNT_TABS = new Set(['users','points'])`，
  单条/批量/快照排除三处共用；`SNAPSHOT_EXCLUDED_TABS` 改为它的副本后删除（恒假分支也一并去掉）。
- 新增 `deleteAdminAccounts(items)`：逐条 RPC，分 `deleted / skipped / failed`。
  `deleteAdminUser` 失败时把 RPC 的 `code` 挂到 error 上（`CANNOT_DELETE_SELF` /
  `USER_NOT_FOUND` 归 skipped，其余归 failed）——**别靠 message 字符串匹配**。
- `batchDelete` 账号分支单独收尾：只把失败项留在 `selectedItems`（可直接重试）、
  提示「已删除 N 个账号，跳过 M 个（当前登录账号不能删除），失败 K 个」，
  审计 `meta` 记三个计数。
- 文案 `buildDeleteConfirmMessage` / `buildBatchDeleteConfirmMessage` 加 `accountMode`：
  说「N 个用户账号」+「连带登录凭证与全部关联数据」，不再把删号写成「N 条记录」。

守卫：`tests/unit/data-admin-batch-delete-accounts.test.js`（6 条，源码断言）。
**已做反证**：把 ACCOUNT_TABS 临时改回 `['users']`，第 1 条确实变红。

⚠️ 仍未做（成本高、需部署）：`admin_delete_user_accounts(uuid[])` 批量 RPC。
当前逐条串行，删 20 个约 2–4s，可接受。

## 生日邮件开关「点不动 + 显示已关闭」→ 真因是**没给列级 SELECT 授权**

用户报障：「设置里的生日邮件点不动，而且是关的，我不是要求默认开启吗？」

**不是默认值的问题**（`profiles.birthday_mail_enabled` 列默认一直是 true，存量行也是 true）。
真因链条：
1. `2026110308` 把 authenticated 对 `profiles` 的 SELECT 从表级收窄成**列白名单**；
2. `2026111001` 加列时只补了 `grant update`，**漏了 `grant select`**；
3. 前端 `.select('birthday_mail_enabled')` → PostgREST 42501 → `getBirthdayMailEnabled` 返回 error；
4. 组件里「失败不当作 false」的写法只把 `loaded` 留成 false ⇒ `SettingToggle:disabled` 恒 true
   ⇒ 永久置灰且停在初始值 false。**用户看到的就是「点不动 + 已关闭」。**

实测（Management API，非猜测）：`has_column_privilege('authenticated',...'SELECT')` = **false**、UPDATE = true。

修法两层（缺一不可）：
- `2026111002_birthday_mail_select_grant.sql`：`grant select (birthday_mail_enabled)`（敏感列不动），
  已用 Management API `read_only:false` 应用 + 手写 `schema_migrations` 记账（版本 2026111002）。
- 前端 `loadBirthdayMailSetting`：读失败 ⇒ 按服务端默认（开启）显示 + **放开操作** + 文案说明。
  「留一个点不动的灰开关」比「按默认显示」更糟：用户根本不知道发生了什么。

🔴 **可复用规则**：`profiles` 加任何新列，**同一迁移里必须同时 `grant select` 和 `grant update`**。
漏 select 的表现不是「字段空」而是「开关死」—— 排查时先查 `has_column_privilege`，
不要从组件状态往回推。`revoke select (列)` 这种写法也会静默无效（表级权限在时列级 revoke 不生效）。

1. `readPrecachedShellBuildId()` 正面核对预缓存里的 index.html buildId，不一致就降级注销兜底。
2. `recoverStaleLanding()` 启动时自愈：带目标回来仍是旧壳 ⇒ 一次性硬重置；闸门
   `boh_version_hard_reset`，**写不进/读不回标记就绝不重置**（否则变成无限刷新）。

## 商城详情滚动穿透修复（22:5x）—— 真因是「锁错了元素」

用户报障：「商城详情的滚动还是在滚动商品列表页，而不是详情页」（「还是」= 之前修过没修好）。

**真因**（探针实测复现）：`src/style.css` 写死
`html { overflow-y: auto !important }` + `body { overflow-y: visible !important }`
⇒ 文档滚动发生在 **html** 上；而全站（含 `useBodyScrollLock`）只写
`document.body.style.overflow = 'hidden'`（inline、无 important）—— 连样式表都盖不过，**锁了个寂寞**。
`Shop/index.vue` 里那 7 处直写同理，全是不生效的空操作。

修法：
1. `useBodyScrollLock` 同时锁 `documentElement`，必须 `setProperty('overflow-y','hidden','important')`
   才能压过那条 `!important`；并补 `padding-right = 滚动条宽度`（本站 `::-webkit-scrollbar` 是 8px
   常驻滚动条，不补位会上锁瞬间横向位移）；释放时做「还是不是我们设的」归属校验，防永久锁死。
2. `Shop/index.vue` 7 处直写 → `lockPageScroll/unlockPageScroll`（单源、引用计数）；
   `LotteryPanel` 3 处、`OrderDetailSheet` 3 处一并迁；`LotteryDetailSheet`（v-if 挂载）
   与 `AdminOrderSheet`（常驻 + visible）各自在组件内取锁。
3. 新探针 `scripts/probes/probe-shop-detail-scroll.mjs`（11 断言，A 横屏 / B 竖屏 / C 其它分区）。
   **判别性只有 A1–A3**（A4/B2 在没锁时也可能绿，页面到底或 contain 兜住）。

自证：探针 11/11；**反证**把锁根元素那几行注掉 → A1–A3 立刻红（实测 6 passed / 3 failed）；
`npm run test` 342 文件 4489 条全绿（新增 4 条锁根元素单测 + 商城目录单源守卫）；lint 89/90；type-check 绿。

⚠️ 留给下次的教训：**「锁滚动」在本站不等于 `body.style.overflow`**。任何新浮层要防穿透，
一律 `acquireBodyScrollLock`；直写 body 的 inline overflow 永远无效。
