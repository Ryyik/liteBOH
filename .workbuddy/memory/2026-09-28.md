## 多 agent 并行的分区设计（结论：本仓库大部分活不适合并行）

用户问「多 agent 协作如何安排才不会撞文件」。核心结论：**分区键必须是「文件写权」，不是任务主题**。但更要紧的是先判断**哪些活值得并行**。

判据（三条全满足才值得）：① 任务间无共享决策（不需要统一的命名/接口约定）；② 每个任务独占文件；③ 每个任务可独立验证。

| 剩余任务 | 适合并行? | 原因 |
|---|---|---|
| 第 2 批 分层棘轮（46 文件） | ❌ | 核心产物是**一条 lint 规则 + 一个棘轮基线**（单一真源），且 46 处需**一致判断「该调哪个 API」**。并行会让每人造出不同封装 —— 正好制造我们要消灭的重复 |
| CSS 孤儿审计器 | ❌ | 判据必须统一 |
| 第 3 批 scoped @import | ◐ | 各 partial 独立可改，但需**先定统一命名空间约定**；且要视觉回归 |
| 第 4 批 四文件 CSS 外置 | ✅ **最适合** | 四文件互不相干、纯搬运、各自可验证、无共享决策 |

### 三阶段编排（用于真正适合并行的活）
- **阶段 0（单人串行，不可省）**：定命名/接口契约 + 产出「文件→owner」映射 + **把共享文件（eslint.config.js / package.json / 新增 utils）一次性改完并提交**。地基没打好就并行 → 所有 agent 都去改同一共享文件 → 全撞。
- **阶段 1（并行 N agent）**：每人一个 `git worktree`（物理隔离）；prompt 明写「只许改这些文件」+ 事后机器校验；**只跑自己范围的快速门禁**。
- **阶段 2（单人收口）**：依次 rebase/merge；对每个 agent 的 `git diff --name-only` **求交集**检测撞车；跑一次完整 verify + build + 门禁自检。

### 本仓库三条硬约束（直接决定并行方案能不能用）
1. **vitest 限 `maxForks: 2`**，配置注释明写「不要调高并发」→ 并行期间**禁止各 agent 跑全量测试**（会互相拖慢、让 `project-structure.test.js` 超时），测试集中到收口阶段跑一次。
2. **`check:gates-self-test` 会临时改写工作区文件** → **绝不能在任何并行窗口里跑**（会改掉别人正在编辑的文件）。只在收口阶段、确认无人并行时跑。
3. **`.git/hooks` 在 worktree 之间共享** → 所有 agent 的提交都触发同一个 pre-commit 钩子；钩子会改文件，所以每个 agent 都要知道自己「验证的树」可能已变。

## authStore 冗余：实测结论与**不做的理由**（重要）

原先说的「31 处冗余」是**全仓**数字（含 `utils/api`）。UI 层实际只有 **8 处 / 7 文件**，且分成三类：

| 类别 | 处数 | 文件 | 能否替换 |
|---|---|---|---|
| `getUser()` 只为拿 `user.id` | 5 | `useAvatarFrame.js`×2、`TagsImpressions.vue`、`ProfileMain.vue`、`UserSpaceMain.vue` | 理论可用 `userInfo.id` |
| `getSession()` 只为判登录态 | 1 | `Health/index.vue:180` | 可用 `authStore.isLoggedIn` |
| `getSession()` 需要 session 对象本身 | 2 | `AccountSecurity`（`isRecentTokenLogin(session)`）、`ResetPassword`（`waitForSession`） | **authStore 没暴露 session，替不了** |

**决定：不做快扫。** 两个理由：
1. **语义不同**：`getUser()` 是**服务端校验**（会打一次网络），`userInfo` 是**本地缓存**。替换后「会话被撤销」的场景不再被本地拦住 —— 虽然 RLS 仍会在写库时拒绝，但失败位置从「干净的请先登录」变成「一个错误」。
2. **有真实风险**：`authStore` 初始化前 `userInfo.id` 是空的。`TagsImpressions.vue` 这类「没 user 就弹登录框」的写法，盲替会在未初始化时**误弹登录框**。安全替换需要每处都加 `isInitialized` 守卫。

→ 结论：这是一个**需要逐处判断的小任务**，不是一个可以扫一遍的清理。真要做，得先决定「authStore 要不要暴露 session」，再逐处加守卫。

## 多 agent 判断（本轮实际结论）
用户问「可以多agent就多agent」。**这两个任务都不适合并行**，我单 agent 做的：
- 棘轮总账：单一真源（一个脚本 + 要改 `package.json` 共享文件）→ 不满足「任务间无共享决策」
- authStore：8 处 / 7 文件且分三类、有语义分歧 → 协调成本远超收益
判据（三条全满足才并行）：① 无共享决策；② 每任务独占文件；③ 可独立验证。

## 第 3 批 CSS：scoped @import 重复（报告这条**是对的**，但归因不全）

### 先纠正我自己的一次误判
我先只统计了 `.g-*` 选择器的 scoped 副本，得出"重复只有 24KB（3.8%）"，并据此认为报告夸大了。
**这个结论是错的** —— `g-` 只是 DataManagement 全区命名约定之一，base/console/responsive 用的是**别的前缀**，所以那个统计漏掉了重复的主体。

### 正确测量法（关键方法）
不要去数产物里的选择器（前缀不同、易漏），**直接数「每个 partial 被几个组件 scoped 导入」**，`重复字节 = 体积 × (导入方数 − 1)`：

| partial | 体积 | 导入方 | 重复字节 |
|---|---|---|---|
| base.css | 13,929 | 6 | 69,645 |
| console.css | 41,643 | 2 | 41,643 |
| google-components.css | 29,832 | **7** | **178,992** |
| responsive.css | 30,544 | 6 | 152,720 |
| overlays.css | 24,327 | 1 | 0 |
| **合计** | 140,275 | | **443,000** |

产物 `DataAdmin-*.css` = **641,924 bytes**，而 DataManagement 源 CSS 只有 **254,706 bytes** —— 差 387KB，与估算吻合。**642KB 里 443KB（69%）是重复**。

### 机制（报告说得对）
Vue 把 `[data-v-X]` 加到**元素自身**（产物形如 `.g-btn[data-v-7417c07e]`，实测 5633 处复合形态、**0 处后代形态**）。所以：
- N 个组件各编译一份字节副本；
- 且父组件的副本**匹配不到子组件内部的元素**（那些元素带子组件自己的 scope id）→ 这就是"互相失效"，也是为什么每个用到它的组件都不得不各导一份。

### 已做的修复：google-components.css 改真全局（−164KB）
选它的理由：**75 个顶层类全部带 `g-` 前缀，0 个泛名** → 改全局不会泄漏。其余 4 个 partial 仍含泛名（`.drawer` / `.sidebar-link` / `.tab-group-nav`…，共 444 个），需先补容器命名空间才能照办。

- 发现**仓库既有先例**：`DataAdmin.vue` 的非 scoped `<style>` 块早已这样处理 `overlays.css`（唯一 1 个导入方、0 重复）。
- 做法：把 `google-components.css` 加进 DataAdmin 的非 scoped `<style>`；移除 7 处 scoped 导入；**保留** `main.js` 的延迟全局加载（有 3 个非 DataManagement 文件在用 `g-` 类：`BOHAI/BohaiSettingsPanel`、`UserSpace/ProfileHomePanel`、`ProfileMain`）。
- **实测结果：DataAdmin chunk 627KB → 463KB（−164KB / −26%）**；全站 CSS 3296KB → 3132KB；`.g-btn` 出现次数 **43 → 7**；整份副本 **8 → 2**（路由 chunk + 全局延迟 chunk）。
- 级联风险已评估：7 个组件自有样式与 gc 有 33 处类名重叠，但**组件自有规则是 scoped（0,2,0）、gc 改全局后是（0,1,0）→ 自有规则仍胜出**，结果不变。

### 过程中的一次失误（记下来）
编辑 `AdminSidebar.vue` 时我把 `@import '../styles/google-components.css';` 的 `new_string` 误写成 `@import '../styles/console.css';` —— **那是新增一个导入，会加重重复**。已当场发现并修正（该文件现在无 partial 导入）。
**教训：批量 Edit 时 new_string 必须逐条核对，不能套用同一个模板。**

### 机械验证（比"推理没变"更硬）
对修复前后的产物做**声明级归一对比**：抽所有含 `.g-` 的规则、剥掉 `[data-v-x]`、规整空白，比对集合。
- 差异只有 keyframe 名的 scope 后缀（Vue 也会给 `@keyframes` 加 scope 后缀）：修复前 `@keyframes gSpin` 有 **8 个**（1 个裸名 + 7 个 scoped），修复后只剩 **1 个裸名**；引用数 11 → 4。
- keyframes 定义总数 441 → 427，**无任何"引用了未定义 keyframe"**（两个构建都是 0）。

### ⚠️ 一次自己的误报（教训）
我一度报告"发现既有 bug：3 处 spinner 动画引用了未定义的 `gSpin-*`"。**是错的** —— 我的正则 `(gSpin[A-Za-z0-9_-]*)` 没有左边界，把 `animation: imageLoadingSpin ...` 里的子串 `gSpin` 截了出来。
**教训：检测 keyframe/类名这类标识符时，正则必须带边界（前面不能是字母/数字/连字符），否则子串匹配会造出假 bug。** 这类假阳性比漏报更耗信任 —— 差点让我去"修"一个不存在的问题。

### 下一步（未做）
1. 其余 4 个 partial 需先补**容器类名命名空间**（444 个泛名）才能改全局 → 潜在再回收 **~264KB**
2. 2 份副本能否降到 1 份：需要重构 `main.js` 的延迟全局加载（那 3 个非 DataManagement 使用者要么各自导入、要么改成别的全局层）

## 导航栏二级菜单异常空隙（用户报，附截图）

### 先做的归因（重要）
用户报的是**导航栏子菜单内部的空隙**。我先确认**不是本轮 CSS 改动造成的**：Forum 相关文件不引用 google-components/DataManagement，且 `ForumMain-*.css` 改动前后**字节完全相同**（264,450，hash 也一致）。

### 导航栏几何事实（后续改这块必读）
- `#unified-nav-container`：`position: fixed; top: 0; min-height: 78px; z-index: 9999`
- `.unified-nav-surface`：**全局**（非仅移动端）`height: 58px` + `transform: translateY(10px)` + `border-radius: 100px`
  → **视觉底边 = 10 + 58 = 68px**
- 展开态（`has-status-card` / `has-task-card` / `has-custom-card`）：高度 = `--global-nav-open-height` = 79 + 58 + 7 = **144px**
- `--global-nav-rest-height` 定义在 `.unified-nav-surface` 上，**其子孙可继承**（`.nav-submenu`、`.nav-menu-mobile` 都在 surface 内部）

### 两套菜单的互补关系（易踩坑）
- `≤768px`：`.nav-menu` → `display: none`，走汉堡 → `.nav-menu-mobile`
- `≥769px`：`.nav-menu` 可见，`.nav-submenu` 的覆盖写在 `@media (min-width: 769px)`
**两者正好互补**，所以 vendor 里 `.nav-submenu` 的 `padding: 48px 48px` 在窄屏永远不会被用到 —— 我一度以为那是"子菜单内部空隙"的来源，**排除了**。

### 改了什么
1. `src/styles/vendor/unified-nav.css` 的 `.nav-menu-mobile`：硬编码 `top: 64px` / `height: calc(100dvh - 64px)` → 改为 `calc(10px + var(--global-nav-rest-height, 58px))`（= 68px）。
   理由：64px 是更早版本的高度，比岛的实际底边（68px）高 4px，**菜单顶边会被悬浮岛盖住**。改成推导式后岛高再变会自动跟随。
2. `src/components/UnifiedNavbar/style.scoped.css`：新增 `#unified-nav-container.mobile-menu-open .unified-nav-surface { box-shadow: none }`。
   理由：菜单紧贴岛底，岛的 `0 8px 32px` 下投影会横跨菜单上沿 → 视觉上就是一条灰色错位缝。`.mobile-menu-open` 已由组件挂在容器上（`index.vue:6`），无需新增状态。

### 排除掉的假设（省得下次重走）
- `.nav-mobile-submenu-container` 收起态用 `visibility: hidden` —— 但它同时是 `position: absolute`，**不占流**，不会留空隙 ✗
- `.nav-submenu` 的 `padding: 48px` —— 窄屏下 `.nav-menu` 被隐藏，用不到 ✗
- `.nav-menu-mobile-content { padding: 20px }` —— 属正常内边距 ✗

### 未验证的部分（诚实标注）
**我无法做视觉确认**（需要真机/浏览器 + 登录态）。上面两处是**确定存在的几何缺陷**，但用户截图里那条缝是否就是它，需要开一次移动端菜单核对。若仍在，下一步该量的是菜单打开时 `.unified-nav-surface` 的实际 `getBoundingClientRect()` 与 `--global-nav-rest-height` 的运行时值。**
