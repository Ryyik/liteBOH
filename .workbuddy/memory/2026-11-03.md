### ① profiles 列级 SELECT 收窄（P0）

- **根因**：`2026090803_security_hardening.sql` ③ 段只对 **anon** 做「表级 revoke + 列白名单 grant」，
  ④ 段只收紧 `authenticated` 的 UPDATE / INSERT，**唯独漏了 SELECT**。
  实测 `has_column_privilege('authenticated','public.profiles','shipping_phone','SELECT') = true`
  ⇒ 任何注册用户一条 REST 请求可读全站收货人/电话/地址 + PushPlus token。
- 🔴 **PostgreSQL 语义坑**：表级 SELECT 存在时，**列级 revoke 不生效**。必须两步：
  `revoke select on table public.profiles from authenticated;` → `grant select (列白名单) ...`。
  只写 `revoke select (shipping_phone)` 会静默无效（`has_column_privilege` 仍为 true）。
- 迁移 `2026110308_profiles_restrict_authenticated_select.sql`：52 列 = 56 总列 − 4 敏感列。
  已用脚本与线上 `information_schema.columns` 交叉验证：grant 里无拼错列、未授予列正好是那 4 个。
- 前端配套 3 处（revoke 后它们会 403，且本就冗余）：
  - `profile-api.js` `.select()` 空参 → `.select('id')`（空参会 returning 全列）
  - `AddressManager.vue` 删掉直连 profiles，只走 `get_my_sensitive_profile`
  - `pushplus-api.js` 删掉必然 403 的降级直连
- 管理后台走 `admin_list_users_with_sensitive` RPC，**不受影响**。
- 回滚：`grant select on table public.profiles to authenticated;`

### 本机打不通 `*.supabase.co` 的准确结论（不是沙箱问题）

分层实测：DNS ✅、**TCP 443 OPEN**、TLS 握手被 `Connection reset`。
决定性判据：**同一 IP `104.18.38.10` 只换 SNI** —— `api.supabase.com`→404、`supabase.com`→200、
`<ref>.supabase.co`→reset ⇒ 按主机名拦截，**整个 `supabase.co` 域族被挡**（`supabase.co` 自身也 000）。
系统代理 `127.0.0.1:65506` 对可达域名正常、对 `supabase.co` 同样 `SSL_ERROR_SYSCALL`；
无 AAAA；curl 不支持 HTTP/3。**换代理/换协议/换 IP 都不行。**
这也解释了 `db push` 一直能用：DB 走 `*.pooler.supabase.com`，是另一个域。

能通的通道（以后别再说「无法验证」）：
- Management API（`api.supabase.com`）：权限、函数配置、**日志**；
- 统一日志端点：`/v1/projects/{ref}/analytics/endpoints/logs`（旧 `logs.all` 已 410）。
  三个坑：必须带 `iso_timestamp_start/end`（否则默认只查 1 分钟、静默返空）；
  过滤列是 **`source`** 不是 `source_name`；**函数调用在 `function_edge_logs`，`edge_logs` 只有 REST**；
  连查多次会 429。
- `pg_net` 想从库内发 HTTP 冒烟：**不通** —— 管理 API 身份是 `supabase_read_only_user`，
  写不进 `_http_request_queue`；`supabase/.temp/pooler-url` 里也**没有密码**。

### 由日志取证发现的真问题：CSP 上报能收到但字段全空

6h 内 `csp-report` 被真实浏览器调用 152 次（POST 204 / OPTIONS 200，匿名可达），
但解析结果 `{"directive":"","blocked":"","document":"","source":"","line":null,"disposition":"report"}`。
根因：同时下发了 `report-uri` 与 `report-to`，**两条通道键名不同** ——
legacy 用 `document-uri`，Reporting API 用 `documentURL`/`effectiveDirective`；
只有 `disposition` 两处同名，所以「只有它填上了」。
⇒ 这类漏读**不报错、不 4xx**，只让可观测性静默失效。
修法：解析抽到 `_shared/csp-report-parser.ts`（纯函数可 vitest 直导），两种命名都认，
日志加 `fmt` + `keys`（只记键名，让下一次上报自证形状）。反证已实测会红。
**教训：解析上报/兼容格式时，让日志输出「键名清单」，别靠推断。**

## 人机验证闸门空 payload 修复（登录）

用户报障：闸门一出现就显示「人机验证已完成」→ 点一下变空框 → 再点打勾 → 登录仍提示「请先完成人机验证」。

根因两重（都在前端，服务端只按空 payload 回 ALTCHA_REQUIRED）：
1. **altcha 3.0.3 把事件名拼成 `vefified`**（dist/main/altcha.js 的 dispatch("vefified")），
   只有走 verifyUrl 服务端复核那条路才派发正确的 `verified` ⇒ 我们监听 `verified` +
   读 FormData 的通道**从未触发过**。唯一可靠通道是 `statechange.detail.payload`
   （detail 里带 state 与 payload，且 payload 已写入）。
2. `AltchaWidget` 里 `watch(() => props.disabled, d => d && reset())` 是拿 reset 冒充禁用
   （altcha 3.0.3 的 props 根本没有 disabled）。Login 的 `isSubmitting=true` 之后还有
   `await warmLoginDeviceIdHash()`，等它回来读 `altchaPayload` 时已被清成空串。

修法：payload 统一走 `readAltchaPayloadFromStateChange()`（新增于 utils/altcha.js，
只有 state==='verified' 才认 payload，其余状态归零——证明是单次消费的）；
删掉 disabled→reset，禁用改用 class + pointer-events；`auto="onload"` 改 `auto="off"`
（消掉「挂载即自动打勾、用户一戳反而取消」的观感）；Login 在 await 前快照 payload，
且闸门已展示但未勾时本地先拦（不发请求，免得白记一次失败把 requireCaptcha 门槛推高）。

守卫：tests/unit/altcha.test.js 新增 8 条（4 条纯函数 + 4 条源码守卫），
已做反证注入（加回 props.disabled / 直读 altchaPayload.value 都当场变红）。
verify 全绿 307 文件 / 3935 用例。
