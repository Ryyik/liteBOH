# 横屏左栏（UserSpaceSideRail）指示器几何修复 + 优化方案

参考小红书 PC 侧栏，实测 `/user-space` 横屏左栏（`.userspace-rail`）。三档：隐藏 / 88px 窄栏
（landscape+≥1024+≥600）/ 240px 宽栏（+≥1280）。实测视口 1440×900、1100×900、1024×600。

## 修掉的（一行，已反证）

`.userspace-rail-group` 是 `position: static` → 滑动胶囊指示器的 `left/right:0` 包含块上溯到
`.userspace-rail`（absolute）的 padding box，而不是 group：

| 视口 | dTop 首屏 | dLeft | dWidth |
|---|---|---|---|
| 1440×900 | −56 → 0 | −12 → 0 | +24 → 0 |
| 1100×900 | −56 → 0 | −10 → 0 | +20 → 0 |
| 1024×600 | −56 → 0 | −10 → 0 | +20 → 0 |

- **dLeft/dWidth 恒定错**（与时机无关）：指示器 239×47 vs 条目 215×47 @left12。
- **dTop 只在首屏错、切一次 tab 自愈**：挂载时读到的是 `--userspace-rail-top-h` 更新前的
  offsetTop（96，随后导航状态卡片出现 → 138 → padding 152），而 RO 只观察 group
  （尺寸未变）→ 不重算。
- 修法：`side-rail.css` 的 `.userspace-rail-group` 加 `position: relative`。一行同时修两个
  —— 指示器成为 group 子元素后，随 group 被 padding 推下而同步下移。
- 反证：`git stash push -- side-rail.css` → 三档全部复现（−56/−12/+24 与 −56/−10/+20），
  `stash pop` 后归零。
- 验证：`vite build` 通过；`probe-user-space-ia.mjs` 撤前/撤后同为 **78 PASS / 1 FAIL**，
  唯一 FAIL（点「发布」打开发布会话）是**既有问题**（与本次改动无关）。

## 未改、待拍板的建议（plans/011-landscape-rail-optimization.md）

## TWA（Android APK）更新语义 — 代码级确认

用户反复确认「推新版官网后，已装 APK 会不会自动变最新」。结论：**内容是自动更新的，
但形态是「冷启动静默切新 + 使用中需用户点一下」，外壳层永不自动变。**

三层语义（别混为一谈）：
1. **APK 外壳**（图标 / 应用名 / 启动屏 / 包名 / 主题色）**烘焙进 APK**，只随外壳层文件
   （`android-twa/**`、`public/icons/**`、`vite.config.js`）变动触发重打包，**已安装用户必须覆盖安装**。
   线上换图标 ≠ 用户桌面图标变。签名不可换（换 = 另一个应用，老用户只能卸载重装）。
2. **应用壳**（带 hash 的 JS/CSS chunk）由 SW 预缓存，两条路径：
   - 冷启动：`version-checker.js:355` `autoCheck({autoApply:true})` 比对 `version.json` 的 `buildId`
     （`cache:'no-store'` + `?_t=` 绕 CDN）→ 旧构建**自动强刷一次**（`shouldAutoApplyVersion` 钉死
     同一目标只试一次，防刷新循环）。
   - 使用中：每 5 分钟轮询 + `visibilitychange` → 派发 `boh:update-available` → `PWAUpdateToast`
     弹窗，**用户点确认才刷**。`main.js:218` 的 `controllerchange` 有意不自动 reload；
     `version-checker.js:328` 用户在 input/textarea/contenteditable 打字时**跳过**自动强刷（防打断发帖）。
3. **内容与数据**：Supabase 直查，与更新机制完全无关。

⚠️ **脆弱点（无断言保护）**：线上 `sw.js` 响应头被 CF 加了 `cache-control: max-age=14400`（4 小时）。
现在靠 `main.js:67-70` 的 `updateViaCache: 'none'` 绕过（该选项让浏览器不拿 HTTP 缓存参与 SW 更新检查）。
**谁删掉这行 → 更新延迟最多 4 小时，且不报任何错。** 现有注释只写了半个因果（"避免新旧应用壳混用"），
没点破"删了就延迟 4h"，也没探针钉住。

其他边界：离线打开 = SW 缓存旧壳 + 数据请求失败（不是报错白屏）；域名/服务挂 = 白壳；
assetlinks 校验失败 = 退回带地址栏的 Custom Tab（视觉上"变回浏览器"）。

### 缺口（要新建）
1. `push_subscriptions` 表（endpoint 唯一，允许多设备）+ RLS —— 注意 `revoke all` 后必须**分别** grant anon/authenticated（漏 anon 的 select 时 RLS 再对也 42501）

### 三个关键设计决策
1. **触发方式**：推荐「触发器 `after insert` → `net.http_post`」为主（最实时、不阻塞事务、与既有范式一致），配一个定时扫描兜底重试表（pg_net 失败无重试）。**不用 Dashboard Database Webhook** —— 配置不入代码，违反单一真相源。
2. **防打扰聚合**（决定成败）：5 分钟窗口内同一 post 的同类通知合并成「XXX 等 3 人赞了你的帖子」；每用户每分钟 ≤1 条。不做的话一条热帖就能把用户刷到关权限，而 Chrome 一旦 blocked 基本不会再问 → **不可逆**。
3. **角标数字的单一真相源**：必须钉死「唯一计算入口 = `get_unread_notification_count`」。服务端算好 count 随 payload 下发，SW 直接用 payload 里的 `badge`，**禁止在 SW 里另算一套**（SW 无登录态）。前端 store 打开时走同一个 RPC → 两处同源。
   VAPID 公钥也不硬编码进前端：由 Edge Function `GET ?action=config` 运行时下发，换密钥不用重新部署前端。

### 真实风险
- **安卓只有圆点、没有数字**（`setAppBadge` 在 Chrome Android 不支持，MDN 兼容表明确 No）→ 产品预期要先对齐，否则会被当成"没做出来"。
- **国内安卓 ROM 对 FCM 有限制**（杀后台/限制后台网络）→ 安卓到达率不保证，这是最现实的风险。
- iOS 必须**装到主屏**才收得到推送（Safari 标签页不行）→ 覆盖率天然低，要不要为它单独做引导得先决定。
- 新 SW 需要用户重开一次应用才生效（`skipWaiting`/`clientsClaim` 已有，所以不会拖太久）。
- 通知滥用后权限被关是不可逆的 → 建议首版先只做「有人回复/转发」这类高价值事件，点赞先不推。

### 对既有网页端提醒的影响面（用户关心的问题）
既有链路 = `stores/notifications.ts` 的 `unreadCount`（`boh_unread_refresh` 事件 + refreshUnreadCount）→
导航栏红点 / Messages / 灵动岛 toast / realtime（`notifications-api.js:458`、`Messages/index.vue:1105`）。

其余全为增量：Pushplus 三个调用点没动、realtime 没动、toast 没动。

### 修掉的真问题（自查发现）
1. **`applyAppBadge` 的 unhandled rejection**：`void setAppBadge()` 不会接住 rejection，
   iOS 未授权时抛 `NotAllowedError` 会变成全局未处理 Promise 拒绝 → 改成 async + await + try/catch。
2. **`renotify: true` 无用且有害**：它只在「复用同一个 tag」时才有意义，而每条通知 tag 是唯一的
   （`boh-<notificationId>`）→ 收益为零，还增加部分浏览器抛 TypeError 导致通知弹不出的风险 → 移除。
   （若以后改按类型合并 tag，才需要打开）
3. **`deliverOutbox` 意外异常时 attempts 不落库 → cron 无限重投**：核心逻辑在写 attempts 之前抛
   （最典型 = VAPID 配错）会让 attempts 永远停 0。→ 拆 `deliverOutboxCore` + 外层兜底，
   无论成败 attempts 都 +1，达 `MAX_ATTEMPTS(3)` 置 failed。
4. **设置页首帧误显「当前环境不可用」**：能力检测同步、服务端配置要等网络 → 加 `pushLoaded` 加载位。
5. **运维坑（文档化，未改代码）**：改 `push-sw.js` **不会触发 SW 更新** —— 浏览器只比对 sw.js 字节，
   push-sw 只是 importScripts 的运行时依赖。改完推送逻辑必须让 sw.js 也变化（如在 vite.config.js 加注释）。

# 横屏左栏文字放大（用户二次反馈）

用户看真机截图后说「侧边栏有点小」「文字可以改一下更大一些」。截图是宽栏档（约 1360 视口）。

## 关键约束

**栏宽不能加**：1280 − 240 = 1040px 是右区容纳 Forum 两栏（主栏 + 240~320 侧栏）的下限
（landscape-rail.css:183 注释明示），栏宽一加右区就跌破。所以放大只能加元素。

## 改动（只动宽栏档 ≥1280 + 菜单浮层）

- 条目 52 → **60**、图标 22 → **24**、文字 15 → **17**、条目 padding 11/14 → 13/16、gap 14 → 15
- 品牌位：logo 26 → **32**、名称 14 → **17**、更多按钮 26 → 30、top 34 → 36
- 菜单项 13 → **15**、padding 9/12、菜单 min-width 150 → 172（浮层，无溢出风险）
- 窄栏完全不动：1100×800 内容 634 = 634 刚好放下，图标/字再大会溢出（紧凑档也兜不住这种"正常窗口"）

## 验证

- `probe-rail-landing.mjs` **39 PASS / 0 FAIL**（断言期望值已同步 60/24/17）
- 1440×900 实测 scrollH 730 = 730 不溢出（内容变高被 flex 撑满吸收）
- 截图 `debug-screenshots/rail-landing/2-wide-1440.png`
