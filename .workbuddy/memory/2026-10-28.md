## 15:00 定时依赖审计首次运行判红 —— 两个真 bug（一个在我自己写的 CI 脚本里）

用户报「构建失败了，以及为啥我现在才收到构建失败通知」。核查结果：

### 结论一：**没有构建失败**

`24100b1d` 上三条 push 触发的工作流全 success：CI Quality Gate、Deploy to GitHub Pages、CodeQL。
红的是 `Dependency Audit (scheduled)`（run 40646157861）—— 那是 10-27 新加的**每日兜底审计**，
`gh run list --workflow=audit-scheduled.yml` 只有这一条记录 ⇒ **它是这个 workflow 的第一次运行**。

### 结论二：为什么「现在才」收到 —— GitHub 的 schedule 被延迟了 5h41m

cron 是 `7 1 * * *`（01:07 UTC = 09:07 CST），实际 started_at 是 `06:48:58Z`（14:48 CST）。
不是 crontab 写错（我核对过），是 GitHub 的 schedule 事件延迟/补跑。
**教训：定时任务的通知时间不能按 cron 反推，查 `started_at` 才算数。**

### 结论三：那次失败**查不出原因**，是我自己写的 workflow 有缺陷

脚本里写的是 `set -uo pipefail`。Actions 的 `run` 默认是 `bash -e {0}`，
**`set -u` 不会关掉 `-e`** ⇒ `npm run security:audit` 一返回非 0，shell 当场退出，
后面的 `code=$?` / `cat audit.log` / 开 issue **全都没执行**。
用户只收到一封「Process completed with exit code 1」，日志里零审计输出，追踪 issue 也没开。

- 修法：脚本开头加 `set +e`（再 `set -uo pipefail`）。
- 反证：`bash -e -c 'false; echo reached'` 打不出任何东西（exit 1）；加 `set +e` 后能拿到 `code=1` 并继续。
- 验证：修完手动触发一次，issue #14 立刻被自动开出（正文里带着审计输出）—— 这就是修复生效的证据。

### 结论四（最要紧）：依赖审计门禁在本地**静默假绿**

拿 issue #14 一看：`low 0 → 4`，来自 `vite-plugin-pwa`（直接依赖）。
可我在本地跑 `npm run security:audit` 得到的是「0/0/0/0 ✅ 通过」—— 两边打架。

真因：`npm audit` 的 `/security/audits/quick` 端点**已退役**，返回 **400**，
而错误响应本身也是一坨合法 JSON（`{"message":"400 Bad Request - POST .../audits/quick ..."}`）。
旧代码判据是 `raw.includes('{')` ⇒ 当成报告 ⇒ `countByLevel` 从缺字段里读出全 0 ⇒ 打印「通过」。

**这是门禁最危险的形态：不是红，是绿得没有依据。** 我按本地结果查了半天网络和公告，方向全错。

- 判据改成 `isValidReport()`：必须存在 `metadata.vulnerabilities` 对象，不是「输出里有花括号」。
- 拿不到报告时把人能看懂的原因打出来（端点退役 / registry 不可达 / 无输出），
  **CI 严格档 exit 1**（兜底门禁宁可红也不能静默放行），本地 exit 0 但明说「这次什么都没验成 —— 不是通过」。
- `--from-json` 回放入口同样严格（它是 check:gates-self-test 的自证通道，不能接受读不懂的报告）。
- 反证：造一个假 `npm`（audit 分支输出 400 JSON + exit 1）→ 本地档 exit 0 且明说没验成、CI 档 exit 1；
  伪造 400 喂 `--from-json` → exit 1。`check:gates-self-test` 18/18 仍会红。

### 4 个 low 的处置：登记基线（low 0 → 4）

链：`vite-plugin-pwa@1.3.0 → workbox-build@7.4.1 → @rollup/plugin-node-resolve@16.0.3 → deepmerge@4.3.1`。
根因 `GHSA-gcqx-w48m-w2h4`（deepmerge `mergeObject()` 原型污染），`fixAvailable: null`
（4.3.1 已是该包最高版），`npm audit fix` 动不了，只有 `--force` 能把 vite-plugin-pwa 连锅端。

可达性实证：四层全 `dev: true`；`grep -rl deepmerge dist/static/js/` **零命中**；
它只在 workbox-build **构建期**生成 SW 时调用，输入是本仓 `vite.config.*` 写死的配置，不经用户输入。

闭环验证：基线更新后手动触发 → run 40647984678 **success**，issue #14 于 07:07:15Z 自动关闭。

### 附带解决：SSH over 443 的 `Connection closed`（这条以前一直靠「重试」绕）

`git push` 连续 6 次失败：`Connection closed by 198.18.0.71 port 443`（198.18.x.x = 代理 fake-IP 段）；
但 `ssh -T git@github.com` 认证成功、443 TCP 也可连 ⇒ 不是网络不通、也不是权限。

真因是 macOS OpenSSH 默认 `IPQoS=lowdelay`，某些中间设备会据此**直接关连接**：
握手能过、认证能过，一传数据就断。加 `IPQoS none` 后**一次就通**。

已写进 `~/.ssh/config` 的 `Host github.com` 段（备份 `~/.ssh/config.bak.20261028`）。
以前 MEMORY.md 里「失败重试 1~2 次即通」的描述其实是这条的症状，别再靠重试。
