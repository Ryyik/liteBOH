## 修：头像框控制台「上传后看不到素材」

- 现象（用户报）：上传「中秋特别.PNG」后 ①提示"没有透明层"，但用户认为图明明有透明 ②画布上**什么都看不到**（素材与头像圆都消失）。
- 实测该文件（`~/Downloads/03_图片素材/头像框/中秋特别.PNG`）：1400²、`sips` 报 `hasAlpha: yes`，但**196 万像素 alpha 全 = 255，0 个真透明像素**，中心是纯白 `(255,255,255,255)`。→ `hasRealAlpha=false` 与 `detectInnerHole r=0` **都是正确判定**；「有透明」是被「文件带 alpha 通道」误导（白底存成 RGBA）。
- 真 bug（P0，已修）：`AvatarConsole/index.vue` 的 `metrics` computed 在 `!hole.r` 时提前 return `{scale,holeShare,offset}`（**没有 k 字段**）→ `layerStyle` 里 `k||0` 取 0 → 图层宽高 0×0 → 素材完全不可见（实测 `getBoundingClientRect` = 0×0，left/top 恒为 191）。运营因此无法判断该不该抠底。
- 修法：几何收进纯模块 `frame-geometry.js` 新增 `layerTransform()`（k 与锚点的唯一实现；**测不出内孔时锚点回退到图片自身中心 = 原图铺满画布**），组件只调它；`metrics` 恒带 k（仅把 scale 压成 NaN 供读数显示「测不出」）；未测出内孔时不再画 6px 假头像圆，改为 `.afc-no-hole` 显式提示；四档 `.sizebox.unknown` + 「框层 —」、「最紧档」文案说明，不再用绿色「通过」骗人；无透明层提示文案改为「没有一个真透明像素 —— 带 alpha 通道 ≠ 有透明区」。
- 该图抠白底后（`resolveWhiteBackground(244)` 清掉 67.49% 背景）：内孔 r=407 / 占比 58.2% / @zoom=1 scale=1.718，四档全 ok —— 即**点一下就能用**，卡点只是"看不见图所以不敢点"。
- 验证：单测 `avatar-frame-geometry.test.js` 32/32（新增 `layerTransform` 5 条，含「r=0 时尺寸必须有限且 >0」）；探针 `probe-avatar-frame-console.mjs` 新增 A2 场景「白底无透明层素材」（31 → 41 断言）**41/41 PASS**。反证：修复前同探针 A2 三条转红（`{"w":0,"h":0}`、`avatar=6`），修复后全绿。

## 头像框：按人发放改「搜用户列表」+ 修「草稿存不进去」

- 用户问「我存的草稿在哪看啊」→ 查线上 `avatar_frames`：**一条草稿都没有**（只有 7 个 published）→ 不是没找对地方，是**根本没存进去**。
- 根因（契约冲突）：`scale numeric(4,2) not null`，而测不出内孔时 `metrics.scale = NaN` → `save()` 拿 `Number(NaN.toFixed(2))` 去 upsert → JSON 序列化成 `null` → 服务端 23502 拒绝；而「存草稿」按钮原先只校验 `draft.id` → 必然白点一次。附带同源问题：`bakeFrame` 在 `hole.r=0` 时把 (0,0) 当孔心 → 成品只剩右下角一块（废图）。
- 修：
  1. `frame-geometry.js` 抽出 `anchorPoint(hole,imgW,imgH)`（**唯一实现**）：有孔用孔心，无孔回退图片自身中心；`layerTransform` 与 `bakeFrame` 共用。

## 修：dev server「Failed to resolve entry for package "https"」报错遮罩

- 现象：Vite 报错遮罩，指向 `node_modules/node-fetch/lib/index.mjs:5:19`；遮罩**吃掉整页点击**（今天把两个探针坑停了两次），那一次模块加载失败还会拖死 tfjs chunk → 论坛图片安全检测（nsfwjs）不可用。
- 根因链：`src/utils/forum-image-moderation.js` 动态 `import('@tensorflow/tfjs')` → tfjs-core 产物里保留 Node 平台分支 `importFetch: () => require('node-fetch')`（浏览器永不执行）→ 但**只要有人真去解析 `node-fetch`**，Vite 就取它的 ESM 入口 `lib/index.mjs`，开头 `import https from 'https'` → `https` 是 Node 内置模块，浏览器端没有这个「包」→ 抛错。
- 关键发现：当年加的 `optimizeDeps.exclude: ['node-fetch']` **只堵住了「预构建扫描」这条路**，代价是真被 import 时 Vite 直接把 Node 版 ESM 源码喂给浏览器：实测 `import 'node-fetch'` 被重写成 `/node_modules/node-fetch/lib/index.mjs` → 请求它返回 **HTTP 500 + 错误页**。
- 修：`resolve.alias['node-fetch'] = scripts/shims/node-fetch.browser.js`（空实现，默认导出不可用函数 + 几个具名导出），两条路一起堵。生产包不受影响（tfjs chunk hash 不变，那句 `require("node-fetch")` 在 `globalThis.fetch == null` 的守卫后面，现代浏览器恒为死代码）。
- 护栏：新增 `scripts/probes/probe-vite-dep-scan.mjs`（6 断言）——清 `node_modules/.vite` 冷启动 + 首页/管理端无遮罩 + **临时建模块走一遍 `import 'node-fetch'` 解析**，断言重写目标是替身且 200（finally 删临时文件）。
- 反证：注释掉别名 → 同探针转红（`→ /node_modules/node-fetch/lib/index.mjs`，请求 **status=500**）；恢复后 6/6 绿。`vite build --outDir dist-check` 通过（55.85s），`check:views` / `check:bundle` PASS。
- 备忘：本机 zsh 的 BSD `grep` 不支持 `\|` 交替（今天第三次静默失效）→ 多模式一律用专用搜索工具。
