## 草稿：僵尸草稿「啊」+ 意外刷新丢内容/图片（同日第二轮，未提交）

### 僵尸草稿根因（已查实，不是猜）

DB 实测 `forum_post_drafts` 里该行 `content='啊'`，`updated_at` 在用户"删完"之后仍被刷新
⇒ 删除**成功过**，是**之后又被 upsert 写回**。链路：

1. `savePostDraftToDatabase(null)` 删除成功后调 `clearDraftClearedMarker()` —— **把「用户明确
   删过」的墓碑清掉了**；
2. 另一个宿主实例（UserSpace keepAlive）正在 `await getForumPostDraft()`，它读到的
   `localDraft` 是删除**前**的值；await 返回 `remoteDraft=null` ⇒ 走
   `if (localDraft) savePostDraftToDatabase(localDraft)` 把「啊」写回云端；
3. `restorePostDraft` 的 `!remoteDraft` 分支原本还**主动** `clearDraftClearedMarker`，等于开第二道门。

修法（单点收口，别在各调用点打补丁）：
- 墓碑只在**新草稿 upsert 成功**后清；delete 成功后不清；restore 路径一处都不清；
- `savePostDraftToDatabase` 加守卫：`draft.savedAt <= readDraftClearedAt()` 一律拒写（它是
  全部云端写入的唯一出口）；
- `applyExternalDraftChange` 收到 clear 时 `postDraftRestoreSeq += 1`，让本实例在飞的恢复失效。

### 刷新/崩溃不丢（新增实时暂存）

`<prefix>_{uid}_autosave`，**不是第二份草稿**：编辑器开着时 debounce 400ms 写、`pagehide`+
`beforeunload` 同步 flush；内容是编辑器本机镜像，图片只存**已上传的持久 URL**（`blob:` 一律丢，
存进去刷新后必成灰块）。恢复时与正式草稿取 `savedAt` 较新的一份；用户明确删除（不保存/清空后
关/发布成功）时一起清。图片回填只在编辑器**一张图都没有**时做（已有图=活会话，不能洗掉）。

### 改动文件

`ForumMain.vue`（墓碑守卫 + 实时暂存 + pagehide + restore 取较新 + removePostImage 跳过无
删除凭据的恢复图）、`useForumPostDraftStorage.js`（autosave 读写 + `normalizeDraftImageList` +

## 第三轮：跨设备僵尸草稿闸门 + 两个"永久卡住"（同日，未提交）

### 僵尸草稿还剩下的那条路

上一轮修的是**同一台设备**内被另一个实例写回。剩下的形态：设备 A 删掉草稿（云端行已被硬删），

  否则 400ms 防抖在删除之后才落盘，下次打开又恢复（"删了又冒出来"）。

## 上传档位收成 1600（2026-10-29 第二轮，产品已拍板）

**决定**：不降画质，删「死像素」。上传长边 2048 → **1600**，目标体积 2MB → 0.9MB。

**依据（代码事实，不是手感）**：展示侧最大只加载 1600 —— 列表 `w_720`、详情
`FORUM_DETAIL_IMAGE_TRANSFORM` 的 `c_limit,w_1600`，而 `ForumImageViewer.vue:45` 的取图顺序是
`[detailUrl, originalUrl, url, thumbUrl]` 且 detailUrl 恒存在 ⇒ `originalUrl` **永不被下载**。
所以 2048 档多出的 39% 像素只付上行与存储，用户看不到。

**实测（先前错误估算已纠正）**：此前文档写「6 张 ≈ 12MB」是拿 2MB **上限**当实际值。用 Chrome
canvas 真编码真实照片（WebP q0.85 ≈ 197KB/MP）：2048 档 620KB/张、6 张 3.6MB；1600 档 378KB/张、
6 张 2.2MB（2Mbps 上行 15s→9s）；单张压缩耗时 200ms→100ms。壁纸类平滑图会低到几十 KB，不能当样本。

**改动**（论坛侧显式传参，不动 `image-compression.js` 的全局 2048 默认，以免牵连影集/云盘）：
- `utils/api/forum-format.js`：新增 `FORUM_UPLOAD_IMAGE_MAX_DIMENSION=1600` /
  `FORUM_UPLOAD_IMAGE_TARGET_SIZE_MB=0.9` / `FORUM_UPLOAD_IMAGE_OPTIMIZE_OPTIONS`（单源，注释写清
  「不得超详情展示宽度」）。
- `views/Forum/forum-config.js`：re-export（沿用该文件既有模式）。
- `views/Forum/ForumMain.vue`：`prepareForumImageForUpload` 改为传常量，不写裸 `{optimizeForUpload:true}`。

### 纠正（同日晚，真实管线实测打回两个数字）

上一段写的「6 张 3.6MB→2.2MB / 压缩 200→100ms」不成立，实测（vite dev 里直接调
`getImageCompressionPlan` + `compressImageFileToUploadLimit`，三个 4032px 样本）：

| 样本 | 2048 档 | 1600 档 | 体积 |
|---|---|---|---|
| 壁纸-渐变 | 2048² 55KB 222ms | 1600² 40KB 269ms | −27% |
| 壁纸-径向 | 2048² 269KB 264ms | 1600² 199KB 205ms | −26% |
| 照片放大 | 2048×1536 379KB 256ms | 1600×1200 249KB 205ms | −34% |

- **体积降幅 −26%~−34%**，不是面积比 −39%（WebP 编码非线性）。
- **压缩耗时基本持平**：worker 启动 + 库质量迭代是固定成本，把省下的编码时间吃掉。
  教训：单次 `canvas.toBlob` 读数 ≠ 真实管线耗时，别拿它写「快了一倍」。
- 只有**相对降幅**可靠，绝对 KB 强依赖内容（同尺寸壁纸 55KB vs 照片 379KB）⇒ 别把样本 KB 当通则。
- 净结果按上行带宽：1Mbps 省 ~8s、2Mbps 省 ~5s、50Mbps 基本无感。它只压了关键路径「上传」段
  的约 30%，**不是「卡」的解药**。

### ② 重试也必须吃剩余预算（顺带发现的第二个翻倍坑）

客户端已 abort」，白扣额度还被记成「云端不可达」触发冷却。
改为 `chainBudgetMs`（循环外算一次）+ `remainingMs`，剩余 < `MIN_HOP_TIMEOUT_MS`(1200)
就 break。非流式 + 流式两处都改。

## 更新后首进「很多正在加载…」四块占位——根因与修复（15:00，未提交）

**报障**：更新完第一次进网页，竖屏出现 4 块「三点 + 正在加载…」竖排（截图 1206×2622，等距 99px）。

**定位（探针实测，非猜）**：`diag` 探针用 playwright 拦截面板 chunk 返回 404，收集 `.async-panel-quiet`
的 `__vueParentComponent` 链 ⇒ 3 块来自 **App.vue 常驻三浮层**（AiEdgeTrigger / AccountBindPrompt /
AdminConfirmModal），99px/块与截图逐像素吻合；第 4 块是页面级内容面板（我的页 ProfileHomePanel 一类）。
**机制**：这些浮层「隐形直到被调用」，chunk 失败后 errorComponent 把**整个组件**替换掉 ⇒ 内部隐藏逻辑消失，
默认的 AsyncPanelQuiet（2026-10-27 定稿的内容面板失败态）就以文档流形态裸露在页面底部。更新窗口期
（旧 SW/旧 hash 404 或弱网 20s×3 超时）多块一起失败 ⇒ 「很多加载中」。恢复链
（recoverDynamicImportFailure → forceCleanAndReload，30s 冷却）是真正出口，占位只是强刷生效前的裸露。
**注意**：AsyncForum（论坛）没有 errorComponent，404 时错误直接击穿到 GlobalErrorBoundary
（「页面出了点问题」卡）——另一族故障，与本次四块占位不同源，未动。

**修复**：`async-component.js` 新增 `silent: true` 选项 + `AsyncPanelSilent`（渲染 null）——
浮层/触发器型面板失败时**什么都不渲染**，恢复链照常发起、上报照常发；内容型面板保持 AsyncPanelQuiet 不变。

## 折叠屏 Web 适配：调研 + 本项目实测（14:40，只调研未改代码）

产出 `docs/2026-10-29-折叠屏适配方案.md`。结论：**不需要折叠屏专属适配，需要补三个断点裂缝。**

### 设备真值（官方，CSS px / vp）
- 华为 Pura X Max：折叠态 **459×672**、展开态 **939×664**（不是"2400 宽"，DPR≈2.75）
- iPhone Duo（WebKit 官方表）：外屏竖 382×580、**外屏横 594×368**、内屏竖 669×867、**内屏横 951×585**

### 三条实测根因
1. **断点裂缝 769–1023px**：导航切移动版是 `max-width:768`（`unified-nav.css:1034`），
   内容切横屏左栏是 `FORUM_LANDSCAPE_QUERY`（`landscape && ≥1024 && ≥600h`，

2. **矮横屏无档**：`max-height` 散点是 500/520/560/600，缺「宽度够、高度不够」。
   368 高时顶栏 78 + 标签栏 ≈50 + 搜索框 56 + `forum-main-grid` padding 80（顶边 204 vs page 顶边 124）
   = 首屏只剩 <100px。
3. **内容无最大宽度**：939 视口下搜索框/卡片铺满 939，行宽远超可读区。
   修法 `max-width: min(100%, 720px)`（**不能裸写 720px**，481–768 窄窗会被硬压）。

### 前沿 API 结论（别再走弯路）

- 🔑 **CLI 部署数据库的正确姿势（下次直接用，别重走弯路）**：
  1. MCP `execute_sql` 是 `supabase_read_only_user` + `default_transaction_read_only=on`
     ⇒ **任何 DDL 都写不了**（`cannot execute CREATE FUNCTION in a read-only transaction`）。
     别再拿它做「事务里试建再回滚」的语法验证，那是假验证。
  2. 直连 `db.<ref>.supabase.co:5432`：TCP 能连但 **TLS 握手 EOF**（SNI 阻断，DNS 还会返
     `198.18.0.70` fake-IP 导致 dial timeout）⇒ 必须走 pooler。
  3. pooler 用 **5432（session 模式）**；用 6543（transaction 模式）会报
     `prepared statement "lrupsc_1_0" already exists (SQLSTATE 42P05)`。
  4. 密码里有 `@` ⇒ 必须 `%40` 编码；连接串在 `.vscode/settings.json` 的 `connectString`。
  5. `db push` 会停在 `[Y/n]` 交互 ⇒ 必须 `</dev/null`，否则前台跑会被杀成 exit 137（假故障）。
  最终命令：
  ```
  npx supabase db push --db-url "postgresql://postgres.<ref>:<pwd%40enc>@aws-1-<region>.pooler.supabase.com:5432/postgres" </dev/null
  ```
  6. `functions deploy` 不需要 db-url，`--project-ref` 即可（CLI 自己的 token 在 keychain 里，
     service=`Supabase CLI`；注意它**不是** PAT，Management API 的 `/database/query` 用它会 401
     `JWT could not be decoded`，那条路走不通，别再试）。
- 语法兜底（无可用 PG 时）：`pgsql-parser`（libpg-query）**是异步的**，`parse()` 返回 Promise，
  直接 `Object.keys(parse(sql))` 得到 `[]` ⇒ 会得出「全部通过」的假绿。必须 `await`，且要先反证
  「坏 SQL 会抛错」。实测 4 个迁移语句数 7/8/3/3，与文件结构逐一吻合（说明 dollar-quote 平衡）。
