## 数据管理面板审查 v2：真 JWT claims 实测（17:55）

**取证方法突破（可复用）**：本机到 `*.supabase.co` 在 TLS SNI 层被断（同 IP 换 SNI 即 200，代理直连/h1/tls1.2 全 000 ⇒ 与 CLI 无关）。
但 RLS **可执行验证**，不必真实登录：
```
begin; set local request.jwt.claims='{"sub":"<uid>","role":"authenticated"}'; set local request.jwt.claim.sub='<uid>';
set local role authenticated; <stmt>; rollback;
```
`auth.uid()` 读这两个 GUC ⇒ `auth.uid()=id` / `current_user_is_admin()` 全真实生效。
**正反对照**：普通用户改他人 username/posts.status → 0 行；admin 改 → 各 1 行。
**神技**：把 `grant` 写进同一事务再 rollback，可在线上安全试算「补授权后会发生什么」，ACL 零变更。

**推翻 v1 的结论**：
- P0-1 修法「GRANT UPDATE(role,points,…)」**作废**——实测普通用户可自升 `role='admin'`、自刷 `points=999999`、补 SELECT 后遍历全员手机号。
  因为 `profiles_update_self` qual 只有 `auth.uid()=id`，与列级授权叠加＝提权。必须走 SECURITY DEFINER RPC。
- P0-1 有**第二层**：`.update().select()` = `RETURNING *`，撞上 `shipping_*` 的 SELECT 收窄（`2026070802` H-1 有意 revoke）
  ⇒ 只改用户名也挂。修授权之外**必须**把 `.select()` 改显式列。
- P0-2「新增用户」补授权后**仍 RLS violation** ⇒ 唯一根因是缺 admin INSERT 策略（只有 `profiles_insert_self`）。
- P1-5「列级授权全仓 0 命中」**撤销**：迁移在 `2026090803_security_hardening.sql:68-84`（UPDATE 白名单排除 role/points/experience/tags/hide_online_status，INSERT 只 5 列）。v1 是 grep shim 对 `\|` 的假阴性。
- P0-3 归因正确：`ai_pricing_config` 纯缺 GRANT，且补授权**已验证安全**（普通用户被 `current_user_is_admin` 策略拦 0 行）。

**影响面**：全库 22 张表有列级收窄，落在面板内的只有 `profiles`（users/points 两页签）。
**报告**：`docs/2026-11-11-数据管理面板功能可行性全量审查.md`（已重写为 v2，含 §8 修订记录）
