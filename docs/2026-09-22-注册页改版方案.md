# 注册页（`/#/join`）现状分析与改版方案

日期：2026-09-22
范围：`src/views/Join/index.vue`（注册页）、`src/views/Login/index.vue`（登录页/弹窗的注册入口）、`src/utils/auth-validation.js`（校验单源）、`src/utils/api/auth-api.js#signUp`（落库链路）
取证方式：源码通读 + Playwright 实测（`scripts/probes/probe-join-audit.mjs`、`probe-join-mobile-metrics.mjs`，截图见 `debug-screenshots/audit-join-*.png`）

## 一、现状结构

### 1.1 路由与入口

- 注册页路由：`/#/join`（`src/router/routes/public.ts`）。
- 入口共 6 处，全部落在 `/join`：登录页页脚「立即注册」、登录弹窗「注册 BOH 账户」/「注册 BOH ID」、`Shows` CTA、`AboutUs`「加入方块之家」、首页 Hero 与页脚「加入我们」、8 周年活动页步骤按钮。
- 反向出口：注册页底部「已有账户？」→ `/login`。**注册页没有「返回上一页/来源」的能力**，从活动页进来的用户只能跳去登录页。

### 1.2 页面结构（单页单列，无分步）

```
join-page
└─ join-container (max-width 800, 居中)
   └─ apple-style-wrapper
      ├─ Step 1 注册表单
      │  ├─ logo-section      36 个点组成的旋转圆环 + 内层 "BOH"
      │  ├─ h1 一个账户，尽享 BOH。
      │  ├─ p  副标题（价值主张）
      │  ├─ form.apple-form
      │  │  ├─ apple-input-group（一张白卡，内部用 1px 分割线分 6 行）
      │  │  │  1 方块 ID（input text，maxlength 20，autocomplete="off"）
      │  │  │  2 电子邮件（input email）
      │  │  │  3 密码（input password）
      │  │  │  4 确认密码（input password）
      │  │  │  5 生日（月 select + 日 select，无年份）
      │  │  │  6 头像（点击 → 文件选择 → 裁切弹窗 → 压缩 → 上传）
      │  │  │  每行右上角一枚「必填 / 选填」角标
      │  │  ├─ honeypot（离屏 input，反爬）
      │  │  ├─ p.apple-error-text（唯一的错误出口，红色胶囊）
      │  │  ├─ agreement-section（勾选用户协议 + 隐私政策，弹窗内嵌 DOMPurify 消毒内容）
      │  │  └─ apple-action-section
      │  │     ├─ AltchaWidget（人机验证，auto=onload）
      │  │     ├─ button 继续
      │  │     └─ 冷却提示（30s）
      │  └─ apple-privacy-info（隐私说明卡）
      │  └─ apple-footer-links（已有账户？ / 忘记密码 / ?）
      └─ Step 3 成功页
         ├─ 分支 A（需邮箱确认）：注册成功，还差一步 + 重发验证邮件（60s 冷却）+ 去登录
         └─ 分支 B（直登模式）：注册成功 + 去登录
```

> ⚠️ `currentStep` 只用到了 `1` 和 `3`，模板注释写着「Step 3: Success Message」，**Step 2 不存在** —— 分步流程被砍过一半，遗留了「继续」这个按钮文案（暗示还有下一步，实际点完直接结束）。

### 1.3 字段构成

| # | 字段 | 类型 | 必填 | 校验（`auth-validation.js`） | 数据库落点 |
|---|---|---|---|---|---|
| 1 | 方块 ID | text | ✅ | 3–20 字符；中英文/数字/`_`/`-`；禁首尾 `_-`；禁纯数字；16 个保留词 | `profiles.username`（UNIQUE） |
| 2 | 电子邮件 | email | ✅ | `^[^\s@]+@[^\s@]+\.[^\s@]+$` | `auth.users.email`（profiles 已 drop 该列） |
| 3 | 密码 | password | ✅ | 长度 ≥ 6 | `auth.users` |
| 4 | 确认密码 | password | ✅ | 仅做 `===` 比对 | — |
| 5 | 生日 | 月 + 日 select | ⬜ | 无（可只填月、或 2 月 31 日） | `profiles.birth_month / birth_day`（varchar） |
| 6 | 头像 | file → 裁切 → 压缩 → 上传 | ⬜ | 客户端压缩至 ≤0.5MB / ≤800px | `storage.avatars` + `profiles.avatar_url` |
| 7 | 协议勾选 | checkbox | ✅ | 驱动提交按钮 disabled | `localStorage: boh_agreed_to_terms` |

**必填项 4 个，实际需要 3 个**（确认密码可用密码可见开关替代）；**选填项 2 个被塞进同一个必填流程**。

### 1.4 提交链路

```
submitForm()
├─ 冷却检查（30s）
├─ honeypot 非空 → 拒
├─ 填表耗时 < 5s → 拒（MIN_FORM_FILL_MS）
├─ validateUsername → validateEmail → validatePassword → 两次密码一致
├─ startSubmitCooldown()（无论成败都进 30s 冷却）
└─ signUp(username, email, password, metadata, altchaPayload)
   ├─ 客户端预查重：profiles.ilike(username).limit(5) → 精确比对 → USERNAME_TAKEN
   ├─ supabase.auth.signUp({ data: { ...metadata, username } })
   ├─ error 分支：USER_ALREADY_REGISTERED / EMAIL_RATE_LIMIT / CAPTCHA_FAILED / USERNAME_TAKEN / INVALID_*
   ├─ 客户端写 profiles.insert（role/points 只走白名单字段，23505 静默忽略）
   └─ if (data.user && avatarBlob) → 上传 avatars → 回写 profiles.avatar_url（失败回删文件）
└─ 成功分流：data.session 存在 → 直登模式；不存在 → 需邮箱确认（发重发按钮，60s 冷却）
```

服务端还有一层：`auth-login` EF 负责登录侧「方块 ID → 邮箱 → 密码校验」的整链（见 `docs/2026-09-21-*`），注册侧仍是 `supabase.auth.signUp` 直连。

### 1.5 反滥用策略（当前生效）

| 手段 | 位置 | 对真人的代价 |
|---|---|---|
| Altcha PoW 人机验证 | 客户端组件（`VITE_ALTCHA_ENABLED=true`） | 需等待解题，实测进入页面即 `Verifying…` |
| Honeypot（离屏 `website`） | 客户端 | 无（对自动填充工具也可能误伤） |
| 填表耗时 ≥ 5s | 客户端 | **密码管理器/浏览器自动填充用户几乎必踩** |
| 提交后 30s 冷却 | 客户端 | 一次报错后要等 30s 才能改错重试 |
| 重发邮件 60s 冷却 | 客户端（对齐 Brevo 限速） | 合理 |
| 用户名/邮箱唯一性 | 客户端预查 + DB UNIQUE | — |

## 二、可优化问题清单

按优先级排列。P0 = 影响注册成功率或真实性，P1 = 体验与可及性，P2 = 一致性/工程债。

### P0

1. **「填表 < 5s 直接拒绝」会误杀真实用户。** 使用 1Password / iCloud 钥匙串 / Chrome 自动填充的用户，从进入页面到点提交可能不到 5 秒；被拒后还要等 30 秒冷却，等于「用密码管理器的人注册不了」。且该判定纯在客户端，绕过成本为 0 —— 代价给了真人，好处给了机器人。
   *落点*：`src/views/Join/index.vue:255`（`MIN_FORM_FILL_MS`）、`submitForm()` 中 `filledDurationMs` 判定。

2. **唯一的错误出口是一个远离字段的红条，且服务端错误用 `alert()`。** 所有校验错误（用户名、邮箱、密码、协议、风控）都写进 `passwordError`，渲染在**协议勾选上方**，与出错字段不邻接；用户改完用户名后红条位置不变，容易看漏。字段级错误在数据层面直接丢失（不知道错在哪个字段）。
   *落点*：`Join/index.vue` 模板 `p.apple-error-text`；`submitForm()` 的 6 处 `passwordError.value = ...`；`catch` 里的 `alert(error.message)`、`handleCropConfirm` 里的 `alert('头像处理出错，请重试')`。

3. **可及性缺口让部分用户无法正确完成注册：**
   - 6 个字段**全部没有 `<label>`**，靠 placeholder 当标签 → 输入后标签消失；placeholder 颜色实测为 `rgb(0,0,0)`（与正文同色），视觉上像已填好的内容。
   - **无 `autocomplete` 属性**，方块 ID 上还显式写了 `autocomplete="off"` → 密码管理器无法识别字段语义、无法生成/回填密码。
   - 输入框 `outline: none`，focus 只把背景从 `#fff` 换成 `#fcfcfc`（对比度约 1.01:1）→ **键盘用户基本看不出焦点在哪**。
   - 注册页**没有「显示密码」开关**（登录页有），确认密码只能盲打。
   - 协议勾选行实测高 21px，小于触控建议的 44px。
   *落点*：`Join/index.vue` 模板输入行 + `.apple-input:focus` / `.apple-input::placeholder` / `.agreement-checkbox` 样式。

### P1

4. **唯一性口径前后不一致。** 前端用 `ilike` 做**大小写不敏感**查重，DB 是 `profiles_username_key UNIQUE (username)` —— **大小写敏感**。结果：用户看到「已被注册」（`bohai` 撞 `Bohai`）而数据库其实允许；反之若预查因 RLS 收紧而静默失败（`catch` 里只 `warn`），重复用户名要到 insert 时才暴露。
   *落点*：`auth-api.js#signUp` 的 `usernameRows` 查询 + `docs/database/schema/tables/profiles.sql`。

5. **生日收集不完整、且无年份 → 无法做任何年龄相关判断**（未成年人保护、生日祝福、年龄分层推荐都拿不到）。另 `birth_day` 固定渲染 1–31，2 月 31 日可选。
   *落点*：`Join/index.vue` 模板生日行；`signUp` metadata `birth_month/birth_day`。

6. **头像 / 生日被塞进注册必填流程，摩擦与失败面都放大。** 头像行需要「文件选择 → 裁切弹窗 → 压缩（动态 import 压缩库）→ 上传 storage → 回写 profiles」五步，任一失败静默不阻断 —— 用户以为设好了，其实没有；而注册页首屏高度实测 1531px（移动端），大量用户根本滚不到头像行。
   *落点*：`handleCropConfirm` / `uploadAvatarToSupabase` / `deleteAvatarFromSupabase`。

7. **`continue` 按钮语义错误**：「继续」暗示还有下一步，实际没有 Step 2。按钮文案与实际流程不符。
   *落点*：`Join/index.vue:363` `submitButtonLabel`。

8. **`signUp` 的 metadata 里塞了 `role` / `points` / `nickname`**，写入 `auth.users.raw_user_meta_data`。虽然落库侧有白名单，但把权限语义字段放进用户可控的 metadata 属于历史包袱，建议清掉。
   *落点*：`Join/index.vue` `signUp(...)` 第 4 参。

### P2

9. **协议勾选状态跨页持久化且与登录页共用同一个 key**（`boh_agreed_to_terms`）→ 用户在登录页勾过一次，之后进注册页**默认就是已勾选**，注册时并未重新确认。合规上是灰色地带。
10. **第三方登录能力已实现但无入口**：`auth-api.js#signInWithOAuth` + `stores/auth.ts#loginWithOAuth` 都在，**没有任何 UI 调用**。注册页完全没利用这个降门槛的机会。
11. **无邀请码 / 推荐码机制**：全仓搜索 `邀请码 / inviteCode / referral` 无命中，社区产品的推荐裂变入口是空的。
12. **注册成功后没有承接**：成功页只给「去登录」，跳过了生日/头像/兴趣这些能提升留存的资料，也没有任何「你的 BOH 主页长这样」的正反馈。
13. **登录/注册双份表单代码**：`Login/index.vue` 里 modal 模式与 page 模式各写了一遍完全相同的表单（约 110 行 × 2），注册页再写第三遍 —— 同一套字段三处维护。
14. **`sizes="(max-width:900px) 100vw, 50vw"` / `srcset` 等登录页优化没有在注册页复用**（注册页用的是 CSS 绘制的圆环 logo，这块无需图片，属于对比说明）。

## 三、主流平台优秀实践提炼

按类别，只列与 BOH 场景真正相关的。

### 社交 / 社区类（Discord、Reddit、小红书、即刻、X）
- **先给内容再要账号**：游客可浏览，触发「点赞/回复/关注」时再弹出注册 —— 用动机驱动转化。
- **降门槛：邮箱验证码 / 魔法链接优先于密码**（Discord、Medium）。用户先进入，密码作为后置设置项。
- **用户名即时可用性反馈**（Reddit、Twitch）：输入 300–500ms 防抖后给「可用 / 已占用」+ 推荐候选（`bohai` → `bohai_2026`、`bohai_x`），而不是提交时才报错。
- **身份选择分流**（小红书「兴趣」、Discord「用途」）：注册后立刻选 3–5 个兴趣标签，为 feed 冷启动提供数据，同时提升「这是我的地方」的归属感。

### 电商类（Shopify、Amazon、SHEIN）
- **「确认密码」几乎被删除**：靠密码可见开关 + 一键生成替代，减少一个必填字段。
- **进度指示**：多步结算流程用 Stepper 明确「还有几步」，降低中途放弃。
- **首单/新人激励前置**：注册前先展示「注册即得 X」，把注册当成收益而不是门槛。
- **游客下单 → 事后转正**：不强制先注册。

### 企业服务 / SaaS（Notion、Linear、Vercel、Stripe）
- **第三方/企业 SSO 优先置顶**，邮箱注册退居次席 —— 对「已有账号生态」的用户是零摩擦。
- **单字段起步**（Notion：先只有邮箱），后续再收集组织名、用途等 —— 每屏只问一件事。
- **「工作邮箱」与「个人邮箱」的错误分流**，并在错误处直接给出下一步动作（如「该域名已注册，去加入团队」）。
- **品牌面板 + 表单双栏**：左栏用大图/产品截图承载信任感，右栏极窄（360–420px）聚焦表单。
- **进度与隐私承诺可见**：「我们不会卖你的数据」这类一句话承诺常驻表单底部。

### 可及性 / 工程通用
- **label 常驻 + 浮动标签**（Material、Apple 新版表单）；错误信息贴在字段下方并与 `aria-describedby` 关联。
- **`autocomplete="username" / "email" / "new-password"`** 是密码管理器能工作的硬前提。
- **focus ring 必须可见**（WCAG 2.4.7 / 2.4.11）。
- **错误摘要 + 字段锚点**：顶部给摘要，点击跳到对应字段。

### 反滥用（现代共识）
- 优先**服务端风控**（行为特征、速率、设备指纹），客户端只做「软提示」，不把真人的时间当成本。
- 人机验证**延迟到可疑时再出现**（隐形验证 / 仅在风控命中时挑战），而不是进入页面就让人等。
- 表单填写时长、honeypot 这类信号**可以用作评分权重，不适合做硬拒绝**。

## 四、四种改版方案

> 共同前提：复用现有 `auth-validation.js`（校订单源）、`AgreementModal`、`AvatarCropModal`、Altcha，保留邮箱确认/直登双分支逻辑与 `signUp` 链路。以下差异集中在**布局、字段节奏、交互与视觉**。

### 方案 A｜极简三字段 · 渐进披露（Minimal Progressive Disclosure）

- **设计思路**：把「注册」压缩成一次 20 秒的决策。首屏只留 3 个必填字段，其余全部推到「注册成功后的一次性引导」。核心假设：字段越少，完成率越高；个性化信息留到用户已投入之后再要，收集率反而更好。
- **布局结构**：单列居中，宽度 440px（现为 500px）。顶部仅品牌标识 + 一句主张；表单为无分割线的独立输入框（非「一张白卡」），字段间距 16px；底部主按钮 + 一行「已有账户？登录」。桌面端右侧留白不做填充（保持呼吸感）。
- **字段构成**：必填 3 —— 方块 ID、邮箱、密码（**删除确认密码**，用可见开关 + 实时一致性提示替代）。生日、头像移入注册成功后引导；协议勾选保留在按钮上方（内联 12px 灰字）。
- **交互方式**：
  - 失焦即校验，错误贴在字段下方并给 `aria-describedby`；
  - 方块 ID 输入防抖 400ms 实时查可用性，占用时给 3 个候选；
  - 密码框内嵌强度条（弱/中/强）+ 可见开关；
  - 人机验证默认折叠为一行「我不是机器人」，可疑时才展开 Altcha；
  - **删除 5s 硬拒绝与 30s 冷却**，转由服务端风控承担。
- **视觉风格**：沿用现有 Apple 浅色语言（`#f5f5f7` / 18px 圆角 / 17px 字号 / `#1d1d1f` 主色），补齐暗色 token、可见 focus ring、常驻 label。整体最「静」。
- **代价**：首屏信息量最小，需要新增「注册后引导」页面（可复用 UserSpace 的弹层）。

### 方案 B｜三步向导（Stepper Wizard）

- **设计思路**：长表单拆成 3 个心理成本极低的步骤，用进度感换取完成率。每屏只问一件事，用户始终知道「还剩几步」。
- **布局结构**：左右分栏。左 42% 品牌面板（大图 / 玻璃卡片 / 步骤说明），右 58% 表单区，居中 380px。进度用 3 个圆点 + 连接线置于表单顶部。**移动端**：品牌区压缩成顶部 120px 条（含进度），表单占满。**协议勾选固定在底部条**，不随步骤滚动。
- **字段构成**：
  - Step 1 账号：方块 ID、邮箱
  - Step 2 安全：密码（强度条）
  - Step 3 完善（可跳）：生日、头像
  - 全局：协议勾选 + Altcha（仅在最后一步出现）
- **交互方式**：`Enter` 推进 / 返回上一步数据保留；步骤切换用横向滑动过渡（复用 `userspace-tab-in/out-*` 的思路）；每步独立校验、通过才解锁「下一步」；Step 3 有显式「以后再说」跳过。
- **视觉风格**：分栏结构下左栏可承载更强的品牌表达（图片 + 玻璃面板）；右栏保持 Apple 白。暗色下左栏用 `--liquid-*` 深色玻璃，右栏浅色 —— **这是四案中唯一天然左右异色的**。
- **代价**：桌面端分栏 + 移动端堆叠需要两套布局；三份步骤状态与校验编排，工程量最大。

### 方案 C｜邮箱优先 · 低门槛双栏（Social-first Split）

- **设计思路**：把注册的「第一道门槛」从密码换成邮箱验证码。用户发一封邮件即进入社区，方块 ID 与密码降级为「进入后设置」。同时把已存在但未接线的第三方登录（`loginWithOAuth`）放上台面。
- **布局结构**：左半 55% 品牌视觉（主图 + 社区实时数据 + 成员头像墙），右半 45% 内 380px 极窄表单区。表单分两层：第一屏只有邮箱 + 「继续」+ 第三方登录按钮；第二屏是 6 位验证码分格输入。
- **字段构成**：第一层：邮箱（唯一）；第三方登录（如已配置）；第二层：6 位验证码 → 设置方块 ID（带候选推荐）→ 设置密码（可「生成强密码」）。生日/头像进「完善资料」，不阻塞。
- **交互方式**：验证码输入框支持自动跳格、整串粘贴、填满自动提交；重发倒计时 60s（沿用现有逻辑）；邮箱已注册时提示「直接登录」而不是报错；ID 与密码两步在同一屏内上下展开，不做跳页。
- **视觉风格**：四案中品牌感最强 —— 左侧大图 + 数据条（「12.8 万块方块已发布」），右侧极窄表单。暗色下左侧图加遮罩，右侧保持浅色卡片。
- **代价**：依赖邮件送达率；**引入验证码会改变现有「注册即登录」的直登逻辑**，需与 `signUp` 的 autoconfirm 分支对齐；改造成本仅次于 B。

### 方案 D｜身份分叉 · 卡片式引导（Persona Fork）

- **设计思路**：把「注册」和「你为什么要来」合成一件事。先用卡片选择身份/用途，页面据此决定后续只收集哪些字段 —— 既降低无效字段，又为推荐系统提供冷启动标签。
- **布局结构**：单列宽版（720px）。上半部分是 2–3 张大卡片（横排，移动端竖排），下半部分是随选择展开的表单区，同屏内过渡、不跳页。顶部一条细进度（身份 → 账号 → 完成）。
- **字段构成**：
  - 身份选择（单选卡片）：如「逛论坛 / 做作品 / 用 AI」
  - 通用：方块 ID、邮箱、密码
  - 依身份追加：兴趣标签多选（社区）/ 主页或作品链接（创作者）/ 用途多选（AI）
  - 生日、头像：进「完善资料」或按身份可选
- **交互方式**：卡片 hover 抬升 + 选中描边；选中后表单从卡片下方平滑展开，可一键「改选身份」回退；兴趣标签用 chips 多选（≥1 即可继续）；最后一步展示「你的 BOH 主页预览」作为完成正反馈。
- **视觉风格**：四案中最「社区感」—— 允许更强的色彩（可直接复用 8 周年活动页的色彩体系与卡片圆角），与 Apple 极简形成对比；暗色下卡片用深色玻璃。
- **代价**：需要定义身份枚举并落库（新字段/新枚举）；对只想快速注册的用户而言是多了一步。

## 七、液态玻璃材质接入（2026-09-22 追加）

### 之前的实际情况（先摆清楚）

第一版 demo **没有**用液态玻璃，是平的（`--surface:#ffffff` / `--surface-2` / `--surface-3` 纯色）。
而且它要替换的那一页 `src/views/Join/index.vue` **本身就是平的** —— 全文件零 `backdrop-filter`、零 `liquid-glass`。
整个 auth 链里只有 `Login/index.vue` 用了（弹窗遮罩 + 移动端容器 + 关闭按钮，都是 `var(--liquid-filter)`）。

项目里的液态玻璃是**成体系的**：`tokens.css` 的 26 个 `--liquid-*`（浅 / 暗 / 不支持降级 三套）
\+ `liquid-glass.css` 的类库（`--strong / --subtle / --overlay / --pill / --inset / --interactive`）
\+ CI 门禁 `check:liquid-glass`（禁在 `liquid-glass.css` 之外裸写 `blur(≥14px)`、禁重复定义）。
`liquid-glass` 类在 7 个组件里实际使用（活动卡 / 订阅计划 / 用户空间侧栏 / 下载页 / AI 广场…）。

### 接入方式

**材质层逐字对齐**：把 tokens.css 的 `--liquid-*` 原样搬进 demo，语义 token 全部派生自材质
（`--surface: var(--liquid-bg-strong)`、`--surface-2: var(--liquid-bg-nested)`），
所以「改材质只改一处」，接入项目时这一整层**直接删掉**换成项目的 `tokens.css` 即可。

**材质分配遵循项目的「一层活跃模糊」约束**（`liquid-glass.css` 里写死的规则：
*One material system, one active blur layer. Nested surfaces use a quiet translucent fill*）：

| 面 | 材质 | 模糊 |
|---|---|---|
| `.jw` 外卡 | `--liquid-bg-strong` + `--liquid-radius-lg(28)` + `--liquid-highlight` + `--liquid-shadow-overlay` | **唯一活跃层**：`--liquid-filter-lg`（blur 36 / saturate 180%） |
| 左栏品牌面板 | 图片底带 + `--aside-band` 玻璃带 | none |
| 品牌文案面板 `.aside-panel` | `--liquid-bg` 填充 + `--liquid-border` + `--liquid-highlight-subtle` | none |
| 输入框 / 下拉 | `--liquid-bg-nested` 填充 | none |
| 协议条（sticky） | `--liquid-bg-strong` | none |
| 移动端内层 | 全部落平（对齐 liquid-glass.css 的「层数 3→1」） | none |

**玻璃必须有东西可模糊**：页面底改成「品牌主图 `main1-1280.webp` + 浅遮罩」。
浅遮罩（`--page-scrim`，α .66~.78）是刻意的 —— 它保证合成后底色仍然浅，
这样**玻璃卡上的深色文字对比度是可预期的**，而不是被图片明暗带着走。

**降级两条路径**：`@supports not (backdrop-filter)` 自动落实色（对齐 tokens.css 同名块）；
控制条上还给了「液态玻璃 / 降级实色」手动切换（也是接入时低端设备 / 省电模式的落点）。

### 接入玻璃后必须回头修的两处（实测）

1. **暗色对比度被玻璃底带下去了**。暗色 `--liquid-bg-strong` = `rgba(40,40,52,.84)`，比原来的实色面
   `#1c1c1e` 更亮 → 错误摘要红字从 4.86:1 掉到 **4.42:1**（低于 4.5）。
   修法：暗色 `--err-soft` 由「亮红冲淡」`rgba(255,105,97,.15)` 改成「深红染」`rgba(78,18,16,.58)`（→5.5:1），
   暗色 `--ink-3` 由 `#9a9aa0` 提到 `#a8a8ad`。
2. **「共两步」的口径错误**：左栏副标题写着「共两步」但向导是三步（第一版就带着这个错）。

### 验收（材质部分，共 9 条断言）

它能证明材质真的在渲染，而不只是 CSS 里写了一行 `backdrop-filter` —— 只看 computed style 是查不出
「写了但没生效」的。

反证也补了两条：撤掉外卡 `backdrop-filter` → `外卡是液态玻璃` 变红；
把外卡底色改成不透明白 → `材质真的改变了渲染像素` 变红（平均差 0.00）。**6 条反证全部成立。**

## 八、注册时可选添加通行密钥（2026-09-22 追加）

### 项目里已经有什么（先说清楚，避免重复造）

| 能力 | 位置 |
|---|---|
| `isPasskeySupported()` 能力检测 | `utils/api/auth-api.js`（`PublicKeyCredential` 存在 + `isUserVerifyingPlatformAuthenticatorAvailable()`） |
| `registerPasskey()` / `listPasskeys()` / `deletePasskey()` / `renamePasskey()` | 同上，supabase-js ≥2.105 的 experimental passkey API（当前 **2.116.0** ✓） |
| 失败文案映射 `toPasskeyRegisterMessage()` / `toPasskeyLoginMessage()` | 同上（后者已经写了「请在 设置 → 账户安全 添加通行密钥」的引导） |
| GoTrue 侧开关 | 已开 passkeys，`rp_id=blockofhome.cn`，origins = www + 裸域（2026-09-21 经 Management API PATCH 启用） |
| **登录**用通行密钥 | ✅ `Login/index.vue` 已有「指纹 / 面容一键登录」（能力检测驱动，不支持则整按钮隐藏） |
| **注册**通行密钥 | ⚠️ 只在 设置 → 账户安全（`AccountSecurity/index.vue#addPasskey`），**登录之后才能到** |

所以本次做的是：**把这个可选动线前移到注册流程**，API 一行都不用新增。

### 三条硬约束（决定了方案形态）

1. **`registerPasskey()` 是 authenticated API** —— 必须有已建立的会话。
   直登模式（`mailer_autoconfirm=true`）`signUp` 直接返回 session ✓；
   但**邮箱验证模式（`mailer_autoconfirm=false`）无 session** → 注册完立刻添加必然 401。
2. **WebAuthn 的 `credentials.create()` 需要瞬时用户激活**（窗口约 5 秒）。
   提交点隔着一次 `signUp` 网络往返，激活可能已过期 → 不能"在提交那一次点击里顺手做掉"。
3. **需要 HTTPS + 域名匹配**（`rp_id=blockofhome.cn`）。本地 `[::1]:5173` 是 secure context
   （localhost 豁免）但 rp_id 不匹配 → **本地只能验能力检测，真跑仪式必失败**。

### 方案形态

**Step 3（完善资料）放一个可选开关收意图，成功页用一个明确按钮执行仪式。**

- Step 3 新增「本机快速登录 · 选填」：`role="switch"` 开关 + 一句说明
  （「下次登录不用输密码，直接用指纹 / 面容。密钥只保存在本机，BOH 只拿到公钥。」）
  + 一句可逆性说明（「也可以稍后在 设置 → 账户安全 添加或删除」）。**默认关闭**。
- **不支持的浏览器整行隐藏，不置灰**（沿用登录页的能力检测做法）。
- **邮箱确认模式下不出现这个开关** —— 因为无 session 时添加必然失败。
  改为在成功页给一行**延后提示**：「邮箱验证完成后，可以在这台设备上添加通行密钥」。
  这是本方案最关键的一处取舍：**宁可少一个入口，也不给一个点了必然失败的按钮。**
- 成功页（直登 + 已勾选）：出现卡片「为这台设备添加通行密钥」+ 主按钮「用指纹 / 面容添加」
  + 次按钮「以后再说」。四态：`idle` → `running`（按钮禁用，文案「请在设备上完成验证…」）
  → `ok`（收起按钮，显示「已添加」）→ `error`（给原因 + 「重试」，仍可跳过）。
- **没勾选就完全不出现卡片** —— 尊重选择，不做二次打扰。

## 十、密码长度口径统一（2026-09-22 追加）

起因只是一句文案：`Login/index.vue` 里写着「密码长度至少6位」。全仓排查后发现**不是一处文案问题，是 8 处口径分裂**，其中两处是真问题。

### 排查结果（8 处）

| # | 位置 | 原值 | 性质 |
|---|---|---|---|
| 1 | `supabase/functions/_shared/auth-validation.ts#validatePassword` | 6 | **服务端真源落后于前端** |
| 2 | `ResetPassword/index.vue` 的 `length < 6` + 文案 + placeholder | 6 | ⚠️ **真漏洞：重置密码可绕过 8 位下限** |
| 3·4 | `Login/index.vue` 两处静态提示「密码长度至少6位」 | 6 | 文案与实现不符（该 div 只在密码为空时显示） |
| 5 | `stores/auth.ts#deleteAccount` 的 `< 6` | 6 | 重复定义 |
| 6·7 | `AccountSecurity` 的当前密码 `< 6`、注销密码 `< 6` | 6 | 重复定义 |
| 8 | `AccountSecurity` 的新密码 `< 8` + 提示文案「至少 8 位」 | 8 | 值对但硬编码 |

> 第 8 处是**门禁脚本先抓到的**，人工排查时漏了 —— 这本身就说明「靠人记住有几处」不可靠。

### 两个真问题（比文案严重）

1. **重置密码页只要求 6 位**。注册要求 8 位，但重置页给了一条把密码设回 6 位的合法路径 —— 8 位策略形同虚设。已改走 `validatePassword`。
2. ⚠️ **服务端真正的闸门是 GoTrue 自己，实测 `password_min_length = 6`**（`GET /v1/projects/{ref}/config/auth`）。
   `signUp` 走的是 `supabase.auth.signUp`（客户端 SDK → GoTrue），而 **`auth-register` 这个 EF 前端根本没有调用**
   （`grep -rn "auth-register" src/` 为空）—— 所以上面第 1 处的修改只是**纵深防御**，
   8 位策略当前**纯粹是浏览器里的一道门**，直连 API 即绕过。

### 修法

- **单一真源**：前端 `src/utils/auth-validation.js` 的 `PASSWORD_MIN_LENGTH = 8`；
  服务端是**独立副本** `supabase/functions/_shared/auth-validation.ts`（Deno 不能 import `src/`），只能锁一致性、无法合并。
- `Login/index.vue` 两处改成「请输入密码」—— 该提示只在 `passwordInvalid = !password` 时出现，
  讲长度本来就是错的；而且**登录不该校验密码长度**（长度策略变化不能锁死老用户）。
- `stores/auth.ts#deleteAccount`、`AccountSecurity` 三处改为调用 `validateCurrentPassword` / `validatePassword`，
  调用方不再关心数字。
- ⚠️ 「当前密码」刻意用 `PASSWORD_MIN_LENGTH_LEGACY = 6`（低于新密码下限）：
  跟着涨到 8 会让历史 6~7 位密码的用户**改不了邮箱、删不掉账号**。

### 新增门禁（`npm run check:auth-validation`）

`scripts/check-auth-validation-parity.mjs`，已接进 `build:ci`（纯静态、不联网、不需要凭据，所以可以安全进 CI）：

- **A**：两份真源的常量必须存在且相等；且 `PASSWORD_MIN_LENGTH_LEGACY` 必须**严格小于** `PASSWORD_MIN_LENGTH`。
- **B**：真源之外不得出现「密码变量 `.length` 与数字字面量比较」。
- **C**：真源之外不得出现写死数字的密码长度文案（走常量插值不算违反）。

**反证 5/5 成立**：服务端下限回退 6 / 前端回退 6 / LEGACY 追平 MIN / 真源外硬编码比较 / 写死文案，
五种改法各自都让门禁变红。
