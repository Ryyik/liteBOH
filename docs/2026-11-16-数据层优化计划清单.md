## 0. 关于「不走代理」——沙箱内外都绕不过，原因是路由表

> **2026-11-16 复测修正**：上一版把原因写成「沙箱内无法绕开」是错的。
> 沙箱外（`dangerouslyDisableSandbox`）复测，**结果完全一致**。真正原因在**内核路由表**，不在进程环境。

本机是 **TUN 全量接管 + fake-ip**，八段路由把几乎所有公网 IP 都压进隧道：

```
netstat -rn -f inet | grep utun8
  1/8      → 198.18.0.1  utun8      # 1.0.0.0/8
  2/7      → utun8                 # 2.0.0.0/7
  4/6      → utun8                 # 4.0.0.0/6
  8/5      → utun8
  16/4     → utun8
  32/3     → utun8
  64/2     → utun8
  128.0/1  → utun8                 # 128.0.0.0/1 = 后半段全部
```

八段叠加后覆盖**除 `0.0.0.0/8` 以外的全部公网地址** ⇒ 任何目标 IP 都查不到 en0 的直连路由。

| 探测（均为**沙箱外**执行） | 结果 | 说明 |
|---|---|---|
| `scutil --proxy` | `HTTPProxy 127.0.0.1:7890`（HTTP/HTTPS/SOCKS 全开） | 系统级代理 |
| `dig <ref>.supabase.co` | `198.18.0.38` | fake-ip（198.18.0.0/16） |
| `dig @223.5.5.5 <同上>` | **同样 `198.18.0.38`** | 外部 DNS 也被劫持，换 DNS 无效 |
| `route -n get 104.18.38.10`（DoH 查到的**真实** Cloudflare IP） | gateway `198.18.0.1`, iface **utun8** | 用真 IP 也进隧道 |
| `env -u HTTP_PROXY … curl --noproxy '*' --resolve …104.18.38.10` | `connect=0.0006s` / `tls=0.48s` / 出口仍 `172.96.141.94` LA | 摘掉代理变量 + 指定真 IP 仍被内核送进隧道；connect 0.6 ms 是 TUN 本地握手 |
| `curl --interface 192.168.31.173`（en0 真实 IP） | 出口仍 LA | 绑源地址不改变路由查找 |
| `dig @223.5.5.5`→真实 IP 段（DoH） | supabase `172.64.149.246`/`104.18.38.10`，站点 `172.67.197.73`/`104.21.52.89` | 都在 Cloudflare 上 |

⇒ **唯一解是退出代理 App（Nextin）**；这属于你的机器设置，我不动。加更具体的静态路由需要 sudo，也不该由我改。
⇒ `0.0.0.0/8` 那个例外没有实用价值（没有服务在 0.x 段）。

**退而求其次**：用同一出口的已知快站做标定，把代理开销从读数里扣掉。

| 目标（复用连接） | 耗时 |
|---|---|
| `ipinfo.io/ip` | 207 ms |
| `cloudflare.com/cdn-cgi/trace`（LA 边缘） | 159 ms |
| `supabase.co/auth/v1/health` | 756 ms |

⇒ 代理固定开销约 **150–200 ms/请求**，剩下的 ~550 ms 是真实的 **LA→新加坡**。
**国内用户到新加坡通常是 60–120 ms RTT，比我快**，所以我全部绝对毫秒都是偏悲观的。
结构类结论（几波、几条往返、谁在等谁）不受影响，**本清单刻意只依赖结构类证据**。

## 2. 逐条证据（只列关键项）

### A1 开场画预发 feed

- 证据：两轮 4G 探针里 `posts` 请求都在 `ForumMain` chunk 完成后 **30–40 ms** 才发；开场画期间只有 `avatar_frames`（idle 任务）一条请求。
- 收益上限为什么是「区间」而不是确定值：首条数据请求之前已发 **58 个 JS（460 KB）+ 20 个 CSS（129 KB）**，1.6 Mbps 下约 3 s。提前发只是**并行**，不是跳过。
- 负面作用的具体形态：`request-core` 的 key 含 `userId`，首页若以 guest 身份预发、`ForumMain` 以登录身份再请求 ⇒ **两笔**。所以必须抽 `buildForumFeedParams()` 单源，且用持久化的 `userInfo.id`。
- 验证：A/B 跑 `probe-forum-feed-load --only=4g`，只看 `firstCardMs` 与 `dataChainStart` 两个字段，各 3 轮取中位。

### A5 列表 embed 裁剪（数字最实的一条）

实测（同一查询，11 条）：

| 变体 | raw | gzip |
|---|---|---|
| 线上现状 | 29,934 | 7,580 |
| 去 counters + 限 4 图 + 去 `public_id` | 22,840 | **5,414** |

拆解（raw）：基础 `*` 15,001 · counters 539 · author 2,582 · **图片 11,812**。
图片何以这么重：11 帖共 **36 张图**（5,1,1,6,0,2,4,4,2,5,6），8 个字段里 `url` 3,857 B、`public_id` 1,476 B、其余元数据 6,420 B。
`forum_post_images.limit=4` 实测生效（返回 4,1,1,4,0,2,4,4,2,4,4）。
⇒ 收益是真金白银，但**只有 4G 下 11 ms 的传输时间**；真正的价值是「卡片只需要 4 张预览图」这个语义对齐。

### 冗余计数器可以安全去掉

`posts.comment_count` / `like_count` 与实际聚合值抽查 **11/11 完全一致**，所以 `comments:comments(count)` / `likes:likes(count)` 两次 COUNT 是纯重复。

### B4 头像迁 Cloudinary 的真实边界

| | 现状（Storage） | Cloudinary |
|---|---|---|
| 边缘 | `server: cloudflare`, `cf-cache-status: HIT` | `server: Cloudinary` / Fastly |
| 缓存 | `max-age=3600`（1 小时） | `immutable, max-age=2592000`（30 天） |
| 单张体积 | 21,964 B | ≈1,549 B（`w_96,f_auto,q_auto`） |

⇒ 首字节打平（两边都是 CDN），收益在**缓存寿命**与**体积**。**不要用它当提速理由。**

## 4. A4 / A5 复核结论（2026-11-16 18:30，含实测）

### A4 快照加 tier —— **方向对，但形态该改**

原方案「把 tier 塞进 feed 快照」有两个硬伤：快照 TTL 只有 15min（只覆盖近期回访），且要改快照 schema/版本。**改成把 `tierCache` 持久化到 localStorage 更划算**：档位是低频变更，可以给 6～24h TTL，与快照解耦。

支撑数据（均为只读实测）：

| 项 | 数字 |
|---|---|
| `get_user_subscription_tiers` 执行耗时 | **34.5 ms**（10 个 id；SECURITY DEFINER 跨表读 `user_subscriptions`） |
| 对照：整个 posts 列表查询 | 0.26 ms（含两个 count 子查询 6.2 ms） |
| 批量函数是否在"全命中缓存"时跳过 RPC | **是** —— `useUserTier.js` 里 `if (uncached.length === 0) return result;` |
| tier 在 UI 上的作用 | 不只是徽章：`authorTierClass` 决定**昵称颜色**，`tier-plus/pro/max/ultra` 决定**卡片皮肤** ⇒ 现在会"先出灰名、再变色" |

⇒ 收益：回访少 1 次往返（DB 34ms + 网络 0.2～1.4s）+ 消除昵称变色闪。成本约 40 行 + 1 条单测。
⇒ 风险：档位升降后 TTL 内显示旧颜色（纯观感，不涉及权限）。
**结论：值得做，但不是"塞快照"。**

### A5 列表 embed 裁剪 —— **不必要**

| 项 | 数字 |
|---|---|
| 去掉两个 `count` embed 省下的 DB 时间 | 6.19 ms → **0.26 ms**（省 5.9 ms） |
| 数据正确性 | `comment_count` / `like_count` / `image_count` 与真实聚合 **165/165 全部一致** |
| 响应体积（11 帖） | gzip 7,580 → 5,414 B（省 2.1KB，4G 下 ≈ 10 ms） |
| 图片限制是否破坏"+N 张" | **不破坏** —— `imageCount` 取 `posts.image_count` 列，`hiddenImageCount = image_count − 已加载`，本来就有 `load-more-images` 补全路径 |

⇒ 全部加起来约 **16 毫秒**，却要动唯一真源的 select 串 + 校验编辑/删图路径。**不划算，不做。**

### 头像迁 Cloudinary —— **按规模判断，现在不必迁；但可以先吃两条便宜收益**

现状：33 个用户里 **17 个** 用了 Storage 头像；`avatars` 桶 34 个文件 / **5,673 KB** / 平均 **167 KB** / 最大 **520 KB**（512px webp 本该 15–40KB ⇒ 存量里有改造前的老文件）。

**首屏真实头像账（最近 40 帖）**：只有 **4 个不同作者**，当前引用的 4 个头像分别 **30,056 / 24,664 / 21,964 / 8,294 B = 85 KB**，而它们在卡片里渲染成 **32–40px**。
⇒ 这不是 TTFB 问题，是**字节问题**：一个 40px 的点位在下载 512px 的原图。
Cloudinary 的 `f_auto,q_auto,w_96` 对同图实测 **1,549 B（−93%）**，4 个头像 ≈ 8 KB。
⇒ 用户量上来后（假设 10 个不同作者/次）单次浏览从 ~220 KB 降到 ~20 KB。

| 判断依据 | 结论 |
|---|---|
| 提速 | **否**。Storage 已在 Cloudflare 后面（`cf-cache-status: HIT`），TTFB 与 Cloudinary 打平 |
| 字节 | **是**（真正的理由）。Storage 不做图片变换 ⇒ 40px 点位下 512px 原图；Cloudinary 免费做 `w_96` 变体 |
| 什么时候才该迁 | **不看"用户多了"这个感觉，看两个可测信号**：① Storage 出口进套餐红线（Pro 250GB/月）；② 单次浏览的头像字节 > 200KB。当前 4 个作者 / 85KB，两个信号都远未触发 |
| 迁之前的两条便宜收益 | ① `AVATAR_CACHE_CONTROL` 从 `3600` → `31536000`（1 年）。URL 自带 `?t=<上传时间戳>` 且换图会换路径 ⇒ **破缓存安全**，回访头像直接 0 请求，等价于 Cloudinary 的 30 天缓存，零迁移。⚠️ **只对新上传生效**，存量 17 张的 `cache-control` 在对象元数据里，改常量改不动（要 service role）；② 存量 34 个文件重压一遍，5.6MB → 约 0.6MB（磁盘/带宽，不是速度） |
| 不迁也能拿到约 80% 的字节收益 | 上传时同时产出 **96px 变体**，feed 用小的、个人页用 512px。代价：改上传 + 路径约定 + 17 张回填。**和迁 Cloudinary 是二选一，别两个都做** |
| 真要迁时的前置 | 桶**不要删**（旧 URL 继续活）；`extractAvatarPath()` 只认 Storage URL，迁移后旧文件清不掉，必须一起改；`cloudinary-sign-upload` 有 **10 分钟限流**，换头像会开始吃这套额度 ⇒ 要单独给头像开豁免，否则"换头像"变成有配额的动作（产品行为变化，要先确认） |
