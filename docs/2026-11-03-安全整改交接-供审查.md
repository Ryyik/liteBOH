## 1. 项目背景（审查所需的最小上下文）

- **技术栈**：Vue 3 + Vite 前端，Supabase（Postgres + RLS + Edge Functions）后端，托管在 GitHub Pages，Cloudflare 在前做响应头注入与缓存。
- **规模**：`src/` 604 个源文件，`scripts/` 281 个脚本，305 个单测文件 / 3887 条用例。
- **当前阶段**：RC 版收尾，正在做安全整改。此前已有一份审计报告（`docs/2026-11-02-RC版安全审计-增量复审.md`）。
- **关键约束**（审查时必须知道，否则会给出不可执行的建议）：
  1. **本机无法访问 `*.supabase.co`**：DNS 与 TCP 443 正常，但 TLS 握手被按 SNI 重置；同一 IP 换 SNI 即通。所以 `supabase db push` 能跑是因为走 `*.pooler.supabase.com`，而**任何 `*.supabase.co` 的 HTTP 请求在本机都失败**。线上取证只能走 Supabase Management API（`api.supabase.com`，可达）。
  2. **数据库身份是只读**：Supabase MCP 用的是 `supabase_read_only_user`，能查不能写；写操作走 `supabase db push`（迁移文件）或 Management API。
  3. **GitHub Pages 不支持自定义响应头**：`public/_headers` 线上不生效，安全头只能由 Cloudflare Transform Rule 注入（`scripts/cloudflare-security-headers.mjs`）。
  4. **门禁体系**：`npm run verify:fast`（约 10s）、`npm run prepush`（全量）、`check:db-advisors`、`security:anon-check`（匿名执行面棘轮基线）。基线只能通过显式收权下调。

## 2. 今天做了什么（按批次）

### 第一批：4 项「能直接造成数据泄露」的修复

| 项 | 内容 | 关键迁移 |
|---|---|---|
| profiles 敏感列 | 对 `authenticated` 关闭表级 `SELECT`，改为 52 列白名单视图/授权；4 个敏感列不可读 | `2026110308` |
| 生日接口 | limit 夹紧、返回脱敏、过滤被封禁用户 | `2026110307` |
| 登录风控闸门 | 登录接 Altcha 人机验证 + 服务端失败计数 | `af0f276b` |
| CSP 上报 | 新增 `csp-report` Edge Function + 线上下发 `report-uri` / `report-to` | `csp-report` v4 |

附带修了一个**死锁**：Altcha 的渲染条件与 `VITE_ALTCHA_ENABLED` 构建期开关耦合，如果构建时关闭、服务端却要求验证码，前端永远不渲染 ⇒ 所有人无法登录。新增 `canRenderAltcha()` 与服务端要求解耦（`3b81e2ba`）。

### 第二批：登录旁路收口

**发现**：邮箱登录走的是 GoTrue 直连（`signInWithPassword`），完全绕过第一批刚接的登录风控闸门——不写 `auth_attempt_events`，`security_captcha_enabled=false`，等于闸门只挡方块 ID 用户。

**处理**：邮箱与方块 ID 统一走 `auth-login` Edge Function（`a8101f1b`），`signIn()` 删除按 `@` 分流。**这是一个有意的产品取舍**：EF 成为登录唯一入口，EF 故障时邮箱用户也无法登录，不做静默降级（§5.3）。

**附带**：`_rate_limits` 加保留策略（删 `reset_at` 过期 1 小时的行 + 每小时 cron），避免匿名可写的表无限增长（`e9739e13`）。刻意**不删进行中的窗口**，否则会把攻击者的计数清零。

### 第三批：A 组（有实际后果）+ B 组（纵深与卫生）

**A1 `refund_lab_usage`（本批最重要）**
原实现是 `SECURITY INVOKER`，而 `lab_usage_records` 没有 DELETE 策略 ⇒ 函数**永远删 0 行、返回 false**，配额只在前端本地回退，数据库侧一直对不上账。同时旧 WHERE 是 `(p_user_id is null or user_id = p_user_id)` ⇒ **匿名用户凭一个 device_id 就能删任意用户的记录**。

**A2 `user_impressions`**：公开读策略从 `qual = true` 改为 `moderation_status = 'approved'`。全表 21 行均为 approved ⇒ 对现有可见性零变化。

**A3 订单节流**：`create_shop_order` 加 5 单/小时 + 已付未发货（`status='preparing'`）≤ 10；`cancel_shop_order` 加 20 次/小时。前端把新拒绝码（`RATE_LIMITED` / `TOO_MANY_OPEN_ORDERS`）翻成中文。

**B 组**

| 项 | 结果 |
|---|---|
| anon 表级 SELECT | 79 → 61（第一批 18 张，标准 = `src` 零 `.from()` 引用） |
| 触发器函数 anon 执行权 | 37 → 0（共 53 个触发器函数） |
| `check:db-lint` | 2 → 1 |
| 匿名执行面基线 | 152 → 116 |
| cron 明文令牌 | jobid 24/30 的 `'Bearer <64位十六进制>'` 改为 `vault.decrypted_secrets`，token 已轮换 |
| 推送端点 | `push_subscriptions.endpoint` 加 DB `CHECK` 约束 + EF 两条发送路径过滤（`push-send` v14） |

**B 组三个意外发现**
1. 37 个触发器函数全部 `anon` 可执行。触发器以表 owner 身份运行，Postgres 不检查调用者 `EXECUTE`，这 37 条授权纯冗余，其中含 `handle_new_user`、`apply_yearly_membership_gift`。
2. `place_shop_order_with_points` 是死函数：写**库里已不存在**的 `shop_orders` 表、引用不存在的 `pg_temp` 表，每次调用必抛 42P01；却是 `SECURITY DEFINER` + anon 可执行。已 drop。
3. cron 的 Bearer token 是明文内联的。改 Vault 后**同时删掉了 `extractTokenFromCommand`**——留着「从命令里捞 token」的能力，旧路径会悄悄复活。

### 第四批（今天最后一轮）：CSP 域名补全（`9d6665c5`）

**取证方法**：用 Playwright 在线上页面 `fetch` 一个白名单外域名 → `securitypolicyviolation` 触发 → 查 Management API 的 `logs` 表（`source='function_logs'`，`event_message like '%[csp-report]%'`）。

**两个结论**

1. **上一批「驼峰键名导致字段全空」的修复确认生效**：新格式 4 条全部 `format: "reporting-api"`、`directive` 非空、`keys` 完整。此前 92 条旧记录（03:39–03:43）`directive`/`blocked` 全空，且**原始 body 未保留**（旧实现只打解析后字段），无法回溯补漏。

2. **发现真 bug**：`profiles.avatar_url` 里 **17/17 非空头像全部指向 `<ref>.supabase.co/storage/v1/object/public/avatars/…`**，而 CSP 的 `img-src` 只有 `res.cloudinary.com` 与 `cdn.blockofhome.cn`——两个都不是头像的真实来源。Report-Only 期间表现为持续噪音；**一旦转 enforce，全站头像变白框**。

**改动**：`CSP_IMAGE_ORIGINS` 补 `https://*.supabase.co`；`script-src` 放行 `https://static.cloudflareinsights.com`（Zone 级 Web Analytics 自动注入，非项目代码引入）。

## 4. 我认为最可能被审出错的地方

**这一节是我主动列的「可疑清单」，请重点攻。**

### 4.1 `refund_lab_usage` 的提权与判权

改动后逻辑（简化）：

```sql
security definer
set search_path = public
...
if p_user_id is not null and (v_uid is null or v_uid <> p_user_id) then return false; end if;
if p_user_id is null and v_uid is not null then return false; end if;

delete from lab_usage_records
 where id = (
   select id from lab_usage_records
    where case when p_user_id is not null then user_id = p_user_id
               else user_id is null and device_id = v_device_id end
      and (p_flow_type is null or flow_type = p_flow_type)
    order by created_at desc
    limit 1
 )
```

**与原实现的差异（审查者需要确认这两点是否有意为之）**

| | 原实现（`2026070802`） | 现实现（`2026110310`） |
|---|---|---|
| 删除条数 | 只删 1 条（`limit 1`） | 只删 1 条（**未变**） |
| 匿名越权 | `p_user_id is null` 时匹配任意 user_id，只按 device_id 过滤 ⇒ 凭一个 device_id 可删**别人**的记录 | 只删 `user_id is null` 的记录，且要求调用者未登录 |
| `p_device_id` 过滤 | 传 `p_user_id` 时**仍**按 device_id 过滤 | **丢掉了**——传 `p_user_id` 时只按 user_id 匹配 |
| 登录用户走 device 通道 | 允许 | 禁止 |

**可疑点**：

1. **丢掉 `p_device_id` 过滤是一个未声明的行为变化**。同一用户在多设备上都有记录时，现在会删掉该用户**最新的一条**，可能来自另一台设备。不越权（都是自己的记录），但会造成配额账目错位。**这是我的实现遗漏，不是有意的收紧。**
2. `p_flow_type` 允许为 `null`，此时退的是「该用户最新一条记录」，可能是另一个 flow 的。因为只删 1 条，**不会**「清空全部配额」（此前的判断有误，已修正）；风险是退错流程的一条记录。
3. `device_id` 从客户端传入，无签名、无 IP 关联。匿名通道的「凭证」就是一个可猜可伪造的字符串——这是 Lab 允许未登录试用带来的固有权衡，不是本次引入。
4. 函数是 `SECURITY DEFINER`，已固定 `search_path = public`；但审查仍应确认函数体内引用的对象都在该 schema 下。

### 4.2 触发器函数收权

`REVOKE EXECUTE ... FROM anon, authenticated` 覆盖 37 个函数。**没有验证**是否存在：
- 代码里直接 `select public.handle_new_user(...)` 之类的显式调用；
- `SECURITY DEFINER` 函数内部调用这些触发器函数（依赖 owner 权限，通常不受影响，但要确认 owner 是否 superuser / 是否有显式 grant）。

### 4.3 删除 `place_shop_order_with_points`

依据是 grep。**风险**：如果它被 cron 或某个外部运维脚本调用，删了会静默失败（错误只出现在 `cron.job_run_details`）。建议审查者确认这个判断的充分性。

### 4.4 anon 表级收口的入选标准

只看 `src` 的 `.from('table')` 静态引用。**可能遗漏**：
- 通过 `supabase.from(variable)` 动态表名；
- 通过 view（`select * from some_view`）间接读被收权的表——view 的权限是独立的，revoke 基表不影响 view，所以这条其实**不会**导致故障，但会让「收权」的纵深效果打折；
- 通过 RPC 返回该表数据（`SECURITY DEFINER` 函数以 owner 身份读，不受 anon 授权影响）——同理，不影响功能，但意味着「revoke 表级授权」对这些表并不等于「匿名读不到」。

**这是需要审查者重点判断的语义问题**：revoke 表级授权防的是「直接 PostgREST 访问」，防不了「经 RPC 出口」。如果目标是后者，还需要审计所有 `SECURITY DEFINER` 函数的返回值。

### 4.5 推送端点白名单

当前实现（`supabase/functions/_shared/push-endpoint.ts` + 迁移 `2026110315`）：
- 必须是 `https:`
- host 必须在白名单（Apple / Mozilla / Windows / FCM 的已知域名）
- 加 `CHECK` 约束，已有数据必须合规（迁移成功 ⇒ 现有数据都合规）

**可疑点**：
- 白名单是否覆盖所有真实浏览器端点？如果某个 Firefox 版本用了新域名，推送会**静默失败**（用户收不到通知，但不报错）。
- 选了白名单而不是「禁内网 IP」，理由是黑名单永远漏（十进制 / 八进制 / IPv6 / DNS 重绑定）。这个取舍是否正确？
- `CHECK` 约束意味着「将来新增合法端点必须先改约束」，是刚性的。

### 4.6 CSP 的 `img-src` 用了通配符

`https://*.supabase.co` 覆盖所有 Supabase 项目，而不只是本项目 `<ref>.supabase.co`。

- **理由**：`connect-src` 本来就已经是 `https://*.supabase.co`，两者保持一致；本地/预览分支也能工作。
- **代价**：任何 Supabase 项目的图片都能被加载。`img-src` 只影响显示、不执行代码，风险低，但确实比最小权限宽。
- **副作用**：`CSP_IMAGE_ORIGINS` 现在含一个带 `*` 的项，而 `isAllowedImageSrc()` 用 `origins.includes(parsed.origin)` 精确比较——**通配符对它永远不匹配**。目前该常量只被 CSP 插值消费（已 grep 确认），但这是一个隐藏的耦合陷阱，将来若有人拿它做别的判断会静默失效。

## 5. 已知残留与未修项

### 5.1 今天新发现但**没有修**的

| 项 | 说明 | 严重度 |
|---|---|---|
| `create_shop_order_with_points` 冗余函数 | 前端零调用，`SECURITY DEFINER`，**没有加节流**。不是死函数（能跑），所以没删 | 中 |
| `total_points > 0` 约束与 `rmb_only` 冲突 | 纯人民币订单 `v_total_points = 0` ⇒ 插入违反 CHECK ⇒ 抛异常。当前 `products` 表**没有** `rmb_only` 商品（4 个 points_only + 2 个 combined 在架），所以未触发 | 中（潜伏） |
| `create_shop_order` 的 anon EXECUTE | 函数第一行 `if v_user_id is null then return NOT_AUTHENTICATED`，安全；但授权冗余 | 低 |
| CSP `frame-ancestors` 在 Report-Only 下无效 | 规范规定该指令在 report-only 模式被忽略。当前点击劫持防护实际靠 `X-Frame-Options: DENY` | 低 |
| 92 条旧 CSP 上报无法回溯 | 原始 body 未保留，无法从中补出更多域名缺口 | 信息缺失 |

### 5.2 已知的架构性残留

- **EF 是登录唯一入口**：`auth-login` 挂掉 ⇒ 邮箱用户完全无法登录。这是有意选择（不静默降级到 GoTrue，否则风控闸门又被绕过），但可用性风险转嫁到了 EF。
- **旧 PWA 缓存用户**：装了旧 Service Worker 的客户端会继续加载旧 bundle，服务端无法强制刷新。新 CSP 规则对他们可能误伤。
- **61 张表仍对 anon 有表级 SELECT**：其中约 20 余张是**真匿名可读**（`posts`、`comments`、`activities`、`news`、`products`、`home_heroes`、`boh_cloud_entries`），**不能动**，动了未登录首页白屏。

**理由**：这三批改动里，登录链路是完全替换（不是叠加），订单链路新增了拒绝分支。任何一处失败都是用户直接进不来、下不了单。代码侧再审计也无法替代。

### P1｜修 §4.1 的 `p_device_id` 过滤丢失（这是我今天引入的回归）

原实现在传 `p_user_id` 时仍按 `p_device_id` 过滤，现实现丢掉了这个条件 ⇒ 同一用户多设备时会退错记录（只影响账目，不越权）。修复成本很低：在 `p_user_id is not null` 分支补 `and (v_device_id is null or device_id = v_device_id)`。

同时建议把 `p_flow_type` 改为必填（当前允许 `null`，会退到「最新一条任意 flow」的记录）。

### P2｜61 张表的第二批：只动「策略给到 anon 但条件是 `current_user_is_admin()`」的那组

- 真匿名可读的（约 20 余张）：**不动**。
- 只有登录策略的（13 张）：需逐页确认「未登录时是否会发请求」。revoke 后失败形态从 `200 + 空数组` 变为 `42501`，而 `normalizeDbError` 把 42501 翻成「您的账号已被封禁或禁言」（`src/utils/request-core.js:259-266`）。这是 2026-10-17 出过的事故同款。
- admin 条件那组（`notifications`、`moderation_logs`、`user_subscriptions`、`bohai_model_configs`、`cloudinary_pending_uploads` 等）：**这才是真正该收的**，属于「两道门只关了一道」的冗余授权。

**必须先产出「表 → 前端调用点 → 登录守卫位置」清单，不能批量 revoke。**

### P3｜CSP 转 enforce：仍不做，但理由已变

不再是「数据不够」，而是「已知缺口刚补完，要观察一轮噪音是否归零」。观察通过后，按指令分批：先 `object-src` / `base-uri`（几乎不可能误伤），最后 `script-src` / `connect-src`。

### P4｜清理项（可合并一次迁移）

- drop `create_shop_order_with_points`（前端零调用）
- 修 `total_points > 0` 与 `rmb_only` 的冲突（改成 `total_points >= 0` 或按 payment_mode 分别约束）
- 收回 `create_shop_order` 的 anon EXECUTE（函数内已拒，授权可精简）

-- 匿名表级 SELECT 面
select count(*) from pg_tables
 where schemaname='public'
   and has_table_privilege('anon', quote_ident(schemaname)||'.'||quote_ident(tablename), 'SELECT');

-- 触发器函数是否仍对 anon 开放
select count(*) from pg_proc p join pg_namespace n on n.oid=p.pronamespace
 where n.nspname='public' and p.prorettype='trigger'::regtype
   and has_function_privilege('anon', p.oid, 'EXECUTE');

-- cron 是否还有内联令牌
select jobid, jobname from cron.job where command ~ 'Bearer [0-9a-f]{64}';

-- 头像来源分布（CSP img-src 的依据）
select case when avatar_url like '%supabase.co/storage%' then 'supabase'
            when avatar_url like '%res.cloudinary.com%' then 'cloudinary'
            when avatar_url is null or avatar_url='' then '(empty)'
            else 'other' end as src, count(*)
  from public.profiles group by 1;
