## 1. 逐条详述

### A1 — 共享全局 `.fade` 被加 `transform`，全屏遮罩弹窗边缘漏光（高）

**现象**
打开「发帖」「编辑资料」等弹窗时，全屏深色遮罩在入场的前 220–260ms 内会整体**下移 10px 并缩小到 97%**，四周露出一圈未被遮罩覆盖、也未被 `backdrop-filter` 模糊的页面内容，形成一次可见的「漏光/边框闪烁」。

**证据**
`src/views/user-center/UserSpace/styles/responsive-integrations.css`

```css
.fade-enter-active { transition: opacity 220ms …, transform 260ms …; }   /* :498 */
.fade-enter-from   { opacity: 0; transform: translateY(10px) scale(0.97); } /* :506 */
```

该文件是**全局**样式：

- `src/views/Profile/index.vue:33-38` —— `<style>`（**无 scoped**）内 `@import` 了 `responsive-integrations.css`
- `src/views/user-center/UserSpace/async-loaders.js:84` —— 动态 `import('./styles/responsive-integrations.css')`

而 `name="fade"` 是**全站共享**的过渡名，共 18 处使用。其中**未定义本地 `.fade-*` 规则**、因而直接吃全局规则的有：

| 组件 | 结构 | 是否全屏遮罩 |
|---|---|---|
| `src/views/Profile/components/PostCreateModal.vue:3-4` | `<Teleport to="body">` + `.modal-overlay` | 是（`:63-65` `position: fixed; top/left/right/bottom: 0`） |
| `src/views/Profile/components/ProfileEditModal.vue:3-4` | `.modal-overlay` | 是（`:503-504` `position: fixed`） |
| `src/views/HeroConsole/index.vue:778` | `.lottery-picker-overlay` | 需实测确认 |

其余 15 处（AvatarCropModal、BlockWall、Download、Gift、Birthday、Messages、Newsroom、Lab、CreatorShowsPanel、Forum/styles/base.css 等）各自定义了本地 `.fade-*`，不受影响。

**根因**
计划 017 只针对 ThemeModal 设计，但把改动写在了共享的 `.fade` 上。计划内已意识到「`transform` 加在 overlay 上没问题（整体浮起 10px），但 scale(0.97) 会让背景遮罩也轻微缩放」——**但仅评估了 ThemeModal 一处，未评估 `fade` 这个过渡名的全站爆炸半径**。对全屏遮罩而言，`scale(0.97)` 会真实露出边缘。

**修复建议（推荐）**
不要动共享的 `.fade`。给 ThemeModal 换独立过渡名：

```html
<!-- ThemeModal.vue:2 -->
<transition name="theme-fade">
```

```css
/* responsive-integrations.css —— .fade 保持纯 opacity */
.fade-enter-active { transition: opacity 220ms cubic-bezier(0.23, 1, 0.32, 1); }
.fade-enter-from   { opacity: 0; }          /* 去掉 transform */
.fade-leave-active { transition: opacity 160ms ease-out; }

/* 新增：仅供 ThemeModal */
.theme-fade-enter-active { transition: opacity 220ms cubic-bezier(0.23, 1, 0.32, 1), transform 260ms cubic-bezier(0.23, 1, 0.32, 1); }
.theme-fade-enter-from   { opacity: 0; transform: translateY(10px) scale(0.97); }
.theme-fade-leave-active { transition: opacity 160ms ease-out; }
.theme-fade-leave-to     { opacity: 0; }
```

若坚持保留全局 transform，至少要把 `.modal-overlay` 类排除掉：

```css
.fade-enter-from:not(.modal-overlay) { transform: translateY(10px) scale(0.97); }
```

**复现（1 分钟）**
进 `/profile/<你的用户名>` → 点「发帖」→ 用 DevTools Animations 面板 10% 速度看遮罩入场。

### A2 — `animation-fill-mode: both` 锁死 `transform`，`.ah-smart-focus` 交互反馈失效（中高）

**现象**
资产总览顶部的「智能聚焦」卡（`.ah-smart-focus`）入场后，**鼠标悬停不再上浮、按下不再缩小**。

**证据**
`src/views/user-center/UserSpace/components/AssetsHubPanel.vue`

```css
/* :1770 —— 本批新增 */
.ah-smart-focus { … animation: ah-materialize 260ms cubic-bezier(0.23, 1, 0.32, 1) both; }

/* :1733-1736 —— 关键：末帧包含 transform */
@keyframes ah-materialize {
  from { opacity: 0; transform: translateY(6px) scale(0.985); }
  to   { opacity: 1; transform: translateY(0) scale(1); }
}

/* :1800 —— 失效 */
.ah-smart-focus:active { transform: scale(0.99); }

/* :2220 —— 失效（门控媒体查询内） */
.ah-smart-focus:hover { transform: translateY(-3px); box-shadow: …; }
```

**根因**
CSS 层叠中 **「动画声明」的优先级高于「普通作者声明」**（Cascade L4：normal author < animation）。`animation-fill-mode: both` 含 `forwards`，动画结束后仍**持续应用末帧值**。末帧写了 `transform: translateY(0) scale(1)`，于是该元素的 `transform` 被永久锁定为动画末帧值，` :hover` / `:active` 的 `transform` 声明被完全压制——**与选择器特异性无关**。

注意：同文件 `:2186` 的 `.ah-gift-status-icon` 也用了 `both`，但它没有 hover/active transform，因此无害；`:2442` / `:2474` 的 `.ah-sponsor-section` / `.ah-lottery-section` 是容器，hover 作用在子元素 `.ah-sponsor-card` 上，同样无害。**只有 `.ah-smart-focus` 因为自身带交互 transform 而踩中**——即本批新引入的回归（此前该元素无动画，hover 正常）。

**修复建议（任一）**
```css
/* 方案 1（最小改动）：填充模式改为 backwards，动画播完即释放 transform */
.ah-smart-focus { animation: ah-materialize 260ms cubic-bezier(0.23, 1, 0.32, 1) backwards; }

/* 方案 2：keyframes 不写 transform，改用 translate 独立属性（不参与 transform 冲突） */
@keyframes ah-materialize {
  from { opacity: 0; translate: 0 6px; }
  to   { opacity: 1; translate: 0 0; }
}
```
方案 1 会丢掉「入场前不可见」的 `backwards` 效果吗？不会——`backwards` 同样在动画开始前应用首帧，只是**不再锁定结束后状态**，正是所需。

**复现**：进「资产」页签 → 鼠标移到顶部智能聚焦卡上。

### A3 — `shell-community.css` 的 reduce 新增规则大面积失效（中）

**现象**
开启系统「减少动态效果」后，UserSpace 里**骨架 shimmer 仍在闪、帖子卡入场仍在动、展开/收起仍在动**。

**证据**：新增的 reduce 规则被写进了文件靠前的既有 reduce 块（`:307-341`），而它们要覆盖的目标规则在**同一文件更靠后**的位置。同特异性下**源序靠后者胜**：

| reduce 规则（位置） | 目标动画规则（位置） | 结果 |
|---|---|---|
| `.expand-enter-active/.expand-leave-active { transition-duration: 1ms }`（`:321`） | `.expand-enter-active…{ transition: grid-template-rows 280ms … }`（`:834`） | ❌ 失效 |
| `.skeleton-block, .skeleton-line, .badge-loading::after { animation: none }`（`:319-323`） | `.skeleton-line { animation: skeleton-shimmer 1.4s linear infinite }`（`:474`）；`.badge-loading::after { animation: badge-shimmer … }`（`:732`） | ❌ 失效 |
| `.user-space-page .forum-page.embedded-mode .post-card/.post-composer { animation-name: reduce-fade }`（`:330-334`） | 同名选择器 `{ animation: forum-card-in 280ms … both }`（`:532-533`） | ❌ 失效 |
| `.community-users-list .user-item { animation-name: reduce-fade }`（`:336-339`） | `.user-item { animation: userspace-list-item-in 300ms … }`（`:1004`） | ✅ 生效（reduce 侧特异性 0,2,0 > 0,1,0） |

**根因**
reduce 规则被追加到**文件顶部**的既有 reduce 块里，而没有考虑「目标规则在文件后半段」。唯一侥幸生效的一条，是因为它碰巧特异性更高。

**修复建议**
把这几条 reduce 规则移到**文件末尾**新增独立 `@media (prefers-reduced-motion: reduce) { … }` 块（与 `profile-panels.css:1730` 的正确做法一致），或与目标规则同块紧邻其后。另外 `.community-users-list .user-item` 只覆盖了社区伙伴列表，`shell-community.css:2211 / 2560 / 2794` 的生日列表 `.user-item` 未被覆盖——若想全量降级，选择器应写成 `.user-item, .community-users-list .user-item`（计划 019 原文如此）。

### A5 — Tab 切换的 reduce 降级特异性不足（中，既有缺陷未修复）

**现象**
开启 reduce 后，UserSpace 的 Tab 切换**仍然播放** 180ms 出场 + 300ms 入场动画（计划 013 的验收标准写的是「reduce 模式：页签瞬时切换，无任何位移动画」）。

**证据**

```css
/* shell-community.css:271-290 —— 方向规则，特异性 0,4,0 */
.user-space-page.tab-transition-forward .tab-page:not(.is-leaving) { animation: userspace-tab-in-forward 300ms … backwards; }
.user-space-page.tab-transition-forward .tab-page.is-leaving      { animation: userspace-tab-out-forward 180ms … forwards; }

/* :307-313 —— reduce 块，特异性 0,3,0 */
.user-space-page.tab-transition-forward .tab-page,
.user-space-page.tab-transition-back .tab-page { animation: none; }
```

`:not(.is-leaving)` 会贡献其参数的特异性（`.is-leaving` = 1 个类），所以方向规则是 **0,4,0**，高于 reduce 的 **0,3,0**。特异性优先于源序，reduce 规则**无论放在哪里都会被压制**。

**根因**
计划 013 的 Target 里写的就是这组 0,3,0 选择器——**这是计划本身的缺陷**，执行者忠实实现了。原代码用 `animation-duration: 1ms` 配同样选择器，所以这是**既有缺陷的延续**，不是本批新引入；但本批声称要「修正 reduce」，实际并未修好。

**修复建议**：把 reduce 选择器补齐到与方向规则同级：

```css
@media (prefers-reduced-motion: reduce) {
  .tab-page,
  .tab-page.is-leaving,
  .user-space-page.tab-transition-forward .tab-page,
  .user-space-page.tab-transition-back .tab-page,
  .user-space-page.tab-transition-forward .tab-page:not(.is-leaving),
  .user-space-page.tab-transition-back  .tab-page:not(.is-leaving) {
    animation: none;
  }
}
```

### A6 — reduce 下庆祝猫整只消失（中）

**现象**
开启 reduce 后，赞助页的 4 只庆祝猫（`sponsor-party-cat`）**完全不可见**。

**证据**

```css
/* profile-panels.css:1408-1412 —— 基础态 opacity: 0，可见性完全依赖动画 */
.sponsor-party-cat { position: absolute; opacity: 0; … animation: sponsorCatPop 1.8s cubic-bezier(0.16, 1, 0.3, 1) both; }

/* :1447-1463 —— 末帧把 opacity 抬到 .68，靠 both 填充维持可见 */
@keyframes sponsorCatPop { … 100% { opacity: 0.68; transform: translateY(0) scale(1) rotate(0deg); } }

/* :1730+ —— reduce 块（本批新增） */
@media (prefers-reduced-motion: reduce) {
  .gift-progress-badge,
  .sponsor-party-cat { animation: none; }   /* ← 关掉动画 → 回落到基础态 opacity: 0 */
}
```

**根因**
这是一个「可见性寄生在动画末帧上」的元素。直接 `animation: none` 会退回到 `opacity: 0`。计划 019 的 C2 原则写明「保留 opacity/color 反馈，砍位移/缩放与无限循环」，此处**违反了自家原则**：应当保留「可见」这一静态结果。

**修复建议**

```css
@media (prefers-reduced-motion: reduce) {
  .sponsor-party-cat {
    animation: none;
    opacity: 0.68;          /* 补回静态可见态 */
    transform: none;
  }
}
```

对照：`.sponsor-hero-cat { animation: none }` 是**正确**的——它的基础态本身可见（`opacity: 0.28`），关掉漂浮动画后只是静止。`.gift-progress-badge` 同样正确（基础态无 `opacity: 0`）。

### A8 — `apple-card` / `profile-follow-btn` 的 reduce hover 复位被反超（低）

```css
/* profile-base.css:775-791 —— reduce，0,2,0，位置靠前 */
.apple-card:hover, .profile-follow-btn:hover { transform: none; }

/* :940-946 / :1104-1110 —— hover 门控，0,2,0，位置靠后 → 胜出 */
```

**影响**：桌面端（`hover: hover` 为真）同时开启「减少动态效果」时，hover 上浮依然发生。触屏设备因 `hover: hover` 为假而不受影响。属轻微无障碍缺口。

**修复**：把这两条 hover 复位移入 `profile-panels.css` 风格的**文件末尾** reduce 块，或提高特异性（`.apple-card:hover:hover` 这类写法不推荐，直接后置即可）。

### A9 — `.ah-skel` 改 `linear` 属越界且手感倒退（低）

```diff
/* AssetsHubPanel.vue:2061 */
-  animation: ah-skel 900ms ease-in-out infinite alternate;
+  animation: ah-skel 900ms linear infinite alternate;
```

```css
/* :2063 */
@keyframes ah-skel { to { opacity: 0.52; } }
```

**问题**：这是一个 `alternate` 的**透明度脉冲**（1 ↔ 0.52 往复），不是横向移动的 shimmer 渐变。计划 019 的 B 组清单明确列出 7 处「恒定运动用 ease-in-out 应改 linear」，**不包含这一处**（正确样例是 `:1720` 的 `ah-shimmer 1.2s infinite linear`，那是真正移动的渐变）。`linear` 会让脉冲变成匀速三角波，在两个端点出现生硬折角，观感比原来更机械。

**修复**：回退为 `ease-in-out`。

**⚠️ 风险提示（需实测）**：`src/style.css:62` 的 `body { overflow-x: hidden !important }` 正是**通过「根元素溢出传播」把横向裁剪传给视口**的那一条。改为 `visible` 后，About 页若存在任何横向溢出元素（该页有 `filter: blur()` 与 transform 装饰），**可能出现横向滚动条**。代码注释里「根元素的横向溢出裁剪属于视口滚动，不影响 sticky」的说法不严谨——被传播到视口的恰恰是 body 的 `overflow`。

**验证方法**：打开 `/about`，在窄窗口下检查有无横向滚动条；`document.documentElement.scrollWidth > clientWidth`。

> 注：该 hack 本身**是必要的**——`position: sticky` 相对最近的滚动祖先定位，body 一旦成为滚动容器，`manifesto`/`chapters` 的钉住段就失效。问题只在于副作用需实测。

**更优解（建议采用）**：本项目此前已在订阅页吸顶工具条的走查中定位过**同一个根因**（`src/style.css:54-66` 给 `html` 与 `body` 同时写了 `overflow-x: hidden` → 一个轴非 `visible` 时另一轴计算为 `auto` → body 成为滚动容器 → 全站所有 `position: sticky` 失效），当时的建议是 **`overflow-x: hidden` → `overflow-x: clip`**（`clip` 不创建滚动容器，既保留横向溢出防护又让 sticky 恢复）。相比本批采用的 `html.about-scroll body { overflow: visible }`，`clip` 是**根治且无副作用**的方案，且能一并修好全站其余 sticky（含订阅页对比表 `thead th`），无需逐页挂类。

```css
/* src/style.css:54-66 —— 根治方案 */
html, body { overflow-x: clip; }   /* 原为 overflow-x: hidden */
```

若采用 `clip`，`AboutUs/index.vue` 的 `onMounted/onUnmounted` 挂类逻辑与 `style.global.css:471-477` 的 `.about-scroll` 规则**可整体删除**。

### 级联断言脚本（本次新增的可复用验证手段）

因为 A3/A4/A5/A7/A8 的根因都是「reduce 规则在层叠中输了」，仅靠肉眼审查极易漏判。因此写了一个 postcss 断言脚本：对每条「目标动画规则 ↔ 对应 reduce 规则」配对，计算特异性与源序，判定 reduce 是否真能胜出。

**它当场抓出了一处我第一轮修复的漏网**：reduce 块里只写了 `.… .tab-transition-* .tab-page`（特异性 0,3,0），而方向规则是 `.… .tab-page.is-leaving`（0,4,0）—— **两个方向的「出场」动画在 reduce 下仍会播**。补上显式选择器后 14/14 全绿。

修复前后对比（节选）：

```
修复前 ❌ .user-space-page.tab-transition-back .tab-page.is-leaving 在 reduce 块中缺失
修复后 ✅ .user-space-page.tab-transition-forward .tab-page.is-leaving  normal(L329) vs reduce(L2884, 更高特异性)
修复后 ✅ .user-space-page.tab-transition-back  .tab-page.is-leaving  normal(L329) vs reduce(L2884, 更高特异性)
```

> **教训**：`.tab-page` 这种「不带状态类」的选择器**能匹配**带 `.is-leaving` 的元素，但**特异性更低**，所以「看起来覆盖了」≠「层叠上赢了」。reduce 规则必须与目标规则的**选择器形态**对齐，而不只是语义对齐。
