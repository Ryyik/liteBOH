## 1. 结论速览

**总体判断**：这个站的**基础设施层安全做得相当扎实**——RLS 全覆盖、函数级 ACL 收口、上传签名化、安全头齐备、依赖与 DB 双棘轮门禁、无第三方跟踪器、无 Cookie。**真正的风险不在「数据库被拖库」，而在「认证入口的机器人对抗」与「无界资源消耗」两块**，且这两块都集中在 RC 前最容易加新功能的地方。

| 级别 | 数量 | 一句话 |
|---|---|---|
| **P0** | 2 | 人机校验服务端失效（撞库可绕过）；邮件发送接口可被用作任意收件人发信（待 5 分钟确认） |
| **P1** | 6 | 限流器 fail-open + 限流表无界增长；SSRF 重定向绕过；CSP 无上报端点；隐私政策合规缺口；AI 记忆数据可删除性；账号级限流缺失 |
| **P2** | 9 | 过滤器转义单源缺失；**78 张表**对 anon 保留 SELECT 授权；广告点击无节流；孤儿安全代码；COOP/CORP 缺失；`cron.job` 明文令牌等 |
| **P3** | 5 | 明文邮箱落 localStorage；外链 http；AES-GCM 无 AAD；`.orig` 文件；依赖待重扫 |

**六大维度核验表**

| 维度 | 结论 | 关键证据 |
|---|---|---|
| 数据传输加密 | ✅ 良好 | HSTS `max-age=31536000; includeSubDomains` 实测命中；全站 HTTPS；Supabase/Cloudinary 均 TLS；仅 1 处 `http://` 外链（P3-2） |

### P0-1 🔴 人机校验在服务端完全失效，且登录失败无任何累积对抗

**位置**

| 文件 | 事实 |
|---|---|
| `supabase/functions/auth-login/index.ts:45-47` | 请求体只读 `loginId` / `password`。全文**无 `altchaPayload`、无 `should_require_login_altcha`、无 `record_auth_attempt`**，只有第 35 行一个 `10 次/分/IP` 的限流 |
| `supabase/functions/auth-register/index.ts` | 同上，只做 `5 次/分/IP` |
| `supabase/functions/_shared/altcha.ts:78` | `verifyAndConsumeAltchaProof` 已导出，但**全仓零调用**（`rg` 只命中定义行本身）。校验器是死代码 |
| 库内（2026-10-31 直连实测） | `auth_altcha_proofs` 表**仍存在**（15 行，`max(created_at)=2026-06-01`）；`auth_attempt_events` 表**也还在**（77 行，同样停在 `2026-06-01`）；`record_auth_attempt` / `should_require_login_altcha` / `should_require_action_altcha` / `should_allow_signup_attempt` 四个函数**全部存活且 `SECURITY DEFINER`** |
| EF secrets（实测） | `ALTCHA_ENABLED` / `ALTCHA_HMAC_KEY` / `ALTCHA_MAXNUMBER` / `ALTCHA_TTL_MS` **四个密钥都在**，且 `ALTCHA_ENABLED` 为真 |
| `src/views/Login/index.vue:624,805`、`src/views/Join/index.vue:344,1142` | 前端渲染 `<AltchaWidget>`，`altchaPayload` **也确实提交**给了 `signUp(...)` |
| **线上部署包**（`supabase functions download`，2026-10-31） | `auth-login/index.ts` 与仓库**逐字节一致**（`diff` 空）；包内 `_shared/` 只有 5 个模块，**没有 `altcha.ts`**（未被 import）；对线上 `index.ts` 跑 `grep -ci altcha` = **0** |

**根因（已修正）**：不是「被删了」，是**接了一半就断了**——挑战签发（`altcha-challenge` EF）、签名密钥、验证器、防重放表、失败计数函数、决策函数，六件套全部就位，**唯独没有任何调用点把它们串起来**。数据侧的铁证：`auth_altcha_proofs` 与 `auth_attempt_events` 最后一条记录都是 `2026-06-01`，此后 5 个月零写入 ⇒ **这条链路自上线以来从未真正生效过**。

这种形态比「没有防护」更危险：所有代码审查、依赖扫描、密钥检查都会看到「altcha 已接入」，只有把调用链真正追到最后一个 `import` 才会发现缺口。

**影响**

1. **撞库/凭证填充零成本**：攻击者直接 `POST /functions/v1/auth-login` 只带 `loginId`+`password`，完全绕过 widget。单 IP 10 次/分，1000 个代理 IP = **10,000 次/分**；对「用户名+弱密码」的社区站，这足以批量接管账号。
2. **无失败累积**：同一账号可被无限次尝试（只受 IP 维度限制），不存在锁定、渐进延迟、风险评分。
3. **账号接管 → PII 泄露**：接管后可读私信、`boh_cloud_entries`（云相册）、`user_addresses`（收货地址含手机号）、`points_transactions`。**这是本站唯一能把「低危缺口」串成「高危事件」的链路。**

**修复（按投入排序，全部可当天完成）**

1. **接上现成的校验器（必做，约 1 小时 —— 比原估算便宜，因为不用造轮子）**
   - 在 `auth-login` 拿到 `loginId` 后、调 `signInWithPassword` **之前**插入：
     ```ts
     const ipHash = await hashIp(clientIp, Deno.env.get('AUTH_IP_HASH_SALT'));
     const need = await serviceClient.rpc('should_require_login_altcha', {
       p_login_key: loginId.toLowerCase(), p_ip_hash: ipHash, p_device_id_hash: body?.deviceIdHash ?? '',
     });
     if (need.data) {
       const v = await verifyAndConsumeAltchaProof(body?.altchaPayload, 'login', { loginKey, deviceIdHash });
       if (!v.ok) return jsonResponse({ ok: false, code: v.code, message: v.message }, 400, origin);
     }
     ```
   - `verifyAndConsumeAltchaProof` **已经写好了防重放**（`auth_altcha_proofs` 唯一约束 + `ALTCHA_REPLAYED` 分支），**不要再新建 `auth_challenge_used` 表**。
   - 每次尝试结束（成功/失败都算）补一行 `record_auth_attempt(...)`，参数签名已存在：`p_event_type / p_login_key / p_ip_hash / p_device_id_hash / p_succeeded / p_used_altcha / p_failure_code / p_user_agent`。
2. **把「账号维度」的退避规则显式化（必做，约 2 小时）**
   - `should_require_login_altcha` 目前只决定「要不要弹验证码」，**不构成锁定**。建议在同一处加读：同一 `login_key` 近 10 分钟失败 ≥ 10 → 返回 `429 ACCOUNT_THROTTLED`（带 `retryAfter`）。
   - 关键：**这是「账号维度」限流，与现有「IP 维度」正交**——两者都要有，缺一都能被单边绕过（分布式撞库绕 IP 维度，单 IP 打一个号绕账号维度）。
   - `login_key` 用 `sha256(lower(loginId))`，**不要存明文账号**；`auth_attempt_events` 已有 `login_key` 列，沿用即可。
3. **风控可观测（建议，几乎零成本）**
   - 数据已经落在 `auth_attempt_events`（`failure_code` / `ip_hash` / `succeeded` 都有）。**先把它跑起来再谈告警**：现在这张表 5 个月没新行，等于没有可观测性。
4. **Cloudflare 侧兜底（建议，零代码）**
   - 对 `/functions/v1/auth-login` 路径加 Rate Limiting 规则（如 30 次/分/IP），把第一层拦在边缘，不让请求打到 Supabase。

**验收标准（可直接做成门禁）**

- 新增探针 `scripts/probes/probe-auth-challenge.mjs`：不带 payload 调 `auth-login` → 断言 **400**；带过期 payload → 断言 **400**；带有效 payload → 断言进入密码校验。
- 新增单测：`auth_login_attempts` 的退避曲线（5/10 次边界）。
- 反证：把 `verifyAltchaPayload` 调用注释掉，上述探针必须变红。

### P0-2 🔴 `email-send` 的 `gift` 模板透传任意模板参数 —— 可能成为「任意收件人发信机」

**位置**：`supabase/functions/email-send/index.ts`

```
allowedTemplates = ['gift', 'merchandise_settlement']
...
if (templateType === 'merchandise_settlement') { 服务端按 orderId 取快照，安全 ✅ }
else { safeParams = sanitizeTemplateParams(templateParams); }   // ← gift：任意参数，仅 trim + slice(0,5000)
```

`sanitizeTemplateParams` 只做 `String().trim().slice(0,5000)`，**不做字段白名单**。参数被原样塞进 EmailJS 的 `template_params`。

**为什么是 P0（待确认）**：EmailJS 模板的收件人通常是 `{{to_email}}`。如果该模板的收件人字段来自 `template_params`（而不是模板内写死），那么**任何已登录用户**都能以站点名义向任意地址发信，速率 `20 次/分/（用户×IP）`。后果：① 站点邮箱配额被烧穿（邮件服务停摆，注册验证码发不出）；② 品牌被用于钓鱼/垃圾邮件，域名进黑名单。

**必须先做的一步（5 分钟，你来判断）**：登录 EmailJS 控制台看 `EMAILJS_TEMPLATE_ID` 对应模板的 To 字段——
- 若是**固定值**（如站点自己的邮箱）→ 降级为 P2（仅配额滥用）。
- 若是 `{{to_email}}` 之类的变量 → **保持 P0**。

**修复（无论哪种都建议做）**

1. **字段白名单**：`gift` 分支只允许 `['orderNo','giftName','userName','message']` 这类展示字段，其余丢弃；**显式拒绝任何形如 `to`/`to_email`/`email`/`reply_to` 的键**。
2. **收件人服务端决定**：若业务上「礼物通知」就是发给当前用户自己，直接把 `to_email` 从 `template_params` 里剔掉，改由 EF 从 `auth.users` 取当前用户邮箱注入。
3. **加审计**：每次发送写 `mail_outbox`（表已存在），带 `template_type` / `user_id` / 参数键名（**不记值**）。异常时能查「谁在刷」。
4. **降低速率**：`20/分` 对「用户主动触发的一次性通知」偏高，建议 `5/分 + 20/天`。

**验收**：单测断言「传入 `to_email` 时该键不出现在最终 payload」；反证：删掉白名单，测试必须红。

## 3. P1 级（RC 前应修，或明确接受风险并记录）

### P1-1 🟠 限流器 fail-open + `_rate_limits` 表**永不清扫** ⇒ 一条无界增长的存储耗尽通道

**位置**

- `supabase/functions/_shared/rate-limiter.ts:22-35`：RPC 出错 → `return { ok: true }`；`catch` → 同样 `ok: true`。
- `supabase/migrations/2026070104_check_rate_limit_rpc.sql`：函数体只有 `INSERT ... ON CONFLICT DO UPDATE`，**没有 `DELETE`、没有过期清理**。
- 全仓 grep `_rate_limits`：**无任何 `delete from` / cron 清理任务**。

**影响（两条独立的问题）**

1. **fail-open**：DB 抖动、连接池打满、`_rate_limits` 表被锁时，**全站所有限流同时静默失效**，且只留一行 `console.error`。攻击者虽不能直接制造 DB 故障，但「先打满连接/把表撑大」再触发抖动，是可行的组合拳。
2. **无界增长（更现实）**：`check_rate_limit` 的 key 是**外部可控字符串**。`auth-login` 的 key 是**裸 `clientIp`**（`auth-login/index.ts:32-35`）——匿名、无需登录。攻击者用 IPv6 轮换或代理池，**每个新 IP 永久留下 1 行**。10 万个 IP = 10 万行且永不回收。表越大，`INSERT ... ON CONFLICT` 的索引维护越贵，形成正反馈。在共享实例上，这最终表现为**整库变慢甚至写满**——即用户要求的「资源被恶意消耗」。

**修复**

1. **给 `_rate_limits` 加 TTL 清理**（必做，1 个迁移）：
   ```sql
   -- 每日清理过期桶（pg_cron，与现有周报 cron 同款）
   delete from public._rate_limits where reset_at < now() - interval '1 day';
   ```
   同时在 `check_rate_limit` 内做**概率清理**（如 `if random() < 0.01 then delete ... end if`），避免完全依赖 cron。
2. **给 key 加维度上限**：对匿名入口，key 改为 `sha256(ip)` 并**截断到 /64 前缀**（IPv6 一个用户常占整段），把「轮换地址」的基数从 2^128 压到可管理量级。
3. **fail-open → fail-closed（分级）**：
   - 认证类（`auth-login` / `auth-register` / `email-send`）：**改为 fail-closed**（RPC 失败 → 503 + 退避），因为「限流失效」的代价远高于「短暂不可登录」。
   - 展示/读类：保持 fail-open（不因基础设施抖动误伤浏览）。
   - 实现上给 `checkRateLimitDb(key, max, window, { failMode: 'open' | 'closed' })` 加参数，**默认 closed**，读类显式传 `open`。
4. **加监控**：`_rate_limits` 行数 > 50 万 时告警（一条 `pg_cron` + `net.http_post` 即可）。

**验收**：`select count(*) from _rate_limits` 在压测后回落；单测覆盖 `failMode` 两分支。

### P1-2 🟠 出站请求未禁用重定向 ⇒ BYOK 端点可绕过 SSRF 白名单

**位置**：`supabase/functions/api-key-vault/index.ts`

- `:106-140` `isPrivateOrLocalHost()` —— 拒绝 `localhost` / 私网段 / `169.254.169.254`，判据正确 ✅
- `:3253` `fetch(baseUrl, {...})`、`:3316` 模型发现 —— **均未设置 `redirect: 'manual'`**

**根因**：SSRF 防护只校验**用户填写的 hostname 字符串**，但 `fetch` 默认 `redirect: 'follow'`。攻击者把自己的端点返回 `302 Location: http://169.254.169.254/latest/meta-data/`（或内网服务），请求会被**自动跟随**，白名单形同虚设。

**影响**：Edge Function 运行在云厂商内网 ⇒ 可探测/读取元数据服务、内网 HTTP 服务。同时 `Authorization` 头可能随重定向被带到内网目标（用户自己的 key，危害有限；**平台内网可达性才是重点**）。

**修复**

```ts
const response = await fetch(baseUrl, {
  ...init,
  redirect: 'manual',            // 1. 不跟随
});
if (response.status >= 300 && response.status < 400) {
  throw new Error('ENDPOINT_REDIRECT_NOT_ALLOWED');  // 2. 直接拒绝
}
```
- 同时给 `fetch` 加 `AbortSignal.timeout(30_000)`（当前未见超时，见 P2-6）。
- 建议再加**解析后 IP 校验**：`Deno.resolveDns(host, 'A')` 后逐条比对私网段，防 DNS rebinding（成本略高，可作为第二阶段）。

**验收**：单测断言「302 响应 → 抛错且不发第二次请求」；反证：改回 `follow`，测试红。

### P1-3 🟠 CSP 是 Report-Only **且没有上报端点** ⇒ 既无防护也无数据，CSP 投入归零

**位置**：`scripts/cloudflare-security-headers.mjs:88-99`

```js
const CSP_VALUE = [
  "default-src 'self'",
  "script-src 'self' 'unsafe-inline'",
  ...
  "object-src 'none'",
].join('; ');            // ← 没有 report-uri / report-to
```

**实测**（本轮现跑）：线上返回 `content-security-policy-report-only: ...`，**无 `report-to`**。

**为什么这是「配置错误」而不是「低危」**：Report-Only 的唯一价值是**收集违规报告**，据此把 `'unsafe-inline'` 换掉、再转 enforce。现在没有上报端点，浏览器把违规**直接丢弃**——团队永远不会知道哪些内联脚本在拦路，于是永远转不了 enforce。**这是一个自锁死的状态**。

**叠加风险**：会话存在 `localStorage`（`supabase-client.js:18`），一旦出现 XSS（哪怕通过第三方库供应链），token 可被直接读走；而 `script-src 'unsafe-inline'` 让 CSP 对 XSS **毫无拦截能力**。

**修复（三步，两周内可完成 enforce）**

1. **立即加上报端点**（30 分钟）：
   ```
   report-to csp-endpoint
   # 响应头另发：Report-To: {"group":"csp-endpoint","max_age":10886400,"endpoints":[{"url":"https://<你的收集端>"}]}
   ```
   收集端可用 Cloudflare Worker（免费额度足够）落到 R2/Logpush。
2. **消除 `'unsafe-inline'`**（主要工作量）：`index.html` 有 4 段内联 `<script>`（主题引导、SW 清理、资源恢复、骨架超时兜底）——把每段内容算 SHA-256 写进 `script-src 'sha256-...'`，或给它们加 `nonce`（需要 Cloudflare Worker 改写 HTML）。`style-src` 的 `'unsafe-inline'` 因 Vue scoped + 内联骨架样式短期难消除，可先保留并记录为例外。
3. **转 enforce**：报告收敛 1-2 周、违规清零后执行 `node scripts/cloudflare-security-headers.mjs --csp-enforce`。

**验收**：线上 `curl -I` 出现 `content-security-policy:`（非 report-only）且无 `unsafe-inline`（`style-src` 除外，需在脚本注释里写明例外理由）。

### P2-2 🟡 **78 张表**对 `anon` 保留 SELECT 授权，安全全靠 RLS 单点

**实测（2026-10-31 直连库，权威判据 `has_table_privilege`）**

```sql
select c.relname from pg_class c join pg_namespace n on n.oid=c.relnamespace
where n.nspname='public' and c.relkind='r'
  and has_table_privilege('anon','public.'||quote_ident(c.relname),'SELECT');
-- → 78 行（public 共 100 张表）
```

其中包含**用户 API Key 密文**（`api_key_vault`）、**积分流水**（`points_transactions`）、**收货地址**（`user_addresses`）、**云相册**（`boh_cloud_entries`）、**订单**（`shop_points_orders`）、**订阅**（`user_subscriptions`）、**AI 记忆**（`boh_ai_*` 六张）。`INSERT/UPDATE/DELETE` 对 anon **全部为 false**（这点是好的）。

**RLS 确实在兜底**（本轮实测策略原文）

| 表 | 策略 | 结果 |
|---|---|---|
| `api_key_vault` | 仅 1 条 `api_key_vault_admin_all`，`roles={public}` 但 `qual=current_user_is_admin()` | anon 取 0 行 ✅ |
| `user_addresses` | 5 条全部 `roles={authenticated}` + `user_id = auth.uid()` | anon 取 0 行 ✅ |
| `points_transactions` | `owner_select` 要求 `user_id = auth.uid()` | anon 取 0 行 ✅ |

**含义**：这不是「已经泄露」，而是**纵深防御只剩一层**。任何一次误加 `using (true)`、任何一次迁移漏写 `enable row level security`、任何一次把策略 `roles` 从 `authenticated` 放宽到 `public`，这 78 张表立刻对匿名可读。而 `check:layering` 这类现有门禁**看不见表级 ACL**。

> ⚠️ **测量陷阱（本轮踩到，记下来）**：用 `information_schema.role_table_grants where grantee='anon'` 查会得到**全空**，因为该视图只显示「授权方或受权方是当前已启用角色」的授权 —— 当前是 `supabase_read_only_user`，看不到 anon 的授权。**必须用 `has_table_privilege('anon', …)`**。我上一版报告正是因为 REST 探测只覆盖了 20 张表，把数量低估成 8 张。

**修复（不能一刀切 revoke）**：`posts` / `comments` / `news` / `products` / `activities` 等公开内容表**确实需要** anon SELECT。做法：
1. 跑上面那条 SQL 导出 78 张清单，人工标注「公开可读」白名单（预计 15-20 张）。
2. 对白名单外的表 `revoke select ... from anon`（一次性迁移）。
3. 新增门禁 `check:anon-table-grants`：断言「anon 有 SELECT 的表 ⊆ 白名单」，**在预发先跑**再上生产。

### 6.3 建议补的三道「兜底闸」

1. **全局预算闸**：给「AI 调用 / 邮件 / 上传签名 / 导出」各设**日总量上限**（不是速率，是总量），到顶自动降级并告警。速率限制防爆发，总量限制防慢速渗透——**两者缺一不可**。
2. **Kill Switch**：一张 `feature_flags` 表（或复用现有配置表）+ 前端读开关。出事时能 30 秒内关掉 AI / 上传 / 注册，而不用发版。这是 RC 上线前**性价比最高**的一件事。
3. **异常告警**：把 `admin_audit_logs` / `auth_attempt_events` / `_rate_limits` 的异常模式（失败登录激增、单账号请求激增、表行数激增）接到一个 Webhook（企业微信/飞书机器人即可）。注意 `auth_attempt_events` **当前 5 个月零写入**，先接上调用再谈告警。

## 8. 防护性编程的具体建议（不只修 bug，改「让 bug 写不出来」）

本仓已有很强的「门禁文化」（棘轮 + 反证 + 探针）。下面几条是**顺着这个文化**补的：

1. **安全常量单源化**：新建 `supabase/functions/_shared/security-policy.ts`，把所有限流阈值、超时、体积上限、模板白名单集中定义。**禁止在 EF 内散写魔数**（现在 `10` / `20` / `60` 散落 6 个文件）。
2. **默认安全（secure by default）**：
   - `checkRateLimitDb` 默认 `failMode: 'closed'`，读类显式 opt-out。
   - 新表默认 `enable row level security` + `revoke all from anon`（写进迁移模板，`check:db-advisors` 兜底）。
3. **入站白名单优于黑名单**：`sanitizeTemplateParams` 改「只保留允许的键」；EF 的 `body` 解析统一走 `pickFields(body, allowed)`。
4. **出站统一出口**：`fetchWithGuard()`，默认 `redirect: 'manual'`、`timeout`、`maxBytes`。任何 EF 直接 `fetch` 外部 URL 应被 lint 规则拦下（可加一条 ESLint `no-restricted-syntax`，只允许从 `_shared/outbound.ts` 导入）。
5. **反证式测试**（本仓已有 `frontend-fix-reverse-proof` 的成熟做法）：每个安全修复都配一条「撤掉修复必须变红」的测试，并把「撤掉后变红」写进 commit message。
6. **安全回归探针**：新建 `scripts/probes/probe-security-baseline.mjs`，把本轮实测项固化成断言：① 6+2 个响应头齐全；② 匿名访问 8 张敏感表返回 401 或空集；③ `auth-login` 无 payload 返回 400；④ `_rate_limits` 行数 < 阈值。**接入 `npm run prepush`**，让安全基线像 `probe-dark-surfaces` 一样变成发布前硬闸。
