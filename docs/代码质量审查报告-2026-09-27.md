## 一、总体判断

先说结论：**这个仓库不是"乱写"，是"长出来的"**——工程意识其实很强（42 个 npm 门禁脚本、131 个测试文件、DataAdmin 已经抽出 13 个 composable），但增长过程中缺少持续的结构性收敛。

问题集中在三条主线上：

| 主线 | 症状 | 严重度 |
|---|---|---|
| **体量失控** | 37 个文件超 1000 行，最大 6638 行 | 高 |
| **真源分裂** | 色值硬编码 2848 处，而 `tokens.css` 已存在；`supabase.from()` 散落 72 个文件 | 高 |
| **门禁空转** | CI 里测试被注释掉、PR 门禁 `ci.yml.disabled`、版本库 499M | 高 |

第三条最容易被忽略，但它决定了前两条会不会复发——**没有跑在 CI 上的约束，等于没有约束**。

## 三、P0 问题（建议本迭代处理）

### P0-1 硬编码色值 2848 处，`tokens.css` 名存实亡

**证据**

- `#RRGGBB` 字面量 **2848 处**，分布在 **134 个文件**
- 重灾区：`AssetsHubPanel.vue`（267 处）、`BohaiSettingsPanel.vue`（116）、`LabQuotaIsland.vue`（86）、`Login/index.vue`（75）、`AiQuotaSidePanel.vue`（64）
- 而项目已有单源 `src/styles/common/tokens.css`，记忆里也明确写着「玻璃单源 tokens.css（--liquid-*），子组件禁压父级变量」

**影响**：暗色主题一致性靠 `!important` 硬压（见 P1-4），形成「改一处动四处」的典型局面。新加一个组件，默认就会写出新的硬编码色。

**修法**

1. 先补门禁，别先改代码：`scripts/check-dark-tokens.mjs` 已有 `--strict` 模式，把它从可选脚本挂进 CI。
2. 按文件倒序清理，一次一个组件：色值 → `--liquid-*` / 语义 token；同时把该文件的 `!important` 一并减掉。
3. 清理顺序建议：`AssetsHubPanel` → `BohaiSettingsPanel` → `LabQuotaIsland` → `Login` → `AiQuotaSidePanel`（这 5 个占 608 处，约 21%）。

### P0-2 `DataAdmin.vue` 6638 行上帝组件

**证据**

- 单文件 6638 行，其中 `<script setup>` **4645 行**、`<template>` 593 行、`<style>` 897 行

- 一个组件里同时塞了 8 个业务域：表格/看板/时间线/卡片四套视图、Toast 与字段校验、审核动作、抽奖动作、新闻模板、筛选视图、产品选择器、CRUD 与分页

**影响**：这个文件已经超出单人可维护范围。改任何一个 tab 的行为，都要在 4645 行里定位，且回归面是全站管理台。

**修法**（按业务域抽 composable，落点 `src/views/DataManagement/composables/`）

### P0-3 数据访问层被绕过：`supabase.from()` 散落 72 个文件

**证据**

- `supabase.from(...)` 调用 **370 次**，分布在 **72 个文件**
- 组件层直接查库：`DataAdmin.vue` 18 次
- store 层直接查库：`stores/health.ts` 13 次、`stores/homeHeroes.ts` 12 次
- api 层本身也不薄：`utils/api/forum/post-api.js` 1712 行、`treehole-space-api.js` 1091 行

**影响**：`utils/api/*` 名义上是数据层，实际只是"部分数据层"。加索引、改字段、加 RLS 时，找不到全部调用点——记忆里「撤权前五查：pg_depend/函数定义全库扫/EF/前端调用点/RLS」之所以要五查，根源就在这。

**修法**

1. 先立规矩：组件与 store 内禁止出现 `supabase.from`，用 ESLint `no-restricted-syntax` 拦（白名单：`src/utils/api/**` + `src/stores/**` 过渡期）。
2. 存量按模块迁，优先级：`stores/health.ts`、`stores/homeHeroes.ts`（store 层最容易迁，收益最直接）→ `DataAdmin.vue` 的 18 处 → 其余。
3. `post-api.js` 1712 行建议按域拆：`post-read.js` / `post-write.js` / `post-search.js`。

### P0-4 CI 门禁空转：测试从不运行

**证据**

- `.github/workflows/ci.yml.disabled` —— PR 质量门禁**处于禁用状态**
- `.github/workflows/deploy.yml` 里：
  ```yaml
  # 跳过测试（需要 Supabase 环境变量）
  # - name: Test
  #   run: npm run test
  ```
- 而仓库里有 **131 个 `*.spec.js` / `*.test.js`**
- 同时 `package.json` 有 42 个 scripts，`scripts/` 下约 50 个脚本，其中 `check:important-budget` / `check:dark-tokens` / `check:liquid-glass` / `check:first-paint` 这一批**未在 CI 中调用**

**影响**：所有靠"自觉执行 npm script"维持的规范（暗色 token、!important 预算、液态玻璃）实际无强制力。P0-1 的色值问题会持续复发。

**修法**

1. 让 vitest 在无 Supabase 环境变量时也能跑：加 `tests/setup.js` 已有 mock 能力，把需要真实后端的用例打 `@requires-backend` 标签并默认跳过（记忆里已有 Supabase mock 与 `--pool=forks` 的坑位记录）。
2. `deploy.yml` 恢复 Test 步骤（跑标签过滤后的用例集）。
3. 把 `check:dark-tokens` / `check:important-budget` / `check:liquid-glass` / `check:first-paint` / `check:shell-precache` 挂进 `build:ci`。
4. `ci.yml.disabled` 要么删掉，要么重命名为 `ci.yml` 启用——留一个 `.disabled` 文件在 workflows 里是个持续误导。

## 四、P1 问题（下 1-2 个迭代）

### P1-1 `localStorage` 无 key 注册表 —— 167 处 / 47 文件

`useModelConfig.js` 21 处、`useForumPostDraftStorage.js` 9 处、`AnniversaryCafe` 8 处、`DataAdmin` 8 处、`GlobalSearchIsland` 7 处。

**风险**：key 拼写散落各处，重名冲突与清理遗漏只是时间问题（比如 `dm-view-${tab}` 这类模板 key 一旦改 tab 命名就会留下孤儿数据）。

**修法**：建 `src/utils/storage-keys.js` 集中导出所有 key + 一份迁移/清理清单；ESLint 禁止裸字符串 `localStorage.getItem('...')`。

### P1-2 绕过 Vue 直接操作 DOM —— 81 处 / 33 文件

`document.querySelector` / `getElementById` 81 处：`offline-export.js` 9、`SubscriptionPlans.vue` 6、`Download` 5、`Messages` 5、`ForumMain` 4。配合 `window.*` 505 处 / 50 文件。

**风险**：这类代码在响应式更新后容易失效，也是「`animation-fill-mode` 覆盖」「dataset 状态与组件状态双份」这类历史 bug 的温床。

**修法**：除第三方库集成（导出、canvas）外，一律改 `ref` + 模板引用。

### P1-3 `v-html` 28 处，其中 4 处用 `eslint-disable` 绕过检查

```
views/PostDetail/PostDetailMain.vue:2146   v-html="officialContent.html"   ← 带 disable
views/PostDetail/PostDetailMain.vue:2334   v-html="officialContent.html"   ← 带 disable
components/UnifiedNavbar/ContentDetailIsland.vue:115  v-html="html"        ← 带 disable
views/Newsroom/NewsDetailPage.vue:184      v-html="sanitizedHtml"          ← 带 disable
```

项目已装 `dompurify`，大量组件也确实在消毒（`sanitizedTitle` / `safeAgreementContent`）。但 `PostDetailMain` 那两处直接渲染 `officialContent.html` 且**用 disable 注释跳过了 lint 检查**，需要人工确认上游是否消毒——这是唯一一处"用户可见内容 + 无消毒证据 + lint 被关"的组合。

**修法**：确认 `officialContent.html` 来源，未消毒则补 DOMPurify 白名单；能确认的话把 `eslint-disable` 换成带理由的行内说明，别让它继续当"永久豁免"。

### P1-4 `!important` 1694 处

`BOHAI/BOHAI/styles/adaptive-layout.css` 302 处、`vendor/unified-nav.css` 157、`BohaiSidebar.vue` 154、`themes/forum-dark.css` 106、`BOHAIIsland.vue` 91。

**修法**：先进 CI 冻住总量，再随 P0-1 的色值清理逐文件下降。

### P1-5 Tailwind 装了但零使用

- `vite.config.js:8` 引入 `@tailwindcss/vite`，`vite.config.js:198` 注册插件
- `src/style.css:1` `@import "tailwindcss";`
- 全 src 扫描：**0 处** Tailwind 工具类使用（无 `tailwind.config.*`）

**影响**：白白引入一个构建插件 + 依赖，且 Tailwind preflight 与手写 CSS 的层叠关系是个隐形变量。

**修法**：直接移除（依赖 + 插件 + `@import`）。如果确实想用 Tailwind，那是另一个更大的决策，不该以"装了没用"的状态挂着。

### P1-6 样式有三套并行体系

- `src/styles/**` 28 个全局 CSS（含 `tokens.css`、`themes/*.css`）
- 24 个手工 `*.scoped.css`（用文件名模拟 scoped，真实作用域靠约定）
- **191 个 `.vue` 自带 `<style>`**

加上 86 个 css 文件总量 1.06 万行。同一个视觉概念（玻璃、卡片、按钮）可能同时存在于三处。

**修法**：统一走「`tokens.css` 定变量 → 组件内 `<style scoped>` 消费」，逐步把 24 个 `*.scoped.css` 收编回组件。

## 七、不建议做的事

- **不要做全量 TypeScript 迁移**。现在 26 个 `.ts` vs 252 个 `.js`，迁移成本极高而收益主要在长期；先把 `vue-tsc` 能覆盖的部分守住即可。
- **不要一次性重写任何巨型组件**。`DataAdmin` 已经有 13 个 composable 作范本，增量抽取是安全的；推倒重来会丢掉大量边界处理（那些"看起来冗余"的判断往往对应真实 bug）。
- **不要在清理色值前动暗色主题**。两者耦合，先 token 化再改主题，否则会陷入 `!important` 军备竞赛。
- **不要急着做 `git filter-repo`**。先把 `.gitignore` 补上止血，历史瘦身可以等一个无人提交的窗口。
