## 1. 总体评价

这套面板的**工程底子明显高于它的视觉表达**。表格能力（服务端真分页、粘性表头 + 粘性操作列、`aria-sort` 排序、列显隐/排序、紧凑-舒适密度、表格/卡片/看板/时间线四视图、行内编辑、命令面板、导出、变更日志）几乎覆盖了成熟控制台的功能面；RBAC 甚至做到"无权限模块**置灰而非隐藏**"这种审计友好型处理，这在自建后台里是加分项。

问题不在能力缺失，而在**把能力平铺**：一屏之内出现三层标题（顶栏 H1 / 区块 Hero / 表格 H2）、八条横向工具条、三个搜索框、两个"新增"、两个"刷新"，首屏真正留给数据的行数被压到个位数。运营的核心任务是"找到一条、改一下、确认生效"，而现在**找**和**改**之间的路径被工具条切碎了。

更值得优先处理的是三个**语义缺口**（不是美观问题，是信任问题）：界面写"跨页全选"但实际只选了当前页；"导出"只导出当前页却提示"导出成功"；筛选到 0 条时提示"这张表还没有数据，点新增"。

结论：**不需要重做布局，需要一次"减法 + 语义修正"**——先让每个按钮说的话和它做的事一致，再把首屏还给表格。

## 2. 高优先级问题 Top 5

### P0-1　批量操作链路：全选语义是假的，删除确认给不出影响范围

| 项 | 内容 |
| --- | --- |
| **位置** | 批量操作条 `.bulk-bar`（`DataAdmin.vue:421-461`）、`selectAllResults`（`:3649-3653`）、`batchDelete`（`composables/useDataAdminMutations.js:151-192`） |
| **现状问题** | ① 点"全选全部 {totalRecordCount}"后，代码执行的是 `selectedItems.value = [...currentData.value]`——而 `currentData` 是**服务端 range 分页返回的当前页**（`:3118-3119` 注释明确"直接展示当前页数据"）。于是"已选 20 项（跨页全选）"里的 20 就是每页条数，**并不是全部结果**。<br>② 批量删除的确认文案只有"确定要删除选中的 N 条记录吗？此操作不可恢复"，没有表名、没有记录标识、没有关联影响（删用户会连带积分/订阅/礼物）。<br>③ 变更日志 `addChangeLogEntry` 写的是**前端本地存储**，不是服务端审计表，事后无法证明"谁在什么时候删了什么"。 |
| **影响** | 用户以为在批量处理全部结果，实际只处理了当前页——**批量编辑尤其危险**：以为改全量，其实只改 20 条，且没有失败提示。反向也成立：想"全选全部"再删，删完发现还剩几万条，会重复操作。删除用户类记录不可恢复，且无服务端审计可追溯。 |
| **具体建议** | ① 全选三态明确：`本页 N 条` / `全部 M 条（含未加载）`，跨页全选时**不要**把 id 塞进 `selectedItems`，而是记录一个 `selectionScope = 'all'` + 当前筛选快照，执行时用同一套 filter 走服务端批量 RPC；若短期做不到，就把文案改成"全选本页"并**移除**"跨页全选"字样。<br>② 删除确认弹窗升级为「影响清单」：表名 + 前 3~5 条标识（标题/邮箱/ID）+ 关联对象计数 + 不可恢复声明；批量 ≥10 条时要求勾选"我确认删除 N 条"。<br>③ 成功 toast 附「查看变更日志」动作（toast 已支持 action，`:1640-1642`）；变更日志落服务端表。 |
| **参考模式** | Cloudflare 的批量选择条会明确写 "N selected" 并在危险动作前展示资源清单；AWS Console 的删除确认要求输入资源标识；Stripe Dashboard 的批量操作给出"将影响 X 个对象"的预检摘要。 |
| **成本** | 中（文案 + 确认弹窗改造为低；跨页真全选需服务端批量 RPC，中） |

| 项 | 内容 |
| --- | --- |
| **位置** | `composables/useDataAdminExport.js:24-48`（`exportData`）、入口按钮 `DataAdmin.vue:194-202` |
| **现状问题** | `exportData` 直接读 `currentDataRef`，即**当前页 10/20/50/100 条**，生成 CSV 后 `showToast('数据导出成功', 'success')`，文件名 `tab_日期.csv`，**没有任何条数提示、没有"仅当前页"的说明**。而同一个文件里另有 `exportBackupData`（`:97-190`）会 `range` 逐页拉全量并写 `exported/total` 摘要——说明"全量导出"能力是有的，只是按钮没接。 |

| **成本** | 低（菜单 + 复用既有全量导出逻辑） |

### P1-4　筛选到 0 条时的空状态会骗人，且没有"清空筛选"出口

| 项 | 内容 |
| --- | --- |
| **位置** | 空状态 `DataAdmin.vue:616-634`；清空筛选按钮 `:273-280`（位于 `.filter-bar` 内，而 `.filter-bar` 由 `showFilterBar` 控制，`:221`） |
| **现状问题** | 空状态条件是 `totalRecordCount === 0 && hasLoadedOnce`，文案只判断 `searchQuery`：<br>· 有搜索词 → "没有找到匹配的数据"（正确）<br>· 无搜索词 → "当前模块还没有数据，点击新增按钮添加第一条记录" + 一个主按钮"新增数据"<br>但 `totalRecordCount` 是**含筛选的 count**（`:3074-3080` 注释明确）。所以只用了状态/日期/高级筛选筛出 0 条时，页面会告诉用户"这张表是空的"，并引导他去新增。更糟的是"清空筛选"按钮在折叠的筛选条里，**此时页面上没有任何重置入口**。 |
| **影响** | 误判"数据没了"→ 重复新增 → 造出不符合当前筛选的脏数据；或反复刷新页面。这是运营侧最常见的"我明明有数据"类报障来源。 |
| **具体建议** | 空状态分三支：`无数据（真）` / `筛选无结果` / `搜索无结果`。后两者：显示已生效条件的 chips（`状态=待审 ×`、`2026-10-01~10-17 ×`）+ 主按钮"清除全部筛选"，**隐藏"新增"主按钮**（或降为次按钮并注明"新增的记录不会出现在当前筛选下"）。筛选条折叠时，在 toolbar 的"筛选"按钮上加生效条件数徽标（`筛选 · 2`）。 |
| **参考模式** | Cloudflare 的 "No results found for these filters" + 一键 Clear filters；Linear 在空结果页直接列出可移除的 filter chip。 |
| **成本** | 低 |

## 4. 改版原则建议（6 条）

1. **一个动作只有一个入口，且入口说的话必须等于它做的事。**
   现状是"新增"3 处、"刷新"2 处、"搜索"3 处，而"跨页全选"和"导出"说的话和做的事不一致。先做语义对齐（P0-1/P0-3），再做减法——顺序反了会把错误藏得更深。

2. **首屏归数据，不归装饰。**
   任何占据表格上方纵向空间的东西，必须回答"它是否帮助用户更快找到那一行"。Hero 卡片、metric 卡片、重复 H2 都不合格。目标：表格首行 ≤240px，1366×768 下可见 ≥12 行。

3. **筛选是一等公民，必须"可发现、可组合、可撤销、可见"。**
   生效条件要常驻可见（chips + 计数徽标），撤销要在**出错的地方**（0 结果页）而不只是筛选条里。现在筛选能力很强（高级规则 + 保存视图），但"已生效"这件事在折叠后就消失了。

4. **破坏性操作先给影响，再给确认，最后给回执。**
   三步：影响清单（哪些、多少、连带什么）→ 确认（大数量加勾选）→ 回执（成功条数 + 审计入口）。现在只有第二步，且第一步的信息量为零。

5. **表是数据工作台，不是表单集合。**
   浏览态要"安静"（不可编辑的单元格不要伪装成按钮），编辑态要"显式"（进入编辑模式或点编辑按钮）。现在双击即改 + 全表格 tabindex，会让浏览和编辑互相干扰。

6. **53 张表必须能被"搜到"，而不是被"记住"。**
   导航的可扩展性靠搜索索引 + 溢出菜单 + 置顶，不靠加宽侧栏。凡是新增一张表就要在 3 个地方改的做法（`tabs.js` / `tabModules.tabIds` / `TABS_ACTIONS`）应尽快收敛成单一真源。

## 5. 组件/交互级建议

### 5.1 导航（侧栏 / 顶栏 / 面包屑）

- **侧栏**：搜索框索引从"模块"扩到"模块 + 子表"，结果分组展示，回车直达；匹配到子表时同时把父模块展开高亮。无权限模块保持置灰（这是好设计，别改成隐藏）。
- **侧栏底部"快捷操作"整行删除**（`:73-91`）：它和顶栏的"新增记录/刷新数据"完全重复，且只有图标 + `title`，在 260px 栏里既占位又低识别。
- **顶栏**：保留"返回首页 / 刷新 / 新增"三个文字按钮即可，删除"通知"与"主题"之外的冗余；把全局搜索升级为 ⌘K 面板（已有 `openCommandPalette` 基础），输入时**分两组**返回：`跳到表（导航）` / `记录（跨表）`——现在顶栏搜索只搜记录，搜"积分流水"这种表名会一无所获。
- **面包屑**：模块名做成下拉，支持跨模块跳转；当前 tab 作为末级不可点。现在只能"回模块首页"，等于退一步再点两步。

### 5.2 表格

- **列配置**：把 `editor-panel` 内联面板改为右侧 popover（不再把表格推走）；`上移/下移` 换成拖拽（HTML5 `draggable` 足够，不必引库）；补列宽拖拽与"应用到所有表"。
- **浏览 vs 编辑分离**：默认单击选中行，双击/Enter 进编辑（保留现有快捷键），但把单元格的 `tabindex` 收敛为"行内一个编辑入口"，否则键盘用户 Tab 一行要按十几次。
- **密度**：现在只有紧凑/舒适两档且靠 `data-density`；建议三档（紧凑 32px / 标准 40px / 宽松 48px），默认"标准"，并把选择按用户持久化（已有 persistence composable 可复用）。
- **粘性列**：表头与操作列已粘性（`google-components.css:759-793`），建议**再加首列（主标识）粘性**——横向滚动到第 8 列时，用户仍需要知道自己在看哪条记录。
- **行操作**：主操作 ≤2 个按钮 + ⋯ 菜单（现状已如此），但 ⋯ 菜单需要方向键导航；菜单已在滚动/resize/Esc 时关闭（`:4979-4990`），这点保持。
- **空/加载/错误**：加载已有骨架屏（好）；补**错误态**——目前 `fetchData` 失败只走 toast，表格区会退化成空状态，用户会误以为"没数据"。建议表格区加 persistent error banner（"加载失败 + 重试"），并区分"权限不足（RLS 拒绝）"与"网络失败"。

### 5.3 筛选

- **一行 chips 承载所有筛选**：`全部 128 | 待审 6 | 已通过 122` 与高级筛选的生效条件合并成同一行，每个 chip 可 `×` 移除，末尾"清除全部"。
- **保存视图**：已有 `saveCurrentFilterView` / `applySavedFilterView`，但入口藏在"筛选"展开后的按钮里。建议把已保存视图做成 chips 常驻在筛选行左侧（`我的视图：待审帖子 · 本周订单`）。
- **高级筛选**：规则行现在"字段/操作符/值/删除"四列平铺，缺"且/或"逻辑与括号分组；若短期不做，至少在 UI 上声明"多条件之间为 AND"，避免误判。
- **0 结果**：见 P1-4，必须在空状态内提供"清除筛选"，而不是让用户去找折叠的筛选条。

### 5.4 状态与反馈

- **四类状态分色分形**：成功（toast，2~3s）/ 失败（toast + 可关闭 banner，因为需要行动）/ 部分失败（banner + 明细 + 重试）/ 进行中（行内 spinner + 禁用，不弹 toast）。现在"部分失败"和"失败"都挤在 toast 里。
- **禁用 vs 无权限**：无权限的动作建议**不渲染**，无权限的模块**置灰 + 锁图标**（现状正确）；禁用态要带 `title` 说明原因（部分按钮已有，建议补齐）。
- **自动刷新**：`secondsUntilRefresh` 在顶栏可见是好的，但抽屉/批量编辑打开时应暂停并显示"自动刷新已暂停"，避免列表被替换造成"改动丢失"的错觉。

### 5.5 危险操作

- 统一一个 `<DangerConfirm>` 组件，必填三项：`影响对象清单`、`不可恢复声明`、`大数量的二次确认`。删除用户/订阅/订单类必须展示关联计数（可复用"关联记录"面板的数据源 `relatedJumpsForItem`）。
- 批量删除成功后，toast 的 action 指向"变更日志"并高亮本次批次。
- 建议把"软删除"作为默认（`deleted_at`），"物理删除"降为二次入口——这需要数据层确认，属于**需补充信息**项。

## 6. 验收清单（改版后逐条检查）

1. 1366×768 下，表格第一行数据的 `getBoundingClientRect().top ≤ 240px`，首屏可见数据行 ≥ 12 行。
2. 页面上"新增"入口只有 1 处、"刷新"只有 1 处、"搜索"输入框只有 1 个（表内筛选不算搜索框）。
3. 点击"全选全部 N 条"后，批量删除确认弹窗中的数字 = `totalRecordCount`；若实现为服务端全选，需有一条断言证明影响行数 = 全量筛选结果数。
4. 导出菜单至少两项："当前页（N 条）"与"全部筛选结果（M 条）"；导出完成 toast 内含条数，文件名含范围。
5. 构造"筛选 0 条"场景：空状态文案为"没有符合筛选条件的结果"，出现"清除全部筛选"按钮，**不出现**"新增数据"主按钮。
6. 筛选条折叠状态下，toolbar 的"筛选"按钮显示生效条件数徽标；点击徽标可一键清空。
7. 删除任意一条记录：确认弹窗内出现表名、记录标识、关联影响（若有）；成功后 toast 有"查看变更日志"入口。
8. 侧栏搜索输入"积分"：返回"用户 › 积分流水""用户 › 积分发放"等子表结果，回车可直达。
9. 运营模块（11 个 tab）在 1280px 宽下 tab 行高度 ≤ 1 行（44px），溢出项收进"更多 ▾"。
10. 键盘走查：Tab 从页面顶部到表格，可聚焦元素 ≤ 8 个；表格行内每行可聚焦元素 ≤ 3 个；所有可聚焦元素有可见焦点环。
11. 表格横向滚动到最后一列时，首列（主标识）仍可见；操作列仍粘性。
12. 断网后刷新页面：表格区出现"加载失败 + 重试"，而不是空状态；重试成功后数据恢复。
13. 移动端 390×844：主操作"新增"保留文字，次操作收进 ⋯；分页组件与桌面复用同一实现。

| 低装饰、克制粗体与边框 | Hero 卡片 + 实心蓝选中项 + 胶囊 tab + 阴影 | 去 Hero、选中项改浅底 + 左强调条、tab 改下划线 | 已改（见 8.1） |

**一个反直觉的实测结论**：字号从 13.1px 提到 14px 之后，表格首行只从 234px 变成 **237px**，可见行数仍是 **13 行**——因为密度是靠**行高 42px + padding 9/12px** 控制的，不是靠缩字号。所以"要密度就得小字"是伪命题，Kumo 的做法（大字号 + 紧行距）反而更耐读。

### 8.6 关于"按任务意图分组"：该改的是 tab 层，不是 rail 层

Cloudflare 把顶级导航从"产品名"改成"功能意图"（IP 前缀 → Routes，隧道 → Connectors），这个转向值得学，但**不能直接套到左侧 rail**：

- 你们的 rail 已经是**数据域层级**（用户 / 礼物 / 商城 / 社区 / 运营 / 审核 / 抽奖 / AI 配置 / 日志）。再往上抽象一层"用户与权益 / 内容与社区 / 活动与运营"，会出现大量**单条目分组**（礼物→用户与权益、社区→内容与社区），层级变多、扫描变慢，收益为负。
- 真正"按内部模块命名"的地方在 **tab 层**：运营模块把 11 张表平铺成 `新闻 / 活动 / 发帖有奖 / 官方事实 / 创作者展示 / 生日活动 / 生日祝福 / 活动平台 / 报名明细 / 发放台账 / 海报申请`，这些名字是**表名**，不是任务。运营同学的心智是"我要发一条内容""我要看活动报名"，不是"我要打开 campaign_rewards 表"。

建议按意图重排 tab（映射如下，仅重排不删表）：

| 意图组 | 包含的表 |
| --- | --- |
| 内容发布 | 新闻管理 · 官方事实 · 创作者展示 |
| 活动运营 | 活动管理 · 活动平台 · 活动报名明细 · 活动发放台账 |
| 互动与激励 | 发帖有奖 · 生日活动 · 生日祝福 · 海报申请 |

这样 11 个 tab 变成 3 组、每组 3~4 个，天然解决 8.1 里的"溢出菜单"问题，也让"更多 ▾"有内容可放。代价是 `tabs.js` 要加一个 `intent` 字段（单一真源，加一次即可）。

### 8.7 编辑器相关：本产品没有代码编辑器，但三条结论仍然成立

Cloudflare 的 Quick Edit 是代码编辑器，本产品的 `EditDrawer` 是表单，不能直接类比。但其中三条可迁移：

1. **"主工作区敢占最大权重"** → 详情/编辑抽屉现在固定窄宽（`EditDrawer.vue` 1558 行，表单字段多），建议支持 640 / 880 / 全屏三档，按字段数自动选档。字段 20+ 的表（用户、订阅、活动）挤在窄抽屉里，滚动长度是当前编辑效率的隐性瓶颈。
2. **"预览必须可信"** → 对应本产品的**保存前差异预览**（`confirmPayloadDiffs`）。这个已经做了，但只在保存时才弹。建议把差异做成抽屉右侧的常驻 "变更 3 项" 面板，编辑过程中就能看到，而不是最后一次性确认。
3. **"错误状态界面化"** → 现在保存失败只有 toast（`showToast(err, 'error')`），关掉就没了，用户不知道哪个字段错了。应改为：字段级红框 + 顶部错误摘要 + 保留用户输入（当前 `clearFieldErrors` 已有基础设施，只是覆盖不全）。

### 8.8 密度取舍：不复制 CF 的"极紧"

Cloudflare 的紧凑服务于**每天数小时**的专业运维。本产品的使用者是运营/管理员，频次中等，且要在同一屏里读中文长文本（帖子标题、活动名）。因此建议：

- **默认「标准」密度**：14px 正文 + 42px 行高（原型采用）
- **可选「紧凑」**：13px + 34px 行高，给需要一屏看 20+ 行的场景（对账、批量审核）
- **不做「宽松」**：后台场景没有阅读型需求，宽松档只会被误选

一句话：**结构学 CF（层级、任务流、密度可调），字号不学 CF 的极限值，视觉不学 CF 的橙色。**

## 9. 编辑形态：抽屉还是内嵌子页？（原型第三个视图「编辑子页」）

> 原型 `demo-data-admin-cf-layout.html` 顶栏第三个按钮可直接切到子页形态：4 级面包屑 + 8 字段表单 + 右侧变更摘要/关联/审计 + 吸底操作条。

### 9.1 先给结论：做「详情子页」，不做「编辑页」

**编辑是模式，不是位置。** 如果做成独立编辑页，会连锁出现三个问题：

1. 面包屑变成 5 级，末级是动词（`… › 八周年庆典 › 编辑`），用户读不出"我在哪"；
2. 刷新后停在编辑态、把链接发给同事也进编辑态——**URL 承诺了不该承诺的状态**；
3. 编辑页和详情页要各维护一套字段渲染，`config/fields.js` 的单一真源被复制成两份。

正确形态是：**列表 → 详情（只读）→ 页内切编辑态 → 保存后回到只读并高亮变更**。URL 只到实体：`#/data-management/:module/:tab/:id`。

### 9.2 什么情况子页更清晰，什么情况抽屉更好

| 场景 | 建议形态 | 理由 |
| --- | --- | --- |
| 字段 > 12（用户 ~25、订阅、活动 ~15、帖子正文） | **子页** | 抽屉纵向无限滚动，改完不知道改到哪 |
| 需要并排看关联数据（报名 2,841 / 发放 12 / 审计） | **子页 + 右侧栏** | 抽屉里没有空间放第二列信息 |
| 长文本（帖子正文、活动说明） | **子页** | 抽屉宽度不足，编辑器被压成窄条 |
| 需要分享/深链给同事 | **子页** | 抽屉没有地址 |
| 改 1~2 个字段 | **行内编辑 / 抽屉** | 跳页成本远高于收益 |
| 批量编辑、审核通过/拒绝 | **抽屉/浮层** | 要保持列表上下文连续，不能离开列表 |
| 关联记录"看一眼" | **抽屉** | 只读预览，不进入编辑 |

现状是一个 `EditDrawer.vue`（1558 行）同时服务 53 张表，字段数从 8 到 25 都有——这是"抽屉对宽表单不够用"的根因，不是抽屉本身错了。

### 9.3 面包屑规则（A › B › C 怎么写）

推荐形态（原型已实现）：

```
数据管理 › 运营 › 活动管理 › 八周年庆典 · 主会场
```

| 规则 | 做法 | 理由 |
| --- | --- | --- |
| 层级上限 | **4 级**，超过就把中间层折叠成 `…` | 5 级以上扫读成本陡增 |
| 分隔符 | 用 `›`（单箭头），**不要 `>>`** | `>>` 在无衬线字体里像代码管道符，两级以上视觉过重；CF / GCP / AWS 都用单箭头 |
| 末级 | 实体名，**不可点**，`aria-current="page"` | 末级可点会让用户以为还有下一层 |
| 末级重名 | `名称` + 下方小字 ID，或 `名称（#018）` | 两个"周年庆"无法区分，回退时容易点错 |
| 中间层 | 可点 + 带下拉（`运营 ▾` 直接跳同模块其他表） | 省掉"返回列表再点两次" |
| 编辑态 | **不进面包屑**，用组件内 state 或 `?mode=edit` | 避免出现动词末级与"链接即编辑态" |
| 与左侧 rail 的关系 | rail 高亮必须能从 URL 的 `module` 推导 | 否则刷新/深链进来 rail 选中态丢失 |

### 9.4 真正的成本：返回列表要能"原样回来"

列表 → 详情 → 返回，必须带回 **筛选条件、页码、排序、滚动位置、选中项**。现在这些都在 `DataAdmin.vue` 的内存 ref 里，一跳路由就没了。

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A. 状态进 query | `?status=pending&page=2&sort=updated_at:desc&q=周年` | **推荐**。单一真源、可分享、刷新不丢；与现有 `useDataAdminFilterState` 天然契合 |
| B. keep-alive 缓存列表 | `<KeepAlive>` 包列表组件 | 省事，但刷新即失、内存里会有两份状态 |
| C. sessionStorage 存快照 | 返回时读回 | 容易和 query 打架，只建议用来存**滚动位置** |

建议 **A + C（仅滚动位置）**。

### 9.5 路由与迁移（53 张表共用一个详情页）

```
#/data-management/:module/:tab/:id          → 详情（只读）
#/data-management/:module/:tab/:id?mode=edit → 详情（编辑态，可选）
```

- **不要**给 53 张表各写页面：`config/fields.js` 已是字段真源，详情页直接消费即可。
- RBAC 复用 `TABS_ACTIONS[tab]`，与列表页同一套判定，不要新开一套。
- 草稿 key 现为 `tab:recordId`（`getDraftKey`），迁到详情页天然兼容；未保存守卫复用 `dialog.confirmThree`，**不要**新写一套。
- 面包屑由 `module → tab → record` 三段推导，`currentAdminPageMeta` 已有所需标题。

**迁移三步（每步可独立上线）：**

| 步骤 | 内容 | 风险 |
| --- | --- | --- |
| 1 | 「查看」先做成子页（只读详情 + 关联 + 审计），编辑仍走抽屉 | 低。先解决"抽屉里看不到上下文" |
| 2 | 字段 >12 的表（用户/订阅/活动/帖子）在详情页内开编辑态 | 中。需保证保存逻辑与抽屉共用同一 `useDataAdminMutations` |
| 3 | 抽屉只保留 ≤12 字段的表 + 批量编辑 + 关联预览 | 低 |

### 9.6 落地前必须确认的两件事

1. **主键是否稳定**。`getRowIdentity` 在无 `id` 时会退化成随机串（`DataAdmin.vue:3123-3131`），说明存在**没有稳定 id 的表**（复合键/派生表）。这类表无法用 `:id` 做深链，需要先定义业务键（如 `user_id + campaign_id`），否则详情页会出现"刷新后 404"。
2. **列表与详情的数据一致性**。详情页若独立拉一次单条，会与列表缓存出现"改完返回列表还是旧值"。建议保存后统一走 `refreshCurrentViewAfterMutation()`，并让详情页读同一份 store 而不是自己再发一次请求。

## 10. 还能从 CF 借什么（不重复前文的布局/字号/编辑器）

### 明确不借的

| CF 的东西 | 为什么不借 |
| --- | --- |
| 产品矩阵式导航（Products → 二级产品） | 你们是单一站点后台，14 个数据域已经是二级；再套一层会变成"为了像 CF 而加层级" |
| 极紧密度（14px + 32px 行高 + 零留白） | 使用者是运营不是 7×24 运维，中文长文本需要呼吸；保留"标准/紧凑"两档即可 |
| Workers Quick Edit / VS Code for Web | 本产品没有代码编辑场景，`EditDrawer` 是表单；只借"错误界面化"和"主工作区占权重"两条结论 |
| 橙色品牌色 + 深色顶栏 + 大面积留白概览 | 视觉不抄，只借层级与任务流（已在 §8.2 说明） |

### 建议的三个批次

| 批次 | 内容 | 特点 |

| **批 1（低风险，1~2 天）** | 6 悬停复制 · 8 Shift 选择 · 1 时间范围预设 · 7 字段帮助 · 12 空状态文案 · 13 快捷键帮助 | 全是纯前端、不动数据层，可当天验证 |
