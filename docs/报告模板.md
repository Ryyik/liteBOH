# 报告 / 方案文档模板（量化结论必须带判据）

> 这条规则来自 `docs/规范体系设计-2026-09-28.md` 的 P0-4，执行方式是**评审时打回**（无机器门禁，原因见文末）。
> 目的只有一个：**让每个数字都能被下一个人重跑出来。** 跑不出来的数字不是数据，是观点 —— 而观点会带着权威感被照做。

---

## 一、必须的格式

任何量化结论（「N 处重复」「省 X MB」「X% 死代码」「有 N 个孤儿类」）都要写成三件套：

```
结论：<可证伪的陈述>
判据：<能在任意 commit 上重跑并给出同一个数的命令>     （<实测日期>）
```

### 合格示例（取自本仓库真实记录）

```
结论：Forum 目录仍余 569 处 hex 色值，集中在 composer.css(138) / replies-responsive.css(98) / feed.css(71)
判据：node -e "走目录统计 src/views/Forum/**/*.{vue,css} 里 /#[0-9a-fA-F]{3,8}\b/ 的出现次数"   （2026-09-29 实测）
```

```
结论：z-index 裸数字 586 处，而用 var() 的只有 1 处
判据：node -e "统计 src/**/*.{vue,css} 里 /z-index:\s*-?\d/ 与 /z-index:\s*var\(/ 的出现次数"   （2026-09-29 实测）
```

### 不合格示例（本仓库真实踩过的三个坑）

| 当时的写法 | 实测 | 照做的后果 |
| --- | --- | --- |
| 「`formatDate` 有 26 处重复，可收敛」 | 实为 **15 处 / 8 种互不相同的展示契约** | 合并即**改变视觉**（名字相同、语义不同） |
| 「`Skin/transparent/` 是 1:1 重复，删掉省 1.5M」 | 31 个同名文件**字节全不同**，两套各有独立消费者 | **删掉线上功能** |
| 「CSS 孤儿约 311 个类」 | 自建严格审计实测 **1404 个**（报告数字的 4.5 倍） | 删除范围失控 |

三个错结论的共同特征：**数字很精确（26 / 1.5M / 311），判据却经不起跑。** 精确度制造了可信度，而可信度替代了验证。

---

## 二、四条附加要求

1. **判据必须是命令，不是散文。** 「已人工核对」不算判据。
2. **必须区分「实测」与「估计 / 外推」。** 外推要写明外推基数（例：给 1 个文件加 `@ts-check` 暴露 77 行错误 → 按 5 个文件线性外推 ≈ 400 处，**这是外推不是实测**）。
3. **判据一变，结论自动作废。** 工具改了、口径改了，旧文档里的数字就不再有效 —— 要么重跑更新，要么显式标注「判据已失效」。
4. **实测与上游结论不符时，以实测为准并当场更正上游文档。** 只在聊天里说一句「报告那条不对」是不够的：下一个读文档的人看不到聊天记录。

---

## 三、为什么没有机器门禁

按设计文档原则 1，规则要么能被 CI 拦下、要么能被测试断言，两者都不是的必须**明确标注为不强制**，而不是伪装成有门禁。

这条刻意**不做脚本**，理由：

- 「哪个数字是结论、它对应的判据应该是什么」无法机器化。文档里合法数字很多（日期、版本号、行号、表格里的计数），硬做一个正则门禁会满屏假阳性；
- 一个满屏假阳性的门禁会被习惯性绕过（本仓库已有先例：`prettier --check` 式严格钩子在 513 个未格式化文件面前只会被 `--no-verify` 绕过）；
- 一个能被绕过的门禁比没有门禁更糟 —— 它会签发「已验证」的假签名。

所以本条的**执行者就是评审**：没有判据的量化结论，评审时一律打回。
