## 四、本轮真正的坑：闸门接上了，前端却渲染不出验证码

接线后新增了一条**必然出现**的故障路径：

1. 服务端 `ALTCHA_ENABLED=true`，闸门按 `auth_attempt_events` 计数要求验证码；
2. 前端渲染条件是 `isAltchaEnabled()` → 读 `VITE_ALTCHA_ENABLED`；
3. 该变量**只在未跟踪的本地 `.env` 里**，CI 的 build env 只注入了 3 个变量 ⇒ 线上恒为 `false`；
4. 于是「服务端要验证码、前端永远不渲染组件」→ 用户交不出 payload；
5. 更糟：**每次重试都会再记一笔失败**，15 分钟窗口被无限续期 ⇒ **永久锁死**。

**修法**：新增 `canRenderAltcha()`（`isAltchaEnabled() || Boolean(SUPABASE_URL)`），登录页改用它。
组件是否真的显示仍由服务端 `requireCaptcha` 决定，其他页面行为不变。

**没有**去 CI 补 `VITE_ALTCHA_ENABLED=true`：那会连带打开注册等页面的验证码，爆炸半径未知；
只在「服务端已经要求」的登录路径上解耦，是最小改动。

**反证已实测**：把 `canRenderAltcha` 改回 `isAltchaEnabled()`，
`tests/unit/altcha.test.js` 的「构建期开关为 false 仍必须可渲染」立刻变红。

## 七、补充取证：本机为什么打不通，以及由此发现的解析缺陷

### 7.1 「连不上」的准确结论（不是沙箱问题）

分层测试，每层单独确认：

| 层 | `*.supabase.co` | `supabase.com` / `api.supabase.com` |
| --- | --- | --- |
| DNS | ✅ 正常解析（Cloudflare 104.18.x） | ✅ 正常 |
| TCP 443 | ✅ **OPEN**（`nc -z` 成功） | ✅ OPEN |
| TLS 握手 | ❌ `Recv failure: Connection reset by peer` | ✅ 正常 |

决定性判据：**同一个 IP `104.18.38.10`，只换 SNI 就能区分**——

```bash
curl --resolve api.supabase.com:443:104.18.38.10      https://api.supabase.com/   # 404（通）
curl --resolve supabase.com:443:104.18.38.10          https://supabase.com/       # 200（通）
curl --resolve <ref>.supabase.co:443:104.18.38.10     https://<ref>.supabase.co/  # reset（不通）
```

⇒ 拦截发生在 TLS ClientHello 之后按主机名匹配，**整个 `supabase.co` 域族被挡**（`supabase.co` 本身也是 000）。
加固措施一并验证过：⚠️ 系统代理 `127.0.0.1:65506` 对可达域名返回 200，但对 `supabase.co` 同样 `SSL_ERROR_SYSCALL`；
IPv6 无 AAAA 记录；本机 curl 不支持 HTTP/3。**换通道、换代理、换协议都不行。**

这也解释了为什么 `supabase db push` 一直能用：数据库走 `*.pooler.supabase.com`，是另一个域。

### 7.3 由此发现的真问题：CSP 上报能收到，但字段全空

实测（上线后 6 小时内）`csp-report` 被真实浏览器调用了 **152 次**，`POST → 204`、`OPTIONS → 200`
—— 匿名可达、CORS 预检、部署参数全部符合预期。但函数自己打出的解析结果是：

```
[csp-report] {"directive":"","blocked":"","document":"","source":"","line":null,"disposition":"report"}
```

**只有 `disposition` 有值。** 根因：我们同时下发了 `report-uri` 与 `report-to`，浏览器两条通道都会用，
而字段命名不同：

| 通道 | Content-Type | 键名 |
| --- | --- | --- |
| `report-uri`（legacy） | `application/csp-report` | `document-uri` / `blocked-uri` / `effective-directive` / `line-number` |
| `report-to`（Reporting API） | `application/reports+json` | `documentURL` / `blockedURL` / `effectiveDirective` / `lineNumber` |

原实现只认连字符键名，而 `disposition` 两种写法同名 —— 于是「只有它填上了」。
**这类漏读不报错、不 4xx、HTTP 状态码全对**，只会让可观测性静默失效，比直接报错难发现得多。

修复（提交 `9b0a87c2`）：解析逻辑抽到 `supabase/functions/_shared/csp-report-parser.ts`
（纯函数、无 Deno 依赖，可直接被 vitest 导入），两种命名都认，日志增加 `fmt` 字段标明通道；
`index.ts` 只保留 HTTP 外壳（限流 / 8KB / 204 / 405 行为不变）。
反证：临时去掉驼峰键支持后，新增 3 条 report-to 用例立刻变红。函数已重新部署。

追加（提交 `1f5cc2b7`）：日志再增加 `keys` 字段 —— 只记报告对象的**键名清单**（截断到 12 个 / 200 字符，
不含任何值）。理由是上一版「驼峰键名」仍属**推断**：如果真实载荷是第三种形状，修复会再次静默记录空字段。
有了键名清单，下一次真实上报到达时一条日志即可自证形状，不必再猜、不必再发版。
测试 13 条，其中一条专门断言 `keys` 不含 URL 路径与查询串，避免把自证字段做成隐私泄露。

> 截至本节撰写时，修复后尚无新的真实违规上报到达（此前那批集中在 03:41–03:43 UTC，是页面上报的突发），
> 因此缺的是**真实上报的行为证据**；单测与包体证据见下。**待下一次违规出现后复核 `fmt` 与 `keys`**
