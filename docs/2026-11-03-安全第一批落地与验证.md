`information_schema.column_privileges` 对 `anon` / `authenticated` **返回 0 行**（假阴性）。

  `PROFILE_SELECT_COLUMNS` 都是显式列名，且不含 4 个敏感列。

## 四、本轮真正的坑：闸门接上了，前端却渲染不出验证码

接线后新增了一条**必然出现**的故障路径：

1. 服务端 `ALTCHA_ENABLED=true`，闸门按 `auth_attempt_events` 计数要求验证码；
2. 前端渲染条件是 `isAltchaEnabled()` → 读 `VITE_ALTCHA_ENABLED`；
3. 该变量**只在未跟踪的本地 `.env` 里**，CI 的 build env 只注入了 3 个变量 ⇒ 线上恒为 `false`；
4. 于是「服务端要验证码、前端永远不渲染组件」→ 用户交不出 payload；
5. 更糟：**每次重试都会再记一笔失败**，15 分钟窗口被无限续期 ⇒ **永久锁死**。

**修法**：新增 `canRenderAltcha()`（`isAltchaEnabled() || Boolean(SUPABASE_URL)`），登录页改用它。
组件是否真的显示仍由服务端 `requireCaptcha` 决定，其他页面行为不变。

**没有**去 CI 补 `VITE_ALTCHA_ENABLED=true`：那会连带打开注册等页面的验证码，爆炸半径未知；
只在「服务端已经要求」的登录路径上解耦，是最小改动。

**反证已实测**：把 `canRenderAltcha` 改回 `isAltchaEnabled()`，
`tests/unit/altcha.test.js` 的「构建期开关为 false 仍必须可渲染」立刻变红。
