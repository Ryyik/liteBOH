**为什么没顺手做「按谁用切分」**（三条实测理由，不是偷懒）：
1. **切分会打乱层叠顺序**：按「消费者集合」分桶后，各桶在原文里是交错的；某组件按桶序 import，看到的相对顺序 ≠ 原文顺序（例：桶 A 在第 1、5 条，桶 B 在第 2、3 条 ⇒ 合并后变 1,5,2,3）。要保序就得切连续段，可维护性更差。
2. **「改成全局单份」的风险是可量化的，而且不低**：postcss 逐规则判定「选择器里是否含至少一个论坛专属类名」——**542 条安全 / 208 条不安全**。不安全的典型是 `.posts-list`、`.reply-item`、`.fade-enter-active`、`.editor-header` 这类裸类名，全球化即全站泄漏。
3. **scoped 模型下重复是「功能必需」**：每个 `<style scoped>` 的 `@import` 都被编译成该组件自己的 scope 后缀，子组件内部节点只认自己的 hash。所以「同一规则两份」在 Vue scoped 里不是失误，是机制 —— 想真去重只能动模型（全局化 / 合并组件），那是 P1-1 量级的改动。

**结论**：死规则已清完；剩下的重复要跟「乐观卡模板合并」一起做（P1-2 的 B 方案），单独做收益不抵风险。

### 8.3 一个必须记住的工具坑（它直接造成了 v1 的 2 条错结论）

**v1 把根因归错了，这里更正**：不是「BSD grep 不支持 `\|`」。按 `docs/AI-ENV.md` §3 坑 #5 的实测矩阵 ——
PATH 上的 `grep` 是 **WorkBuddy CLI 的 toybox shim**（既不是 BSD 也不是 GNU），
`\|`、`\b`、`\s`、`\w`、`\d` **全部静默 0 命中，exit 1，不报错**；`-E` 能救交替（`\|`→`|`）但救不了 `\s`。
系统自带的 `/usr/bin/grep`（BSD）反而**全功能**。

v1 的「`stripLegacyTitlePrefix` 全仓只有 2 处」「`getPostsCount` 无调用点」正是从这两条坏 grep 得来的。

**纪律**：本仓库做符号统计，三选一 —— ① `grep -E`（够用就不折腾）；② `/usr/bin/grep`（要 `\b`/`\s` 时）；
③ Grep 工具（ripgrep，最稳）。`check:shell-grep` 那道门禁只管**可执行 shell 面**，**管不到一次性诊断命令** ——
也就是说，这类错误不会被任何门禁拦住，只能靠这条纪律。

### 12.5 ⚠️ 本轮踩到的一个工具坑（比上述任何一条都值得记）

**本机的 `grep` 是 shim（`brokered-bin/grep`），带 `\|` 的 BRE 双模式会静默返回空** ——
既不报错也不匹配，`exit code` 仍是 1（看起来和「真的没有」一模一样）。

实测：
```
grep -n "onUnmounted" src/views/Forum/ForumMain.vue          → 命中 3 处
grep -n "onUnmounted\|onDeactivated" src/views/Forum/ForumMain.vue  → 空
```

**后果**：我据此判断「整个 `src/views/Forum/` 目录没有 `onUnmounted`」——
而实际上 `ForumMain.vue:10` 就 import 了它、`:1435` 就在用。差一步就把一条
不存在的问题写进报告。

**规避**：
- 交互式检索一律用 **`Grep` 工具**（原生 ripgrep，alternation 写 `|` 不用转义）；
- 或退回**单模式** grep 多次；
- 仓库本身有 `check:shell-grep` 门禁，但它守的是**脚本文件**里的 grep 用法，
  **守不住 AI 在终端里敲的命令** —— 这是门禁覆盖不到的一层。
