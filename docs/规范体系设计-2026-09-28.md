# 代码规范体系设计（2026-09-28）

> 目的：让 AI 和人写代码时**必须**遵循同一套约束，且这套约束本身**不会腐烂**。
> 本文不是规则清单，是**规则如何产生、如何执行、如何防止失效**的机制设计。
> 配套阅读：`AGENTS.md`（索引）、`PROJECT_MANUAL.md`（手册）、`docs/PROBES.md`（探针）。

---

## 一、先定义问题：这个仓库缺的不是规则

现状盘点：20 道门禁、`AGENTS.md` 双入口、`PROJECT_MANUAL.md`、`docs/PROBES.md`、`plans/` 20 份方案、131 个单测文件。
**规则的数量早就够了。** 报告自己也写了「已有 20 个棘轮门禁，缺的是执行力不是检测力」。

但 2026-09-28 一天之内，实测出三种失效模式——它们都不是「规则不够」：

| 失效模式 | 本仓库实例 | 为什么比「没有规则」更危险 |
| --- | --- | --- |
| **假绿** | ① `check-project-structure.mjs:58` 只过滤 `.js`，而路由全是 `.ts` → **53 条路由一条没查，却输出 `Passed. clean`**；② `check:dark-tokens` 跑在观察档（总量上升只打 ⚠️，`exit 0`）→ **永不阻断任何构建** | 它签发了一张「已验证」的假签名。人看到绿就跳过审查，AI 看到绿就宣布完成 |
| **文档幽灵** | `AGENTS.md:74` 写着「暗色裸色值同理（`check:dark-tokens`），两个门禁都**只允许下降**」——但该门禁当时根本不阻断 | 文档承诺了一个不存在的约束。人和 AI 都相信它，于是没人再去确认真实边界 |
| **不可复现结论** | `formatDate`「26 处收敛」实为 **15 处 / 8 种不同语义**；`Skin/transparent`「1:1 重复省 1.5M」实为**两套字节全不同的资源**；CSS 孤儿「311 个类」实测 **1404 个** | 结论带着权威感却无法证伪。照第 2 条执行会**删掉线上功能** |

**所以规范设计的第一目标不是「写更多规则」，而是让每条已存在的规则可被证伪。**
一条无法被证伪的规则，等于一条不存在的规则——只是它还会持续消耗信任。

## 二、六条设计原则

### 原则 1：规则只有两种合法形态

一条规则要么是 **(A) 能被 CI 拦下的机器检查**（违反时 `exit` 非 0），要么是 **(B) 能被测试断言锁住的行为**。
两者都不是的，它是**愿望**，不是规则。

处置方式只有三条路，没有第四条：
1. 实现成 A 或 B；
2. 明确标注「**风格约定，不强制**」，并接受它会被违反；
3. 删掉它——因为它只制造「我们管了这件事」的错觉。

> 反面教材就是 `AGENTS.md:74`。写的时候是 A 的形态，实际是 C（愿望）。**已修**：`check:dark-tokens:strict` 入链，现在它真的是 A 了。

### 原则 2：每条机器检查必须自证「会红」

新增或修改门禁时，**必须用一个已知违规样本证明它 `exit` 非 0，再把样本撤掉**。
没有自证的检查，无法与「已经假绿」区分——而假绿是静默的，它能潜伏数周（`check-project-structure` 就是这样）。

最小可行的自证格式：

```
门禁：check:dark-tokens:strict
违规样本：在 src/styles/themes/dark-mode.css 的 [data-theme="dark"] 块内加 --probe: #ff00ff;
期望：exit 1，且报错信息点名该文件
实测：exit 1，输出 "src/styles/themes/dark-mode.css: 58 → 59 (+1)"
```

这条自证应当**沉淀成脚本**（见第四节 P0-1），而不是每次手做——手做的东西不会被执行第二次。

### 原则 3：棘轮是处理存量债的唯一合法方式

新规则对存量代码必然红（第 2 批那条 `supabase-client` 分层规则一落地就红 **46 个文件**）。
一次性清完不现实，放弃又不甘心，**唯一可持续的形态是棘轮**：

- **基线**：把现状数字登记下来，作为天花板；
- **只许降不许升**：任何上升即失败；
- **抬基线必须显式且留痕**：走 `--update` 出口，并在 commit message 里交代理由；
- **不要按文件判红**：`check-dark-tokens.mjs` 的注释讲得对——把一段样式从 A 挪到 B 会假红，债务没增加。

本仓库已有的三个棘轮就是标准样板，应当**作为新增门禁的默认形态**：

| 棘轮 | 基线 | 抬基线出口 |
| --- | --- | --- |
| `check:important-budget` | 1331 | 脚本内 `--update` |
| `check:dark-tokens:strict` | 2902 | `npm run check:dark-tokens:update` |
| `security:anon-check` | 154 | `npm run security:anon-check:update` |

### 原则 4：结论必须可复现

任何量化结论（「N 处重复」「X% 死代码」「省 Y MB」）**必须附判据命令**，且该命令能在任意 commit 上重跑给出同一个数。

没有判据的数字不是数据，是观点。本次三个错误结论全都有这个特征——数字很精确（26 处、1.5M、311 个），判据却经不起跑。

推论：**报告类文档应当带「判据版本」**。判据一变，结论自动作废，而不是继续被引用。

### 原则 5：验证的树 = 提交的树

`pre-commit` 跑 `prettier --write` 会**在提交瞬间修改文件**。于是「你本地验证过的树」和「实际提交的树」不是同一棵。
本仓库已经因此挂过一次 CI：9-27 那次 prettier 重排 `UserSpaceMain`，让三个**格式敏感的源码正则断言**失配——本地全绿，CI 红。

两种修法，选一种即可：
- **A（推荐）**：钩子只检查不修改（`prettier --check` + `eslint`），格式化交给显式 `npm run format`。代价是多一步手动操作，收益是**钩子不再有不可见副作用**。
- **B**：保留 `--write`，但钩子格式化后**拒绝本次提交**，提示「文件已被重排，请重新验证并重新提交」。

无论选哪种，都要把「本地绿 ≠ CI 绿」写进硬规则：**判绿必须以提交后的树为准**。

### 原则 6：命名即契约

同名不同义是最难查的一类缺陷。`formatDate` 在 15 个文件里有 8 种语义，每个单看都「对」，合起来是陷阱。

可执行的约束：
- **跨模块的通用名必须带语义限定**：`formatDateTimeFull` / `formatDateOnly` / `formatRelative`，而不是三个都叫 `formatDate`；
- **同名函数跨文件重复定义超过阈值时报警**（审计工具，不阻断——因为合法的同名是存在的）。

## 三、规范的分层载体（防止文档腐烂）

| 层 | 载体 | 定位 | 更新频率 |
| --- | --- | --- | --- |
| L0 索引 | `AGENTS.md` | 每次必读，只放**改动→门禁映射**与硬规则 | 随门禁变动 |
| L1 手册 | `PROJECT_MANUAL.md` | 数据层、架构、表结构 | 低 |
| L2 专题 | `docs/*.md`、`docs/PROBES.md` | 单点深挖 | 中 |
| L3 方案 | `plans/NNN-*.md` | 动效/交互等既定方案 | 一次性 |
| L4 记忆 | `.workbuddy/memory/` | 事故复盘与「为什么这么定」 | 每轮 |

**关键机制：L0 里每条硬规则必须标注「执行者」。**

```
- 暗色裸色值只允许下降 —— 执行者：check:dark-tokens:strict（棘轮，基线 2902）
- 禁止从 utils/auth 聚合入口 import —— 执行者：eslint no-restricted-imports
- <script setup> 里 ref/computed 必须显式 import —— 执行者：eslint no-undef（仅 js/vue）
- 不要新增 create*Center 工厂 —— 执行者：无（人工评审）
```

这张表的价值在于**它让文档腐烂变得可见**：如果某条标注的执行者不存在、或实测不阻断，那它就是一个文档幽灵，能被立刻发现。没有这张表，幽灵可以永远藏在文档里。

## 四、立即可落地的四件事（P0）

> 进度：**P0-1 已实现**（`npm run check:gates-self-test`，7 道门禁自证会红）；P0-2 未做——它是**工作流决策**（会改变每个人的提交习惯），已在 `AGENTS.md` §5 记为警告，等确认后再动；P0-3 / P0-4 未做。

### P0-1 门禁自检：`npm run check:gates-self-test` ✅ **已实现（2026-09-28）**

为每道门禁声明一个**已知违规 fixture**，脚本逐个注入 → 跑门禁 → 断言 `exit ≠ 0` → 撤销。

- 样本声明：`scripts/lib/gate-fixtures.mjs`；执行器：`scripts/check-gates-self-test.mjs`
- 首轮结果：**7 道门禁全部自证会红**（views / structure / auth-validation / liquid-glass / important-budget / dark-tokens:strict / first-paint），耗时约 45s
- 未覆盖 2 道，均已登记原因：`check:shell-precache`（要 dist 产物）、`security:anon-check`（要 Management API token，离线造不出违规）

三个设计要点，缺一个这个工具就会变成新的假绿：

1. **注入必须真的改变内容**。`editFile()` 断言 `mutated !== original`，否则直接抛错——否则会出现「样本没生效、门禁自然绿」这种自欺。
2. **还原必须兜底**。`prepare()` 返回 `restore()`，注册进 `pending` 集合，并在 `SIGINT / SIGTERM / SIGHUP / uncaughtException / exit` 上全部还原。已验证：跑完后工作区逐字节干净。
3. **工具自己也要被负向测试**。曾临时加一个永远 `exit 0` 的假门禁 + 对应 fixture，确认工具报 `❌ 没红` 并以 `exit 1` 结束——否则无法区分「工具在报告」和「工具在装作报告」。

**不要塞进 verify/build:ci 主链**（它会临时改写工作区）。要进 CI 请单开 job——CI 跑在干净检出上，改坏也只影响那一个 job。

输出示例：

```
[gates-self-test] 本次跑 7 条，自证会红 7 条
                  链上门禁总数：9，已有 fixture：7，未覆盖：2

⬜ 未覆盖（尚无法自证，属已知盲区）：
   check:shell-precache         读 dist/ 产物，需先构建
   security:anon-check          需要 Supabase Management API token 读 pg_catalog，离线无法造违规
```

**这是本设计里性价比最高的一条**——它把「假绿」从一种需要运气才能发现的病，变成一种能被周期性量化的指标。

### P0-2 pre-commit 改为只检查不修改

见原则 5 的 A 方案。同时补一条硬规则：**判绿以提交后的树为准**。

### P0-3 棘轮总账

在 `verify` 输出末尾打印所有棘轮的当前值 / 基线 / 距基线余量。让「债务在减少还是增加」一眼可见，而不是散在十几个脚本里。

### P0-4 报告模板强制判据

报告/方案类文档的每条量化结论必须写成：

```
结论：X 处重复
判据：grep -rEn "..." src | wc -l     （2026-09-28 实测）
```

没有判据的结论，评审时一律打回。这条几乎零成本，但能拦住本次那三个错误结论里的全部。

## 五、AI 协作的硬约束

AI 有几种**人类较少犯**的特有失败模式，需要单独约束：

| AI 特有失败模式 | 表现 | 对应约束 |
| --- | --- | --- |
| **盲从上游结论** | 报告说「26 处重复」就照做，不先复现判据 | 动手前**必须先复现判据**；判据与结论不符时，以实测为准并**更正上游文档** |
| **为过测试而绕过** | 加 `!important`、加 window 全局、复制第二份定义 | 已有棘轮拦（`important-budget` / `liquid-glass`）；新增门禁优先考虑这种「绕不过去」的形态 |
| **不跑门禁就宣布完成** | 「我已经改好了」但没有输出 | 声称完成**必须附门禁输出**（命令 + 结果），不接受「我认为通过了」 |
| **给不可复现的数字** | 精确到个位却没有判据 | 见原则 4 |
| **静默抬基线** | 用 `--update` 把红的门禁弄绿 | 抬基线必须在 commit message 里交代理由；禁止把抬基线混进功能提交 |
| **以「报告说了」为由跳过验证** | 「按报告第 9 条删 Skin/transparent」 | 破坏性操作（删文件、改权限、改表结构）**必须先复核引用**，上游结论不能作为唯一依据 |

**一句话：AI 的产出质量取决于它被要求提供多少证据。** 所以规范的着力点不是「告诉 AI 该怎么做」，而是「规定 AI 必须交付哪些可验证的证据」。

## 六、怎么知道规范生效了

**不要用「新增了多少门禁」当 KPI** —— 那只会制造更多假绿。反向指标才有意义：

| 指标 | 目标 | 怎么测 |
| --- | --- | --- |
| **假绿门禁数** | 0 | `check:gates-self-test` 里「未自证」的门禁数 |
| **文档幽灵数** | 0 | L0 硬规则表里「执行者：无」的条目数 + 标注了执行者但实测不阻断的条目数 |
| **无判据结论数** | 0 | 报告评审时统计 |
| **棘轮总量趋势** | 单调不增 | 棘轮总账的历史曲线 |

这四个都是**可测量**的。规范体系的健康度因此不再依赖「感觉」，而是四个能跑的脚本。
