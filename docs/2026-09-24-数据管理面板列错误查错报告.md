## 一、结论先说

你点到的「列错误」不是偶发，也不是权限或网络问题。全库 45 个表格页签里：

- **14 个页签「点开就报」** —— 一切进去就弹 toast：`获取数据失败: column xxx.xxx does not exist`
- **另有 20 处**在用了搜索框 / 日期筛选 / 状态筛选 / 点表头排序之后才报

报错形态统一：PostgREST 返回 **HTTP 400 + `42703`**，前端把它渲染成红色提示条。

**根因只有一个**：`src/views/DataManagement/query-config.js` 里声明的列名，与数据库实际列对不上。分三种成因：

| 成因 | 例子 |
|---|---|
| 列名写错（改名后没同步） | `anniversary_subscription_claims.plan_code` → 实际叫 `granted_plan_code` |
| 引用了从来就不存在的列 | `birthday_wishes.updated_at`、`lab_usage_records.username` |
| 内嵌关联里取了不存在的列 | `profile:user_id(username,email)` —— `profiles` 表**没有 email 列** |

第三条是最大的一块，单独吃掉了 6 个页签。

## 二、点开即报的 14 个页签

### A 组｜抽奖模块 6 个页签 —— 都栽在 `profiles.email`（6 个）

```
lotteryFulfillments / lotteryEntries / lotteryDrawLogs /
lotteryNotificationJobs / lotteryJoinAttempts / lotteryAuditLogs
```

**现象**：`column profiles_1.email does not exist`

**成因**：`profiles` 表从设计上就没有 `email` 列 —— email 一直存在 `auth.users`，前端是通过 RPC `admin_list_users_with_sensitive` 单独补的（`users` 页签已经这么做了）。但抽奖这几个页签的内嵌写法漏改了，仍在向 PostgREST 要 `email`。

**落点**：`query-config.js` 的 `TAB_SELECT_COLUMNS`，第 190 / 217 / 226 / 256 / 273 / 283 行

```
内嵌里出现的 email 全部删掉：
  profile:user_id(username, email)      →  profile:user_id(username)
  drawer:drawn_by(username, email)      →  drawer:drawn_by(username)
  actor:actor_id(username, email)       →  actor:actor_id(username)
```

`profiles.username` 是存在的，保留即可。若抽奖页签确实要显示中奖人邮箱，得另走 RPC 补，不能靠内嵌。

## 四、`cloudinaryUploads`（上传队列）：建议**摘掉页签，保留表**

### 4.1 这张表实际是什么

它**不是**上传队列，而是「上传归属台账」—— 三个使用方：

| 时机 | 调用 | 效果 |
|---|---|---|
| 上传完图片 | `cloudinary-client.js#registerCloudinaryPendingUpload` | 插入一行，`claimed_at/deleted_at` 均为 null |
| 发帖/发布成功 | `#markCloudinaryUploadsClaimed` | 回填 `claimed_at` |
| 用户删图 | EF `cloudinary-delete` → `filterOwnedCloudPublicIds` | **靠查这张表判定"这张图是你的"**，删完回填 `deleted_at` |

关键在第三条：**删图接口的第一道归属校验就是查这张表**（`supabase/functions/cloudinary-delete/index.ts:167`）。
台账行没了 → 查不到 → 返回 403「只能删除当前账号 Cloud+ 内容中已保存的图片」。所以**表不能删**。

### 4.2 页签为什么建议摘掉

1. **列配置是上一版语义**。表里没有 `status` / `error_message` / `retry_count`，现有列是
   `public_id / url / resource_type / source / folder / claimed_at / deleted_at`。语义已从「失败重试队列」变成「上传归属台账」。
2. **`fields: []`**（`config/tables.js:1229`）—— 本来就不能编辑，纯只读。
3. **唯一动作 `delete` 是硬删台账行**。`useDataAdminMutations.js:131` 走的是
   `.from(table).delete().eq('id', ...)`，**不碰 Cloudinary 上的文件**。data-management 目录下
   grep 不到任何 `cloudinary-delete` 调用 —— 面板没有清理云存储的能力。
   于是这个按钮的实际效果是：**删掉台账 → 用户再也删不掉那张图**，是反向作用。
4. **看到的数据没法直接判断该不该清**，见下。

### 4.3 为什么不能简单按「孤儿」清理（重要）

实测 182 行里 63 行 `claimed_at is null and deleted_at is null`，看起来很像是垃圾。逐个查引用方：

| source | 行数 | 孤儿 | 其中**正被线上引用** |
|---|---|---|---|
| `forum` | 155 | 42 | **0** ← 真垃圾（用户传了没发出去） |
| `hero-console` | 13 | 13 | **4**（首页 hero 图） |
| `shop-console` | 2 | 2 | **2**（全部，商城商品图） |
| `avatar-frames` + `-source` | 5 | 5 | **2**（头像框 PNG） |
| `points-card` | 4 | 1 | —— |

**「孤儿」≠ 垃圾**。装修台（HeroConsole / ShopConsole / AvatarConsole）上传的素材图有 8 张正在线上用着，
只是因为它们**从不调用 `markCloudinaryUploadsClaimed`**（全仓只有 3 个调用点：`post-api.js:924`、
`block-wall-api.js:104`、`UserSpaceMain.vue:2301`）—— 装修台没接，所以永远停在孤儿态。
按 `claimed_at is null` 一刀切会误伤线上素材。

### 4.4 真正的两个问题（建议单独排期）

- **台账卫生**：给装修台 3 处上传补 `markCloudinaryUploadsClaimed`。不补，台账永远脏，
  任何「清理孤儿」的运维动作都不可能安全做。
- **清理缺口**：**全库 6 个 cron 里没有任何一个碰这张表**，孤儿在持续累积
  （5 月 1、6 月 23、7 月 0、8 月 15、9 月 24）。真该清的是
  `source='forum' and claimed_at is null and created_at < now() - 7d`，且必须**走 EF 删 Cloudinary 文件 +
  标 `deleted_at`**，不能硬删行。

### 4.5 建议落点

1. `config/tabs.js:66` 摘掉 `cloudinaryUploads` 的页签声明，`tabModules.logs.tabIds`（第 185 行）同步移除；
   `config/tables.js:1218` 与 `query-config.js` 的 5 处配置一并清掉。
2. 若你仍希望保留可见性，正确形态是：真实列 + 虚拟「状态」列
   （`deleted_at` 非空 → 已清理；`claimed_at` 非空 → 已发布；都空 → 未归属）、
   **去掉 `delete` 动作**（`tabs.js:253`），并明确标注「未归属 ≠ 可删」。

## 五、怎么自己复跑（一键查错）

已经固化成 4 条命令，`package.json` 里可直接跑：

```bash
# ① 刷新远端 schema 快照（列清单，约 5 秒）
npm run audit:dm-schema-refresh

# ② 静态比对：前端所有列引用 ↔ 真实 schema（不需网络，秒出）
npm run audit:dm-columns

# ③ 真打验证：用 PostgREST 实际请求，判定「列到底存不存在」（决定性）
npm run audit:dm-columns:live

# ④ 浏览器探针：伪造 admin 登录，逐个模块逐个页签点一遍，采集真实报错与 toast
npm run probe:dm-errors
```

对应脚本：

- `scripts/probes/fetch-db-schema.py` —— 走 Management API 只读拉 schema
- `scripts/probes/audit-datamanagement-columns.mjs` —— 静态 7 类引用全覆盖
- `scripts/probes/verify-datamanagement-columns-live.mjs` —— 三轮真打（扁平列 / 筛选排序搜索列 / 内嵌关联）
- `scripts/probes/probe-datamanagement-errors.mjs` —— UI 层点击采集

输出明细：`output/datamanagement-column-audit.json`、`output/datamanagement-column-live.json`、`output/datamanagement-error-scan.json`。

### 为什么要静态 + 真打两层

静态比对只能说「配置里写了、schema 快照里没有」。真打是决定性判据，因为 PostgREST 的列解析发生在 schema cache 层，**与 RLS / 角色权限完全无关** —— 所以用 anon key 也能准确判定列是否存在。三层加起来才能同时覆盖「列错」「关系错」「用户实际看到的报错」。

## 六、结论边界（哪些不是 bug）

必须把下面两类噪声和真问题分开，否则会误修：

1. **`userFollows` 页签报 401 `permission denied for table user_follows`** —— **不是 bug**。经数据库侧核实：`authenticated` 角色有该表 SELECT 权限、5 条策略齐全（含 `user_follows_admin_select`）。401 只是探针手里只有 anon key。真实管理员登录不受影响。
2. **探针里满屏 `permission denied for function admin_*`** —— **不是 bug**，同上，探针没有真实管理员会话。已用 route 打桩滤掉，避免淹没真信号。

另外两点方法学边界：

- UI 探针的模块切换在部分模块（AI 配置 / 日志监控 / 系统）未能成功点击（侧栏被权限门置灰 + 会话检查覆盖注入态），因此**页面级覆盖不完整**。这不影响结论 —— 全量判定来自真打脚本（45/45 页签，0 未验证）。
- 本机到 `*.supabase.co` 有间歇性 `fetch failed`，脚本已内置 6 次重试 + 退避；重试仍失败的一律标记为「未验证」而非「通过」。

### 9.3 新增/调整的查错工具

```bash
npm run audit:dm-columns      # 静态：select/筛选/排序/搜索/写入白名单 全量比对（离线秒级）
npm run audit:dm-columns:live # 真打：三轮（扁平列 / 筛选排序搜索 / 内嵌关联）
npm run audit:dm-writable     # 真打：写入白名单 193 个字段逐条验证
npm run audit:dm-schema-refresh
npm run audit:dm              # 串起来跑
```

> 写入白名单那轮用 `update <table> set <col> = <col> where false` 判定 —— `where false` 永不匹配，
> **不改任何数据**；语法解析失败发生在执行前，因此能精确区分「列不存在」与「其它错误」。
