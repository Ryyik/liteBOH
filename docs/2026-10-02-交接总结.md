## 3. 响应速度：实测结论

**同机 A/B**（`git show HEAD:` 还原 11 个前端文件 vs 工作树；新会话→热身→测第 2 轮短追问；DOM 测量；各 4 次）：

| | 短追问首字中位数 | 区间 | 每轮 LLM 调用 |
| --- | ---: | --- | ---: |
| 线上版（含追问改写） | **3309 ms** | 2833~3605 | 2 |
| 我的改动 | **1612 ms** | 1521~1779 | 1 |
| | **−1697 ms（−51%）** | 区间不重叠 | −1 |

对照：热身轮（不触发改写）两组一致（~2.1s）；主生成流式耗时两组相当（1.1~1.5s）
⇒ 差异全部来自删掉的那次调用。非流式 `runtime-chat` 单独 curl 实测 **1.81~2.13s**。

### 还能再提速吗？

**剩余 ~1.6s 的结构**：本地阶段只占 5~26ms（埋点实测），其余都在「Edge Function + 上游模型」。
**prompt 大小不是杠杆** —— 实测首字节：

- 极短 prompt：1.39 / 1.63 / 2.17 s
- 加 6000 字 system：1.53 / 1.66 / 1.80 s

两组区间重叠，**加 6000 字几乎没有影响**。所以：

- ❌ 精简系统提示 / 裁剪证据 —— 收益约等于零
- ⚠️ Edge Function 内部还有 `auth.getUser`（30~80ms）+ 若干 DB 往返，量级只有百毫秒
- ✅ **唯一有量级的杠杆是模型本身**：`fast` 现在用 `THUDM/GLM-4-9B-0414`，TTFT 1.4~2.2s。
  换更快的模型或更近的接入点，才是真正能压下来的地方（这是**产品/成本决策**，不是代码能定的）

## 9. 三条踩过的坑（接手别重踩）

1. **测 AI 首字/落定必须用 DOM，不能用 `localStorage`** —— 会话持久化有 500ms 防抖，
   轮 2 起读到的是上一轮内容 ⇒ 我据此得出过「只差 100ms」的**错误结论**（真实是 −1.7s）。
   用 `.message-content` 最后一条的 textContent。
2. **`squeezeSource` 会把换行压成空格** ⇒ 块边界正则**不能写 `\n};`**，要写 `};`。
3. **bash 的 `grep "a\|b"` 在本环境恒返回 0 匹配**，做否定性结论必须用 **Grep 工具（ripgrep）**，
   否则会得出「全站没有这个东西」的假阴性。
