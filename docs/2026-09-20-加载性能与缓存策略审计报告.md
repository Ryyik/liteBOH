## 1. 首屏关键路径现状（基线）

### 1.1 启动壳构成

首屏渲染前必须全部到位的资源，共 **9 个 JS + 2 个 CSS**：

| 资源 | 类型 | gzip | 角色 |
| --- | --- | --- | --- |
| `ui-components-*.js` | JS | **76.3KB** | 导航栏 + 页脚 |
| `supabase-vendor-*.js` | JS | **42.7KB** | 数据层 SDK |
| `vue-vendor-*.js` | JS | 41.7KB | Vue + Router |
| `index-*.css` | CSS | 25.6KB | 入口样式（tokens / 玻璃 / App 全局） |
| `vue-utils-vendor-*.js` | JS | 15.3KB | `@vueuse/*` |
| `app-*.js` | JS | 15.1KB | 应用入口 |
| `ui-icons-*.js` | JS | 12.9KB | lucide 图标 |
| `ui-components-*.css` | CSS | 10.4KB | 导航栏 / 页脚样式 |
| `ui-sanitize-*.js` | JS | 10.3KB | dompurify |
| `auth-store-*.js` | JS | 6.6KB | 认证状态 |
| `state-vendor-*.js` | JS | 2.9KB | pinia |
| **合计** | | **≈260KB** | 全部并发发起、**全部阻塞首次渲染** |

`index.html` 通过 `<link rel="modulepreload">` 提前声明了其中 8 个 JS，2 个 CSS 是 render-blocking 样式表 —— 这也是「首屏不可能无样式」的结构性来源。

### 1.2 实测数字

| 场景 | 网络 | 首屏 FCP | DOMContentLoaded | 骨架消失（首屏路由就绪） |
| --- | --- | --- | --- | --- |
| A 本机冷启 | 不限速 | 84ms | 57ms | **122ms** |
| B 冷启受保护路由 | 1.2Mbps / 150ms RTT | **1532ms** | 2130ms | — |
| D 二次访问（SW 已激活） | 不限速 | — | 59ms | 切路由到 `#/ai-chat` 178ms |

场景 A 的关键路径特征：**11 个壳资源在 7ms 时全部并发发起**，最慢的 `ui-components` 26ms 完成。这说明关键路径不是「串行瀑布」，而是**一次并发波次的总体积**问题 —— 壳越大，限速下这波就越晚结束（场景 B 中最慢的 `ui-components` 耗时 1916ms）。

### 1.3 启动骨架（已具备的护栏）

`index.html` 内联了完整骨架样式与「Vue 未挂载」兜底，并由 `scripts/check-first-paint.mjs` 作为门禁钉住三件事：

1. 骨架色值必须等于 `tokens.css` / `dark-mode.css` 里的同名 token；
2. 骨架 `<style>` 必须早于 `</head>`、早于 `<body>`，且**早于任何 `<link rel=stylesheet>`**；
3. `index.html` 内联的 `VALID_THEMES` 必须与 `theme-manager.js` 同步。

这是本仓库质量最高的一个防线，**任何优化方案都不得触碰它**（见 4.4）。

### 2.2 四个重点问题模块

#### ① AiChat（`/ai-chat`）— 单点最大

`BOHAIMain-*.js` 单文件 **132.9KB raw / 129.8KB gzip**，且是**单一 chunk**，没有任何二级拆分。加上 `markdown-vendor`（marked + highlight.js，29.2KB gzip）与 `BOHAIMain-*.css`（23.0KB gzip），整个 AI 页首屏增量 204.1KB。

- 问题本质：AI 主界面把「对话外壳」「消息渲染」「设置面板」「知识检索 UI」全压在一个模块里。
- 落点：`src/views/BOHAI/BOHAI/BOHAIMain.vue` 及其同级 composables。

#### ② Home（`/`）— 62KB 但可再挤

`homeArchiveData` 11.8KB + `homeHeroes` 10.6KB + `agreementData` 9.7KB + `AltchaWidget` 相关。`agreementData`（用户协议正文数据）出现在首页依赖里值得复核 —— 若首页不直接展示协议，应挪到弹窗打开时再取。

#### ③ Birthday（`/birthday`）— html2canvas 44.3KB 前置

`image-processing-vendor`（html2canvas）**44.3KB gzip** 占该路由增量的 74%。生日页只有「保存海报」需要它，却跟随路由入口一起加载。同类问题存在于所有含导出/截图能力的页面。

#### ④ DataManagement（`/admin/data-management`）— 路由表里「看不见」的 209KB

从 `app-*.js` 的依赖表反解时该路由只显示 1.4KB 增量，**这是假象**：`DataAdmin-*.js`（117.9KB gzip）与 `DataAdmin-*.css`（**91.3KB gzip**，raw 626.9KB）是通过路由 chunk 内部的**二级动态 import** 拉起的，不在 JSON 依赖表里。

- 真实成本 ≈ 209KB gzip，是后台单页最重的一个。
- 但它的受众是管理员，问题不在「用户会被拖慢」，而在 **它被 SW 全量预缓存给了所有匿名访客**（见 3.2 ③）。

### 2.3 非 JS 瓶颈：远端媒体（受限网络下的真正大头）

场景 B 限速实测的「最慢资源 Top 5」**全部是远端图片**，且比任何 JS chunk 慢一个数量级：

| 资源 | 耗时（1.2Mbps） |
| --- | --- |
| `avatar_1774331536882.png` | **10525ms** |
| `avatar.png` | 10267ms |
| `elf-flower-frame.png` | 5148ms |
| `spxs7hnxoztmeljpowz5.webp` | 3583ms |
| `ybibjuox7zsia13aif8d.jpg` | 3392ms |

结论：**首屏交互并不慢（122ms 就绪），慢的是首屏之后的媒体填充**。头像/头像框素材尤其突出 —— 头像框是 1:1 透明 PNG，未按展示尺寸出图，也未做响应式取图。

## 3. 缓存现状评估

### 3.1 四层缓存总览

| 层 | 载体 | 覆盖 | 生命周期 | 现状 |
| --- | --- | --- | --- | --- |
| L1 数据读缓存 | `request-core.js` 内存 `Map` | 全部 Supabase 读请求 | 5s–120s（TTL 分级） | 设计完整，3 处缺陷 |
| L2 静态资源 | Workbox SW（`sw.js`） | 预缓存 117 条 + 3 条运行时规则 | 见 3.2 | **预缓存名单过宽** |
| L3 HTTP 缓存 | GitHub Pages 固定头 | 全部 | `max-age=600` | **`_headers` 全部失效** |
| L4 会话快照 | `sessionStorage` | 仅论坛主 feed | 2 分钟 | 单点特例，无统一抽象 |

### 3.2 L2 Service Worker 预缓存 —— 本次审计的最大发现

实测 `sw.js` 的预缓存清单：

| 类别 | 条数 | raw | gzip |
| --- | --- | --- | --- |
| HTML | 1 | 13KB | 5KB |
| JS（应用壳） | 9 | 699KB | 221KB |
| **CSS** | **102** | **2975KB** | **535KB** |
| 其他（图标 / manifest） | 5 | 37KB | 24KB |
| **合计** | **117** | **3723KB** | **785KB** |

三个具体问题：

**① 预缓存的 CSS 总量超过了首屏本身。** 785KB gzip 的预缓存是 260KB 首屏的 **3.0 倍**。首次访问的总下载量因此从 260KB 膨胀到约 **1045KB**。

> **⚠️ 口径订正（2026-09-20 实测）**：本报告初稿曾写「实测 `load` 之后 SW 又额外拉走 1018.8KB」。该数字**归属错误** —— 页面 `performance` 时间线**不包含** Service Worker 自行发起的预缓存抓取，那 1018.8KB 实际是远端图片等清单外资源。预缓存流量的权威口径只有一个：**读 `dist/sw.js` 的清单，按磁盘文件求和**（上表 + 546KB 一条已按此口径重算）。`scripts/perf-probe.mjs` 的场景 C 已改为按清单归属切分，并显式标注该限制。

**② 其中 98 个 CSS 与当前访客无关。** 一个匿名访客访问首页，会把 `ForumMain`（42.5KB gzip）、`BOHAIMain`（23.0KB）、`ProfileMain`（12.3KB）、`PostDetailMain`（12.1KB）以及**全部管理端控制台样式**一并下载并写入磁盘。

**③ 最贵的单项是管理员专用的 `DataAdmin.css`（89.2KB gzip / 626.9KB raw）**，被下发给了每一位匿名访客。

**决策依据已过时。** `vite.config.js` 里给 `globPatterns` 写的理由是：

> 「CSS 通常远小于图片和页面 JS，完整预缓存可保证应用壳版本一致。」

实测反证：CSS 2975KB raw **大于**全部页面 JS 与图片；单个 CSS 已达 626.9KB。该前提在 Beta 5/6 的功能扩张后已经不成立。

> ⚠️ **减预缓存不是无脑减。** 当前「全量预缓存 CSS」同时承担了第二个职责：**保证任意路由在弱网/离线切换时样式都在本地**。若只删名单而不补机制，就会出现「路由能切过去、但该路由无样式」——正是用户最不能接受的状态。因此对应建议（6.P0-1）把「补机制」列为**前置条件**，并新增门禁断言。

### 3.3 L3 HTTP 缓存 —— 策略文件在线上不生效

`public/_headers` 声明了规范的长期缓存策略（`/static/js/*`、`/static/css/*` → `public, max-age=31536000, immutable`），但文件自身第 2 行就写明：

> 当前部署目标 GitHub Pages 不支持自定义 HTTP 头，此文件为迁移到其他平台时备用。

部署链路已确认：`public/CNAME` = `www.blockofhome.cn`，`.github/workflows/deploy.yml` = Deploy to GitHub Pages。GitHub Pages **固定下发** `Cache-Control: max-age=600`，无法覆盖。

后果链条（这解释了仓库里一整套看起来「过度设计」的兜底为什么必须存在）：

- 带 hash 的资源本可永久缓存，实际 600 秒后就要重新验证；
- `index.html` 同样只有 600 秒，且**无法主动失效** → 发布后最长 10 分钟内新访客仍可能拿到引用旧 hash 的 HTML；
- 于是需要 `version.json` + `boh-build-id` 比对 + `forceUpdate` 清缓存 + `index.html` 的 `<link>` 404 恢复 + `router.onError` 的 `unable to preload css` 兜底这一整套。

**评估：这套兜底写得很扎实，但它是在为一个可以被平台配置解决的问题付出长期复杂度。** 建议将其定性为「部署平台限制的补偿」，并把迁移到支持 `_headers` 的平台（如 Cloudflare Pages，`_headers` 已就绪、迁移即生效）作为独立议题记录，而不是继续在客户端加兜底。

### 3.4 L1 `request-core` 数据读缓存 —— 设计完整，三处缺陷

**已实现（质量较高）：** TTL 五级分类（`cache-strategy.js`）、tag 级联失效（`invalidateByTags`，支持 `tag` 与前缀 `tag:` 匹配）、in-flight 去重、并发队列（上限 6）、指数退避 + 抖动重试、分级超时、AbortController 统一出口（`code: 'ABORTED'`）。

| 缺陷 | 位置 | 影响 | 修法 |
| --- | --- | --- | --- |
| ① **纯内存，刷新即失** | `const requestCache = new Map()` | 每次硬刷新（PWA 独立启动、切回 App）后所有读缓存归零，重新回源 | 可接受；若要提升，考虑对「静态数据」级（120s）落 IndexedDB |
| ② **注释称 LRU，实为 FIFO** | `getCache()` 命中时不回插；淘汰用 `keys().next().value` | 高频命中的热点条目会因「插入早」被先淘汰，命中率低于设计预期 | 命中时 `delete` + `set` 重新入队，或改用显式访问计数 |
| ③ **`clearAuthReadCache` 全仓无人调用** | `utils/auth.js` 导出 `clearRequestCache as clearAuthReadCache`；仅 `utils/auth.d.ts` 有类型声明 | `logout()` 走 `signOut()` + `resetState()`，**不清理读缓存**。切号后旧账号的列表/计数在 TTL（5–30s）内仍可能被读到 | 在 `logout()` 与 `resetState()` 中显式调用 |

关于 ③ 的严重性需给准确判断：`buildRequestKey(scope, params)` 包含 params，而绝大多数按用户维度的读取都把 `userId` 放进 params，**因此不构成跨账号数据泄露**；真实症状是「切号后 5–30 秒内看到上一个账号的残留计数/列表」以及一个死掉的导出 API。

| 补充观察 | 说明 |
| --- | --- |
| 无 stale-while-revalidate | TTL 过期即阻塞回源（`getCache` 返回 `null` → 走网络），用户会再次看到 loading。若要「秒开 + 后台校正」，可先返回过期值并标记 `stale: true` |
| TTL 校验只告警不拦截 | `executeRead` 会对不在 `CACHE_TTL_LEVELS` 里的 TTL 打 warn 但继续执行 —— 这是刻意的灵活性，建议保持 |

### 3.5 L4 会话快照

## 4. 样式加载安全保障（专项）

> 这是本次审计的硬约束：**任何优化都不得让用户在资源未就绪时看到失去 CSS 控制的页面。**

### 4.1 现有防线逐条核对（8 道）

| # | 防线 | 机制 | 状态 |
| --- | --- | --- | --- |
| 1 | 内联骨架早于一切样式表 | `index.html` 内联 `<style>`；由 `check-first-paint.mjs` 断言「第一个 `<link rel=stylesheet>` 必须晚于骨架」 | ✅ 有门禁 |
| 2 | 骨架色值 ↔ token 同步 | 门禁逐条比对 7 组色值 ↔ `tokens.css` / `dark-mode.css` | ✅ 有门禁 |
| 3 | 主题属性早于模块执行 | `index.html` 内联脚本同步设 `data-theme` + `.dark` | ✅ |
| 4 | 暗色底色提前垫层 | 内联 `[data-theme="dark"]{background-color:#0a0a0f}` + `[data-theme="dark"] body{...}` | ✅ |
| 5 | **入口 CSS 走 render-blocking `<link>`** | `dist/index.html` 含 `index-*.css`（25.6KB）+ `ui-components-*.css`（10.4KB）两个样式表 | ✅ **核心保障** |

### 4.2 实测证据（三组场景）

#### 场景一：暗色用户冷启（1.2Mbps，无 SW）

| 观测点 | 实测值 |
| --- | --- |
| 最早可采样时刻 | t=1542ms，`data-theme` **已是 `dark`** |
| 该时刻 body 底色 | `rgb(10, 10, 15)` ✅ 正确暗色 |
| 该时刻骨架底色 | `rgb(10, 10, 15)` ✅ 正确暗色 |
| 导航栏底色出现过的取值 | `rgba(0,0,0,0)` → `rgba(10,10,15,0.85)` |
| 主题 CSS 到位区间 | 2169ms → 2693ms（6 个文件） |

**结论：没有出现亮色闪烁。** 关键点是导航栏底色只经历过「透明」和「正确暗色」两个状态，**从未出现亮色中间态** —— 因为导航栏容器的基础样式本身就是透明的，暗色玻璃由 `navbar-dark.css` 提供。

#### 场景二：受保护路由的登录弹窗（1.2Mbps，无 SW）

| 观测点 | 实测值 |
| --- | --- |
| `.boh-login-modal-overlay` 首次出现 | t=3673ms |
| 出现瞬间的计算样式 | `position: fixed`、1280×800、**已带样式** |
| 该时刻样式表数量 | 15 |
| `login-modal-*.css` 请求窗口 | 2140ms → 2509ms（**早于遮罩出现 1.16s**） |
| 「有 DOM 无样式」采样次数 | **0 / 61** |

**结论：未复现无样式弹窗。**

#### 场景三：路由切换

路由级 CSS 由 Vite preload helper 以 `<link>` 注入，且 helper 会 `await` 全部 CSS 就绪后才执行模块 —— 组件渲染时其自身样式必已生效。这是**结构性保证**，不依赖时序。

### 4.3 残余风险（3 项）

#### R1（P1）暗色「页级」CSS 的防线靠时序巧合，不是结构保证

**事实：** `data-theme=dark` 在 **1542ms** 就位（内联脚本，必然早），而 8 个暗色 CSS 直到 **2693ms** 才全部到位。错配窗口 ≈ **1151ms**。

**本轮为什么没出事：** 导航栏基础样式是透明的，且其 chunk（`ui-components`，限速下 1916ms 完成）恰好晚于 `navbar-dark.css` 开始到达（2169ms），两个曲线刚好错开。这是**巧合，不是设计**。

**什么情况下会退化为可见问题：** 暗色 CSS 组体积增长、chunk 拆分调整、或更差的网络 —— 三者任一变化都可能让「导航栏首帧」早于「navbar-dark.css」到达，用户将看到一段「无玻璃面」的导航栏（若基础样式将来被改为亮色底板，则会变成真正的亮色闪烁）。

**修法（具体）：** 把暗色组按「壳级 / 页级」二分。

| 子集 | 文件 | raw | 处理 |
| --- | --- | --- | --- |
| 壳级（首帧就要） | `dark-mode.css` 6785B + `navbar-dark.css` 4440B | **≈11KB**（gzip ≈3KB） | 在 `index.html` 内联主题脚本判定为 `dark` 时，**当场**插入 `<link rel=stylesheet>` |
| 页级（跟随页面） | `bohai-dark` 29948B、`forum-dark` 20888B、`post-detail-dark` 16885B、`user-space-dark` 14578B、`user-center-dark` 9961B、`messages-dark` 11096B | ≈103KB | 保持 `theme-css-loader.js` 懒加载不变 |

代价 3KB gzip，换来「壳级暗色与首帧同步」的结构性保证。落点：`index.html` 内联脚本 + `theme-css-loader.js` 的模块表。

#### R2（P2）`login-modal.css` 挂在 idle 上，与「弹窗何时出现」无耦合

`main.js` 的 `deferredGlobalStyleLoaders` 把 4 个全局样式挂在 `requestIdleCallback(..., {timeout: 2500})` 上：

| 文件 | 体积 | 风险 |
| --- | --- | --- |
| `login-modal.css` | 9.3KB / 510 行 | **弹窗壳层的唯一来源**（`overlay`/`container`/`close`/`form`/`btn` 全部在此；`Login/index.vue` 的 `<style scoped>` 不含这些） |
| `google-components.css` | 29.8KB | 仅 `DataManagement` 使用，却是**全局** idle 加载 —— 建议直接改为该路由内 import |
| `cursor.css` | 2.0KB | 低风险 |
| `page__animate.css` | 3.0KB | 低风险 |

实测余量 1.16s，但原因是「`Login` 异步组件 chunk 恰好比 idle 回调慢」——同样是巧合。

**修法：** `login-modal.css` 移入入口 CSS（`main.js` 顶部静态 import）；`google-components.css` 移出全局名单、改为 `DataManagement` 内部 import；其余 2 个保留 idle。

#### R3（P3）预缓存体积硬上限

`maximumFileSizeToCacheInBytes = 4MB`，而 `nsfw-weights` 为 3.6MB raw。当前它走 `runtimeCaching`（未列入 `globPatterns`）所以没事，但**模型权重再增长就会静默跳过预缓存**。建议在 `check-shell-precache.mjs` 中加一条「runtimeCaching 覆盖的 path 不得同时出现在 globPatterns」的反向断言。

### 4.4 明确「不要做」的事

以下做法会让 4.1 的防线失效，**应作为评审红线**：

| ❌ 不要做 | 原因 |
| --- | --- |
| 把入口 CSS 改成动态 `import()` 或 `preload + onload` 技巧 | 会丢掉 render-blocking 保证 → 真 FOUC（防线 5） |
| 把骨架 `<style>` 抽成外部文件 | 骨架必须零额外请求（防线 1，门禁会拦） |
| 给骨架加 `media="print"` 等取巧属性 | 同上 |
| 给入口 CSS 加 `content-visibility: auto` | 已知会与首屏测量冲突（见项目既有约定） |
| 直接删 `globPatterns` 里的 `static/css/*.css` 而不补机制 | 会制造「路由可切换但无样式」——用户明确禁止的状态 |
| 把 `check-first-paint.mjs` / `check-shell-precache.mjs` 从 `build:ci` 摘掉 | 这两条是样式安全的唯一自动化保障 |

### P0（✅ P0-1 已实施并验收；❌ P0-2 已尝试后撤回，见第 7 节）

#### P0-1 收窄 SW 预缓存：壳样式进预缓存、路由样式交给运行时缓存 —— **已实施**

- **落点（已改）：** `vite.config.js`（新增 `bohShellCssScopePlugin` + `workbox.manifestTransforms` + `/static/css/` 运行时规则、`SHELL_CHUNKS` 单一数据源）、`scripts/check-shell-precache.mjs`（新增 3 条断言）、`scripts/check-route-css-runtime-cache.mjs`（新增，行为验收）
- **前置条件（已先做）：** 原 `check-shell-precache.mjs` 只校验 **JS** 壳依赖，对 CSS 零覆盖。已补：
  - **断言 A**：`index.html` 里 `<link rel=stylesheet>` 引用的每个 CSS 必须进预缓存 —— 这是「离线首屏仍有样式」的唯一保证，也是任何收窄改动的安全底线；
  - **断言 C**：每个动态 import 的路由 chunk 携带的 CSS，必须被预缓存命中**或**被某条 `runtimeCaching` 规则覆盖；
  - 以及「解析失配即报错」的防假绿守卫。
- **做法（最终形态）：**
  1. 新增构建期插件 `bohShellCssScopePlugin`，在 `generateBundle` 里用 `viteMetadata.importedCss` + `index.html` 实际引用**取并集**，算出「壳样式允许清单」（本产物 = 2 个）；
  2. `workbox.manifestTransforms` 按该清单过滤预缓存清单；**清单为空时 fail-safe 保留全部 CSS**（宁可多缓存，也不能让壳样式掉出预缓存）；
  3. 新增 `runtimeCaching`：`/\/static\/css\/[^/]+\.css$/` → `CacheFirst`，`cacheName: 'route-css'`，140 条 / 30 天 —— 带 hash 的文件名内容不可变，用户访问过的路由 CSS 从此永久本地化；
  4. `globPatterns` 仍保留 `'static/css/*.css'` 仅作**发现**用途（产物里路由 CSS 与入口 CSS 同名 `index-<hash>.css`，glob 无法区分，收窄只能放在 transform 里）。
- **实测收益（非估算）：** 见第 7.1 节 —— 预缓存 117 条 / 785KB gzip → **17 条 / 286KB gzip（-64%）**，其中 CSS 535KB → **35KB（-93%）**；首次访问总量 1045KB → **546KB（-48%）**。首屏 260KB 不变。
- **样式安全影响：** 壳样式**仍在预缓存**（离线首屏保证不变）；已访问过的路由其 CSS 落入 `route-css` 运行时缓存 → 弱网/离线切换安全（已实测：二次访问 0 字节传输）。**唯一取舍**：离线且访问**从未打开过**的路由会缺该页样式 —— 但路由 **JS** chunk 本来就不在预缓存里，该场景在本次改动前同样不成立，不是新增故障模式。
- **验证（已执行）：** 静态门禁 + 3 组反证 + 运行时行为验收，见第 7.1 节。

#### P0-2 AiChat 路由瘦身 —— **已尝试，因真实回归而撤回**

### 7.2 P0-2：已尝试 → 发现真实回归 → 撤回

**做过什么**：把 `BohaiSettingsPanel`（1181 行）与 `AiQuotaSidePanel` 从静态 import 改为 `defineAsyncComponent`，并用「闩锁式 `v-if`」推迟挂载（首次打开后保持挂载，以免打断内部 `<Transition>` 关闭动画）。

**拆分确实生效**：`BOHAIMain` 383.64 → 354.41KB raw（134.88 → **127.68KB gzip**），两个面板另起 chunk 共 **9.7KB gzip JS + 5.6KB gzip CSS**。占 AiChat 路由增量 204KB 的约 **7.4%**。

**回归（由新增探针抓到）**：面板能打开、样式完全正常（`backdrop` 白底、drawer 1160×828、`position: relative`），但

```
[ai-panels] 焦点：{"insideDrawer":false,"activeTag":"button","activeClass":"full-ai-toolbar-btn"}
[ai-panels] ✗ 设置面板无法关闭（Esc 后 .ai-settings-drawer 仍在）
```

而基线（惰性化之前）同一条断言是 `insideDrawer: true`、`activeClass: "ai-settings-close-btn"`。

**根因**：两个面板的焦点/数据生命周期都挂在 `watch(() => props.modelValue)`（额度面板是 `props.visible`）上，且**都没有 `immediate`**。惰性化让组件「**挂载时就已经是打开状态**」，于是这个 watch 永不触发：
- 焦点不进入面板 → `@keydown.escape` 收不到事件 → **Esc 关不掉**、焦点陷阱失效；
- `BohaiSettingsPanel` 的 `getAiQuotaStatus()` 不执行 → 面板内额度摘要空白；
- `AiQuotaSidePanel` 的 `fetchQuota()` 不执行 → 面板停在空态。

**尝试过的修法（无效）**：给两个 watch 都补 `{ immediate: true }`。补齐后焦点仍在 `full-ai-toolbar-btn`、Esc 仍失效，说明「惰性挂载 + 挂载即打开」与该面板焦点生命周期的交互不止这一处，不是一行能补干净的。

**决定：撤回。** 依据：
1. 收益仅 7.4%（~15KB gzip），且只作用于单个路由；
2. 回归落在 **a11y/可达性**上（键盘用户无法关闭设置面板），严重度高于收益；
3. 完整回归该链路需要登录态 + 真实模型调用，本轮无法端到端验证，不适合边猜边改。

三个文件已用 `git checkout` 精确恢复（它们是改动前唯一的差异来源，撤回后 `git status` 为空）。

**再次尝试的正确路径（留给下一个人）**

1. **先补 `{ immediate: true }`** 到两个面板的 watch —— 这本身是它们该有的健壮性（面板应能自洽处理「挂载即打开」），但**单独补它不足以**支撑闩锁式惰性挂载；
2. **不要用「`v-if` 闩锁 + 挂载即打开」**。改为**先预热再打开**：
   ```js
   const openSettings = async () => {
     if (!settingsPanelMounted.value) {
       await import('./components/BohaiSettingsPanel.vue');  // 与 defineAsyncComponent 共用同一 promise
       settingsPanelMounted.value = true;
       await nextTick();          // 组件以「关闭」状态挂载
     }
     settingsOpen.value = true;   // 随后发生 false→true 跳变，焦点/额度逻辑照常触发
   };
   ```
   这样面板始终「挂载时关闭、随后打开」，与既有生命周期自洽。注意入口不止一处（`openSettings`、`closeQuotaPanel`、`openQuotaPanel`），需一并覆盖。
3. **验收必须跑** `node scripts/probes/probe-ai-panels.mjs 'http://[::1]:4180'`——它已包含焦点断言，正是本次抓住回归的那一条；
4. **不要顺手异步化 `markdown-vendor`**：`highlight.js/styles/github.css` 是代码块样式的唯一来源，异步化会出现「代码块先裸文本、后上色」，与本次审计的样式安全硬约束冲突。若要做，只异步化语言包，主题 CSS 保持静态。

## 8. 页面/分区切换流畅度（2026-09-20 追加，目标「APP 级手感」）

### 8.1 结论

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| UserSpace「切回来」平均 / 最慢 | 44ms / 63–75ms | **19ms / 29ms** |
| 每次切换回数据请求数 | **14–28 个** | **0 个** |
| `community` 分区逐层节点身份 | shell / tab-page / panel **全部重建** | **三层全部复用** |
| 20 条公开路由切换「导航→主内容出现」 | — | 中位 **29ms** / 最慢 52ms |

一句话：**问题不在动画，在于每次同页切换都把整棵页面树销毁重建。**

### 8.2 根因：错误边界的 key 挂了 `route.fullPath`

```js
// src/App.vue（修复前）
watch(() => route.fullPath, () => { boundaryKey.value += 1; });   // fullPath 含 query
```
```html
<GlobalErrorBoundary v-else :key="boundaryKey">   <!-- 包住整个 RouterView -->
```

UserSpace 切分区是「同 path 改 query」（`?tab=…&view=…`），`fullPath` 一变 → `boundaryKey` 自增 →
**错误边界连同整棵页面树被销毁重建**：

- `UserSpaceMain`（1.2 万行 + 5 个面板）每次切换全部重挂载，所有 `onMounted` 取数重跑；
- 社区分区宿主 `ForumMain` 每次回来重跑 `initializeForumData()` + `loadForumWeeklyReport()` + `loadActiveAds()`，即每张表各一次，共 10–14 个请求；
- **路由级 `<KeepAlive>` 同时失效**（外层 key 变了，缓存被顶掉）——这也解释了为什么 `/user-space` 明明标了 `keepAlive` 却没有任何收益。

**修法**：`route.fullPath` → `route.path`。换页面才重置边界，同页改参数不动树；原意「一次崩溃不污染后续页面」完整保留（错误卡片本身仍有 retry / 回首页 / 硬刷新三个出口）。

### 8.3 顺带补上的一处漏配

`messages` 分区的面板宿主没有 `<KeepAlive>`（社区论坛宿主有），离开即销毁。已按其同款写法补上，
补后 `messages` 也是 shell / tab-page / panel 三层全复用。

**仍有重建的两处（有意保留）**：`assets` 与 `settings` 的 tab-page 在模板里本就是 `v-if`
（`AssetsHubPanel` 2676 行，long-lived 常驻的内存代价更大）。它们的切回耗时实测 14–24ms、
且**零数据请求**，故不改。

### 8.4 过渡动画：尝试过，**未落地**（附证据）

用户明确希望「优雅的过渡动画」。我按「只做 enter、不做 leave」实现路由级 `<Transition>`，
理由是 `mode="out-in"` 会**先等旧页面淡出**，等于给每次切换硬加一段等待，与「点下去就出来」冲突。

**结果：过渡从未触发。** 两种独立探测一致确认（MutationObserver 监听 class 变化 + rAF 高频采样），
且**控制台没有任何告警**。逐项排除：

| 假设 | 验证 | 结论 |
| --- | --- | --- |
| 编译没进去 | 读产物 JS：确为 `Transition{name:"route-enter",mode:"out-in"}` 包住路由组件，CSS 也在产物里 | 排除 |
| `out-in` 死锁导致新页面不出现 | 实测新页面正常渲染（`.newsroom-page` 挂载、内容确实换新） | 排除 |
| 结构问题（KeepAlive / 双 Transition / key） | 换成最简形态（无 KeepAlive、无 key、单 Transition）**同样不触发** | 排除 |
| 外层 `<Suspense>` 吞掉过渡 | 可疑：App.vue 自己的注释写着「fallback 永远不会进入 pending（实测 0 次）」，即它是**死重量**；移除它的实验因模板手术出错未完成 | **待查** |

**为什么「没有告警」不能当作证据**：生产构建会剥掉 Vue 的开发告警（如
"Transition expects exactly one child element or component"）。所以必须靠 DOM 侧的独立观测判定，
不能靠控制台。

**结论与建议**：路由级全局过渡需要专门一轮（第一步就是查 `<Suspense>` 与异步路由的交互），
**不应在未验证的情况下塞进最关键的壳层文件**。本轮已把 UserSpace 分区过渡保留并复用
（`shell-community.css` 的 `userspace-tab-*`，280/250ms、方向感知、`contain: layout paint`、
reduced-motion 齐备）——即用户最常感知的「userspace 来回切」场景已有优雅过渡。

### 8.5 验收与探针

| 探针 | 用途 |
| --- | --- |
| `scripts/probes/probe-userspace-switch.mjs` | 逐层节点身份（定位重建层级）+ 每次切换的请求分布 + 往返耗时 + 长任务 |
| `scripts/probes/probe-route-switch.mjs` | 逐 20 条公开路由巡检「主内容可见」+ 无报错 + 真实计时 |

**测量上的两个坑（已写进脚本注释）**：

1. 逐层身份必须**逐层**比对（壳 → 分区容器 → 面板）。只比面板那一层，会把「整个页面被重建」误判成面板问题，修错地方。
2. 判「主内容是否渲染」**不能用 `#app > *` 的最后一个元素**：`#app` 下常驻导航栏、移动端手势触发层、隐藏 `<input>` 包装，末位往往是 `display:none` 的 `SPAN` → 满屏假阳性。要按「排除壳层类 + 可见面积最大」挑。

**没有靠改断言变绿**：改为校验 `route.path`，并**新增反向断言禁止改回 `fullPath`**（附原因注释）——
