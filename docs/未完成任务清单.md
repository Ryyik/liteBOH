## ⭐ 2026-10-16（续）：AI 回答图文并茂 —— Phase 1（论坛帖配图）已实现

用户诉求：BOH AI 的回答能带上联网搜索的图片或论坛图片（先探讨可行性 → 选定先做 Phase 1）。

### 可行性结论（决定「联网配图」不能直接做）

| 图源 | 现状 | 结论 |
| --- | --- | --- |
| **论坛帖配图** | `posts.cover_image_url` + `forum_post_images`（后台有审核 tab）；`utils/api/forum-format.js` 的 `normalizePostListRecord` 已做 `db-image-url` 解析 + Cloudinary 改写 ⇒ 拿到手就是 CDN 地址 | ✅ **本次做掉** |
| 联网搜索配图 | Tavily 未开 `include_images`；结果经 `api-key-vault` 的 `runtime-search` 代理 | ⏳ 必须先做「落图到自己 CDN」 |
| 官方事实配图 | `boh_ai_core_memories` 无图片字段 | ⏳ 表加 `image_url` + 后台表单加一项 |

**两堵墙**（`联网配图` 的硬约束）：
1. **CSP `img-src` 白名单**：`scripts/cloudflare-security-headers.mjs` 只允许
   `'self' data: blob: res.cloudinary.com cdn.blockofhome.cn`。
   ⚠️ `CSP_ENFORCE` 需 `--csp-enforce` 才强制，**当前是 Report-Only** ⇒ 属「计划中的墙」。
2. **大陆可达性（真墙）**：`res.cloudinary.com` 实测 000 不可达、`cdn.blockofhome.cn` 200
   （`utils/db-image-url.js` 头部有实测记录）⇒ 外部图必须落盘到自建 CDN。
3. 附带：两个图源都是**不可信外部内容**，应加 `referrerpolicy=no-referrer` 并复用既有 NSFW 管线。

### Phase 1 已实现（代码在工作树，未提交）

1. **新增 `src/utils/image-origins.js`（图片域名白名单单一真源）**
   - `CSP_IMAGE_ORIGINS`（页面级外边界，含 Cloudinary 原址）
   - `AI_ANSWER_IMAGE_ORIGINS`（**子集**，只放行自建 CDN —— Cloudinary 原址大陆不可达，
     宁可不出图也不给裂图）
   - `isAllowedImageSrc()`：拒协议相对地址 `//host`、拒非 https、拒非图片 `data:`、
     拒相对路径；`new URL()` 天然挡住 userinfo 与后缀伪装。
2. **`src/utils/dompurify.js` 加 `img[src]` 白名单钩子**
   - 注册一个 `afterSanitizeAttributes` 钩子，**仅当调用方传 `config.allowedImageOrigins`** 时生效
     ⇒ 其他消费方行为逐字不变。
   - ⚠️ 校验必须在 DOMPurify 这一层：`marked` 会原样透传模型输出的**裸内联 HTML**
     （`<img>` 不走 `renderer.image`），渲染器侧过滤能被绕过。
   - 不能用 `ALLOWED_URI_REGEXP`：那是全局的，会把 `<a href>` 也限制成只允许图片域名，
     而 AI 回答必须能引用任意来源链接。
3. **`views/BOHAI/BOHAI/components/boh-markdown.js` 放行 img**
   - `ALLOWED_TAGS` 加 `img`；`ALLOWED_ATTR` 加 `src/alt/loading/referrerpolicy/width/height`；
     把 `AI_ANSWER_IMAGE_ORIGINS` 作为 `allowedImageOrigins` 传下去。
4. **`useKnowledgeRetrieval.getForumContext` 带配图进上下文**
   - 每个 `[Fn]` 加一行「配图：<CDN 地址>」（无图不写该行）；
   - 构建期先用同一份白名单筛一遍 ⇒ 模型根本看不到不合规地址（渲染侧是第二道防线）；
   - 只在**确实有可引用配图**时追加「配图约束」：仅当与回答直接相关才用 markdown 引用、
     最多 1~2 张、不要为好看而配图、不要编造图片地址。
5. **`scripts/cloudflare-security-headers.mjs` 的 `img-src` 改由 `CSP_IMAGE_ORIGINS` 插值**
   - 消除「渲染器放行 / CSP 拦截」的静默漂移；已验证 `--dry-run` 输出与改动前**逐字一致**。
6. **新增 `tests/unit/ai-answer-image-policy.test.js`（17 断言）**
   - src 判定逐条覆盖绕过手法（协议相对 / 非 https / userinfo / 后缀伪装 / `data:text/html` / 相对路径）；
   - 不变量：`AI_ANSWER_IMAGE_ORIGINS ⊆ CSP_IMAGE_ORIGINS` + CSP 脚本不再手写域名；
   - 接线守卫（源码文本，先 `stripComments` 防注释自证）。
   - ⚠️ 仓库 vitest 是 `environment: 'node'` 且**未装 jsdom/happy-dom** ⇒ DOMPurify 的 DOM 行为
     无法在本仓断言，退化为源码守卫 + 人工冒烟。若要真 DOM 断言，得先引入 jsdom（属独立决定）。

### 9.2 两个报障的候选根因（**未实测，按可能性排序**）

**① 缩略图不立即出现**

- **B** `<img loading="lazy" decoding="async">`（`PostComposer.vue:836`）—— 网格恒在视口内，lazy 只有风险没有收益。
- **C 已出的图会再闪一次**：上传完成后 `updatePendingPostImage(uploadId, {...result.data, …})` 把 `url` 从 `blob:` 覆盖成 Cloudinary 远端地址（`forum-format.js:261 normalizeForumImage` → `getCloudinaryTransformedUrl`）。移动网络下这张图要重新下载 ⇒ 白块/回退。

**② 慢 + 输入无响应 + 无提示**

  > 而**超时**（`API_KEY_RUNTIME_TIMEOUT`）归类为 `timeout`，`isRetryableFailureKind` 返回 false ⇒ **不重试**。
  > 所以真实最坏是「单张 8s，之后进冷却」，不是 96s。**别拿 96s 当论据。**

**落地结构（推荐给 src/ 的形态）：覆盖层，而非包裹层**

```
宿主(position:relative)                    // composer 加 anchor；两个 .boh-mode-wrap 现成
  .glass-under (absolute; inset:0; pointer-events:none; border-radius; overflow:hidden)   ← 折射玻璃实例
```

- `glassSize: { width:'100%', height:'100%' }`（组件的 `autoPx` 对字符串原样透传）⇒ **textarea 自动增高零 JS 跟随**（实测 84→197px 全程对齐 0/0/0/0）；菜单内容变化同理。

**⚠️ 新硬约束：背板采样根（接线第一验证项）**

- 规则：玻璃祖先链上出现**堆叠上下文**（z-index / isolation / opacity<1 / filter / transform / mix-blend）⇒ 背板采样被限制在该上下文内；子树不含背景内容时**模糊完全消失**，即使子树含背景（本例 `.boh-main` 内含 `.stream`）**也会明显降级**。
- 实测矩阵（整页新建 + 同一 clip 的开/关梯度能量）：

| 玻璃祖先链状态 | 输入框 blur Δ | 菜单 blur Δ |
| --- | --- | --- |
| 无堆叠上下文（干净） | **-32.47（全效）** | **-37.60（全效）** |

**⚠️ 关于 §21.7 那条约束：结论不变（附一条作废的「修正」）**

曾在本节写过「`z-index` / `position: fixed` / `transform` **不会**切断 backdrop 采样，§21.7 过度泛化」——
**那条已作废，别再引用**。错因：当时测的是**岛自身**的 `backdrop-filter`（`on=0.05 / off=34.54` 有效），
就外推成「子代也有效」。**元素自己的** filter 不受自己所在堆叠上下文影响，而**子代**的会被祖先堆叠上下文裁掉 ——
两者不是一回事。实测子代玻璃在顶栏里 **`on=off`（完全不糊）**，三种配置复现。
⇒ §21.7 的规则成立：**子代**玻璃的祖先链上不得有堆叠上下文（`z-index` / `position: fixed|sticky` /
`transform` / `isolation` / `filter` / `opacity<1` / `mask` / `mix-blend` / `will-change`）。
判据：`node scripts/probes/probe-navbar-glass.mjs`（会打印祖先链与阻塞点）。

**自证**：`npm run verify` 全绿（4 棘轮持平）；`bohai-glass-surfaces` + `bohai-glass-look-spec` **20/20**；
`probe-bohai-glass` **23/23**（令牌搬迁后运行时无回归）；`probe-navbar-glass` **2/2**（顶栏现有玻璃基线）。

**下一步（顶栏接线）：被一条结构约束挡住，需要拍板** ⛔

用户口径是「**把顶部导航栏整体自身作为液态玻璃**」（折射级）。已接线并实测：玻璃能挂上、与岛逐像素对齐、
边框/投影保留、圆角跟随状态 —— 但**完全不糊**（`on=off`）。阻塞点已定位：

> `#unified-nav-container { position: fixed; z-index: 9999 }` 是玻璃祖先链上的**堆叠上下文**，
> 子代玻璃的背板采样被限制在它的子树内（子树里没有页面内容）⇒ 采到空背板。
> 排除项：`transform` 与 `will-change` 都做过**整页重建 A/B**，数值一字不变（不是它们）。
> 已把接线**回滚**（半接线状态不许落地，探针里有对应断言）。

三条路，代价各不相同：
1. **玻璃独立成层**（不与岛同 DOM）：`#app` 下放一层 `fixed` 玻璃，几何镜像岛的
   `max-width / height / border-radius / transform`。✅ 祖先链干净、能糊；❌ **几何规则要复刻一份**
   （岛有常态 / has-status-card / has-task-card / has-custom-card / nav-mini-caps / nav-immersive
   六种形态 + 断点），是典型的「改一处要动两处」。
2. **动容器的堆叠上下文**：让 `#unified-nav-container` 不再是堆叠上下文。❌ 它是 `fixed`（本身就建堆叠上下文），
   且 `z-index: 9999` 承担「压住全站一切」的职责，动它风险最大。
3. **顶栏保持模糊级**（现状），把预算投到别处：✅ 零风险、今天就有玻璃；❌ 不是折射级。
   （顺带可做的小事：岛的颜色还是写死 `rgba(255,255,255,0.66)`，可收敛到 `--liquid-*`。）

**⛔ 2026-10-14 追加实测：路径 1 也**没成**（两次尝试都回滚了）**

用户口径是「顶栏要**折射**，不要模糊」。于是按路径 1 实现了「玻璃独立成层」并逐项自证通过：

| 项 | 结果 |
| --- | --- |
| 玻璃 Teleport 到 `body`、**不在岛内** | ✅ |
| 几何从真岛 `getBoundingClientRect()` **量**出来（不复刻规则） | ✅ 与岛对齐 `0/0/0/0` |
| 圆角跟随（`--glass-refract-radius`） | ✅ 100px / 100px |
| 玻璃祖先链 | ✅ 只剩 `body`（无 filter/opacity/isolation/mask/mix-blend） |
| 岛只让出实底、边框+投影保留 | ✅ |
| 模糊度链（CSS + JS 两侧读同一个数） | ✅ `blur(16.8px)` → 落盘 0 后 `blur(4px)`（地板） |
| **玻璃真的糊/折射** | ❌ **`on=off`（91.66 / 101.79）—— 完全不糊** |

同轮排除项（都做了**整页重建 A/B**，数值一字不变）：大圆角（`corner-radius` 100→24）、
`transform`、`will-change`。

**✅ 根因已证实（2026-10-14 晚）：玻璃宿主只要是堆叠上下文，背板采样就被裁空**

官方 `demo-wxperia-liquid.html` 内联源码的三层宿主：

```
外层 div   class="relative …"                       ← position: relative（**无 z-index**）
  └ .glass  position:relative; overflow:hidden; box-shadow
      └ span.glass__warp  {…style, position:absolute, inset:0,
                            backdropFilter:`blur((overLight?12:4)+blurAmount*32 px) saturate(…)`,
                            filter:`url(#<uuid>)`}    ← **真正带 backdrop-filter 的那层**
      └ div（内容）position:relative; z-index:1
```

**验证方式（独立静态对照页，层级完全自控）**：`src/views/Dev/GlassBackdropRepro.vue`
（DEV-only 路由 `/#/__dev/glass-repro`）+ `scripts/probes/probe-glass-repro-page.mjs`。
三组宿主**唯一差别 = 是不是堆叠上下文**，判据是「玻璃开着 / 关掉」的梯度能量：

| 组 | 宿主 | 结果 |
| --- | --- | --- |
| **H1** | `position: relative`（无 z-index） | ✅ **能糊** `on=0.15 / off=102.09`（对照组，证明实验台有效） |
| H2 | `position: relative; z-index: 1` | ❌ 采不到 `on=91.91 / off=102.07` |
| H3 | `position: fixed` | ❌ 采不到 `on=51.46 / off=57.20` |

⇒ **规则（判据落在采样层 `.glass__warp` 的祖先链上，不是「玻璃根」也不是「岛」上）**：
祖先链上任何一级是堆叠上下文（`z-index` / `position: fixed|sticky` / `transform` / `isolation` /
`filter` / `opacity<1` / `mask` / `mix-blend` / 相应 `will-change`），折射玻璃**完全失效**。

⚠️ 这也解释了两次顶栏尝试的失败：① 玻璃挂岛内 → `#unified-nav-container` 是堆叠上下文；
② 玻璃根设 `position: fixed` → 玻璃根自己成了堆叠上下文。**两次都不是调参问题。**

**⇒ 结论：`position: fixed` 的宿主 = 折射玻璃不可用。** 而顶栏要「固定在屏幕上」就必须 fixed。
所以现状下 **「视口固定」与「折射玻璃」互斥**。

### 21.12 全站玻璃「模糊度」规范（2026-10-14 **已落地**；用户可调档留待接设置）

> 需求：用户以后要在设置里**一处调全站玻璃模糊度**；且**后续可能把所有玻璃统一升级为液态玻璃**
> ⇒ 规范必须保证「一处驱动全站」，否则升级会退化成逐处改。

**量纲问题（设计的出发点）**：全站玻璃有两套材质、量纲不同 ——
模糊级是 px（`--liquid-blur` 28/18/36 三档），折射级是 `blurAmount` 0~1 的无量纲
（组件内部换算 px）。**只有无量纲倍数能同时驱动两边**，所以档位定成「倍数」，不是「模糊半径」。

**单源与链路**：

| 层 | 落点 | 说明 |
| --- | --- | --- |
| 单源（默认/上下限） | `src/config/liquid-glass-spec.js` 的 `blurScaleDefault: 1` / `Min: 0` / `Max: 2` | 与白膜 α 同处一个 spec（「官方样貌单源」） |
| 唯一写入者 | `src/composables/useGlassBlur.js`（新） | 钳制 → 持久化 `boh_glass_blur_scale_v1` → 写根 `--glass-blur-scale` |
| CSS 消费 | `tokens.css`：`--liquid-blur* = calc(基准px * var(--glass-blur-scale))` | 全站模糊级玻璃只读 `--liquid-filter*` ⇒ **一处生效** |
| JS 消费 | `BohGlassRefract.vue`：`blurAmount × blurScale` | 折射级吃同一个数（同一个写入者） |

⚠️ **「唯一写入者」是这条规范的核心**：CSS 与 JS 两条链必须读同一个数；两处各写一份 =
用户调了模糊度**只有一半玻璃跟着变** —— 那是最难查的半失效。

⚠️ **所有基准档都必须乘倍数**（本次一并修掉三处漏网）：`tokens.css` 的 `.boh-perf-lite`
（低性能模式）、`liquid-glass.css` 的 ≤768px 档、`glass-ui.css` 的窄屏断点档。
漏一处的症状是「**只在某页 / 某模式不跟**」。守卫已加反证锚：全仓不许再有 `--liquid-blur*: NNpx` 裸基准。

**自证**：
- `bohai-glass-look-spec.test.js` **11/11**（新增 4 条：spec 冻结值 / 根变量默认值 == spec 默认值 +
  三档全是 calc / 三处基准档无裸 px / 唯一写入者 + 折射级消费同一倍数）；`bohai-glass-surfaces` 14/14。
- `probe-navbar-glass.mjs` **8/8**，含端到端实证：`--glass-blur-scale: 0` ⇒ 顶栏玻璃**不再模糊**
  （`zero=35.47 ≈ off=34.54`）⇒ 顶栏的模糊确实由那一档驱动，不是写死的 `18px`。
- `npm run verify` 全绿（4 棘轮持平）。

**未做（刻意留待）**：设置面板的滑杆。接的时候只需在 BOHAI「设置→外观」与「玻璃透明度」成对加一行，
调 `useGlassBlur().setGlassBlurScale()` 即可 —— 链路与持久化都已就位。
⚠️ 但要注意：这条偏好是**站点级**（全站玻璃都在同一棵树里，无域要隔离），
而「玻璃透明度」是 **AI 域**偏好（写根后需被站点 chrome 显式遮蔽）。两者语义不同，别混。
