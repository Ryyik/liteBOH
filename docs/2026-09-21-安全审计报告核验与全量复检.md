## 三、本轮新发现（报告未覆盖）

### P0-1 🔴 匿名可枚举「用户名 → 邮箱」

`public.resolve_email_for_login(p_username) RETURNS text`，SECURITY DEFINER，**anon 有 EXECUTE**。

**生产实证**：
```
POST /rest/v1/rpc/resolve_email_for_login   (仅 anon key，无任何登录态)
{"p_username":"<任意用户名>"}   → HTTP 200，返回该账号邮箱明文
```

**限流实测**（做了正反两组实验，结论与初始假设相反，按实测记录）：

| 实验 | 设计 | 结果 | 结论 |
|---|---|---|---|
| A | 固定伪造 `X-Forwarded-For` 连打 11 次 | 第 11 次 `400 rate_limit_exceeded` | 限流**生效**，键 = `resolve_email:<ip>` |
| B | 每次换一个伪造 `X-Forwarded-For` 再打 3 次 | **3 次全部 400 被拦** | 该请求头**不可伪造**，网关覆写为真实 IP |

→ 更正：**不存在「换头绕限流」**。真实可利用面是 **10 次/分/IP = 约 14,400 次/天/IP**：已知用户名时一次请求即可拿到邮箱；批量爬取会被限流挡住，但换 IP 仍可推进。

**根因**：函数体 `select au.email from auth.users au join profiles pr ...` 直接把邮箱当返回值交付给调用方。`2026090910_fix_sensitive_rpc_no_email` 这个迁移名字暗示做过一次「去 email」处理，但实测现状仍返回邮箱。

**修法**（三选一，推荐 ①）：
1. 改造为**不返回邮箱**：登录链路改为「EF 服务端用 service_role 解析」（EF 已有 `auth-login`，把解析挪进去，客户端不再有该 RPC）。
2. 保留 RPC 但加 **Altcha 人机校验**（项目已有 `altcha-challenge` EF + `auth_altcha_proofs` 表）。
3. 最低限度：返回布尔「是否存在」而非邮箱。

落点：`supabase/migrations/<新>_resolve_email_no_plaintext.sql`、`src/utils/api/auth-api.js:209,625`、`supabase/functions/auth-login/index.ts`

### P0-2 🔴 `cron.job` 内嵌明文 `sb_secret_` 高权限密钥

生产库 `cron.job#8`（`generate_forum_weekly_report_weekly`）的 `command` 里**明文内嵌了一个 41 字符的 `sb_secret_` 密钥**——这是 Supabase 新版 **service_role 等价密钥，可完全绕过 RLS**。

**已核验的边界**：
- ✅ 仓库工作区**无**该密钥（grep `sb_secret_` / `sb_publishable_` → 空）
- ✅ **Git 全历史无**（`git log --all -S"sb_secret_"` 命中的 2 个提交，经逐条 `git show` 确认都是**文档/注释里的占位符**，不是真密钥）
- ❌ 但库里是明文，且 `cron.job_run_details` 已累积 **11,296 行**——job 的 command 一并留痕，会进**数据库备份**

**风险**：任何能看 Supabase Dashboard / 拿到备份的人，即获得项目最高权限；一旦泄露无法通过 RLS 挽回。

**修法**：
1. **先轮换**该 secret key（Dashboard → Settings → API keys）。
2. 不再内联，改为从 DB 级设置读取——项目里已有现成模式：
   `alter database postgres set "app.settings.service_role_key" = '<新值>';`
   然后 `cron.job` 里用 `current_setting('app.settings.service_role_key')` 拼接 header。
   （`.workbuddy/memory/2026-09-15.md` 记录过同样的处置路径，本次是同一坑复发。）
3. 清理 `cron.job_run_details` 中的历史 command 留痕（`cron.job` 已有 7 天保留策略，但要确认它覆盖到含密钥的那批行）。

落点：`cron.job#8`（库内对象，非文件）+ 迁移文件里注册该 job 的 `do $cron$` 块

### P0-3 🔴 匿名可用 149 个 SECURITY DEFINER 函数，其中 33 个无任何身份校验

**规模实测**（远端库 `pg_proc` + `has_function_privilege`）：

```
public schema 中 anon 可 EXECUTE 的函数          232 个
  └─ 其中 SECURITY DEFINER                      149 个
       ├─ 有守卫（函数体内 current_user_is_admin() / auth.uid()）  93 个  ✅
       └─ 无守卫且非触发器函数（真实暴露面）        33 个  ❌
```

**根因**：Supabase 默认 `alter default privileges` 会给 `public` 下**新建函数自动授 anon EXECUTE**。项目已在 `2026090906_rpc_revoke_anon.sql` 做过一轮 revoke，但**没有覆盖全量**——存量函数仍是默认放开。记忆里那条「`auth.uid() is null` ≠ service_role」的教训就是这个坑，本次是**同一坑的存量部分**。

**已实测确认「有守卫」的一类（安全，但授权应收窄）**：
`admin_supabase_project_status` → 匿名调用返回 `{"ok":false,"error":"需要管理员权限"}`；`admin_delete_user_account` / `admin_get_user_sensitive` / `admin_grant_points` / `admin_ban_user` 等函数体内均有 `current_user_is_admin()` 前置门。**结论：不可利用**，但把 149 个 admin 类函数暴露给 anon 的 EXECUTE 是纯粹的纵深防御负债。

用户 UUID 可从公开可读的 `profiles`（`profiles_select_public` = true）直接获得 → **UUID 不是秘密，不构成防护**。

**修法（已实施；原始建议中有三条被实测推翻，勿照旧照抄）**

实际采用的写法（迁移 `2026092101`，已应用）：

```sql
-- 函数撤权：**必须同时撤 public** —— 只撤 anon 无效
--   （函数 EXECUTE 同时有 PUBLIC 内建授权，anon 经 PUBLIC 继承；已 A/B 实测）
revoke execute on function public.<fn>(<args>) from anon, public;                   -- 只需挡匿名
revoke execute on function public.<fn>(<args>) from anon, authenticated, public;    -- 仅服务端调用
-- 表级授权是对 anon 的**显式** grant（无 PUBLIC 份额）→ 撤 anon 即可
revoke insert, update, delete, truncate on all tables in schema public from anon;
```

| 原始建议 | 实测结论 |
|---|---|
| `alter default privileges … revoke … from anon` 可防复发 | ❌ **不成立**。`pg_default_acl` 另有一条 `defaclrole=supabase_admin` 改不动（42501），PUBLIC 内建 EXECUTE 仍在 → **新建函数照样匿名可调**。增量防护改由仓库侧棘轮 `scripts/check-anon-execute.mjs` 承担（§6.7） |
| `revoke execute on all functions … from anon` 一刀切 | ❌ **不可行**。`current_user_is_admin` 被 RLS 策略引用，撤 anon 会让**游客浏览论坛直接 42501**；且逐函数撤权更安全（每项可附白名单理由）→ 采用逐函数写法 |
| 回授 `resolve_email_for_login` 给 anon | ❌ **不需要**。登录已改走 EF，该函数已撤权（§6.9） |
| 「给无守卫函数补函数体内门」 | 🔄 **实际改为撤 anon EXECUTE**（更彻底：攻击者连调用都进不去，而非进去后再判断）。仅 `authenticated` 仍可调、且**身份参数由客户端传入**的 3 个函数需要改函数体（见第七章第 5 步①） |

> ⚠️ **落点约束（仍成立）**：撤权后须**分别** `grant execute` 给 `authenticated` 与 `service_role` —— 本项目 `authenticated` 持**显式**授权、不受撤 public 影响，但新增对象时容易漏。
> ⚠️ 原「门必须写在函数体内」的约束，在**撤权路线**下不再是主要手段（撤权已让攻击者无法调用）；仅当某函数**确实要开放给某角色**时才需要函数体内门。

**结果**：anon 可执行函数 **232 → 155**；anon 可写表 **75 → 0**；`authenticated` 表写权限不变。

落点：`supabase/migrations/2026092101_revoke_anon_execute_and_table_writes.sql` + `2026092102_fix_anon_default_privileges.sql`（均已应用）

### P2-1 🟠 线上零安全响应头

**生产实测** `https://www.blockofhome.cn/`：

```
HTTP/2 200
content-type: text/html; charset=utf-8
server: cloudflare
access-control-allow-origin: *
cache-control: max-age=600
```
**缺失**：`Content-Security-Policy`、`Strict-Transport-Security`、`X-Content-Type-Options`、`Referrer-Policy`、`X-Frame-Options`、`Permissions-Policy` —— 一项都没有。

`public/_headers` 里也只有 `Cache-Control`，且**注释自己写明**：GitHub Pages 不支持自定义 HTTP 头，此文件是给迁移到其他平台备用（与记忆「`public/_headers` 线上完全不生效」一致）。

**叠加放大**：与「Session 存 localStorage」（报告 S-6 仍属实）组合 → 一旦出现 XSS，token 无任何缓解层可挡；且站点可被任意第三方 iframe 嵌套（点击劫持）。

**修法（2026-09-21 复核补充）**：
- Cloudflare **Transform Rules → Modify Response Header 免费版即可用**（免费版共 10 条规则、单条最多改 10 个响应头）。域名已在 Cloudflare 之后（实测 `server: cloudflare` + `cf-ray` + `cf-cache-status`），故此为唯一顺路落点。
- **分两步走**：
  - **第一步（零风险，可立即做）**：`X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`X-Frame-Options: DENY`、`Permissions-Policy: camera=(), microphone=(), geolocation=()`，以及 HSTS（Cloudflare 有独立开关：SSL/TLS → Edge Certificates）。这 4+1 个只收紧默认行为、**不拦截任何现有资源**，能拿到大部分收益。
  - **第二步（需灰度）**：CSP。站点有大量 inline 样式与动态 chunk、且跨源到 `*.supabase.co` / `res.cloudinary.com`，**一次性上强制 CSP 极可能白屏** → 必须先上 `Content-Security-Policy-Report-Only` 观察收敛（响应里已有 `report-to`/`nel` 通道可用），稳定后再改强制。
- 备选路线：写 Cloudflare Worker 注入（仓库已有 `cloudflare/gemini-proxy/` 的 Worker 部署链路可复用），但 Worker 挂到 `www.blockofhome.cn/*` 会接管全部请求，需正确回源，风险高于 Transform Rules。
- 同步更新 `public/_headers` 以保持单一源（该文件线上不生效，仅作迁移备用）。

**✅ 自动化已就绪（2026-09-21）**：`scripts/cloudflare-security-headers.mjs` + CI 步骤（`deploy.yml` 的 "Apply Cloudflare security headers"）。
- 安全设计：只管理带 `[boh-security-headers]` 标记的那一条规则（读-改-写），**不会覆盖**手工加在同 phase 的其他规则；未配 token / 权限不足 / 任何失败一律「告警 + exit 0」，**不阻断发布**（与仓库既有 purge 步骤同策略）。
- 默认下发「零风险四件套 + HSTS」，CSP 以 **Report-Only** 下发；`--csp-enforce` 才转强制。`--remove` 只删自己那条。
- ⚠️ **前置**：现有 `CLOUDFLARE_API_TOKEN` 注释写明只有 **Zone.Cache Purge** 权限，跑该 phase 会 403。需在 Cloudflare → My Profile → API Tokens 给该 token 追加 **Zone / Transform Rules / Edit**。补齐后每次发布自动保持。

**落点**：`scripts/cloudflare-security-headers.mjs`、`.github/workflows/deploy.yml`、Cloudflare 控制台（token 权限）+ `public/_headers`（保持单一源，非生效路径）

### 6.3 复验中发现 2 处缺陷（均已修复）

#### 缺陷 1（影响修复的**持久性**）—— 防复发语句只撤 `anon`

`2026092101` 原第 120 行：
```sql
alter default privileges in schema public revoke execute on functions from anon;   -- ❌ 无效
```
函数在 PostgreSQL 里**默认对 `PUBLIC` 授予 EXECUTE**，anon 经 PUBLIC 继承后照样能执行——这正是该文件 `:9-13` 自己实测证明过的机理，只是防复发语句没跟上。

**后果**：存量函数已被收紧，但**此后新建的任何一个 public 函数都会重新变成匿名可调**，修复会随时间衰减。

**已修**：改为 `from anon, public`，并补注说明「必须同时撤 public」以免后人"简化"回去。

> ⚠️ **本节结论已被后续实测部分推翻 —— 请以 [6.7](#67-2026092102-应用与实测结论修正) 为准。** 改正语句本身是对的（`from anon, public` 对**存量**函数有效），但它**无法防住增量**：新建函数仍会被 anon 执行。原因是 `defaclrole=supabase_admin` 那条默认权限我们碰不到（42501），而新函数仍从 PUBLIC 拿到 EXECUTE。

**关键补充动作**：`2026092101` **已在远端库执行过**（并写入 `supabase_migrations.schema_migrations`），改它的文件内容**不会重跑它**。因此另建后续迁移 `2026092102_fix_anon_default_privileges.sql` 来纠正**已生效**的默认权限。→ 这是「改文件救不了已应用的迁移」的典型场景，容易漏。

#### 缺陷 2（影响**事故恢复**）—— 回滚附录 73 行语法错误

回滚附录全部写成：
```sql
-- revoke execute on function public.xxx(...) to anon, authenticated;   -- ❌ 恢复授权要用 grant
```
`revoke ... to` 不是合法语法。这 73 行一旦在事故中被取消注释执行，**每一条都报语法错误**——这份回滚附录在最需要它的时候是失效的。

**已修**：73 行全部改为 `grant execute on function ... to ...`（残留 0 行），并注明「PUBLIC 的隐式 EXECUTE 有意不恢复，避免回滚时把匿名调用面一并还原」。

#### 修复的精准性自证

```
活跃语句（非注释）差异：仅 1 行    ← 只有防复发那行变了，73 条 revoke 一条未动
注释区：73 行 revoke→grant + 防复发注释 + 回滚说明
文件行数：214 → 218
```

| 检查项 | 实测结果 |
|---|---|

#### 结论修正（重要）

**6.3 缺陷 1 里「已改为 `from anon, public` 即可防复发」的说法不成立。** 准确表述应为：

- ✅ **存量侧有效**：`revoke execute ... from anon, public` 对**已存在**的函数确实有效（本会话早前对 `admin_ban_user` 做过 A/B 实证：只撤 anon 无效、撤 anon+public 后 `anon_can_execute=f`）。这也是 `2026092101` 把 anon 从 224 降到 160 的机制。
- ❌ **增量侧无效**：`alter default privileges` 这条路在本环境**保证不了**「新建函数不被 anon 执行」。已排除「`from public` 没写上」这一解释（该条目里 PUBLIC 确实已消失），真实障碍是**另一条我们碰不到的默认权限条目（`supabase_admin`）+ PUBLIC 的内建 EXECUTE**。

#### 另一个值得记住的推论

全库 **160** 个 anon 可执行函数里，有 **92** 个同时带着 PUBLIC 的 EXECUTE → 对它们**只撤显式 anon 授权是无效的**，必须连 `public` 一起撤。这解释了为什么任何「只 `revoke ... from anon`」的写法都会静默失效——`2026092101` 从一开始就用 `from anon, public`，所以存量侧没有踩这个坑。

#### 增量防护的两条可行路线（默认权限路线已排除）

1. **逐条显式撤权**（与 `2026092101` 同法）：每次新增函数时，在同一迁移里显式 `revoke execute on function ... from anon, public`。可控、无依赖，但要靠人记得。
2. **加一道检测**：定期 / 发布前扫描 `public` 下 anon 可执行函数，超出白名单即告警。项目已有十余个 `scripts/check-*.mjs` 门禁，符合现有工程惯例，且**不依赖任何我们改不动的数据库权限**。

> 建议：新增函数时用 ①，同时用 ② 兜底（防止漏写）。**不要再用 `alter default privileges` 当作防复发手段**。

#### 对第七章执行顺序的影响

第七章「第 1 步」已完成（`2026092102` 已应用）。**第 6 步「第二阶段撤权」的优先级应上调**——因为「新增函数自动不开放」这条护栏实际不存在，每多一个未加固的新函数就是一个新的匿名入口；在护栏补齐前，撤权与检测的价值更高。

#### 6.9.2 为什么「先撤权、不直接 drop」

撤权对调用方的效果与 drop **完全相同**（旧路径一律失败），但恢复成本差一个数量级：

| 方式 | 旧客户端表现 | 回滚成本 |
|---|---|---|
| `revoke` | 调用失败（42501） | **一条 `grant`，秒级** |
| `drop` | 调用失败（404 PGRST202） | 需重建函数体（含限流逻辑），有写错风险 |

因此顺序是：**撤权 → 观察 → 再由后续迁移 drop**。这与 §6.3 缺陷 2 的教训同源：**回滚路径要在平时就想清楚，别等事故时才发现不可用。**

#### 6.9.5 残余风险与回滚

**残余（刻意保留的两项）**：

1. 函数本体**未 drop** —— 这是刻意的，用于保留秒级回滚能力。观察确认后再由后续迁移清理。
2. 旧客户端兼容窗口**未完全关闭** —— 停留在旧页面且不触发 `version-checker`（`visibilitychange` / 路由跳转）的用户，其登录会失败。考虑到该接口 6 个月真实调用近零、近 24h 仅 1 个账号登录，且旧页面一旦有交互即被 `buildId` 比对强制刷新，实际风险面很小。

**回滚（一条命令，立即恢复可调用）**：

grant execute on function public.resolve_email_for_login(text) to anon, authenticated;
