## 2. P0 阻断项

### P0-1　用户管理 / 积分管理「保存」必然 42501（双层阻断）　✅ 已修复（见 §9）

**位置**：`DataAdmin.vue:7341`（`.update(dataToSave).eq('id', ...).select()`）、`config/saveStrategies.js:65 / :119`

**第一层：5 列没有 UPDATE 授权。** 来源是 `supabase/migrations/2026090803_security_hardening.sql:68-79`，列级白名单**故意**排除 `role / points / experience / tags / hide_online_status`。逐列实测（admin 身份改他人资料）：

| 结果 | 列 |
| --- | --- |
| ✅ 可写（1 行） | `username` `join_date` `bio` `avatar_url` `birth_month` `birth_day` `is_boh_creator` `creator_platform_ids` `creator_platform_visibility` `creator_platform_order` `showcase_post_ids` `profile_background_url` `profile_background_public_id` `hide_follow_data` |
| ❌ 42501（缺 UPDATE 授权） | `role` `points` `experience` `tags` `hide_online_status` |
| ❌ 42501（缺 SELECT 授权） | `shipping_recipient` `shipping_phone` `shipping_address` |

**第二层：`RETURNING *` 撞敏感列。** 这一层 v1 漏了，也是"只改用户名也失败"的真正原因之一：

```
update profiles set shipping_recipient = '字面量' … returning id   → ✅ 1 行
update profiles set shipping_recipient = '字面量' … returning *    → ❌ 42501
```

`supabase.from(t).update(x).select()` 默认发 `select=*`，等价 `RETURNING *`，需要对**全部列**有 SELECT。而 `shipping_*` 的列级 SELECT 是 `2026070802_fix_high_security_issues.sql` 按 H-1 有意 revoke 的（"防止任意登录用户遍历他人敏感信息"）。两条迁移叠起来 ⇒ 保存必挂。

**第三层：RLS 本身是好的。** 事务内临时补授权后（rollback 撤销）验证：22 列整包更新 + `RETURNING *` → **1 行成功**。说明管理员策略（`profiles_admin_update`）在线且生效，不需要动策略。

**修法（唯一正确解）**

1. 新增 `admin_update_user_profile(p_user_id uuid, p_patch jsonb)`：`SECURITY DEFINER` + 首行 `if not current_user_is_admin() then raise exception 'forbidden'`，只允许 patch 白名单键。
2. 前端 `SAVE_STRATEGIES.users/points` 改为：敏感 5 列走 RPC，其余列仍走直更——或者干脆整体走 RPC。
3. **必须同时**把 `.select()` 改成显式列（如 `.select('id, username, role, points, experience, join_date, bio, avatar_url, tags')`），否则第一层修完第二层还在挂。
4. 过渡止血（不动后端）：把 5 列从 `TAB_WRITABLE_FIELDS.users/points` 摘掉 + 表单置灰，让其余 17 列能存。

**为什么不能补授权（实测反证，务必留档）**

在事务内临时 `grant update (role, points, …)`，然后以**普通用户**身份执行：

| 操作 | 结果 |
| --- | --- |
| 把自己的 `role` 改成 `admin` | 🚨 1 行成功 |
| 把自己的 `points` 改成 `999999` | 🚨 1 行成功 |
| 读别人的 `shipping_phone`（补 SELECT 后） | 🚨 1 行成功 |

因为 `profiles_update_self` 策略的 qual 只有 `auth.uid() = id`，与列级授权一叠加就等于"任何登录用户可以自封管理员、自刷积分、遍历全员手机号"。**v1 报告建议的 `GRANT UPDATE (...)` 是错的，已在此更正并作废。**

## 7. 取证方法（v2 已不再有"RLS 不可测"的限制）

**先回答"能不能走 CLI/代理"**：不能，且与 CLI 无关。`*.supabase.co` 的阻断在 TLS SNI 层，沙箱内外一致：

| 测试 | 结果 |
| --- | --- |
| TCP 443 连 `172.64.149.246` / `104.18.38.10` | ✅ 成功 |
| 同 IP、SNI=`www.cloudflare.com` | ✅ 200 |
| 同 IP、SNI=`<ref>.supabase.co` | ❌ `SSL_ERROR_SYSCALL`（curl exit 35） |
| `--noproxy '*'` 直连 / `--http1.1` / `--tlsv1.2` | ❌ 全部 000 |

所以官方探针 `verify-datamanagement-columns-live.mjs` 依然跑不出结果——但 v2 不再需要它。

**v2 的替代路径（等价于真实登录，且能覆盖 RLS）**：Management API 执行

```sql
begin;
  set local request.jwt.claims   = '{"sub":"<uid>","role":"authenticated","aud":"authenticated"}';
  set local request.jwt.claim.sub = '<uid>';
  set local role authenticated;
  <被测语句>;
rollback;
```

`auth.uid()` 读的就是这两个 GUC，所以 RLS 里的 `auth.uid() = id`、`current_user_is_admin()` 全部真实生效。**有效性对照**：

- 普通用户改他人 `username` → **0 行**（RLS 正确拦截）
- 普通用户改他人 `posts.status` → **0 行**
- admin 改他人 `username` / `posts.status` / `news.title` → **各 1 行**

三项形成正反向闭环，说明这套 harness 既能放行也会拦截，不是"看起来 0 行"的假象。

**另一个技巧**：把 `grant` 写进同一个事务再 `rollback`，可以**在线上安全地试算"授权补齐后会发生什么"**——P0-1 的提权反证、P0-3 的安全性验证都是这么做出来的，线上 ACL 零变更（已验证）。

**仍未覆盖**：浏览器端真实点击。本次是 SQL 层等价验证，PostgREST 的 `select=*` 语义按其文档推断（`.select()` 无参 ⇒ `*`）——这一条建议在修复后用一次真实登录点一次"保存"收尾。

### 10.1 用户报障与真实根因

> 「数据管理的搜索没用啊，我搜索**广告**，也没结果」——补充：想找的是**广告管理这个功能**。

线上取证（真实 JWT claims + 全库文本列扫描）：

| 事实 | 证据 |
| --- | --- |
| 全库只有 8 行含「广告」：`boh_ai_core_memories.content` 4 行、`boh_ai_knowledge_chunks.content` 4 行 | 421 个文本列逐列 `ilike '%广告%'` 统计 |
| `advertisements` 只有 1 行，标题是「斜挎包，现已推出。」——**本来就不含「广告」二字** | `select * from advertisements` |

所以「搜不到」是三个缺陷叠加，**没有一个是「数据不存在」**：

| --- | --- | --- |

| S-3 | 默认范围 `本表` + 有表却没配搜索字段的页签（`addresses` / `photoAlbums`）被 `filters.length === 0` 直接跳过 | 同一个词「有时有结果、有时没有」，且没有任何解释 |
