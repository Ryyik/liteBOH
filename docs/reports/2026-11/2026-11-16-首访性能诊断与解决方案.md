### 1.5 入口链路为什么吃掉 4.4 秒

> ⚠️ **本节的两条归因已在 §7.2 被本地实测推翻，勿再引用**：
> ① 「串行发现、每跳一个 RTT」不成立 —— 18 个资源在 193–194 ms 一次性发出；
> ② 「CSS 被饿到 5.3 s」不成立 —— 本地 CSS 194 ms 发起、VeryHigh、1137 ms 完成。
> 真正串行的是**第二层**（Router resolve 后才取首页 chunk，1753 ms）。
> 下面这段保留仅作当时的推理记录。

19 个文件 / 239 KB 传输，在 1.6 Mbps 下**纯传输只要约 1.2 秒**，实测却到 4.4 秒。差额不是带宽，是
**串行发现 + 并发分摊**：`HTML → boot.js（同步、阻塞解析）→ CSS + 17 个 modulepreload` 每一跳都要一个
RTT（150 ms），而 19 路并发把 1.6 Mbps 摊薄成每路约 640 kbps —— 实测三段最大的分别是
`816→2853`(ui-components 60 KB)、`816→2882`(supabase 55 KB)、`816→2517`(vue-vendor 43 KB)，
全部挤在同一窗口里完成。

**推论：这一段对"字节数"近似线性敏感，减 50 KB 约省 600 ms。** 入口里唯一可减的大块是
`supabase-vendor`(55 KB gz)，但它被 `stores/auth.ts` 在 `main.js` 顶部同步使用，要拆得改登录态语义，
风险高 —— 不作为本轮建议。

## 2. 方案 A · Cloudflare 配置（零风险、无需发版、建议先做）

> 现状：`www.blockofhome.cn` → Cloudflare（proxy）→ GitHub Pages（Fastly 源站，美西）。
> `_headers` 文件里的 `immutable` 一年缓存**完全没生效** —— GitHub Pages 不支持自定义 HTTP 头，
> 线上真正生效的是 Cloudflare 的规则，而它把 TTL 统一压成了 4 小时。

### A1. 缓存规则拆成两类（最重要）

Cloudflare → Caching → Cache Rules，新增两条，**顺序敏感**（先具体后笼统）：

**规则 1「静态资源：一年 immutable」**
- 条件（表达式）：
  ```
  (starts_with(http.request.uri.path, "/static/js/")) or
  (starts_with(http.request.uri.path, "/static/css/")) or
  (starts_with(http.request.uri.path, "/static/images/")) or
  (starts_with(http.request.uri.path, "/static/media/")) or
  (starts_with(http.request.uri.path, "/static/fonts/"))
  ```
- Edge TTL：`Override origin` → **1 year**
- Browser TTL：`Override origin` → **1 year**
- 理由：`/static/` 下**全部**带内容 hash，文件名随内容变，一年缓存是安全且标准做法。
  现状 4 小时等于**每 4 小时让每个边缘重新回源到美西**，冷访客直接吃 MISS。

**规则 2「入口与 SW：短边缘 + 不缓存浏览器」**
- 条件：
  ```
  (http.request.uri.path eq "/") or
  (http.request.uri.path eq "/index.html") or
  (http.request.uri.path eq "/boot.js") or
  (http.request.uri.path eq "/sw.js") or
  (http.request.uri.path eq "/push-sw.js") or
  (http.request.uri.path eq "/version.json") or
  (http.request.uri.path eq "/manifest.webmanifest") or
  (http.request.uri.path eq "/404.html")
  ```
- Edge TTL：`Override origin` → **60 秒**
- Browser TTL：`Bypass cache`（发 `no-cache`）
- 理由：现状 HTML 是 `max-age=600`，**发版后最长 10 分钟**边缘还在发旧 HTML，
  而旧 HTML 引用的 hash 资源已被 GitHub Pages 删除 ⇒ 404 ⇒ `boot.js` 的资源恢复逻辑
  带 `bohAssetRecovery` **整页重载一次**。用户感知就是「点进来卡十几秒 / 白屏闪一下」，
  而且只在发版后那一小段时间出现，最难复现。
  缩到 60 秒 + 浏览器 bypass，这个窗口基本消失。

> ⚠️ 不要把 `/boot.js`、`/sw.js` 放进规则 1 —— 它们**没有 hash**，长缓存会让改版最长滞后到缓存过期。

### A2. 压缩：**已证伪，不需要动**

原来判断「线上只发 gzip」是**方法错误**：我用 `Accept-Encoding: br, gzip` 测得 gzip，就推断
「CF 不会把源站 gzip 转成 br」。2026-11-16 在控制台确认后的复测：

```
curl -H 'Accept-Encoding: br'        → content-encoding: br      ← 本来就是 brotli
curl -H 'Accept-Encoding: gzip'      → content-encoding: gzip    ← 同一资源的 gzip 变体
```

即 CF 为同一份资源存了 br 和 gzip **两个变体**，按请求头协商。之前那次读数是命中了 gzip 变体，
不是「没有 br」。**此项无需任何操作**（`_headers` 里的 immutable 也是一样：GH Pages 不认，
同理由 CF 规则接管）。

### A3. 其它三项（开关级）

| 项 | 位置 | 作用 |
|---|---|---|
| **Early Hints** | Speed → Optimization → Protocol | 边缘 MISS 时可先回 `103` 带 preload 头，把 721 ms 的 TTFB 和资源下载叠起来 |
| **Tiered Cache** | Caching → Tiered Cache | 上层缓存命中后，区域边缘不必各自回源到美西 |
| **HTTP/3 + 0-RTT** | Network | 回访少一个握手 RTT |

### A4. 关于「中国大陆」

Cloudflare 免费/Pro 没有中国大陆节点，大陆用户通常落到 **HK / SG / JP**，再回源到美西。
如果目标是大陆移动端体感，真正的解法是把静态资源放进**国内 CDN + 对象存储**（需备案），
让 `/static/*` 走国内节点。这条比前面所有代码优化加起来都大，但属于立项级决策，先摆在这里。

## 3. 方案 B · 代码优化（按收益/风险排序）

### B1. 入口 CSS 非阻断 —— **白屏 −640 ms（推荐，但要你点头）**

现状：`main.js` 把 30 个全局 CSS 静态 import，Vite 抽出 `index.css` + `ui-components.css`
并在 `<head>` 末尾注入 `<link rel="stylesheet">` ⇒ **浏览器在它们下载完成前不许绘制任何东西**。

但 `index.html` 里其实**已经内联了 3.6 KB 的骨架样式**（`.boh-boot`，「正在加载…」+ 三点动画），
它本可以在 ~200 ms 就画出来 —— 现在被那两个 `<link>` 压到 1.0 s 之后。

**⚠️ 这不是"忘了开"，而是有门禁明文拦着的：**
```
scripts/check-shell-precache.mjs:132
  「这通常意味着「入口 CSS 不再是 render-blocking 的静态 <link>」——首屏将失去样式优先加载保证，请不要放行。」
scripts/check-first-paint.mjs:99
  「骨架 <style> 被样式表抢先…骨架会被全局样式覆盖」
```
所以要做，**必须用另一条保证替换掉它**，不能直接删：

1. `index.html` 把注入的 stylesheet 改成 `<meta name="boh-shell-css" content="a.css,b.css">` + `<noscript>` 里的真 `<link>` 兜底；
2. `boot.js`（已在 `<head>` 最前、同步）读 meta，创建 `rel="preload" as="style"`，`load` 后切成 `stylesheet`；
3. 挂载前确认样式已生效（`document.styleSheets` 命中或 3 s 超时强插），避免 FOUC；
4. 同步改 3 条门禁的解析口径（`check:shell-precache` 断言 A、`check:first-paint`、`check:gates-self-test` 的 fixture）。

**收益**：FCP 1016 → 344 ms（本机）；线上约 2.4 s → 1.0 s。
**风险**：boot.js 成了样式应用的必经之路（现在它已经是主题的必经之路，失败模式不新，但后果从"白闪"变成"无样式"，更重）。

### B2. SW 注册延到 LCP 之后 —— **❌ 已试，机制不成立，已还原**

原假设：`src/main.js:85-89` 在 `load` 时注册 SW，随即预缓存 853.89 KiB 抢 LCP 带宽（A/B 屏蔽
`sw.js` 得 −350~400 ms）。于是改成「LCP 候选静默 800ms 再注册」。

**实测推翻了自己**：限速下 3 秒时缓存里已有 28 条 —— 因为**首帧那个"正在加载…"骨架本身就是
早期 LCP 候选**（`P.boh-boot-text`，2044ms 就上报过），静默计时器在约 2 秒就触发，注册根本没被
推迟。改成「等首次交互」也不行：用户可能 1 秒就点，那时图片还没开始下。

结论：**没有一个可靠且低代价的「LCP 已定稿」信号**，这个方向收益（350 ms）与复杂度不匹配。
代码已 `git checkout` 还原，不留无用复杂度。若将来真要治，得从「预缓存清单瘦身」入手，
而不是推迟注册。

### B4. 开场画 —— **⚠️ 上一条判断有误，已更正**

我一度说它"必须手势、没提示、像卡死"。**错了**：`src/views/Home/index.vue:43` 有明确的
`<button class="home-gate-enter">进入方块论坛</button>`，点击即 `commitGate`。所以它不是可用性
陷阱，用户不会不知所措。

仍然成立的小问题只有一个：`utils/home-gate-storage.js:23` 把 `buildId` 拼进 storage key，
**每次发版所有人都要重新看一遍开场画**。频繁发版期间这会放大"怎么又变慢了"的观感，但它是
产品决策（想让人看到新版），不是性能缺陷 —— 优先级低，不改也不影响任何指标。

### B3. 数据瀑布 —— **✅ 已修「我」页的成对重复；但 LCP 主因要另找**

`load` 2.3 s 就结束，图片却到 7.8 s 才完成 —— 中间 5.5 s 花在「取数据 → 渲染 → 才发现图片」上。

**已落地（`5718013f`）**：`/user-space` 首访数据请求 **25 → 18**，统计路径上每个查询都变成 ×1。
两处根因都与登录态无关，用 dev server 给 `fetch` 打桩 + `console.trace` 定位：

1. `watch(..., { immediate: true })` 首轮 `oldVal` 为 undefined，`userId !== oldVal?.userId`
   恒为 true ⇒ 「首次挂载」被当成「换账号」：又调一次 `initUserData()`（同一条 profiles 全字段
   查询同一毫秒发两份），并 `scheduleUserSpaceWarmup({ force: true })` ⇒ 900 ms 后带 force
   再跑一轮（force 同时绕过 5 s 合并窗口与 stats 缓存）。
2. 5 s 合并窗口写在聚合 RPC **之后**，而聚合成功就 `return` ⇒ 窗口对聚合路径从未生效，
   warmup / onActivated 每次都能把 `get_my_user_space_summary` 再打一遍。改成**任何 await
   之前**的同步闸（「成功后才写」的时间戳拦不住同毫秒并发）。

**⚠️ 一个必须交代的测量局限**：`get_my_user_space_summary` 依赖 `auth.uid()`，而探针只有前端
伪造登录态、没有真实 JWT ⇒ 它在探针环境里必然失败并回退旧查询。所以「首访 25~31 个请求」
是**未认证视角**，真实登录用户会走聚合成功分支、请求数应当更少。两处修复对它同样成立
（都是与登录态无关的重复），但「近半是重复」这个**比例不能直接套到真实用户身上** ——
需要一次真实登录的复核。

**另一个反证：首页（`/`）只有 10 个数据请求，全部不重复，LCP 却同样是 6.3 s。**
所以 LCP 的主因不是重复查询，而是**串行结构**：入口 JS 要 4.4 s 才就绪，之后才发数据请求，
再之后才下载图片。要压 LCP，得动 §1.5 那条入口链路（减少字节 / 减少跳数），而不是继续合并查询。

### B4. 开场画不再随每次发版重播 —— **产品决策，非性能 bug**

`utils/home-gate-storage.js:23` 把 `buildId` 拼进 storage key，所以**每次发版所有人都要重看一遍
开场画**，而且是"等用户手势才收起"。频繁发版期间，这就是"怎么又变慢了"的直接来源。
如果这是有意为之（想让人看到新版），保持；如果只是顺手写的，把 buildId 从 key 里去掉、
只留 24h 时间窗即可。

### B5. 入口 JS 208 KB —— 暂不动

`supabase-vendor` 217 KB(55 gz) 是入口第二大块。要拆它得把 auth 会话恢复改成懒初始化，
触及登录态语义（`stores/auth.ts` 在 `main.js` 顶部被 `useAuthStore()` 同步使用）。
收益约 −55 KB gz，风险高，除非 B1~B3 做完还嫌慢，不建议现在动。

## 4. 建议执行顺序

按「真能省多少秒」排，不按「听起来多像性能优化」排：

1. **A1 + A2**（Cloudflare，今天就能做，零风险）—— 唯一不用发版、不碰代码、立刻见效的一项。
   冷边缘 TTFB 721→约 250 ms，并顺手消掉「发版后旧 HTML 引用已删 hash → 404 → 整页重载」
   那个窗口（这才是"偶尔特别慢"的来源）。
2. **B3 数据瀑布** —— 「我」页的成对重复已修（25→18 请求，见下），但**它不是 LCP 的主因**：
   首页只有 10 个请求、全不重复，LCP 仍是 6.3 s。真正要动的是 §1.5 的入口链路
   （239 KB 传输却要 4.4 s，差额花在串行发现与并发摊薄上）。
3. **B1 入口 CSS 非阻断** —— 值得做，但它**不是提速**：总等待时间不变（JS 完成 4525→4391 ms
   几乎不动），只是把开头 1 秒白屏换成骨架。作为"第一印象"修复排在后面。
4. **不做 B2**（已实测证伪）、**B5 暂不动**（改登录态语义，风险收益不匹配）。
5. A4（国内 CDN）视目标用户分布决定是否立项 —— 它比上面所有代码优化加起来都大。

> 一句话：**先让 Cloudflare 别把带 hash 的资源当 4 小时过期品，再去治数据瀑布。
> CSS 那条是"好看一点"，不是"快一点"。**

### 落地后实测（线上，Slow 4G 1.6 Mbps / RTT 150 ms，禁 SW）

```

LCP             5716 ms         （原 5664–7572）
静态资源        cache-control: max-age=31536000, cf-cache-status: HIT, age 0→53
首页            cf-cache-status: HIT（age 14/17/20 → 60 s 一轮），浏览器侧 no-store
```

两条需要如实交代的观察：

- **`/static/` 的 1 年缓存已经生效**：`max-age=31536000` + 边缘 `HIT`。这是本次最实在的收益，
  但它的价值主要在**回访**（不再每 4 小时回源、不再重新下载），而不是首访的绝对秒数。
- **首访 LCP 只小降（5.7 s vs 5.7–7.6 s）**。原因不是规则没用，而是首访的瓶颈仍在
  §1.5 那条入口链（CSS 到 5.3 s、入口 JS 到 5.9 s 才下完），CF 缓存命中也改不了
  「1.6 Mbps 下串行下载 239 KB」这件事。
- **「Browser TTL 绕过」会让 CF 在 HTML 响应上加 `no-store`**，实测不影响边缘缓存
  （`cf-cache-status` 仍是 HIT），但浏览器每导航一次都会重取一次 HTML。这是刻意的：
  HTML 永远拿最新的，代价是每次导航多一个 ~30 ms 的边缘请求。

### 尚未做的（需要评估）

- `icons/` 目录（含 LCP 元素 `icon-512-transparent.png`）**没有**纳入规则 1 —— 它的文件名
  **不带内容 hash**，给 1 年缓存会在换 logo 时造成长期不更新。若要快，正确做法是给这几个
  图标文件名加 hash（构建期改引用），而不是硬上长缓存。
- 未做整站 purge：`/static/` 下全是内容 hash 的不可变文件，旧条目过期后自然换成新 TTL，
  强制 purge 只会让所有用户同时冷启动。

## 7. Phase 0 复测：三处推断被推翻，一处落地生效（2026-11-16 下午）

> 方法：本地产物（无 TTFB 噪声）+ CDP 限速 1.6 Mbps / RTT 150 ms / 390×844 / 禁 SW，
> 新增探针 `probe-waterfall.mjs`（带 priority + initiator）、`probe-boot-timeline.mjs`
> （首屏元素进 DOM 的时刻）、`probe-preload-scope.mjs`（预取作用域）、`probe-ab-lcp-logo.mjs`。

### 7.1 三个问题的答案

| 问题 | 结论 |
|---|---|
| CSS 为什么被饿到 5.3 s？ | **本地不成立。** CSS 在 **194 ms** 就以 `VeryHigh` 发起、1137 ms 完成，FCP 1174 ms 紧随其后。线上那 5.3 s 是 TTFB + 边缘回源，不是排队饥饿。§1.5 的「优先级饥饿」归因作废。 |
| LCP 图与 Vue 挂载的时序 | 挂载 1758 ms，**logo 到 3224 ms 才发起**（晚 1.4 s），4520 ms 完成。发起晚不是 lazy 造成的（见 7.2），是首页 chunk 到 2838 ms 才下完。 |
| 初始路由 chunk 的发现时刻 | **1753 ms**（挂载之后）—— 而 CSS 是 194 ms。**差 1.56 s**，这就是最大的一块可回收时间。 |

### 7.2 两处自我更正

**① 「串行发现、每跳一个 RTT」不成立。** 入口那 18 个文件在 **193–194 ms 一次性全部发出**
（preload scanner 一口气扫完），不存在逐跳串行。§1.5 那句「HTML → boot.js → CSS + 17 个
modulepreload 每一跳都要一个 RTT」是错的，实际只花了一次 RTT。真正串行的是**第二层**：
Vue 挂载后 Router resolve 才去取首页 chunk。

**② `image-optimizer` 的 lazy 降级不是根因。** 它的第 12 行确实给「没有
`fetchpriority=high`」的 img 自动加 `loading="lazy"`，而首屏 LCP 元素
`.street-hero-brand-logo` 恰好没设 —— 看起来很像个完美的元凶。但 A/B 反证：
在 DOM 插入的同一批次里移除 lazy + 置 `fetchpriority=high`，**LCP 4646 → 4638，毫无变化**。
原因：图已经开始取了，优先级此时才设已经晚了。所以这条只解释「优先级是 Low」，
不解释「为什么 3.2 s 才发起」。

### 7.3 一个必须承认的物理约束：带宽守恒

第一次落地只做了「首页链预取」。结果：

```
首页 chunk 发现   1753 → 397 ms   （-1356 ms，预取确实生效）
首页 chunk 完成   2838 → 1739 ms   （-1099 ms）
logo 发起         3224 → 2564 ms   （ -660 ms）
logo 传输耗时     1280 → 1634 ms   （+354 ms，变慢）
LCP               4642 → 4280 ms   （ -362 ms）
```

**预取把「发现」提前了 1.35 s，但 6 KB 的图反而更慢了。** 因为 1.6 Mbps 是硬上限，
提前下载 A 只会让 B 往后排。任何「多加预加载」的方案在这里都只是重新分配等待，
不是消除等待 —— 这也直接推翻了 §1.5 那句「减 50 KB 约省 600 ms」的线性推论：
高优先级资源已经抢在前面时，省下来的字节不一定落在关键路径上。

推论：**首访要真正快，只能减少首屏需要传输的总字节。** 当前首屏（gzip）：
入口 193 KB + 首页链 50 KB + 论坛流 146 KB ≈ 390 KB，1.6 Mbps 下纯传输就是 1.95 s，
加上一次 RTT 与执行，4.2 s 的 LCP 已经贴着这个下限。

### 7.4 本次落地（两个改动）

**① 首页链路按 hash 条件预取**（`vite.config.js` + `scripts/lib/initial-route-preload.mjs`
+ `public/boot.js` 第 0 段）

- 构建期从产物算「首页 chunk 的静态 import 闭包」，剔除入口已 preload 的那批，
  只留 12 个首页独有的 JS（50.3 KB gzip）；
- 写进 `dist/boot.js` 的占位符，由 boot.js 在**同步执行期**按 hash 判断 ——
  只有落在首页才插 `modulepreload`。**非首页访客一个字节都不多付**；
- 白名单：`空 hash` / `#` / `#/` / `#/?*` / `#/forum`。最后一项是 compat 重定向
  （`#/forum` → `/?view=latest`），重定向发生在 Router 起来之后、预取早错过；
  实测 `#/forum` 入口原本要等 1726 ms，补白名单后 426 ms。

**② 品牌 logo 补 `fetchpriority="high"`**（`StreetSceneHero.vue`）
顺带让它避开 `image-optimizer` 的 lazy 降级。单独做它没用（见 7.2 ②），
但和 ① 叠加后才有意义：图被更早插入 DOM，此时优先级才真正决定排队位置。

## 8. 第二步：ForumMain.css 量化 —— 三个假设被推翻（2026-11-16 下午）

> 方法：`probe-css-coverage.mjs` 解析 8 个源 CSS，在真实页面用 `matches()` 判断每条规则
> 是否命中「视口内元素」，取**两个快照**（加载期 / 稳定后）；`probe-composer-scope.mjs`
> 核对 scope 归属。产物口径：本地产物、1.6 Mbps / RTT 150 / 390×844 / 禁 SW。

### 8.1 结论先行：没有死 CSS

| 分类 | 规则数 | 含义 |
|---|---|---|
| A 首屏可见 | 153（15%） | 真正影响首屏画面 |
| B 在 DOM 但不可见 | 33 | 抽屉 / 弹层预渲染 |
| C 条件渲染 | 697（85%） | 源码有引用，当前形态不渲染 |
| D 源码无引用 | 34（0.8 KB raw） | ← **全部是误判** |

那 0.8 KB 的 D 类全是 Vue `<Transition>` 的运行时类（源码只写 `name="composer-image"`，
`-enter-active` / `-leave-from` 由框架拼出来）。**删不掉，也不该删。**

⇒ 「论坛有大量死 CSS 可以清理」这个假设**作废**。真实结构是：
**85% 的规则属于「用户还没进入那个状态」，不是「代码废弃了」。**

### 8.2 「多份 scoped 重复」是真的，但 gzip 已经吃掉了

这些 CSS 被多个组件各自 `@import` 一次：

| 文件 | 引入方 |
|---|---|
| `replies-responsive.css` | ForumMain + PostCard + PostComposer（**3 份**）|
| `composer.css` / `post-polish-sweep.css` | ForumMain + PostComposer（2 份）|
| `feed.css` / `base.css` | ForumMain + PostCard（2 份）|

scoped 转换发生在 SFC 编译期，所以同一份 CSS 会生成带不同 scope id 的副本。产物实测
`.reply-input-section-v2` 确实有 3 个不同 scope。**但**：

```
ForumMain.css  197.9 KB raw  →  33.5 KB gzip   （压缩比 5.9:1，远高于常态 3.5:1）
去重后         162.3 KB raw  →  27.6 KB gzip
                                ↑ 省 35.5 KB raw，但 gzip 只省 5.9 KB
```

**LZ77 会把重复串直接引用前文，重复内容的边际压缩成本接近零。**
⇒ 「去重能省一大块」这个假设**作废**。去重需要在全局/局部样式之间重新划分作用域，
风险远大于 5.9 KB 的收益。

### 8.3 真正的机会：条件渲染组件是静态 import

量化时发现 `forum-feed-cache` chunk 只有两个组件，而**两个都是条件渲染的**：

| scope | 组件 | 渲染条件 |
|---|---|---|
| `68a1603d` | PostComposer（发帖编辑器）| `v-if="isMobileComposerOpen"` |
| `9b39665b` | ImageEditModal（图片编辑）| `v-if="visible"`，上一轮已改异步 |

上一轮把 ImageEditModal 改成异步后，**它和 PostComposer 被 Rollup 合并进同一个 chunk**，
而 PostComposer 仍是静态 import ⇒ 那份异步形同虚设，整个 chunk 照旧进首屏
（实测 2515 ms 发起、23 KB JS + 13 KB CSS，优先级 High / VeryHigh）。

### 8.4 落地：PostComposer 按需加载

`ForumMain.vue`：静态 import → `createPanelAsync(() => import(...), { label, silent: true })`。
用项目唯一实现（退避重试 2 次 + 失败上报 + SW 感知强刷），不裸写 `defineAsyncComponent`。

产物变化：

```
PostComposer-*.js    新增独立异步 chunk   60.3 KB raw / 20.9 KB gzip
PostComposer-*.css   新增独立异步 chunk   79.5 KB raw / 13.2 KB gzip
forum-feed-cache.js  64.7 KB → 6.2 KB     （22.4 → 2.5 KB gzip，只剩工具模块）
ForumMain.css        197.9 KB 不变        ⚠️ 见 8.5
```

CSS 内容字节级一致（79.5 KB、scope 分布 141+444 与改动前完全相同），只是换了归属 ⇒
样式不可能变。面板实测：首屏 0 次请求；点 FAB 后才请求 js+css 各一次；顶栏（返回/标题/
发布）与登录提示正常；关闭后离场 class 仍在。

**首屏实测（3 轮，1.6 Mbps / RTT 150 / 禁 SW）**

```

logo 完成           4048/4024  →  3798/3803 ms   （-245 ms）
load                4199       →  2475/2489 ms
```

净省约 **32.7 KB gzip**（20.9 JS + 13.2 CSS − 2.5 留存的工具模块）。

### 8.5 遗留：ForumMain.css 里还有一份 composer.css 的副本

`ForumMain.vue:4481` 仍 `@import './styles/composer.css'`，产出的是带
`[data-v-ForumMain]` 的那份（197.9 KB 没变）。它只服务 ForumMain 模板里的 3 个 class
（`.mobile-composer-overlay` / `-submit` / `-back`），其余 68 个 class 属于 PostComposer 模板，
**对 ForumMain 的 scope 根本不匹配**。

⇒ 下一步可把这份 @import 收窄成「只留那 3 个 class 的规则」，预计再省 8–12 KB gzip。
风险：`is-*` 状态类可能是动态拼名，收窄前要逐条核对（`composer.css` 里 19 个 class
在两个模板里都搜不到，需先弄清它们由谁生成）。

> 本轮一句话：**CSS 那 34 KB 里没有「垃圾」，只有「还没用到的」。真正能省的不是删规则，
> 而是让「用户还没进入的状态」不要跟着首屏一起下载。**

### 9.1 为什么本地「全绿」却让 CI 红了

**`check:first-paint-budget` 只出现在 `build:ci` 里，`verify` 与 `prepush` 都不跑它。**
因为它依赖构建产物，而 `verify` 不构建；`prepush` 用的是干净检出（没有 dist）——
该门禁在无 dist 时 `exit 0`。

⇒ **本地 `verify`/`prepush` 全绿 ≠ CI 绿，这条只能靠 CI 兜。**（本次踩到）

### 9.2 真正的浪费不是功能，是注释

`public/boot.js` **不过打包器、不删注释**，原样下发给每个访客。全文 11 790 字节里
**6 518 是注释（55%）**，其中我上一轮加的预取段落注释就占 1 102 字节。

做法：把论证与背景搬到 `docs/guides/boot-js-notes.md`（含「顺序有意义」的四段理由、
两处必须同步的跨文件约束），文件内只留「改这里会踩什么」。

```
boot.js  raw 12 257 → 9 232     gzip 5 566 → 4 173
                                 （基线 4 236，比基线还低 63 字节）
```

**结论：首页链预取（换来首访 LCP −410 ms）现在是零字节成本。**
功能实测未变：首页与 `#/forum` 预取 12/12 均在 380–387 ms 触发；`#/about` 0 次；
暗色偏好下 `data-theme=dark`、骨架被 Vue 接管、无页面错误。

### 9.3 CI 结果与遗留风险

```
✅ 首屏预算通过：254.9 / 253.0 KB（容差 2.0，11 个入口）
```

**余量只剩 0.1 KB。** 这一项要清楚地说：下次任何让首屏涨几十字节的提交都会立刻红。
当前超基线部分来自本轮之外的模块（`ui-components.js` +1.6、`ui-components.css` +0.7、
`useKeyboardInset` +0.6、`auth-api` +0.4，以及新进首屏的 `useHomeGate` 0.3 +
`bottom-nav` 0.3）。

三个选择，本轮**刻意没做**（不预先放宽棘轮）：

1. 先减字节，扩大余量（推荐）：`ui-components` 那 +1.6 KB 与 `useKeyboardInset`
   +0.6 KB 值得查是不是真必需；
2. 按实测 `--update` 重建基线 —— 棘轮会一次松 4.6 KB，之后拦不住同类回涨；
3. 什么都不做 —— 下次动首屏时必然再红一次。

> 一句话：**「首屏最贵」这条棘轮是对的，它抓到的正是「注释也随包下发」这种
> 平时没人注意的浪费。**
