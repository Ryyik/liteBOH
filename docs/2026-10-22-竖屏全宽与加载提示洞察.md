# 竖屏「全宽布局 + 加载提示」专项洞察（390×844）

- **日期**：2026-10-22 · **视口**：390×844 @2x（`isMobile + hasTouch`，浅色主题）
- **采集器**：`docs/demos/portrait-adaptive-audit.mjs`（本次新建，可复跑；**诊断脚本不是探针** —— 只出数不做断言）
- **产物**：`debug-screenshots/portrait-adaptive-2026-10-22/`（逐页 `-w-*` 宽度截图 / `-slow` 慢网截图 / `adaptive.json` 数值）
- **与 10-13 报告的分工**：那份查溢出/截断/对比度；这份只查两件事——**内容有没有吃满竖屏宽度**、**请求未回时用户看到什么**。

**方法**：每页两个场景。① 正常网络等数据落定后量 DOM（多列网格的实际列宽、并排卡片宽度、容器留白）；② **只延迟数据面**（`/rest/v1/**`、`/rpc/**` 挂起 15s，鉴权与静态资源放行），在导航后 4s 取快照，此时所有数据请求必然还在 pending —— 这个窗口里看到的 UI，就是用户弱网下真实看到的东西。

**已知局限（必须先说）**：登录态是 pinia 注入的伪会话，`getCurrentUser()` 返回 null。所以**依赖真实会话的页面（消息、概览、资产、礼物、咖啡馆）的慢网结论不可信**——它们显示空态是「没用户」而不是「没加载」。本报告只采信公开页（首页/论坛/商店/抽奖/活动/新闻/相册）与代码层证据。

## 二、竖屏全宽：该改哪里，哪里别乱改

### W1 ·【~~P1~~ → P3，2026-10-22 实测改判】**原结论是错的，别再按它施工**

原文写的是「内容铺满了，顶部却没有为导航岛留安全区 ⇒ 页面根容器要加 `padding-top`」。
**实测证伪。** 390×844 两场景对照（脚本 `docs/demos/w1-island-overlap.mjs`，可原样复跑；
截图落在 `debug-screenshots/w1-island/{first-visit,seen-before}.png`）：

| 场景 | 岛可见面 | 通知卡 | 「空间」tab | 岛下缘→tab | 岛下缘→封面 |
| --- | --- | --- | --- | --- | --- |
| 首次访问（弹引导） | 8→138（h=**130** 展开） | 66→131 | 82→122 | **−56px**（整个落在岛内） | **−3px** |
| 已看过引导 | 8→58（h=**50** 折叠） | 无 | 82→122 | **+24px** | **+77px** |

**折叠态（用户 99% 的时间）布局是健康的**：tabs 距岛下缘 24px、封面 77px，两张截图一对比就看得出来。
「被压住」只发生在**岛展开**时，而展开是 `GlobalNavStatusCard` 撑的 —— 也就是
`UserSpaceMain.vue:1617` 那条「顶部动态导航已启用」引导（与未读通知 `buildUnreadIslandMessage` 共用同一个出口）。
被当成「页面第一个内容块」的那行灰字，**就是这张通知卡的标题**。

三条连带订正（都别再按原文理解）：

1. **「uspace 五个 tab 全部复现」是探针 artifact。** `maybeShowGlobalNavOnboardingNotice` 有 localStorage 标记
   （`boh-global-nav-onboarding-v2-<uid>`），而探针每个场景都是新 browser context ⇒ 每个 tab 各弹一次。
   真实用户**一生只看一次**，5.6 秒后自动消失。
2. **不要给页面根容器接岛高。** 岛展开是 78→130px，页面跟着让位会在通知弹出的瞬间把内容推下 52px，
   比遮挡本身更糟（而且是每个 tab 都抖）。这条比原文「别用 margin-top」更重要 —— 原方案从根上就不该用。
3. **原文引的截图是动画中间帧。** `uspace-posts-w-top.png` 拍的是卡片淡入过程（tabs 还在卡上方露出一半、
   卡片标题被切），稳定态是通知卡**完整盖住** tabs（`debug-screenshots/w1-island/first-visit.png`）。

剩下真问题只有一个、且很轻：**岛展开的 5.6 秒里，通知卡与 tabs / 封面顶部（3px）同区重叠**。
可选修法：通知卡在展开时收窄到不与 tabs 同高；或直接接受浮层代价（iOS Dynamic Island 也这样）。
**不值得按 P1 排期** —— 它不会导致任何内容永久不可达。

### W2 ·【P2 → **已修** 2026-10-22】多 tab 一行塞满

| 位置 | 现状 | 实测/证据 |
| --- | --- | --- |
| 资产页二级 tab | 概览/装扮/积分/订阅/订单/抽奖/赞助 7 项刚好塞满 390，每项 ~50px | `uspace-assets-w-top.png`；10-13 报告 U4 已记「再增一项即溢出」 |
| admin 模块 tab | 密钥与模型/BOHAI 模型/AI 额度/审核模型/实验室模型，总宽 443px vs 容器 357px，第 5 项初始不可见 | 10-13 报告 A6（实测 `sw=443 / cw=357`） |
| 首页顶部 tab | 官方/最新/关注/新闻/活动/成员 6 项，每项 ~58px，可读但已到临界 | `home-w-top.png` |

共同点：**都用「等分一行 + 不 wrap」**。竖屏下正确解法是 `flex-wrap: wrap`（分区不多，两行成本低）或横滑 + 右缘渐隐提示；`overflow-x: auto` 而不给渐隐，用户根本不知道右边还有。

**修复落点（2026-10-22 `449cd343`）—— 分两半，这点最容易漏**：

- **全局 4 处** 写进 `styles/responsive.css` 的

- **另 4 处是 scoped**（`.g-api-key-summary` / `.lottery-metrics` / `.g-freemodels-summary` /

⚠️ **验证缺口**：这 9 处**没有做视觉验证** —— `/admin/data-management` 被权限守卫重定向回首页

但需要真实 admin 账号在 390 宽下过一眼才算收口。

390 视口减两侧留白 ≈ 358px，4 列含 gap 后每列 ~80px，7 列时 ~45px——「活跃 Key / 总调用 / 失败率」这类「数值 + 标签」卡片在这个宽度下必然折成两行或溢出。10-13 报告已证明 admin 确实被移动端访问（顶栏 32px 溢出、tab 行溢出都是竖屏巡检抓到的），所以这条不是「后台只在桌面用」可以搪塞的。

### 该改的边界：这些地方**不要**动

避免下一轮 AI 凭直觉「统一改成单列」，以下是实测合格、改了反而更差的：

- **弹窗体系**：`width: 100% + max-width 440~600px + 外层 16px padding`（`pa-modal` / `bind-prompt-sheet` / `edit-modal`）在 390 下实际宽 358px，已经是「近全宽卡片」的正确做法，不该改成 100vw。
- **商店商品区**：主视觉全宽 + 商品卡 2 列 174px（`shop-w-top.png`），两列是电商竖屏的通行密度，改单列会拉长滚动。
- **首页 feed / 新闻流 / 活动卡 / 生日页**：全宽单列，帖子卡、大图卡、按钮堆叠都吃满 390（`home-w-top.png`、`birthday-w-top.png`）。
- **journey 的 18/9/8 列网格**：`stratum-cut-face`、`memory-inventory` 是像素装饰色带，不是内容栅格，列宽 19~49px 是设计。
- **用户空间页头 3 列**：`user-center-page-header-inner` min 列 52px 看着窄，但那是「返回 / 标题 / 操作」的固定结构，塌成单列反而丢返回键位置——列数不用动。

## 三、加载提示：不是「有没有骨架」，是「有没有出口」

### 先说好消息（阴性结论，别重复排查）

公开页与详情页的骨架覆盖率是 **6/6 + 2/2**，慢网 4s 快照下的可见加载指示数量：

| 页面 | 指示器数 | 形态 |
| --- | --- | --- |
| 首页 feed | 52 | 卡片骨架（头像/标题/正文行） |
| 新闻 `/newsroom` | 48 | 日期/分类/标题块 |
| 相册 `/albums` | 18 | 网格骨架 |
| 商店 `/shop` | 12 | `product-skeleton` 卡 |
| 抽奖 `/lotteries` | 12 | 封面/标题/行 |
| 活动 `/activities` | 6 | 头部 + 卡片 |
| 新闻详情 `/news/1` | 7 | `ndp-skeleton` 全套 |
| 帖子详情 `/forum/post/1` | 29 | `detail-skeleton-block` + 「加载中…」 |

首屏另有 `App.vue` 的 `bootReady` 骨架与 `index.html` 内联兜底（10s/12s 两道超时），这条链路是完整的。

**`Messages/index.vue` 是这一块的标杆**：`withTaskTimeout` 包住每一步 + auth 竞态补拉一次 + `dataLoadedOnce` 保证「拿不到用户也必须落空态」+ 独立错误文案（L1994-2054）。要统一加载规范，照它抄。

### L1 ·【~~P1~~ → P3，2026-10-22 实测改判】**超时层五个月前就下沉了，报告漏看了它**

原文的判据是 `grep "withTaskTimeout" src/` 只命中 2 个文件，据此推断「其余页面全都没有超时」。
**这个推理错了：超时不在页面层，而在 client 层。**

`src/utils/supabase-client.js:53` 的 `timeoutFetch` 从 **2026-05-22** 就存在，通过
`createClient({ global: { fetch } })` 注入，全站所有请求都过它：

| 请求类型 | 超时 |
| --- | --- |
| `GET` / `HEAD` / `OPTIONS` | 8s |
| 其余（写 / `rpc` 的 POST） | 15s |
| `/functions/v1/**` | 180s（**SSE 早就单独放行了**，这正是原文担心的事，实际已解决） |

而且它正确合并了外部 `signal`（外部 abort 会传导进来）。旁路也查过了：`src/` 里没有直连
`.supabase.co` 的裸 fetch、没有第二个 client 实例 ⇒ **覆盖是完整的**。

实测（390×844，脚本 `docs/demos/request-timeout-audit.mjs`，`page.route` 挂起 `/rest/v1/**` 与 `/rpc/**`）：

| 页面 | 时间线 |
| --- | --- |
| `/shop` | 0.8s→8.1s 骨架 18 个 → **8.7s 骨架归零**，页面落静态兜底内容（超时准时，8s = 读超时） |
| `/lotteries` | 骨架 15 个 → **7.5s 落错误态**（「抽奖加载失败 / TypeError: Failed to fetch / 重试」） |

原文说「4s 快照时全部停在骨架」—— 4s 当然还在骨架，因为超时是 8s / 15s。**取样点早于超时点。**

#### 仍然成立、但级别低得多的两个小问题

1. **抽奖页等待偏长**：`rpc` 是 POST ⇒ 吃 15s 写超时，失败后还会走
   `getCommunityLotteriesFallback()`（又是一次 IP 请求）⇒ 真实弱网下 15s + 重试才落错误态，
   比 `/shop` 的 8s 差一截。读路径的 RPC 其实可以按读超时算。
2. **`/shop` 是「静默降级」**：8.7s 后显示的是静态兜底内容，**没有任何「数据可能不是最新」的提示**。
   比永远转圈好，但用户会以为看到的是实时价格。

⇒ 结论：**不需要「下沉超时」这个专项**（原文 §四 排第 1 的那条）。要做的话只剩上面两个打磨点，
加起来是一天的量，不是 P1。

### L2 ·【~~P2~~ 撤销，2026-10-22 复测】**量错了容器：那 2 列 96px 是卡片内部的缩略图**

原文说「骨架 2 列 96px，真实内容全宽单列 ⇒ 数据回来整页重排」。复测（390×844，骨架态 / 真实态各跑一次）发现：
被量到的「2 列 96px」是**卡片内部**的「缩略图 + 文字」两栏，不是列表被拆成两列。

| 页面 | 实际量到的 2 列 [96, 228] | 列表容器本身 |
| --- | --- | --- |
| `/lotteries` 骨架 | `article.community-lottery-card.skeleton-card` —— 卡片内「封面 96px + 内容」 | `.community-lottery-grid` 在 `@media (max-width:640px)` 已降 `1fr` ⇒ **单列** |
| `/newsroom` 真实 | `article.secondary-news-item.news-card` —— 卡片内「缩略图 96px + 文字」 | 父级 `.secondary-news-list` 单列，卡宽 358 |

四条硬证据，都指向「不存在重排」：

1. 两个被量的元素**都是 `<article>` 卡片本身**，不是列表容器；
2. 它们的 2 列是 `96px + 1fr` —— 正是「缩略图 + 正文」的卡片内部布局，两边一模一样；
3. 抽奖页的骨架（`index.vue:132`）与真实历史列表（`index.vue:418`）**用的是同一个类**
   `.community-lottery-grid`，列数不可能不同；
4. 新闻页的 `secondary-news-item` **只出现在真实列表**（`Newsroom/index.vue:162`），骨架根本不用它。

⇒ 骨架与真实内容的栅格本来就是同一套，**不需要改**。原文把「卡片内部的缩略图列」当成了
「骨架的列表列数」，这是一个量错容器的误判。

### L3 ·【~~P3~~ 撤销，2026-10-22 复测】**生日页有加载态，`--` 是「未设置」的正确语义**

原文的判据只有一句 `if (!celebrationDate.value) return '--'`，据此推断「用 `--` 冒充加载态」。
复测两种网络，结论相反：

| 场景 | 可见骨架 | 首屏文本 |
| --- | --- | --- |
| 正常网络 | 0 | `… 距离 -- 还有 -- 天 许个愿 看祝福 …` |
| 数据面挂起 | **44** | `… Make A Wish 点亮蜡烛 点击许愿 …`（倒计时整块不渲染） |

⇒ **数据未到位时页面显示满屏骨架（44 个元素），不是 `--`**。
`--` 只出现在「数据已到位、但这个账号没填生日」时 —— 那正是正确语义，不是冒充加载态
（截图 `debug-screenshots/l34-_birthday-hang-0.png` 能看到成片的灰条骨架）。
