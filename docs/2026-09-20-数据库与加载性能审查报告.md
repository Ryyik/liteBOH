## 0. 结论速览

> **落地状态（2026-09-20 已 push 并验证）**：迁移 `2026092002_cron_job_run_details_retention`、`2026092003_hot_path_fk_indexes`、`2026092004_drop_redundant_indexes` 已应用。实测：`cron.job_run_details` 176,828 行 → 10,094 行；`VACUUM FULL` 后 cron schema 32MB → 2.1MB，**全库 59MB → 29MB（−51%）**；5 条外键索引就位、12 条冗余索引删除、10 条覆盖者全部健在。§1.1 与 §2.3 据此视为已闭环；**瑞一颗已明确不动**的：消息中心轮询、会话心跳、首页立绘。

## 1. 现有配置问题

### 1.1 【P0】`cron.job_run_details` 占全库 53%

| 指标 | 值 |
|---|---|
| 行数 | 176,828 |
| 体积 | **31 MB** |
| 时间跨度 | 2026-05-08 → 2026-09-20（无任何清理） |
| 全库总大小 | 59 MB |
| `public` schema | 8.3 MB |
| `cron` schema | **32 MB** |

`cron` schema 比承载全部业务数据的 `public` 大 **3.9 倍**。成因是 4 个 pg_cron 任务持续写入运行明细，其中 `execute_due_lottery_draws_every_minute`（`* * * * *`）每天产生 1440 行、约 135 天从未回收。

**修复**：新增每日清理任务（保留 7 天足够排障）：

```sql
select cron.schedule(
  'cleanup_cron_job_run_details_daily',
  '10 4 * * *',
  $$delete from cron.job_run_details where start_time < now() - interval '7 days';$$
);
```

预期立即释放约 **31 MB**（占全库 53%），并把每次 cron 运行后的 `update cron.job_run_details` 索引维护成本一并降下来。

### 1.2 【P0→已降级为 P2】Realtime WAL 轮询占 73.9%，但**收窄发布表几乎省不到**

> **本节结论经过两次修正，请以现在这版为准。** 初版写的「收窄发布表 → 数据库执行时间 −70% 量级」是**未经验证的推断，已被实测推翻**。

`pg_stat_statements` 按总执行时间排序，前 3 名全是 Realtime 的 WAL 轮询：

| 排名 | 调用次数 | 累计执行时间 | 占比 | 平均 | 返回行数 |
|---|---|---|---|---|---|
| 1 | 2,780,652 | 13,048 s | **40.9%** | 4.7 ms | 22（旧版函数，无兜底行） |
| 2 | 1,117,713 | 6,193 s | **19.4%** | 5.5 ms | 1,117,720 |
| 3 | 825,605 | 4,326 s | **13.6%** | 5.2 ms | 826,852 |
| — | 合计 4,723,970 | **23,567 s** | **73.9%** | — | — |

三条语句的完整文本都指向同一个函数 `realtime.list_changes($1,$2,$3,$4)`（前两条 Select 列表不同 → 第 1 条是**旧版 Realtime 的函数形态**，说明这段统计跨越了一次 Realtime 升级）。

#### 机制上，收窄是「真的有效」——但收益不在这里

读到 `realtime.list_changes` 定义后确认：**publication 的表列表会被拼成 wal2json 的 `add-tables` 参数下推到逻辑解码插件**，不是应用层过滤：

```sql
WITH pub AS (
  SELECT ..., string_agg(
      realtime.quote_wal2json(format('%I.%I', schemaname, tablename)::regclass), ','
    ) AS w2j_add_tables
  FROM pg_publication pp LEFT JOIN pg_publication_tables ppt ON pp.pubname = ppt.pubname
  WHERE pp.pubname = publication GROUP BY pp.pubname
), w2j AS MATERIALIZED (
  SELECT x.*, pub.w2j_add_tables FROM pub,
    pg_logical_slot_get_changes(slot_name, null, max_changes,
      ..., 'add-tables', pub.w2j_add_tables) x
)
```

所以收窄 `posts`/`likes`/`comments` 确实能让 wal2json 少解码这三张表。**但问题是没有东西可解码**：

| 已发布表 | ins | upd | del | 累计变更 | 占已发布变更 |
|---|---|---|---|---|---|
| `posts` | 235 | 760 | 52 | 1,047 | 44.2% |
| `notifications` | 373 | 333 | 29 | 735 | 31.1% |
| `likes` | 276 | 0 | 40 | 316 | 13.4% |
| `comments` | 184 | 47 | 38 | 269 | 11.4% |
| **合计** | | | | **2,367** | 100% |

**四张表 135 天加起来只有 2,367 条变更（≈17 条/天）。** 4,723,970 次轮询对应 2,367 条变更——99.95% 的轮询是空转。因此这 23,567 s 几乎全是**轮询固定成本**（WAL 顺序扫描 + 每次调用都要重算的 `pub` CTE，其中每张发布表一次 `format(...)::regclass` 目录查找），**与发布表宽度基本无关**。

再把量级换算清楚：**23,567 s ÷ 135 天 ≈ 175 秒 CPU/天**。它跑在 Realtime 自己的连接上，不阻塞用户请求。

#### 修正后的结论

| 动作 | 功能影响 | 性能影响 | 建议 |
|---|---|---|---|
| 从发布表移除 `posts`/`likes`/`comments` | **零**（见下方订阅面核查） | 省掉 `pub` CTE 里 3 次 `::regclass` 目录查找/次 —— 相对 4.7ms 是小头 | **可以做，但理由是语义整洁，不是性能** |
| 整项目关闭 Realtime | 影响「消息中心打开时的新消息实时推送」 | **唯一能让 73.9% 归零的杠杆** | 产品决策，见下 |

#### 订阅面核查（决定「功能影响为零」的依据）

全仓 `postgres_changes` 只有 **2 处**，且都在 `notifications` 上：

| 位置 | 订阅内容 | 状态 |
|---|---|---|
| `src/utils/api/notifications-api.js:451 subscribeToNotifications` | `notifications` / `INSERT` / `filter: recipient_id=eq.<uid>` | **死代码** —— 全仓仅此一处出现（含定义），未被子组件 import，也未经 `utils/auth.js:42-54` 再导出 |
| `src/views/user-center/Messages/index.vue:1104` | `notifications` / `*` / `filter: recipient_id=eq.<uid>` | **唯一活的消费者** |

另外 `supabase/functions/`、`public/`、`cloudflare/`、`android-twa/`、`scripts/` 下**均无** `postgres_changes` / `.channel(` 引用。

**因此 `posts` / `likes` / `comments` 从发布表移除，不存在任何订阅者会受影响。**（初版报告里「需先核对 Realtime 面板在线频道名」这条保守提示，现已被代码级证据取代。）

#### 真正值得考虑的那一步

Realtime 现在的唯一价值是「消息中心页面打开时的新消息即时到达」。而 `src/components/UnifiedNavbar/index.vue:1100` 已经有 **60 秒轮询**兜底（`setInterval(checkUnreadMessages, 60000)`）。若产品上接受「新通知最多晚 60 秒」：

- 关闭 Realtime → 那 73.9% 与每客户端一条长连接一起消失（连接数当前 30/60，长连接占比可观）；
- 代价：从「消息中心」移除 `startRealtimeChannels`（`Messages/index.vue:1096`，3 个调用点：`1175` / `1294` / `1432`）。

**这是产品决策，不是性能决策** —— 只有瑞一颗能拍。

#### 实施注意（已核实，无隐性风险）

- **不需要重建复制槽**：`add-tables` 是每次调用现算的，不烧进槽定义里。
- **改动立即生效**：`pub` CTE 每次调用都重查 `pg_publication_tables`，Realtime 服务端没有需要重启的缓存。
- **一 SQL 可回滚**：`alter publication supabase_realtime add table public.<t>;`
- 复制槽是**按需创建/销毁**的（查询时 10 分钟前有 2 个 active 槽，随后再查为空），因此不存在「槽滞后 → WAL 堆积撑爆磁盘」的风险。
- 唯一要留意的：将来若要做「实时新帖 / 实时点赞」，需记得把表加回去 → **在迁移文件里写注释**。

```sql
alter publication supabase_realtime drop table public.posts;
alter publication supabase_realtime drop table public.likes;
alter publication supabase_realtime drop table public.comments;
```

### 1.3 【P1】RLS 策略里的 `EXISTS (SELECT ... FROM profiles)` 造成 102 万次全表扫描

| 表 | live 行数 | seq_scan | seq/行 | seq_tup_read |
|---|---|---|---|---|
| `profiles` | 32 | **1,020,095** | 31,878 | 17,651,154 |
| `likes` | 229 | 207,453 | 906 | 15,585,531 |
| `comments` | 144 | 141,482 | 983 | 8,354,241 |
| `posts` | 136 | 77,870 | 573 | 3,888,373 |

32 行的表被顺序扫描 102 万次，根因不是"缺索引"，而是**策略把子查询写在了 USING / WITH CHECK 里**：

```sql
-- user_gifts / products / profiles / birthday_* / freemodels / lab_ai_model_configs
-- forum_weekly_reports ... 至少 10 张表共用同一形态
EXISTS (SELECT 1 FROM profiles WHERE profiles.id = auth.uid() AND profiles.role = 'admin')
```

这类策略**对结果集的每一行都要重新求值一次**（`current_user_is_admin()` 虽已存在，但只有 `profiles_admin_update` 用了它，其余仍是裸子查询）。虽然单次扫描只有 32 行、绝对耗时不高（`idx_profiles_role_join_date` 3,018,636 次扫描正是这批策略的产物），但在 `likes`/`comments` 这类逐行调用下会被放大 15 倍量级。

**修复**（两步，先易后难）：

1. 把裸子查询统一替换为已有的 `STABLE SECURITY DEFINER` 函数，让规划器能在语句级缓存结果：

```sql
-- 现状抽样（需逐表替换）
EXISTS (SELECT 1 FROM profiles WHERE profiles.id = auth.uid() AND profiles.role = 'admin')
-- 改为
public.current_user_is_admin()
```

2. 存量策略可脚本化改写：

```sql
-- 先枚举，再逐条改写（示例：只读筛选）
select c.relname as tbl, p.polname,
       pg_get_expr(p.polqual, p.polrelid) as using_expr
from pg_policy p
join pg_class c on c.oid = p.polrelid
join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public'
  and pg_get_expr(p.polqual, p.polrelid) ilike '%from profiles%';
```

### 1.5 【P1】4 张表开启了 RLS 但零策略 = 只有 service_role 能访问

```
_rate_limits, forum_post_submissions, lottery_pity_backfill_runs, subscription_plan_prices
```

`subscription_plan_prices` 值得单独确认：**前端 `src/` 全仓没有任何引用**，且 RLS 零策略。如果定价确实只经服务端 RPC 下发，这是设计正确但遗留了死表；如果哪天后端忘了走 RPC，客户端会拿到空结果且**不报错**（RLS 拒绝返回空集而非错误）——这正是「半截商业化」的典型形态。建议二选一：要么补只读策略（`using (true)` + `grant select to anon, authenticated`），要么把表删掉。

### 1.6 【P2】`execute_due_lottery_draws` 每分钟空转 15.4ms

| 指标 | 值 |
|---|---|
| 调用次数 | 176,708（`* * * * *`） |
| 累计执行时间 | 2,715 s |
| 占比 | 8.5% |
| 平均 | **15.4 ms** |

绝大多数执行没有任何到期抽奖可开，但函数体仍要走完 plpgsql 主体。表结构层面这解释了另一个现象：`lottery_draw_logs` 有 219,192 次 seq_scan 但 `idx_scan = 0`、且全表只有 7 行——**这不是索引问题，是每分钟一次的定时任务在该表上做探测，7 行的表选顺序扫描完全正确**。

**修复**：在函数开头加一个走 `idx_lotteries_draw_at`（已存在且 scans=3,981）的早退判断，无到期任务时直接 `return`：

```sql
if not exists (
  select 1 from public.lotteries
  where status = 'open' and draw_at is not null and draw_at <= now()
  limit 1
) then
  return;
end if;
```

### 1.7 【P1】会话心跳每 2 分钟直写 `profiles`，是业务侧第一大数据库开销

| 指标 | 值 |
|---|---|
| RPC | `update_last_active_at`（SECURITY DEFINER） |
| 调用次数 | **69,203** |
| 累计执行时间 | **781 s** |
| 平均 | **11.3 ms** |
| 调用方 | `src/stores/auth.ts:351` → `setInterval(..., SESSION_HEARTBEAT_INTERVAL_MS)`，`SESSION_HEARTBEAT_INTERVAL_MS = 2 * 60 * 1000`（`auth.ts:12`） |

前端已经做了防抖（函数内 `last_active_at < now() - interval '2 minutes'` 才真正 UPDATE），但**语句本身仍然每次执行**，而 `profiles` 上挂着 5 个触发器（`on_username_updated`、`trg_profiles_enforce_avatar_frame_owned`、`trg_profiles_enforce_points_card_cats_unlock`、`trg_profiles_enforce_points_card_custom_preset`、`trg_profiles_sync_creator_fields`）和 15 个索引。

11.3 ms 对单行 UPDATE 是异常高的数字。三个可叠加的改法（按性价比排序）：

1. **前端把判定前移**：`userInfo.lastActiveAt` 本地已有，2 分钟内不必发起 RPC（省掉全部 69,203 次往返）。
2. **把心跳降频到 5–10 分钟**：活跃时间本身是弱一致指标，2 分钟精度没有产品价值。
3. **削掉触发器**：5 个触发器里 4 个是 `UPDATE OF <列>` 形式（理论上不会在 `last_active_at` 更新时点火），但 `on_username_updated` 是 `AFTER UPDATE` 无列限定形式，**每次心跳都会执行 `sync_username_change()`**。建议改成 `AFTER UPDATE OF username`。

## 2. 建议添加的索引

### 2.1 【P0】高频查询 + 缺索引（建议立即加）

| # | 表 | 建议索引 | 依据 |
|---|---|---|---|
| 1 | `notifications` | `(post_id) where post_id is not null` | 外键 `notifications_post_id_fkey` 无前导索引；删帖级联/「该帖相关通知」全表扫 |
| 2 | `notifications` | `(comment_id) where comment_id is not null` | 同上，`notifications_comment_id_fkey` |
| 3 | `notifications` | `(sender_id)` | `notifications_sender_profiles_fkey`；`notifications` 是应用最热表（343 行 / 208K 索引） |
| 4 | `comment_likes` | `(user_id)` | `comment_likes` 只有 `(comment_id, user_id)` 与 pkey；「我点赞过的评论」与 `user_id` 级联删除均无索引 |
| 5 | `forum_post_images` | `(cloud_entry_id)` | `forum_post_images_cloud_entry_id_fkey`，清理 Cloudinary 待删资源时用 |
| 6 | `user_follows` | 核对 `(follower_id)` / `(following_id)` | 前端 `.eq('follower_id')` ×4、`.eq('following_id')` ×4、`.in()` 各 1；需确认现有索引是否已覆盖 |

```sql
  on public.notifications (comment_id) where comment_id is not null;
```

### 2.2 【P1】其余 46 个无前导索引外键（按业务热度分组，批量处理）

严格口径下共 **52 个**外键无前导索引列。除 2.1 的 6 个外，其余集中在抽奖（`lottery_*` 约 18 个）、活动（`activity_*` / `activity_rewards` 4 个）、AI 记忆（`boh_ai_*` 3 个）与管理员审计列（`created_by` / `updated_by` / `published_by`，约 14 个）。

判定建议：

- **审计列（`*_created_by` / `*_updated_by` / `*_published_by`）**：只在管理后台按人筛审计记录时用，当前 `home_heroes` / `lotteries` / `api_key_vault` 都是个位数或十位数行 → **不加**，加了反成新的未使用索引。
- **抽奖域**：`lottery_entries` / `lottery_draw_logs` 已有业务索引；剩下的 `lottery_notification_jobs` / `lottery_pity_events` / `lottery_winner_fulfillments` 逐个按查询真实写法决定，不要按外键数量一次性补齐。

### 3.1 四场景实测基线（`scripts/perf-probe.mjs`）

### 3.2 【P0】瓶颈一：首屏 20 张立绘同刻并发，把 LCP 顶到 7.12s

`scripts/probe-lcp.mjs` 在 1.6 Mbps / RTT 150ms 下的实测：

```

  2616  SPAN<nav-logo-text>              文本：导航栏 logo

```

```
  img    860 KB  (69.5%)
  script 285 KB  (23.0%)
  link    68 KB  ( 5.5%)
```

**根因（已定位到源码）**：`src/views/Home/components/ShowcaseBookHero.vue`

```html
<img
  :src="char.resolvedSrc"
  :loading="priority && i < 2 ? 'eager' : 'lazy'"   <!-- 已有 lazy，但没起作用 -->
  decoding="async"
>
```

代码**写了** `loading="lazy"`，但实测 **20 张图全部在 t≈3362–3363ms 同一毫秒内发起请求**。原因是这些立绘在 `.showcase-cast` 里以绝对定位 + 错落布局铺开，浏览器判定它们都落在懒加载的视口扩展阈值内，于是被一并唤醒；在 HTTP/1.1 的 6 连接上限下互相排队，最慢一张耗时 **3,810ms**（`end_style.webp`），单张最大 `blockschool-*.webp` **119.8 KB / 2,528ms**。

**这不是"加个 lazy 就好了"的问题，需要真正缩减首屏图片集合**：

1. 首屏只渲染 3–4 张（`v-for` 上 `v-if="i < 4"`），其余在 `requestIdleCallback` 或滚动到再补。
2. 首屏那张 `fetchpriority="high"`，其余 `fetchpriority="low"`，把带宽让给 LCP。
3. 立绘按展示尺寸重新出图——当前单张平均 43 KB，最大 120 KB，而它们在页面上是环绕装饰尺寸。

预期：把首屏 img 传输从 860 KB 压到 **约 150 KB**，1.6 Mbps 下 LCP 有望进入 **2.5–3s** 区间。

### 3.3 【P0】瓶颈二：路由级 JS chunk 既不在预缓存、也没有运行时缓存

已核实 `dist-check/sw.js` 的预缓存清单只有 17 条：

```
index.html
static/js/{vue-vendor, vue-utils-vendor, ui-sanitize, ui-icons, ui-components,
           supabase-vendor, state-vendor, auth-store, app-<hash>}.js   ← 9 个壳 chunk
static/css/{ui-components, index}-<hash>.css                          ← 2 个壳样式
icons/icon-{192,512,maskable-512,monochrome-512}.png + manifest.webmanifest
```

而 `vite.config.js` 的 `runtimeCaching` 只有 4 条规则：`/static/css/*.css`（CacheFirst）、Supabase Storage 公开对象、Cloudinary/`cdn.blockofhome.cn` 图片、NSFW 模型 vendor JS。**没有任何一条覆盖 `/static/js/*.js` 中的路由 chunk。**

后果：访问过的 `BOHAIMain`（**132.9 KB gzip**）、`DataAdmin`（**117.9 KB gzip**）、`ForumMain`（39.5 KB）等路由 chunk，第二次进入只依赖 GitHub Pages 的 HTTP 缓存（`public/_headers` 在线上不生效，固定 `max-age=600`）。**超过 10 分钟再进同一路由 = 完整重下**。场景 D 二次访问仍有 227.9 KB 网络传输，与此一致。

**修复**（与已有 CSS 规则同构，注意 hash 文件名内容不可变）：

```js
{
  urlPattern: /\/static\/js\/(?!app-)[A-Za-z0-9_-]+-[A-Za-z0-9_-]{8}\.js$/i,
  handler: 'CacheFirst',
  options: {
    cacheName: 'route-js',
    expiration: { maxEntries: 160, maxAgeSeconds: 60 * 60 * 24 * 30 },
    cacheableResponse: { statuses: [0, 200] },
  },
}
```

> ⚠️ 必须排除 `app-<hash>.js`（入口在预缓存里，重复管理会产生两处真相源）；且需与 `scripts/check-shell-precache.mjs` 的断言联动——**加这条规则会改变「路由资源归宿」的判定，需要同步扩展断言**，否则门禁会认为路由 JS 无归宿而失败。

### 3.4 【P1】瓶颈三：登录弹窗 CSS 迟到，受保护路由存在 400ms 裸样式窗口

场景 B 实测：`login-modal-*.css` 的请求窗口是 **2140ms → 2536ms**，而路由 DCL 是 2129ms——**模态 DOM 先于样式 ~400ms 就绪**。

成因在 `src/main.js`：`login-modal.css` 被放在 `deferredGlobalStyleLoaders`，由 `initImageOptimizer({ onReady: scheduleDeferredGlobalStyles })` → `requestIdleCallback(timeout: 2500)` 触发。它同时是**弹窗壳层样式的唯一来源**。

本次采样恰好没抓到"有 DOM 无样式"的帧（`遮罩首次出现 3653ms` 时 `stylesheets=15` 已 OK），属于**时序巧合而非机制保证**：一旦网络或设备更慢、或 `image-optimizer` 就绪更早，就会出现裸样式遮罩。

**修复**：把 `login-modal.css` 移出 `deferredGlobalStyleLoaders`，改为入口静态 import（并入壳 CSS）。代价是首屏 CSS +约 3.6 KB gzip，换来顺序确定性。

### 3.5 【P1】瓶颈四：NSFW 模型 3.6 MB，全靠"永远别在首屏触发"

| 项 | 值 |
|---|---|
| `nsfw-weights-*.js` | **raw 3,600,092 B / gzip 2,536,661 B** |
| `tfjs-vendor-*.js` | 269.1 KB gzip |

这是产物里**唯一的 MB 级资源**。目前防护是双重的：既不在 `globPatterns`（不进预缓存），又单列了 `runtimeCaching` 的 `nsfw-model-vendor`（CacheFirst / 90 天）。加载入口在 `src/utils/forum-image-moderation.js:67`，走 `await Promise.all([import('@tensorflow/tfjs'), import('nsfwjs')])`，且上游还有云端视觉模型优先（`forum-images-api.js:41` 注释「云端优先审核管线，本地 nsfwjs 兜底按需懒加载」）。

**结论：现状设计正确，但存在一个必须守住的断言——任何让 `import('nsfwjs')` 变成静态 import 或进入首屏依赖链的改动，都会让首屏多出 2.5 MB。** 建议在 `check-first-paint.mjs` 里加一条断言：`nsfw-weights` / `tfjs-vendor` / `nsfw-vendor` 不得出现在 `app-<hash>.js` 的静态 import 闭包内。

### 3.7 【P2】瓶颈六：全站没有 `fetchpriority`，只有 1 处 `decoding="async"` 习惯性使用

## 4. 预加载与懒加载的适用点

### 4.1 预加载（Preload / Prefetch / Preconnect）

| 优先级 | 位置 | 动作 | 依据 |
|---|---|---|---|
| **P0** | 首页英雄区首图 | 首屏渲染的 3–4 张立绘加 `fetchpriority="high"`；其余 `low` | 3.2：20 张同刻并发是 LCP 主因 |
| **P0** | 首页英雄区图片 URL 已知瞬间 | 数据到达后、`<img>` 挂载前，用 `link rel="preload" as="image"` 提前挂 | `Home/index.vue` 有 `heroLoading` 门闩：**图片要等 DB 查询回来才开始下载**，串行了两段 RTT |
| **P1** | `vite.config.js` `runtimeCaching` | 新增 `/static/js/*.js` CacheFirst（排除 `app-`） | 3.3：路由 JS 无任何缓存归宿 |
| **P1** | 登录弹窗样式 | `login-modal.css` 从 idle 移入入口 CSS（或改为 `<link rel="preload" as="style">`） | 3.4：唯一来源却迟到 2.1s |
| **P2** | 导航栏 hover | 对 `router.resolve()` 命中的路由 chunk 做 `import()` 预热（30–80ms 延迟触发，避免误触） | 场景 D 切路由 163ms，其中大头是 chunk 下载；论坛→帖子详情是最短路径 |
| **P2** | 首页 → 论坛 / 商城 | 首屏稳定后（`requestIdleCallback`）预热 1–2 个最可能的下一跳 chunk | `ForumMain` 39.5 KB + 43.5 KB CSS，预热收益明确 |
| **已正确** | `index.html` | `preconnect` 到 `cdn.blockofhome.cn` / Supabase / `agent.wzbc.edu.cn` | 保持，勿删 |
| **已正确** | `index.html` | 9 个壳 chunk 的 `modulepreload` | 保持 |
| **明确不要** | `DataAdmin`、`nsfw-weights`、`docx-vendor`、`pptx-vendor`、`html2canvas` | 严禁进入任何预加载路径 | 3.5 / 3.6；`DataAdmin` 209 KB 只对管理员可见 |

> ⚠️ **不要给「已经进了预缓存的壳 chunk」再加 `prefetch`**——预缓存已经保证零网络，加 `prefetch` 反而制造第二次请求。

### 4.3 需要保持的既有防护（改动时不要破坏）

以下几条是既有审计已经验收入库的红线，本次审查未发现回退，但改动相邻代码时极易破坏：

1. **入口 CSS 必须保持 render-blocking `<link>`** —— 禁动态 import、禁外置骨架、禁裸删 `globPatterns` 里的 CSS。
2. **预缓存收窄的两半是一对**：`manifestTransforms` 移出路由 CSS + `runtimeCaching` 的 `/static/css/` CacheFirst，删任一半都会「有 HTML 无样式」，由 `check:shell-precache` 断言 A/C 守住。**3.3 新增 JS 规则时需同步扩展该断言。**
3. **`body{overflow-x:hidden}` 是全局的**，任何依赖 `position: sticky` 的新区块都会失效（sticky 的修法是给 `html` 加页级类）。
4. **`boundaryKey` 必须挂 `route.path`**，挂 `fullPath` 会让「同页改 query」重建整棵页面树、路由级 KeepAlive 失效（实测切回 44ms → 19ms、请求 14–28 → 0）。
5. **`public/_headers` 在线上完全不生效**（GitHub Pages + CNAME 固定 `max-age=600`）——这是 3.3 问题能成立的前提，别指望改它来解决缓存。

## 7. 结论边界（本次未能证实 / 需人工确认的点）

1. ~~**Realtime 发布表的实际依赖**：代码里只找到 2 个 `.channel()` 订阅，但不能排除通过封装间接订阅 `posts`/`likes`/`comments` 的路径。~~
   **已结案（第二版补充核查）**：全仓 `postgres_changes` 仅 2 处且都在 `notifications`；其中 `notifications-api.js:451` 是死代码（零引用、也未经 `auth.js` 再导出），唯一活的消费者是消息中心。`supabase/functions`、`public`、`cloudflare`、`android-twa`、`scripts` 均无引用。→ 移除 `posts`/`likes`/`comments` 无订阅者受影响。
   **仍未证实的部分**：无法做「收窄前后解码耗时对比」的因果实验——`pg_logical_slot_peek_changes` 被拒（`42501 Only roles with the REPLICATION attribute may use replication slots`），Management API 角色无 REPLICATION 权限。因此 1.2 的「性能≈0」结论是用**已发布表累计写量仅 2,367 条**做的替代推断，不是直接测量。若将来能拿到 REPLICATION 角色，建议实测一次坐实。

3. **`lottery_scheduler_logs` RPC mean 1343ms**（32 次调用 / 43s）：该函数在远端不存在同名 `pg_proc`（应为前端调用名与服务端函数名不一致或已重命名），未能取到定义。属抽奖后台专用，**建议单独排查**。
4. **`pg_timezone_names` 1435 次 / 平均 604.9ms / 累计 868s（占 2.7%）**：来源不明，不像应用代码所发（应用无此类调用），怀疑来自 Supabase Dashboard / CLI / 连接池探活。**建议确认后再决定是否处理。**
5. **外键缺口 52 个中的审计列**：本次给出了「不建议加」的判断依据（表行数小），但这个判断依赖当前数据量；当 `home_heroes_revisions` 这类表长到万级时需重新评估。
