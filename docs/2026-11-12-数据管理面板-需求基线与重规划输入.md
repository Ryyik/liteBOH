## 0. 一页结论

### 0.1 三个判断

**判断一：这个面板的问题不是"页面不好看"，是"它同时在承担四种不同的产品"。**

它现在既是数据台账（看/改行）、又是配置台（模型、额度、密钥）、又是可视化编辑器宿主（商城/资讯/首页/开屏/头像框）、又是运营发射台（发积分、发订阅、代报名、批量通知）。这四件事的操作节奏、风险等级、使用者完全不同，却被塞进同一套"侧栏 + 模块页签 + 表格"的壳里。所以再怎么调间距、砍列数，都只能缓解，不能解决。

**v2 补充：它其实是第五种产品——"维护台"，而且这才是你的主场景。** 你的清单（用户、商品、积分、礼物、订单、登录、新闻、帖子）全部是**排障与日常事务**，不是数据浏览。维护工作的轴是"人"，面板的轴是"表"，两者错位（§3.0）——这是比"四种产品混在一起"更根本的一层。

**判断二："由谁管理"目前只有一个答案：一个超级管理员。**

角色枚举里有 `admin / moderator / user`，界面也按角色做了置灰逻辑，但路由门禁是 `role === 'admin'` 严格判定（`src/stores/auth.ts:212`），`moderator` 进不了任何后台路由。也就是说：RBAC 是一套**已写好但从未生效**的规则。

**v2 补充（已确认）：这不是"暂时只有一个人"，而是"设计目标就是一个人"。** 站长本人包办全部维护，没有客服、没有版主、不打算分工。因此：

- `moderator` 那套白名单不是"未来扩展"，是**当前就该删掉的死代码**（它每天都在误导读代码的人，也让"按角色置灰"永远测不到）；
- 所有"双人复核""最小权限""审批流"的设计在此项目上都是过度设计；
- 真正需要防的不是"另一个管理员乱来"，而是**"我在手机上误触了一个不可逆操作"**。安全设计的目标要从"权限分配"转向"误操作防护 + 可回滚 + 留痕"。

**判断三：入口的"可达性"和"唯一性"是当前最高性价比的改造点，但它依赖一个 IA 决策。**

同一件事今天有 1–3 个入口（商城 3 个、资讯 2 个、生日 2 个），另有两个后台页只能手敲地址。这些不是"顺手补个链接"能解决的——它们源自"模块按部门分、页面按实现分"这个根因。

## 1. 名词与边界

### 1.1 本文的"站点"指什么

**站点 = 一个有独立前台路由、独立数据域、独立运营节奏的业务面。**

不是"域名"，也不是"Supabase 项目"。按这个定义，本产品当前有 13 个站点（§2.3 表一）。

### 1.2 四种"管理入口形态"（这是混乱的结构性来源）

| 形态 | 技术特征 | 例子 | 交互模型 |
| --- | --- | --- | --- |
| A. 表型页签 | `dataConfig[tabId]` 有 `table`，走通用列表/编辑 | 用户管理、论坛帖子、商品管理 | 表格 + 行内编辑 + 抽屉 |
| B. 页面型页签 | `tabs[].type === 'page'`，但仍挂在模块的 `tabIds` 里 | 积分发放、订阅发放、帮人报名、保底中心、密钥与模型、AI 额度 | 独立表单页，外观像 tab，实际是另一个产品 |
| C. 独立控制台路由 | 独立 `path`，不在 `tabIds` 里，靠 `ROUTE_MAP` 跳转 | 商城装修、就地编辑、资讯编辑、首页装修、开屏管理、头像框 | 全屏可视化编辑器 |
| D. 占位 section | `PLACEHOLDER_ADMIN_SECTIONS`（`media` / `settings`） | 「媒体资源」「网站设置」 | 实际是**卡片跳转页**，不是设置页 |

> 关键事实：B 和 C 加起来 12 个入口，全部寄生在"数据管理面板"这个壳下，但它们的操作对象不是"行"，而是"一次动作"或"一份配置"。用同一套导航描述它们，必然出现"名字像数据、点开是表单"的错位。

### 1.3 本文不覆盖

- 前台业务逻辑与视觉（首页、论坛、商城的前台体验）
- 数据库 schema 重设计（只在"必须动 RLS"的地方标注）
- 具体组件实现与排期

### 2.4 写路径现状（三种并存）

| 路径 | 用在哪 | 特点 | 风险 |
| --- | --- | --- | --- |
| 通用表格写（`data-admin-table-api`） | 大多数表型页签 | 简单，直接 `update/insert` | 无业务校验、无审计强制、失败提示由页面拼 |
| 专用 RPC | 用户敏感列、积分/订阅发放、代报名、抽奖、批量、导出 | 有服务端校验与白名单 | 一次失败可能连坐（历史上出过 42501 静默失败） |
| `splitProfileWritePayload` 双通道 | 仅 `users` / `points` | 敏感列走 RPC、其余走表 | 回读列不含 shipping_*，保存后列表仍显示旧值（已知、非 bug） |

> 同一类"保存"，用户在界面上看到的是同一个按钮，背后是三种语义、三种错误文案、三种审计覆盖。这是"操作不方便"的深层原因之一。

## 3. 核心管理诉求

> 下面 6 条是**我从现状反推的诉求**，按"问题 → 目标 → 可测指标"写。优先级是我给的假设，**需要你确认或改序**（§8 Q2）。

### 3.0 先看清：维护型工作的真实形状（v2 新增）

站长给的清单是：**用户、商品、积分、礼物、订单、登录问题、新闻、帖子**，v3 补入**抽奖**（"也蛮频繁的"）。

这份清单不是"数据分类"，是**工单类型**。把它们翻译成动作，序列几乎是固定的：

```
有人来报  →  定位这个人  →  看他的账号状态 / 积分 / 订单 / 礼物 / 帖子
         →  判断是数据错、权限错、还是流程卡住  →  处置  →  留痕
```

第 2、3 步是全部成本所在，而现在的面板**恰好在这两步上是断的**：

| 环节 | 现状 | 证据 |
| --- | --- | --- |
| 定位这个人 | 可以：`users` / `points` 都按 `username` 可搜 | `实测` `TAB_SEARCH_FIELDS` |
| 看他的订单 | 订单表搜索字段是 `user_id`（UUID）、`order_no`、`contact_value`，**不认用户名** | `实测` 同上 |
| 看他的积分流水 | 搜索字段是 `user_id`、`reason`、`remark`、`batch_id`，**不认用户名** | `实测` 同上 |
| 看他的礼物 | 搜索字段是 `user_id`、`gift_no`、`gift_content`，**不认用户名** | `实测` 同上 |
| 看他的帖子 | 可以：`forum` 有 `author_username` | `实测` 同上 |
| 看他的登录状态 | **没有任何工具**（详见 C17） | `实测` |

所以真实操作是：搜到人 → 复制 UUID → 切到积分流水 → 粘贴 → 切到订单 → 粘贴 → 切到礼物 → 粘贴。**一次报障至少 4 次切页、3 次复制粘贴；实际来回核对时常到 6 次上下。**

结论：IA 的第一性问题不是"按站点还是按任务"，而是——

> **以人为轴，还是以表为轴。**

面板现在是"以表为轴"（表 → 行 → 字段）。维护工作是"以人为轴"（人 → 他的各种记录 → 处置）。这两者不是同一件事，调间距、砍列数、加搜索都改变不了轴。

**但"以人为轴"不是唯一答案。** 抽奖是另一个反例：它的高频工单是"这期中奖没收到""帮我报名""开奖没开"，起点**不是某个人，而是某件事**。所以正确的表述是：

> **工单的起点是什么，轴就是什么。** 用户类工单的起点是人；抽奖、审核、发货类工单的起点是"一件待办"。

这也解释了为什么抽奖是唯一"感觉还不难用"的模块——`LotteryOperationsPanel.vue` 已经按待办组织（见 §5.4 注）。新结构要做的是把这个形态**复制到审核、订单、用户报障**上，而不是把它压平成一个表格页签。


### N1 找得到：任何数据或功能，两步内可达

- 问题：56 个页签 + 8 个独立页，靠侧栏 17 项滚动寻找；两个页面根本没有入口。
- 目标：从进入后台到打开任意目标，≤2 次点击；任意业务词（"补发""开屏""头像"）能命中。
- 指标：入口覆盖率 100%（所有路由都能从界面到达）；关键词命中率 100%（用别名表逐词遍历验证）。
- 现状：侧栏搜索已能吃功能索引（2026-11-12 落地）；但 `/admin/birthday`、`/admin/alert-style-editor` 仍未登记，覆盖率不是 100%。

### N2 看得懂：一屏只有一个决定轴

- 问题：进列表页要串行决定"模块 → 子表 → 搜不搜 → 搜哪 → 筛不筛 → 按什么状态"，前五步都发生在看到第一行数据之前。
- 目标：第一行数据进入首屏上半部；同屏只有一个"选择轴"（要么模块，要么筛选，不同时要求两个决定）。
- 指标：第一行数据 ≤200px（1440×900）；首屏可交互元素 ≤90；首屏文案段数 ≤30。
- 现状：210px / 183 个 / 已压缩一轮，仍未达标。

### N3 改得对：写路径唯一、失败可解释

- 问题：三种写路径并存；错误文案有时是数据库原文（`42501`、`new row violates row-level security policy`）。
- 目标：同一业务动作只有一条写路径；失败必须给出"谁能改、该怎么改"，不吐数据库错误码。
- 指标：错误可读率 100%（无错误码外露）；同义动作路径数 = 1。

### N4 改得安全：高危动作有分级、有留痕、可回滚

- 问题：删除、封禁、发放、改角色混在列表行内；审计是 best-effort；"最近删除"只覆盖部分表。
- 目标：按"可逆/不可逆/影响他人权益"三级分流；不可逆动作必须二次确认 + 强留痕；删除一律先进回收站。
- 指标：高危动作审计覆盖率 100%（强留痕，失败即阻断）；删除可恢复率 100%。

### N5 分得清：角色与范围是配置，不是硬编码

- 问题：只有 admin 一档；模块归属按部门写死在 `tabs.js`；同站点的数据分散在 users / operations / community 三个模块。
- 目标：**站点 → 数据维度 → 角色** 三者可声明、可审计；新增一个站点不需要改四处配置。
- 指标：新增站点只改 1 个配置文件；越权访问 0（含深链直达）。

### N6 手机能用：竖屏是"巡检 + 轻操作"，不是完整后台

- 问题：390×844 下工具栏曾占 165px，第一屏看不到任何数据；编辑是桌面抽屉的等比缩小。
- 目标：竖屏首屏可见 ≥3 行/卡；只读与轻操作（改状态、看详情）完整；重配置引导到桌面。
- 指标：390×844 首屏数据行 ≥3；横向溢出 = 0；点击目标 ≥44px。

## 5. 目标信息架构：两版草案（供讨论，不是定稿）

### 5.1 草案 A：按**站点**分组（我倾向这版）

```
总览（今天要处理什么）
├─ 用户与权益      账号 / 角色 / 积分 / 订阅 / 周年领取
├─ 内容            论坛 / 评论 / 审核 / 举报 / 资讯 / 摄影集
├─ 交易            商品 / 订单 / 礼物 / 地址 / 抽奖履约
├─ 活动运营        活动 / 报名 / 发放 / 海报 / 生日 / 创作者
├─ 站点装修        首页 / 开屏 / 商城 / 资讯 / 头像框   ← 全部是"配置"，不是"数据"
├─ AI 与集成       模型 / 密钥 / 额度 / 记忆 / 用量
├─ 系统与审计      审计日志 / 数据导出 / 通知 / 媒体资源
```

- 优点：与"站点 × 维度"矩阵一一对应，新人按业务找；配置与数据在结构上分开（不再混在 tabIds）。
- 代价：`users` 这类横跨多站点的表要决定归属（我建议归"用户与权益"，其他站点只读引用）。
- 适合：**有多个运营角色**、按站点分工的未来。

### 5.2 草案 B：按**任务**分组

```
总览
├─ 找人（用户 / 作者 / 订单人）
├─ 审内容（待审 / 已拒 / 举报 / 图片）
├─ 发货与履约（订单 / 礼物 / 地址 / 抽奖）
├─ 发权益（积分 / 订阅 / 周年 / 保底）
├─ 配站点（首页 / 开屏 / 商城 / 资讯 / 头像框 / 模型）
└─ 查账（审计 / 用量 / 导出）
```

- 优点：以"我今天要做什么"组织，任务完成路径最短；天然适合移动端巡检。
- 代价：同一个站点的数据会被拆到多个入口（如商城既在"发货"又在"配站点"）。
- 适合：**只有 1–2 个人、以任务为驱动**的现状。

### 5.3 我的倾向（v2 已定）

**A 做骨架，但把"用户"提成第一入口，B 只活在总览页。**

- **侧栏按站点**：结构稳定、与数据归属天然对齐、加站点不改导航；
- **"用户"排第一**：因为维护工作 90% 从"一个人"开始（§3.0），它不是一个"站点"，是**贯穿所有站点的轴**；
- **总览按任务**：今日待办（待审 N、待发货 N、异常 N、未启用功能 N），不按站点罗列数字。

原本考虑的"全按任务分组（草案 B）"在 v2 里**不建议**：任务会变、会增、会合并，导航跟着任务走意味着每季度重排一次侧栏；而站点在可预见的未来是稳定的。

### 5.4 建议的模块结构（v3 草案，**v5 已由 §12 取代**）

| 模块 | 装什么 | 频率 | 与现状的差异 |
| --- | --- | --- | --- |
| **总览** | 今日待办、异常、未启用功能 | 每次进 | 从"统计卡"改成"待办清单" |
| **用户**（第一入口） | 搜人 → 账号状态 / 登录 / 积分 / 订单 / 礼物 / 帖子 / 订阅 → 就地处置 | 每天多次 | 新增"用户 360"，把 7 个页签收进一个人的视图 |
| **内容** | 帖子 / 评论 / 审核 / 举报 / 图片 / 新闻 / 摄影集 | 每天 | 合并"社区 + 审核 + 运营里的新闻/摄影集" |
| **抽奖** | 创建向导 / 奖池排期 / 报名明细 / 代报名 / 保底 / 审计；**履约进度在商城订单**（§11） | **高频**（已确认） | 从"交易"里独立；6 页签 → 3；"履约与通知"移出到订单域 |
| **交易** | 商品（价格库存）/ 订单 / 礼物 / 地址 | 每周 | 只留"钱与货"，不再夹抽奖 |
| **权益** | 积分 / 积分流水 / 订阅 / 周年 / 发放动作 | 按需 | 从"用户"里拆出写操作，避免和 360 视图混在一起 |
| **配置**（折叠） | 首页 / 开屏 / 商城装修 / 资讯编辑 / 头像框 / AI 模型密钥额度 | 季度 | 6 个控制台 + AI 配置归并，明确标"配置"不是"数据" |
| **系统**（折叠） | 审计 / 数据导出 / 媒体 / 通知 | 按需 | 保留 |

> 8 行里有 2 行取决于决策：**权益**是否独立（D12）、**抽奖**是否独立（D13）。
> 若两者都并入，则退回 6 个模块——但按"抽奖很频繁"这个事实，D13 建议独立。
>
> **抽奖这一行是新结构里唯一"已经有正确答案"的模块**：`LotteryOperationsPanel.vue`
> 已经按工单组织（待履约 / 通知异常 / 待开奖 / 报名风控 四个可点指标 + 按优先级排的任务列表 +
> 一键"处理 N 个到期抽奖" + 单条"推进"）。其他模块应该照它做，而不是反过来把它压平进表格。


### 5.5 无论选哪版，都建议守住的三条结构规则

1. **"数据"与"配置"分家。** 表型页签（看行、改行）归数据；可视化编辑器与模型/额度/密钥归配置。两者不复用同一套列表壳。
2. **一个站点只有一个"主入口"。** 其余入口只能是主入口里的跳转，不能是并列的侧栏项。
3. **页面型页签独立成"动作页"。** 发放、代报名这类"一次动作"不该长得像一张表。

## 6. 关键决策（需要你拍板）

> 每条给：选项 / 我的建议 / 影响面 / 不决定的后果。建议不是结论，是供你反驳的起点。

### D1 新 IA 的主轴

- 选项：① 按站点（草案 A）；② 按任务（草案 B）；③ 继续按现状（部门 + 表）；④ **以人为轴**（用户 360 做第一入口，站点做骨架）；⑤ **按工作流**
- 建议：**已定案 ⑤（v5，站长要求"按工作流划分"）**。§12 给出五条工作流的划分、目标形态与 17 模块映射；
  ④ 的"用户 360"沉淀为 W1 的内部形态，站点退为"配置与工具"区
- 影响：模块数 17 → 6（5 条工作流 + 总览）+ 1 个折叠的工具箱；`tabs.js` / 侧栏 / 搜索分组 / 权限矩阵全部要重写
- 不决定的后果：任何"精简侧栏"的改动都会在两个月内长回 17 项；"看一个人"仍需手工 join

### D2 角色模型

- 选项：① 只保留 admin，删掉 moderator 的死代码；② 真引入 operator（可写业务数据，不可改权限/密钥）；③ 真引入 moderator（只读 + 审核）
- 建议：**① 已定案**（v2）。已确认单人使用，②③ 是不存在的需求；继续留着 `moderator` 白名单只会让人误以为有分工
- 影响：删 `MODULE_ALLOWED_ROLES` 里的 moderator 分支与 `filterTabActionsByRole` 的版主路径；同步删掉对应测试，避免"测一个进不去的角色"
- 不决定的后果：所有"谁管理什么"的设计只能是文档；代码里长期存在一套测不到的权限逻辑

### D3 面板与 6 个独立控制台的关系

- 选项：① 全部并入面板（统一壳）；② 分层：面板管数据，控制台管配置，侧栏里分成两组；③ 保持现状（混在一起）
- 建议：**②**。可视化编辑器有真实预览、拖拽、发布态，塞进表格壳里只会两边都别扭；但必须在侧栏里明确标成"配置"，不再伪装成数据模块
- 影响：`tabModules` 要区分 `kind: 'data' | 'config' | 'action'`；`/admin/birthday`、`/admin/alert-style-editor` 必须登记或删除
- 不决定的后果：C1/C2 持续存在，且每加一个控制台就多一个"只能手敲地址"的页

### D4 写路径是否统一收口

- 选项：① 全部走 RPC（安全但工作量大）；② 保留直更，但强制统一错误映射与审计埋点；③ 现状
- 建议：**② 先行，高危动作（删除/封禁/发放/改角色）一律 RPC**。理由：50 张表全部包 RPC 不现实，但高危动作必须可审计、可回滚
- 影响：`saveStrategies` 与 `utils/api/*` 的边界要重划；错误文案要有一张统一映射表
- 不决定的后果：C8/C9 无解，"改得对/改得安全"两个诉求落空

### D5 极简骨架的去留

- 选项：① 替换旧面板（新骨架逐个模块迁移，旧面板下线）；② 长期并行（新旧两套）；③ 废弃骨架，回到旧面板继续优化
- 建议：**①**，但按"站点"为单位迁移，迁完一个删一个，不做大爆炸
- 影响：决定后续是"改造 1 万行"还是"另起一套"；也决定 `/admin/users-minimal` 这个临时路由的寿命
- 不决定的后果：C14 双轨维护，两边都改不彻底

### D6 深链契约

- 选项：① 保留 `?section=&tab=` 作为稳定契约；② 换成 `/admin/:site/:dimension`；③ 不承诺
- 建议：**②**，但为 ① 保留 301 式重定向至少一个版本

## 11. 抽奖工作流重构方案（v4 新增，待确认后施工）

> 需求原话（2026-11-12 17:08）：「能不能全新重构抽奖工作流，创建，到中奖，然后订单进度也放进商城那边订单里管理」。

### 11.1 一句话方案

**把"中奖"定义为"生成订单"的那一刻。** 抽奖域只负责"产生中奖"，履约进度全部交给商城订单域——用户和你在**同一张订单表、同一个订单页**里看进度。

这不是"再做一个抽奖管理页"，是把抽奖从"六个页签的表集合"改造成"一条有始有终的流水线"。

### 11.2 目标流程（5 段，每段只做一件事）

| 阶段 | 抽奖状态 | 谁做 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- | --- |
| 1 创建 | `draft` | 后台向导（3 步） | 改奖品 / 规则 / 排期 / 保底 | 接受报名 |
| 2 报名 | `open` | 用户自助 + 后台代报名 | 报名、取消报名、看风控 | 改奖品（只能改说明） |
| 3 开奖 | `drawn` | 手动或定时 | 生成中奖人 **+ 每人一张订单** | 改奖品；改中奖人只能"作废 + 替补" |
| 4 履约 | `drawn`（进度在订单侧） | **商城订单页** | 联系、发货、完成、作废 | 改抽奖结果 |
| 5 归档 | `closed` | 自动 / 手动 | 只读 | 任何写 |

现状的 `fulfillment_status` 是抽奖行上的**第二个总状态**（`pending_contact/confirmed/fulfilled/voided`），与 `lottery_winner_fulfillments` 每席位状态重复。v4 起它不再作为真源，只做兼容保留。

### 11.3 状态映射（抽奖结果 → 订单进度）

| 履约表状态 | 订单状态 | 用户看到的文案 |
| --- | --- | --- |
| `pending_contact` / `contacted` / `confirmed` | `preparing` | 准备中 |
| `shipping` | `shipped` | 已发货 |
| `fulfilled` | `completed` | 完成 |
| `disqualified` / `forfeited` / `voided` | `cancelled` | 取消 |

"已联系 / 已确认"**不新增订单状态**（用户已明确只要四态：准备中/已发货/完成/取消）。它们保留为履约表上的 `contacted_at` / `confirmed_at` 时间戳。

### 11.4 数据模型（字段均按线上实测，不是按旧迁移文件）

**`shop_points_orders` 已经有的**（比旧迁移看起来多）：`shipping_recipient`、`shipping_phone`、`shipping_address`、`remark`、`items jsonb`、四态 `preparing/shipped/completed/cancelled`、`total_points >= 0`（已放宽，0 元单合法）。

**需要加的 4 列**：

```sql
alter table public.shop_points_orders
  add column if not exists source text not null default 'shop'
    check (source in ('shop', 'lottery')),
  add column if not exists lottery_fulfillment_id uuid
    references public.lottery_winner_fulfillments(id) on delete set null,
  add column if not exists shipping_carrier text,
  add column if not exists tracking_number text;

create unique index if not exists shop_points_orders_lottery_fulfillment_unique
  on public.shop_points_orders (lottery_fulfillment_id)
  where lottery_fulfillment_id is not null;
```

**唯一真正的约束冲突**：`payment_mode='points_only'` 要求 `total_points > 0`，而奖品单是 0 元。必须给 `payment_mode` 加一个 `'free'`，并把校验改成：

```sql
-- shop_points_orders_payment_mode_check: + 'free'
-- shop_points_orders_payment_mode_amounts_check:
--   when 'free' then total_points = 0 and coalesce(rmb_total,0) = 0
```

**`lottery_winner_fulfillments` 的拆法**：保留"谁中奖、第几席、是否替补、资格作废原因、联系时间"；把"地址、承运商、单号、进度"交给订单。新增一列 `order_id uuid unique references shop_points_orders(id)`。

> 不物理删除 `status` / `address_id` / `shipping_carrier` / `tracking_number`：开奖函数仍会写 `status`，删列会当场 42703。先标注 deprecated，等 §11.7 的第 3 步合并完开奖函数再删。

### 11.5 开奖建单：用触发器，不改 7 处开奖 SQL

`lottery_winner_fulfillments` 的 insert 在 3 个迁移文件里共 **7 处**（`2026081406:107/163/344`、`2026081904:119/200/481`、`2026100403:230`）。逐个补"建单"必漏其中一个（历史上就漏过 `fulfillment_id`，见 `2026100403` 文件名）。

因此用 `after insert on lottery_winner_fulfillments` 的触发器统一建单：

```sql
-- 伪代码，实际函数体在施工时展开
create or replace function public.create_order_for_lottery_win()
returns trigger language plpgsql security definer as $$
begin
  insert into public.shop_points_orders (
    user_id, order_no, contact_type, contact_value, items,
    total_points, points_used, rmb_total, payment_mode, status,
    source, lottery_fulfillment_id, shipping_recipient, shipping_phone, shipping_address, remark
  )
  select
    new.user_id,
    'L' || to_char(now(), 'YYMMDD') || '-' || left(replace(new.id::text,'-',''), 8),
    'profile', coalesce(new.username_snapshot, ''),
    jsonb_build_array(jsonb_build_object(
      'title', coalesce(new.award_title, l.prize_title),
      'description', coalesce(new.award_description, l.prize_description),
      'image', l.cover_image_url,
      'quantity', 1, 'points_cost', 0, 'rmb_price', 0,
      'payment_mode', 'free', 'category', '抽奖奖品',
      'lottery_id', new.lottery_id, 'lottery_title', l.title,
      'winner_position', new.winner_position
    )),
    0, 0, 0, 'free', 'preparing',
    'lottery', new.id,
    a.recipient, a.phone, a.region || ' ' || a.detail,
    '抽奖奖品：' || l.title
  from public.lotteries l
  left join public.user_addresses a on a.id = new.address_id
  where l.id = new.lottery_id
    and new.user_id is not null
  on conflict (lottery_fulfillment_id) do nothing;

  update public.lottery_winner_fulfillments f
     set order_id = o.id
    from public.shop_points_orders o
   where o.lottery_fulfillment_id = f.id and f.id = new.id;

  return new;
end $$;
```

好处：手动开奖、cron 开奖、保底礼、替补，**全部自动生成订单**，不需要改任何一份开奖函数。

3. 建触发器（只对新 insert 生效，不碰历史）；
4. 前端切换抽奖页与订单页；
5. 观察一周后，删 `lotteries.fulfillment_status` 与履约表的 `status/address_id/shipping_carrier/tracking_number`；
6. 回滚：`drop trigger` + 删 4 列即可；已生成的订单可保留（它们本身是合法订单）。

### 11.8 风险（已经想到的）

- **通知叠加**：订单 `UPDATE OF status` 上已有站内信 + 邮件触发器。开奖建单是 INSERT，不触发；但如果之后把状态从 `preparing` 推进，就会正常发进度通知——这正是我们要的。要确认的是**建单时是否要额外发"你中奖了"**（现在开奖函数已经发了 `lottery_win` 通知，别再发第二条）。
- **0 元单在用户订单页的展示**：需要确认不显示"实付 ¥0"这种尴尬文案，改为"奖品"。
- **资格作废**：订单取消 + 履约表 `disqualified`，不回积分、不回库存（抽奖奖品不占商品库存）。
- **替补**：作废的订单保留（审计），替补者新建一张订单（`replacement_of` 指向原席位）。

### 11.9 需要你确认 3 件事

1. **什么时候建单**：开奖即建（地址为空，后续补），还是等中奖人填了地址才建？建议前者——否则"中奖但没填地址"的人在你后台是隐形的。
2. **作废 / 替补怎么落到订单**：取消旧单 + 新建新单（建议，留痕完整），还是复用同一张单改收件人？
3. **订单页要不要区分来源**：抽奖单和商城单混在一个列表（按时间排），还是默认分两个 tab？建议一个列表 + `source` 筛选，因为"要发货的东西"应该一起看。

## 12. 按工作流重构（v5，D1 定案）

> 需求原话（2026-11-12 17:15）：「按照工作流划分……对用户管理的工作流、社区运营的工作流、订单抽奖类工作流、AI 类、安全审核类，你洞悉一遍。」
> 同轮确认：中奖才建单；作废 = 取消订单 + 重抽；订单列表合并。

### 12.1 先定义：什么才算"工作流"

不然后面会把"工具箱"也塞进来。三个判据，缺一不可：

1. **有明确起点**：由某个事件触发（用户来报、内容进来、订单产生、告警、举报）；
2. **有队列**：存在"等待我处理的一堆东西"，且能排序（最旧/最急/金额最大）；
3. **有终点**：做完这件事有可判定的完成态（处置完、发出、通过、归档）。

按这三条筛，17 个模块里只有 5 个是真工作流；**"配置/装修"不是**——它没有队列、没有每日起点，是工具箱。这不是贬低它，是它不该占侧栏的常驻位。

### 12.2 五条工作流总表

| 工作流 | 起点（谁触发） | 队列（等什么） | 终点 | 判断依据 |
| --- | --- | --- | --- | --- |
| **W1 用户** | 用户来报 / 例行巡检 | 待处理报障、异常账号 | 处置完成并留痕 | 报障消失 |
| **W2 社区运营** | 内容产生 / 运营排期 | 待发内容、待排活动 | 内容上线并触达 | 前台可见 |
| **W3 订单与抽奖** | 下单 / 中奖 / 收礼 / 申请 | 待备货、待发货、待开奖 | 送达并完成 | 物流签收 |
| **W4 AI** | 模型变更 / 告警 / 月底对账 | 待换模型、待处理失败 | 配置生效、成本可控 | 无 5xx、额度正常 |
| **W5 安全审核** | 举报 / 命中规则 / 人工发现 | 待审内容、待处置账号 | 处置并留痕可检索 | 队列清空 |

> 注意 W2 与 W5 的边界：**"内容该不该发"归 W5，"内容发什么"归 W2。** 一条帖子被举报 → W5；一条新闻要发布 → W2。今天这两件事被拆在"社区 / 运营 / 审核"三个模块里，是最大的错位。

### 12.3 W1 用户：从"有人来找"到"处置完成"

**现状链路**：`用户`模块 7 个页签（含 2 个发放页）+ `礼物`模块 2 个页签，跨 2 个模块。

**三个断点**（都在 §3.0 / C16 / C17 有证据）：
1. 订单、积分流水、礼物三张表**不认用户名**，只能按 UUID 查 ⇒ 看一个人要手工 join；
2. 登录状态**没有任何工具**，唯一杠杆是封禁；
3. 详情页是"通用记录面板"，不聚合这个人的订单/帖子/流水。

**目标形态（一个页面四段）**：

```
搜索框（用户名/邮箱/UUID）
  → 身份卡：头像、角色、注册时间、最后在线、邮箱验证、封禁/禁言
  → 诊断区：积分余额与最近 5 笔流水 / 最近 3 单 / 最近 3 帖 / 订阅状态
  → 处置区：改角色、调积分、封禁禁言、发积分、发订阅、导出数据
  → 留痕：这个人的所有管理员操作时间线
```

**关键设计**：处置动作必须**分级**——"发 100 积分"和"改成 admin"不该长得一样。建议：只读诊断永远显示；写动作折叠在"处置"里，高危（改角色、封禁、导出）二次确认。

**指标**：从报障到看到关联数据 = 1 次搜索（现状 ≥4 次切页 + 3 次复制）。

### 12.4 W2 社区运营：从"内容产生"到"内容流动"

**现状**：`社区` 6 页签 + `运营` 11 页签，跨 2 个模块，其中还混着 `news`（发布）、`campaigns`（活动）、`ads`（广告位）三种完全不同的东西。

**洞悉**：这 11 个页签其实在干两件事，而它们被拍平成了并列的表格：
- **生产/投放**：新闻、活动、发帖有奖、创作者展示、生日、广告位 —— 有排期、有上线态；
- **互动运营**：每周签到、摄影集 —— 看数据、做激励。

**目标形态**：
```
今日待办（待发布 N / 活动进行中 N / 排期冲突 N）
  → 内容库（按类型：帖子·新闻·活动·摄影集·广告），列表只回答：什么、什么时候上、谁负责
  → 编辑器（复用现有的 news-editor / shop-editor 就地编辑，不另造）
  → 触达（通知管理：发给谁、发了多少、失败多少）
```
**注意一**：社区运营**不做审核**。帖子审核、图片审核、举报处理全部归 W5。边界规则：**"该不该发"= W5，"发什么"= W2**。

**注意二（v7 补充）**：内容库里的**帖子是全量库**，不是"待审队列"。全字段、全状态（正常/已拒/已删）、可按作者/标题/状态搜、可改状态 —— 与今天 `社区 › 帖子` 页签的能力**一致甚至更强**。W5 的待审队列只是它的一个筛选视图，共用同一个详情组件。（v6 写"W2 留内容库、W5 只做队列"容易被读成"只能看待审"，在此更正。）

### 12.5 W3 订单与抽奖：从"要发出去"到"送达"

这是本轮最重要的一条，因为有一处**用户侧已经统一、后台却分裂**的事实。

**事实（实测）**：用户在"我的订单"里看到的是**一个列表**——`fetchMyOrders` 把三路 union 后按时间排序：
```js
const [shop, lottery, gifts] = await Promise.all([
  fetchMyShopOrders(userId),     // shop_points_orders
  fetchMyLotteryOrders(userId),  // lotteries + entries
  fetchMyGiftOrders(userId),     // user_gifts
]);
```

而后台是**四张表、四套状态**（第四张是海报申请）：

| 表 | 收件人/地址 | 单号 | 状态 | 金额/积分 | 来源 |
| --- | --- | --- | --- | --- | --- |
| `shop_points_orders` | 有（3 列） | 缺 | 四态 | 有 | 购买 |
| `user_gifts` | 有（3 列） | `gift_no` | 四态 | `gift_points` | 赠礼 |
| `lottery_winner_fulfillments` | `address_id` | `tracking_number` | **八态** | 无 | 中奖 |
| `poster_requests` | `recipient/phone/address` | 缺 | 自有状态 | `material_fee` | 申请 |

**四张表在描述同一件事**：要把一个东西寄给某个人，并跟踪到签收。所以目标不是"抽奖并进订单"，而是：

> **所有"要发出去的东西"都成为订单，`source` 区分来源（shop / gift / lottery / poster）。**

抽奖只负责到"中奖"：创建 → 报名 → 开奖 → **为每个中奖席位建一张订单**；之后发货、物流、完成全在订单域。作废 = 取消订单 + 重抽（你已确认）。

**目标形态**：
```
订单台（一个列表，按时间排；筛选：全部 / 购买 / 赠礼 / 中奖 / 海报）
  → 行内：谁、什么、到哪一步、单号（空则"未填"）
  → 一键发：填单号 → 已发货（自动通知，复用现有触发器）
  → 商品（上架/定价/库存）作为"配置"入口，不占工作流主位
  → 抽奖（创建 → 报名 → 开奖），开奖后跳"订单台?source=lottery"
```
**指标**：发货操作从"进 3 个页签找 3 张表"变成"1 个列表 1 个按钮"。

### 12.6 W4 AI：从"配置"到"成本与故障"

**现状**：`AI 配置` 7 页签（4 个是页面型：密钥与模型、AI 额度、审核模型、实验室模型）+ `日志监控` 里 3 个 AI 相关页签。

**洞悉**：这是唯一**不是每天用**的工作流，却被放在侧栏正中。它实际是两个节奏完全不同的子流程：
- **配置**（月/季度）：场景 → 模型 → Key → 额度；
- **观测**（周/月底）：用量、成本、失败率、Key 审计。

**目标形态**：
```
AI 总览（本周调用量、成本估算、失败率、额度余量）
  → 模型与密钥（按场景列：对话/审核/实验室/搜索，每行一个"当前模型 + 切换"）
  → 用量与成本（按场景/按天，能回答"谁在烧钱"）
  → 异常（额度耗尽、Key 失效、搜索失败）
```
配置项全部折叠，默认只显示"当前生效值"，改的时候才展开。

### 12.7 W5 安全审核：从"信号"到"处置与留痕"

**现状**：`审核` 5 页签 + `日志监控` 8 页签，跨 2 个模块；举报还分散在 `forumPostReports`（社区）与 `reportedPosts`（审核）两处。

**洞悉**：现在的"审核"模块里混了三种东西：
- **队列**：待审帖子、待审图片、举报（这些该合并成一条队列）；
- **结果**：已拒绝帖子/评论（这是归档，不是待办）；
- **记录**：审核日志、通知管理（通知其实是 W2 的触达动作）。

**目标形态**：
```
待处理队列（举报 / 待审内容 / 待处置账号，按时间与严重度排）
  → 判定面板：内容原文 + 作者历史违规次数 + 关联举报
  → 处置：通过 / 限制可见 / 下架 / 驳回 / 封禁 / 禁言（全部写审计）
  → 归档检索：已处置、审计日志（可按人/表/时间）
```
**关键**：处置必须"一个动作带出理由"，理由进 `moderation_logs`，否则半年后无法回答"这条为什么被删"。

### 12.8 新版导航（6 项，替代 17 模块）

```
总览        跨工作流的今日待办（v6：建议降级为侧栏角标，见 §13.2）
用户        W1
社区运营    W2
订单与抽奖  W3
安全审核    W5
AI          W4（折叠在最后）
─────────
配置与工具  装修（首页/开屏/商城/资讯/头像框）、系统设置、媒体、审计导出
```

**为什么总览单独存在**：五条工作流各自的队列互不相通，你需要一个"今天先干哪件"的入口。它不是统计页，是**待办排序器**。

**为什么"配置与工具"不是工作流**：没有队列、没有每日起点。它该是一个折叠的工具箱，而不是第六个工作流。

### 13.2 回答你的感受：总览为什么没用（先修这个）

看现状它到底是什么：**4 张统计卡（用户数 / 帖子数 / 抽奖数 / 刷新时间）+ 常用入口 + 最近更新**。

- 它回答的是"站里有多少东西"，不是"我今天该干什么"；
- 数字**全都不可点**，看完没有下一步；
- 四张卡里还有一张是"最后刷新时间"——这是运维指标，不是管理信息。

所以问题不在"设计不好"，在于**它根本不是工作流**。三个选项：

| 选项 | 做法 | 评价 |
