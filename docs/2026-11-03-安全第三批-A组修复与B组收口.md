# 安全整改 A+B 批：订单节流、配额回滚、匿名面收口、凭证入 Vault、出站白名单

> 2026-11-03 · 承接 `2026-11-02-RC版安全审计-增量复审.md` 与
> `2026-11-03-安全第二批-登录旁路收口与限流表保留.md`。
> 本文只记录**做了什么、怎么自证、还剩什么**，不复述原始审计。

## 0. 一句话结论

审计里「能造成实际数据泄露或资金损失」的项已在上两批清零；本批清掉的是
**一个正在出错的配额回滚**（`refund_lab_usage`）、**一个必然报错的匿名可执行函数**、
**37 个白送的触发器函数执行权**、**18 张表的匿名读授权**、**cron 里的明文令牌**
与**唯一一个用户可控的出站目标**。剩 CSP enforce（需攒流量）和 61 张表的
第二批授权收口（需逐表确认登录守卫）。

## A 组 · 有实际后果的三项

### A1 `refund_lab_usage`：从「永远删不到行」到「能退且不越权」

| 项 | 修复前 | 修复后 |
| --- | --- | --- |
| 函数属性 | `SECURITY INVOKER` | `SECURITY DEFINER` + `set search_path = public` |
| 能否删到行 | **不能** —— `lab_usage_records` 只有 INSERT/SELECT 策略，DELETE 被 RLS 默认拒绝 | 以 owner 身份执行，绕过 RLS 但由函数内判权 |
| 越权面 | `p_user_id is null or user_id = p_user_id` ⇒ 匿名用户凭一个 device_id 可删**任何人**的记录 | 传 uid 必须 `auth.uid() = p_user_id`；匿名通道只删 `user_id is null` 的记录，且登录用户不许借用 |
| 入参 | 无长度上限 | device_id ≤ 128 / flow_type ≤ 64 |

> ⚠️ 现状补充：`src/composables/useLabQuota.js` 头注写明「实验室功能已退场，当前无消费方」。
> 也就是说这条链路现在是**睡着的**，等 BOHAI Work 接入就会开始出账。修在这之前，
> 比出账后再补数据便宜得多。

### A2 `user_impressions`：审核未通过的内容不再公开

策略 `"Impressions are viewable by everyone"` 的 `qual` 从 `true` 改为
`moderation_status = 'approved'`。作者/被评价人仍走 `user_impressions_select_own`
（能看到自己的 pending），管理员仍走 `user_impressions_admin_select`。

**上线前取证**：整表 21 行，`moderation_status` **全部**为 `approved`
⇒ 本次收口对现有可见性**零变化**，只堵将来写入非 approved 的泄漏。

### A3 下单 / 取消：节流 + 存量上限

| 函数 | 节流 | 存量上限 |
| --- | --- | --- |
| `create_shop_order` | `shop_order:<uid>` 5 单 / 小时 | `status='preparing'`（已付未发货）≤ 10 |
| `cancel_shop_order` | `shop_cancel:<uid>` 20 次 / 小时 | — |

设计取舍（写进迁移注释，避免以后被「优化」掉）：

- 检查放在 **auth 判空之后、参数校验之前** —— 无效请求也要计数，否则故意传错参数可以无限探测而不留痕。
- 键用 `user_id` 而不是 IP：两个函数都要求登录，用户维度更准，也不会被运营商 NAT 误伤。
- **节流与上限正交**：节流限「单位时间」，上限限「存量」。只做节流的话，攻击者每小时 5 单、一周也能堆 840 单。
- 新拒绝码 `RATE_LIMITED` / `TOO_MANY_OPEN_ORDERS` 已在前端翻成人话
  （`profile-api.js` 的 `SHOP_ORDER_REJECTION_TEXT`、`shop-orders-api.js` 的 `CANCEL_ERROR_TEXT`），
  否则用户会看到英文码。

## B 组 · 纵深与卫生

### B1 anon 面收口（第一批：零前端引用面）

**为什么只做 18 张，不做 79 张**：`revoke` 会把「RLS 挡住 → 200 + `[]`」变成
「表级拒绝 → 42501」，而 `normalizeDbError` 会把 42501 归到「权限/封禁」分支
（2026-10-17 修过的 42501 误判事故同款）。所以对**前端可能访问**的表，revoke
必须先逐条确认调用点有登录守卫，不能批量做。

本批入选标准可复算：`grep -c "\.from('<表>')" src/**` = **0**。名单：

```
activity_rewards · ai_quota_log · ai_token_reservations · ai_web_search_log
api_key_vault · api_key_vault_audit_logs · boh_cloud_share_viewers
forum_post_reports · forum_rate_limit_events · lottery_admin_audit_logs
lottery_draw_logs · lottery_eligibility_exclusions · lottery_pity_events
lottery_scheduler_logs · post_reward_campaigns · post_reward_claims
poster_requests · subscription_plan_prices
```

保留（**故意不动**）：公开内容表 + 前端会读的私有表（`notifications` /
`points_transactions` / `user_addresses` / `user_gifts` / `shop_points_orders` /
`comment_likes` / `boh_treehole_*` 等），下一批逐表确认登录守卫后再收。

**顺带发现并收掉的两类**：

1. **37 个 trigger 函数全部 `anon` 可执行**。触发器执行以表 owner 身份运行，
   Postgres **不检查**调用者的 EXECUTE 权限 ⇒ 这 37 条授权纯冗余。
   里面有 `handle_new_user`、`apply_yearly_membership_gift` 和一批 `create_*_notification`，
   白送函数名与异常路径。迁移用 DO 块按「当时所有 trigger 函数」遍历收权，
   保留 `service_role`。**收权后实测 `anon` 可执行的 trigger 函数 = 0**。
2. **`place_shop_order_with_points` 直接 drop**：它写的是**库里已不存在**的
   `public.shop_orders`，且引用不存在的 `pg_temp.tmp_shop_checkout_raw`
   —— `supabase db lint` 报 42P01，即**每次调用必抛**。同时它是
   `SECURITY DEFINER` + `anon` 可执行。全仓零调用，`create_shop_order` 是现行唯一入口。
   `check:db-lint` 因此从 2 个 error 降到 1 个（剩 `admin_supabase_project_status`
   的 `storage.objects.size`，属存储面，不在本批）。

**取证**：`anon` 有 SELECT 授权的表 **79 → 61**；匿名可执行函数基线 **152 → 116**。

### B2 cron 里的明文令牌 → Vault

`boh_mail_keepalive_monthly` / `boh_mail_keepalive_watchdog` 的
`Authorization: Bearer <JWT>` 原本**内联在 `cron.job.command` 里**。这张表
`select * from cron.job` 可读，会进备份、日志快照、排障截图。

改动（`scripts/mail-keepalive-ops.mjs` + `scripts/lib/mail-keepalive-policy.mjs`）：

- `--cron` 生成 token 后**多写一处 Vault**（`mail_keepalive_token`，先删同名再 `create_secret`），
  cron 命令改成 `'Bearer ' || (select decrypted_secret from vault.decrypted_secrets where name = 'mail_keepalive_token')`；
- `extractTokenFromCommand` 整个删除 —— 留着「从命令捞 token」的能力，旧路径就会悄悄复活；
- `--watchdog` / `--trigger` / `--cloud-trigger` 改从 Vault 读；
- `--verify` 新增 V11 / V11b：断言两条命令**只存引用、不含 64 位 hex 内联**。

**执行与取证**：`--cron` 4/4 PASS（含 token 轮换，旧 token 随之失效）；
`--verify` **13/13 PASS**；线上 `cron.job` 里 jobid 40/41 → `uses_vault=true`、`inline_token=false`。

### B3 推送 endpoint 出站白名单

`push_subscriptions.endpoint` 是**用户可写**的，`push-send` 拿它直接 fetch
—— 全站唯一「出站目标由用户决定」的入口。虽然推送要 VAPID 签名、回包拿不到，
但「是否收到请求 / 耗时差」足以做内网主机与端口探测（盲 SSRF）。

两处同源落地：

| 层 | 位置 | 作用 |
| --- | --- | --- |
| DB | `public.is_allowed_push_endpoint()` + `check` 约束 | 阻止脏 endpoint 写进来（可见失败优于静默收不到） |
| EF | `_shared/push-endpoint.ts` `isAllowedPushEndpoint()` | 过滤历史脏数据；**两条发送路径**（outbox 投递、action=test）都过 |

白名单：精确 `fcm.googleapis.com` / `android.googleapis.com` / `web.push.apple.com`；
后缀 `.push.services.mozilla.com` / `.notify.windows.com` / `.push.apple.com`。
另拒 http、非 443 端口、userinfo 伪装（`https://可信域名@evil.com`）。

**取证**：
- DB 函数实测 12 个用例全部符合预期（含 `https://web.push.apple.com@evil.com/x` → false、
  `https://evilpush.apple.com/x` → false、`https://evil.com/?x=web.push.apple.com` → false）；
- 现有 3 行订阅（全 `web.push.apple.com`）通过约束，**未被拒**；
- `push-send` 版本 13 → **14**，`verify_jwt=false` 保持不变（公开 config 入口不受影响）。
