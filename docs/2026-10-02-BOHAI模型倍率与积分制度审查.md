## 0. 结论先行

用户问的是「倍率是否被调得太高」。实测后的准确回答是：

> **倍率不是「太高」，而是「与真实成本完全脱钩」—— 5 个在用模式全部跑在零成本 / 免费档模型上，
> 却对其中 4 个收 3×/5×/10×/15× 的倍率。**
> 更具体地说，**最贵的那档（Ultra 10×）跑的是 `openrouter/free`（随机免费模型）**，
> 且对免费用户开放；而**唯一一个真正「只发不收」的东西是积分 —— AI 计费路径上线至今零触发**。

三条最重要的发现：

| # | 发现 | 影响 |
| --- | --- | --- |
| 1 | **`Ultra`（10×，文案「顶级推理」）的真实模型是 `openrouter/free`** —— OpenRouter 的免费模型路由器，随机从免费池里挑一个（可能是 Llama 3.2 3B 这类小模型） | **质量 + 信任双风险**：同一模式每次输出质量不一致；用户花 10 倍额度却可能拿到最弱模型的输出 |
| 2 | **5 个在用模式全部跑在零成本 / 免费档模型上**（智谱 Flash 系列是永久免费、`openrouter/free` 是 $0、SiliconFlow GLM-4-9B 免费、Gemini 走 AI Studio 免费档） | 倍率现在**不承担成本回收**，只承担「档位定价」。这本身可以，但必须把文案与 UI 的暗示改掉 |
| 3 | **积分制度只发不收：`ai_usage` 扣分全时段 0 笔、`points_reserved` 有值的行 0 行** | 「AI 消耗积分」这套机制**从未被真实触发过**，等于未验证。积分目前的实际用途是商城兑换和积分卡面 |

## 2. 逐条分析

### 2.1 Ultra：收 10 倍，给随机免费模型（最该改的一条）

| 面向 | 现状 |
| --- | --- |
| `display_name` / `tagline` | `Ultra` / **「顶级推理」** |
| 倍率 | **10.00**（仅次于 gemini 的 15.00） |
| 真实模型 | **`openrouter/free`** |
| `openrouter/free` 是什么 | OpenRouter 的**免费模型路由器**：随机从当前可用的免费模型池里挑一个，官方明说「You cannot control which specific model is selected」 |
| 上游成本 | **$0** |
| `min_tier` | **free** —— 免费用户也能用 |

三个问题叠在一起：

1. **质量不可控**：同一模式，这次可能是 DeepSeek-R1(free)，下次可能是 Llama 3.2 3B(free)。
   用户付了最贵的倍率之一，拿到的输出质量在每次请求之间会跳变。
2. **文案与实现不符**：「顶级推理」+ 10× 定价，实际是免费池随机模型。这是**信任风险**，
   比「贵」严重得多 —— 一旦用户发现，会怀疑其他模式的定价。
3. **档位逻辑无单调性**：Ultra（10×）对 `free` 开放，而更便宜的 Code（5×）要 coding 包，
   Air（3×）也对 `free` 开放。**「越贵越难用」的直觉在这张表里不成立。**

### 2.2 倍率与实际成本完全脱钩

5 个在用模式的上游全部零成本/免费档（§1.2），但倍率跨度是 **0 → 15**。

这不必然是错的 —— 虚拟商品的「档位定价」本来就可以高于边际成本（卖的是体验与便利，不是 token）。
**但现在的实现有一处真实缺陷**：`Ultra` 的倍率是 10，而它的上游成本是 0，
且模型质量不受控（§2.1）。也就是说，**在唯一「高价档」上，用户付的是最高倍率、拿到的是最低可控性**。
其余三档（Air 3× / Code 5× / gemini 15×）虽然成本也是 0 或免费档，但**模型是确定的**
（GLM-4-Flash / GLM-Z1-Flash / gemini-3.5-flash），质量可预期 —— 这比 Ultra 好得多。

### 2.3 免费档的设计：token 额度 0 + 必须持 1 分

- `free` 的 `daily_token_limit = 0` ⇒ `remainingTokens = 0` ⇒ **必然**走积分兜底。
- `reserve_ai_points()` 里有一条硬门槛：**`points < 1` 直接 `INSUFFICIENT_POINTS`**（`2026092904:92`）。
- 于是免费用户的可用性完全由**签到节奏**决定：注册送 5 分 + 每周签到 5 分。

这本身是一个自洽的设计（免费用户靠活跃度换 AI 用量），但有两个体验缺口：

1. **没有缓冲**：新用户注册当天如果 5 分被 Ultra（10×）烧掉，之后要等下一周签到。
   `fast` 是 0× 无限可用，所以不至于完全不能用 —— 但用户不会知道这个规则。
2. **`daily_points_burn_cap = 20` 形同虚设**：用户积分中位数只有 **11 分**，
   日烧上限（20）比余额还大。这个 cap 起不到「防止一天被烧光」的作用。

### 2.4 `fast` 倍率 0 ⇒ 匿名无限免费（成本敞口）

- `fast`：`quota_multiplier = 0.00`、`min_tier = guest`。
- `reserveTokenQuota` 里 `reserveTokens = billed(raw, 0) = 0` ⇒ 预留 0 ⇒ 每日 30,000 的
  guest 额度**永远不会被消耗**（因为计费恒为 0）。
- **实测确认**：09-29 起 `fast` 的计费 tokens 全为 **0**（§1.3）。

⇒ 匿名用户可以不登录、无限次调用 `fast`（只受 10 次/分钟的服务端限流约束），
`ai_quota_config.guest` 的 30,000 token/天**实际不生效**。

**这不是 bug，是设计选择**（`fast` 就是拿来当免费入口的）。但要清楚它的含义：
**`fast` 是唯一一个没有用量上限的模式，而它恰好是 76% 流量的去向。**
如果哪天要控成本，第一处该动的是这里，而不是倍率。

### 2.5 数据卫生：3 处历史遗留

1. **`ai_quota_config` 3 行死数据**（§1.7）—— 值与不带前缀的完全相同，纯冗余。
2. **`ai_quota_log.billed_tokens` 与当前配置不一致** —— 配置变更的历史痕迹。
   做任何经济分析都要按时间窗切，否则会算出「fast 平均 0.86 倍」这种假结论。
3. **代码里的死模式配置**：`GENERATION_PROFILE_BY_MODE` 有 5 个模式
   （fast / pro / multimodal / plan / agent-cluster），但库里只有 fast 存在。
   后果：
   - `agent-cluster` 的 `status='disabled'` ⇒ 用户选不到 ⇒ `isAgentClusterMode(currentModeId)`
     **永不为真** ⇒ **整条 agent 集群链路不可达**（`agents/**` 约 2,500 行 + 相关探针）。
   - `plan` 不可达：`togglePlanMode()` 直接设 `isPlanModeEnabled = false` 并清 localStorage。
   - 所以 `GENERATION_PROFILE_BY_MODE` 里 pro / multimodal / plan / agent-cluster 四条是死配置。

### 需要产品决策的一条

**既然 5 个模式全部跑免费模型，是否还要保留 0/3/5/10/15 的倍率差异？**

- 若定位是**档位定价**（卖体验差异，不卖 token）→ 可以保留，但**必须**改掉任何暗示成本或能力的文案
  （尤其 Ultra 的「顶级推理」），并把「模型质量可预期」当成硬要求。
- 若定位是**成本回收** → 当前倍率与成本完全无关，需要重算（但重算的前提是先有 §P2-9 的成本档字段）。

# 6. 「降订阅额度 + 提模式可用量」怎么改（2026-10-02 补充）

用户诉求：**① 缩减订阅层级发放的 token 额度；② 提升当前各模式的实际可用量**（尽管上游是免费模型）。

这两个目标方向相反（额度 ↓ 会让次数 ↓），所以能不能同时成立，取决于倍率降得够不够。

## 6.1 先立公式：只有一个解

```
每天可用次数 = 档位日额度 ÷ (模式倍率 × 每次实际 token)
```

所以：

```
次数倍数 = (额度保留比例) ÷ (倍率保留比例)
```

- 只降额度（÷2）→ 次数 **÷2**
- 只降倍率（÷10）→ 次数 **×10**
- **两个都做，且倍率降得更多（÷2 与 ÷10）→ 次数 ×5** ✅

⇒ **「降额度」和「提次数」可以同时成立，但倍率的降幅必须大于额度的降幅。** 这是唯一的路。

## 6.2 ⚠️ 一个必须一起处理的副作用：免费档会跟着变强

倍率是**全局缩放** —— 它同时作用于「会员的 token 额度」和「免费档的积分购买力」。
所以只降倍率的话，**会员和免费档的差距会被一起压掉**（实测：2.8× → 1.4×）。

免费档的预算来自积分，**不受 `daily_token_limit` 影响**：
`5 分/周（签到）→ 摊到每天 714,286 计费 token`。

| 方案 | 免费档（摊日） | pro 会员 | 会员/免费 |
| --- | ---: | ---: | ---: |
| 现状（额度 2M、倍率 10、rate 1M） | 5 次/天 | 15 次/天 | **2.8×** |
| 只降倍率+额度（rate 仍 1M） | 52 次/天 | 73 次/天 | **1.4×** ← 差距被压掉 |
| **同步把 rate 降到 500k** | 26 次/天 | 73 次/天 | **2.8×** ← 恢复 |

⇒ **必须同时把 `ai_pricing_config.rate_tokens_per_point` 从 1,000,000 降到 500,000**
（含义：1 积分从「买 100 万计费 token」变成「买 50 万」）。
否则会员相对免费档的优势会腰斩，直接影响续费。

## 6.3 推荐方案（口径极简：额度 ÷2、倍率 ÷10 ⇒ 次数 ×5）

**① `bohai_model_configs.quota_multiplier`（÷10）**

| 模式 | 现在 | **建议** |
| --- | ---: | ---: |
| fast | 0.00 | **0.00**（不变） |
| Air | 3.00 | **0.30** |
| Code | 5.00 | **0.50** |
| Ultra | 10.00 | **1.00** |
| gemini | 15.00 | **1.50** |

**② `ai_quota_config.daily_token_limit`（÷2）**

| 档位 | 现在 | **建议** |
| --- | ---: | ---: |
| guest | 30,000 | 30,000（不变；fast 0× 实际无限） |
| free | 0 | 0（不变；纯积分） |
| plus | 800,000 | **400,000** |
| pro | 2,000,000 | **1,000,000** |
| max | 5,000,000 | **2,500,000** |
| ultra | 10,000,000 | **5,000,000** |

**③ `ai_pricing_config.rate_tokens_per_point`（÷2）**：1,000,000 → **500,000**

### 效果：每个模式、每个档位都正好 ×5

| 档位（新额度） | Air 0.30 | Code 0.50 | Ultra 1.00 | gemini 1.50 |
| --- | ---: | ---: | ---: | ---: |
| plus 400,000 | 290（58→） | 100（20→） | 29（6→） | 11（2→） |
| pro 1,000,000 | 724（145→） | 250（50→） | **73（15→）** | 28（6→） |

（括号里是现状值；单位：次/天，按 30 天线上实测均值折算）

**⇒ 名义额度砍一半，实际可用次数翻 5 倍。** 而且因为两个系数都是常数，
**所有模式、所有档位的倍数完全一致（5.0x）** —— 这一点很好解释，也不会有「某个模式偷偷缩水」的争议。

## 6.4 改动清单

三个字段，都是**数据**，不需要部署 Edge Function：

```sql

update public.ai_quota_config set daily_token_limit = 2500000 where tier = 'max';

-- ③ 积分汇率 ÷2（保住会员/免费档差距）

**或走管理面板**（推荐，有审计）：
`数据管理 → AI 额度配置`（`AiQuotaConfigConsole.vue`）改 ② ③；

**约束核对**（都已确认合法）：

- `rate_tokens_per_point`：`bigint check (>= 10000)` ⇒ 500,000 合法。
- 前端 `AiQuotaSidePanel.vue:71` 会展示「1 积分 = N Tokens × 档位倍率」，**改完这句话会自动跟着变**（无需改代码）。

最多 5 分钟（或调一次 `clear-model-cache`）。

## 6.5 三条要注意的

1. **上游容量先于额度**。额度给得再多，上游拒了就白给。`gemini` 的迁移自注写着
   「实测 Gemini 免费档额度很紧，十几次调用就 429，而 vault 没有 provider 降级机制」——
   本方案把 gemini 的会员额度提到 **28~139 次/天**，很可能直接撞上游墙。
   **建议：提 gemini 额度之前，先解决它的容量（付费档 / 换模型 / 加降级），
   或本次先只提 Air/Code/Ultra 三个，gemini 的倍率维持不动。**
2. **展示口径要一起改**。只要额度用「token 数」展示，砍一半就会引起「缩水」的观感 ——
   哪怕实际次数翻了 5 倍。**建议把 UI 文案从「500 万 token/天」改成「约 180 次对话/天」**
   （用 §6.3 的折算值），token 数退到后台。
3. **Ultra 的模型问题仍然独立存在**（§P0-1）。本次把 Ultra 倍率降到 1.00 之后，
   它至少不再是「最高倍率配随机免费模型」，但 `openrouter/free` 的质量不可控问题依旧，
   换模型这件事不该被倍率调整掩盖过去。

## 6.6 如果不想这么激进

同一套公式可以按需缩放，改两个系数即可：

| 额度保留 | 倍率保留 | 次数倍数 | 说明 |
| ---: | ---: | ---: | --- |
| ÷2 | ÷10 | **×5** | 本方案 |
| ÷2 | ÷5 | **×2.5** | 更保守，倍率不至于掉到 1 以下太多 |
| ÷4 | ÷10 | **×2.5** | 名义额度砍得更狠，次数涨得少 |
| ÷2 | ÷2 | ×1 | 只换量纲，次数不变（适合只想「挤掉虚高数字」） |

**公式记住一句就够：`次数倍数 = 额度保留比例 ÷ 倍率保留比例`。**

   update public.bohai_model_configs set quota_multiplier = 15.00, updated_at = now()
    where lower(trim(mode_id)) = 'gemini';
   ```
2. **3 行 `boh-*` 死数据现在与正式档位不一致了**（`boh-max` 仍是 5,000,000，而 `max` 已是 2,500,000）。
   它们永远不会被命中（`resolveUserTier` 只产出 `ultra/max/pro/plus/free/guest`），**功能无影响**，
   但会误导后来人。**建议删除**（本次刻意没动，因为它超出「改倍率/额度」的范围）：
   ```sql
   delete from public.ai_quota_config where tier in ('boh-ai-plus','boh-pro','boh-max');
   ```
3. **展示口径还没改**（§6.5 第 2 条）。前端 `AiQuotaSidePanel.vue` 仍在展示 token 数 ——
   名义额度砍半后，用户看数字会觉得缩水，尽管实际次数翻了 5 倍。建议改成「约 N 次对话/天」。
4. **Ultra 的模型仍是 `openrouter/free`**（§P0-1）。倍率降到 1.00 只是让它不再「最贵却最不可控」，
   换模型这件事没做。

## 8.4 Coding 附加包加成：已随档位额度一起 ÷2（2026-10-02）

**Coding 附加包的 `tokenBonus`**（`subscription-benefits.js` 的 `CODING_PACKS`
与 Edge Function 的 `CODING_PLAN_BONUSES`，两处必须一致）：原为 `+50万 / +150万 / +300万 / +600万`。

**已改（÷2）**：

| 包 | 展示（前端） | 强制（Edge Function） |
| --- | --- | --- |
| Coding Lite | `+25 万 Token / 天` | `250_000` |
| Coding Plus | `+75 万 Token / 天` | `750_000` |
| Coding Pro | `+150 万 Token / 天` | `1_500_000` |
| Coding Ultra | `+300 万 Token / 天` | `3_000_000` |

**为什么是 ÷2**：目的是**保持包相对基础额度的占比不变** ——
coding-lite 对 pro：`250k / 1M = 25%`，与改动前的 `500k / 2M = 25%` 一致。

**但要清楚它的连带效果**：倍率同时降了 10 倍，所以包的实际可用量（actual tokens）
**仍然比改动前多约 5 倍**。举例（free 用户，`daily_token_limit = 0`，包加成即其全部日额度）：

| | 改动前 | 改动后 |
| --- | ---: | ---: |
| coding-lite 的日额度 | 500,000 计费 token | 250,000 计费 token |
| Code 模式倍率 | 5× | 0.5× |
| **换算成实际 token/天** | 100,000 | **500,000** |

⇒ 包名义上砍半，实际价值涨 5 倍。**这是「降额度 + 提可用量」的连带结果，不是 bug**；
若要让包的实际价值也保持不变，应改成 ÷20（`25_000`），但那会让包看起来毫无价值（只占 pro 额度的 2.5%），
所以取了 ÷2。**若你觉得包给多了，改这两个常量即可**（有耦合门禁保护，见下）。

### 新增耦合门禁：`tests/unit/ai-coding-pack-bonus-parity.test.js`

这次改动暴露的风险是「**两处天然分居、改一个不会让另一个报错**」——
不一致的症状是「订阅页说 +25 万，实际加 +50 万」，**两边都不报错**。所以补了一道测试：

- 从 `subscription-benefits.js` 解析展示值（`'+25 万 Token / 天'` → `250000`）
- 从 `api-key-vault/index.ts` 解析强制值（`250_000` → `250000`）
- 断言逐包相等 + 两侧键集合一致 + 展示值单调递增
- **反证**：把展示侧改回 `+50 万` 跑 → **必红**，报错直接点出两侧的差异值
  （`coding-lite: 订阅页展示 500000，但 Edge Function 强制 250000`）

⚠️ 它**只锁「两处一致」，不锁具体数值** —— 数值可按运营需要调，但不许只调一边。
