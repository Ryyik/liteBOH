# 首次访问慢 · 诊断与解决方案（2026-11-16）

> 触发：「用户首次访问网页感觉都很慢，有无解决方案？CF 配置，或代码优化」
> 方法：线上真实站点 + 本地产物双测，冷缓存 + 禁用 SW + CDP 限速（1.6 Mbps / RTT 150ms / 390×844），
>      A/B 各 2 轮，只取可复现的差值。脚本见 `debug-screenshots/probe-*.mjs`（已 gitignore）。

## 0. 结论摘要

| # | 成因 | 证据 | 可回收 | 谁来做 |
|---|---|---|---|---|
| 1 | **带 hash 的静态资源只缓存 4 小时**（应 1 年 immutable） | 线上响应头 `cache-control: max-age=14400`，`cf-cache-status` 在 MISS/EXPIRED 间跳 | 边缘频繁回源到**美西**；冷访客每次都可能吃到 MISS | **Cloudflare（零风险，先做）** |
| 2 | **GFW 侧是 gzip，不是 brotli** | 客户端发 `Accept-Encoding: br, gzip`，回 `content-encoding: gzip` | JS 约 −12~15%（205 KB → ~178 KB） | Cloudflare / 换源 |
| 3 | **入口 CSS 挡住首绘** | 本机两轮：FCP 1016/1044ms，而 CSS 完成 4088/4123ms；改成非阻断后 **FCP 392/344ms** | **−640ms 白屏**（线上扣掉 TTFB 噪声后约 −850ms） | 代码（有门禁契约，需决策） |
| 4 | **LCP 是「数据回来之后才被发现」的帖子图** | load 在 2331ms 结束，但最后一张图 7828ms 才完成；LCP 6284–6500ms | 数据瀑布合并（首页/我页重复查询） | 代码（中期） |

## 1. 实测数据

### 1.1 线上真实站点（冷边缘 / 冷缓存 / Slow 4G）

```
TTFB      721–772 ms      ← Cloudflare MISS 时回源到 GitHub Pages（x-github-edge-region: westus3）
FP / FCP  2044–2604 ms    ← 首绘 = 主 CSS 下载完成的那一刻
LCP       5664–7572 ms    ← 元素在 hero logo 与 image-post-thumb 之间摇摆
DCL       2847 ms
load      3990 ms
资源      85 个 / 解码 1.70 MB / 实际传输 0.52 MB
          其中 script 205 KB、CSS 120 KB
```

### 1.2 本地产物（去掉 TTFB 噪声，A/B 各 2 轮）

| 变体 | FP/FCP | 主 CSS 完成 | 入口 JS 完成 | LCP |
|---|---|---|---|---|
| **A 现状** | **1016 / 1044** | 4088 / 4123 | 4525 / 4559 | 4492 / 5212 |
| **B 入口 CSS 非阻断** | **392 / 344** | 4023 / 3948 | 4445 / 4391 | 4412 / 4344 |
| C = B + hero logo preload | 324 / 316 | 3968 / 4040 | 4419 / 4462 | 6076 / 6304 ※ |
| D = B + 去掉 17 个 `modulepreload` | 260 / 268 | 4203 / 4175 | 4640 / 4633 | 6464 / 6436 ※ |

※ C/D 的 LCP 变成帖子缩略图，说明**图片那条链路才是 LCP 的决定者**，preload 那个 6 KB 的 logo 改变不了大局。

**B 的关键读法：JS 完成时刻几乎不变（4525 → 4391）。**
也就是说「解除 CSS 阻断」**不会推迟应用可用**，它只是把白屏换成骨架 —— 纯收益，代价是失去「CSS 必然先于挂载」这条保证。

### 1.3 SW 预缓存对 LCP 的影响

| 变体 | LCP | 图片最后完成 |
|---|---|---|
| A 正常 | 6500 / 6284 | 7828 / 7559 |
| E 屏蔽 `sw.js` | 6168 / 5908 | 7352 / 7084 |

SW 在 `load`（约 2.3s）后注册并开始预缓存 **853.89 KiB**，正好压在 LCP 图片要下载的窗口上。

### 1.4 入口链路体积

```
19 个文件 / 848 KB 解码 / 约 239 KB 传输
  217.3 KB  supabase-vendor      (55 KB gz)
  175.9 KB  ui-components        (60 KB gz)
  114.8 KB  index.css            (24 KB gz)  ← render-blocking
  114.7 KB  vue-vendor           (43 KB gz)
   46.1 KB  ui-components.css    (10 KB gz)  ← render-blocking
   43.1 KB  ui-icons + 40.6 KB vue-utils + 30.9 KB app + 23.0 KB auth-store …
```

### 1.5 入口链路为什么吃掉 4.4 秒

19 个文件 / 239 KB 传输，在 1.6 Mbps 下**纯传输只要约 1.2 秒**，实测却到 4.4 秒。差额不是带宽，是
**串行发现 + 并发分摊**：`HTML → boot.js（同步、阻塞解析）→ CSS + 17 个 modulepreload` 每一跳都要一个
RTT（150 ms），而 19 路并发把 1.6 Mbps 摊薄成每路约 640 kbps —— 实测三段最大的分别是
`816→2853`(ui-components 60 KB)、`816→2882`(supabase 55 KB)、`816→2517`(vue-vendor 43 KB)，
全部挤在同一窗口里完成。

**推论：这一段对"字节数"近似线性敏感，减 50 KB 约省 600 ms。** 入口里唯一可减的大块是
`supabase-vendor`(55 KB gz)，但它被 `stores/auth.ts` 在 `main.js` 顶部同步使用，要拆得改登录态语义，
风险高 —— 不作为本轮建议。

## 2. 方案 A · Cloudflare 配置（零风险、无需发版、建议先做）

> 现状：`www.blockofhome.cn` → Cloudflare（proxy）→ GitHub Pages（Fastly 源站，美西）。
> `_headers` 文件里的 `immutable` 一年缓存**完全没生效** —— GitHub Pages 不支持自定义 HTTP 头，
> 线上真正生效的是 Cloudflare 的规则，而它把 TTL 统一压成了 4 小时。

### A1. 缓存规则拆成两类（最重要）

Cloudflare → Caching → Cache Rules，新增两条，**顺序敏感**（先具体后笼统）：

**规则 1「静态资源：一年 immutable」**
- 条件（表达式）：
  ```
  (starts_with(http.request.uri.path, "/static/js/")) or
  (starts_with(http.request.uri.path, "/static/css/")) or
  (starts_with(http.request.uri.path, "/static/images/")) or
  (starts_with(http.request.uri.path, "/static/media/")) or
  (starts_with(http.request.uri.path, "/static/fonts/"))
  ```
- Edge TTL：`Override origin` → **1 year**
- Browser TTL：`Override origin` → **1 year**
- 理由：`/static/` 下**全部**带内容 hash，文件名随内容变，一年缓存是安全且标准做法。
  现状 4 小时等于**每 4 小时让每个边缘重新回源到美西**，冷访客直接吃 MISS。

**规则 2「入口与 SW：短边缘 + 不缓存浏览器」**
- 条件：
  ```
  (http.request.uri.path eq "/") or
  (http.request.uri.path eq "/index.html") or
  (http.request.uri.path eq "/boot.js") or
  (http.request.uri.path eq "/sw.js") or
  (http.request.uri.path eq "/push-sw.js") or
  (http.request.uri.path eq "/version.json") or
  (http.request.uri.path eq "/manifest.webmanifest") or
  (http.request.uri.path eq "/404.html")
  ```
- Edge TTL：`Override origin` → **60 秒**
- Browser TTL：`Bypass cache`（发 `no-cache`）
- 理由：现状 HTML 是 `max-age=600`，**发版后最长 10 分钟**边缘还在发旧 HTML，
  而旧 HTML 引用的 hash 资源已被 GitHub Pages 删除 ⇒ 404 ⇒ `boot.js` 的资源恢复逻辑
  带 `bohAssetRecovery` **整页重载一次**。用户感知就是「点进来卡十几秒 / 白屏闪一下」，
  而且只在发版后那一小段时间出现，最难复现。
  缩到 60 秒 + 浏览器 bypass，这个窗口基本消失。

> ⚠️ 不要把 `/boot.js`、`/sw.js` 放进规则 1 —— 它们**没有 hash**，长缓存会让改版最长滞后到缓存过期。

### A2. 压缩：现在是 gzip

- 客户端明明发了 `Accept-Encoding: br, gzip`，线上回 `content-encoding: gzip`。
- Cloudflare 不会把源站的 gzip **转**成 brotli（源站已压缩就直传），所以要三选一：
  1. Speed → Optimization → **Brotli 打开**（对未压缩响应有效，对 GitHub Pages 的 gzip 无效）；
  2. 如有 **Compression Rules**（按套餐），加一条 `starts_with(uri.path,"/static/")` → Brotli；
  3. 把 `/static/` 迁到 **Cloudflare R2 / Pages**（自动 brotli + 边缘永久缓存 + 支持 1 年头），
     `_headers` 文件直接可用。这是收益最大也最彻底的一条，但属于迁移。
- 预期：JS 205 KB → 约 178 KB（−13%），首访少约 130 ms。

### A3. 其它三项（开关级）

| 项 | 位置 | 作用 |
|---|---|---|
| **Early Hints** | Speed → Optimization → Protocol | 边缘 MISS 时可先回 `103` 带 preload 头，把 721 ms 的 TTFB 和资源下载叠起来 |
| **Tiered Cache** | Caching → Tiered Cache | 上层缓存命中后，区域边缘不必各自回源到美西 |
| **HTTP/3 + 0-RTT** | Network | 回访少一个握手 RTT |

### A4. 关于「中国大陆」

Cloudflare 免费/Pro 没有中国大陆节点，大陆用户通常落到 **HK / SG / JP**，再回源到美西。
如果目标是大陆移动端体感，真正的解法是把静态资源放进**国内 CDN + 对象存储**（需备案），
让 `/static/*` 走国内节点。这条比前面所有代码优化加起来都大，但属于立项级决策，先摆在这里。

## 3. 方案 B · 代码优化（按收益/风险排序）

### B1. 入口 CSS 非阻断 —— **白屏 −640 ms（推荐，但要你点头）**

现状：`main.js` 把 30 个全局 CSS 静态 import，Vite 抽出 `index.css` + `ui-components.css`
并在 `<head>` 末尾注入 `<link rel="stylesheet">` ⇒ **浏览器在它们下载完成前不许绘制任何东西**。

但 `index.html` 里其实**已经内联了 3.6 KB 的骨架样式**（`.boh-boot`，「正在加载…」+ 三点动画），
它本可以在 ~200 ms 就画出来 —— 现在被那两个 `<link>` 压到 1.0 s 之后。

**⚠️ 这不是"忘了开"，而是有门禁明文拦着的：**
```
scripts/check-shell-precache.mjs:132
  「这通常意味着「入口 CSS 不再是 render-blocking 的静态 <link>」——首屏将失去样式优先加载保证，请不要放行。」
scripts/check-first-paint.mjs:99
  「骨架 <style> 被样式表抢先…骨架会被全局样式覆盖」
```
所以要做，**必须用另一条保证替换掉它**，不能直接删：

1. `index.html` 把注入的 stylesheet 改成 `<meta name="boh-shell-css" content="a.css,b.css">` + `<noscript>` 里的真 `<link>` 兜底；
2. `boot.js`（已在 `<head>` 最前、同步）读 meta，创建 `rel="preload" as="style"`，`load` 后切成 `stylesheet`；
3. 挂载前确认样式已生效（`document.styleSheets` 命中或 3 s 超时强插），避免 FOUC；
4. 同步改 3 条门禁的解析口径（`check:shell-precache` 断言 A、`check:first-paint`、`check:gates-self-test` 的 fixture）。

**收益**：FCP 1016 → 344 ms（本机）；线上约 2.4 s → 1.0 s。
**风险**：boot.js 成了样式应用的必经之路（现在它已经是主题的必经之路，失败模式不新，但后果从"白闪"变成"无样式"，更重）。

### B2. SW 注册延到 LCP 之后 —— **❌ 已试，机制不成立，已还原**

原假设：`src/main.js:85-89` 在 `load` 时注册 SW，随即预缓存 853.89 KiB 抢 LCP 带宽（A/B 屏蔽
`sw.js` 得 −350~400 ms）。于是改成「LCP 候选静默 800ms 再注册」。

**实测推翻了自己**：限速下 3 秒时缓存里已有 28 条 —— 因为**首帧那个"正在加载…"骨架本身就是
早期 LCP 候选**（`P.boh-boot-text`，2044ms 就上报过），静默计时器在约 2 秒就触发，注册根本没被
推迟。改成「等首次交互」也不行：用户可能 1 秒就点，那时图片还没开始下。

结论：**没有一个可靠且低代价的「LCP 已定稿」信号**，这个方向收益（350 ms）与复杂度不匹配。
代码已 `git checkout` 还原，不留无用复杂度。若将来真要治，得从「预缓存清单瘦身」入手，
而不是推迟注册。

### B4. 开场画 —— **⚠️ 上一条判断有误，已更正**

我一度说它"必须手势、没提示、像卡死"。**错了**：`src/views/Home/index.vue:43` 有明确的
`<button class="home-gate-enter">进入方块论坛</button>`，点击即 `commitGate`。所以它不是可用性
陷阱，用户不会不知所措。

仍然成立的小问题只有一个：`utils/home-gate-storage.js:23` 把 `buildId` 拼进 storage key，
**每次发版所有人都要重新看一遍开场画**。频繁发版期间这会放大"怎么又变慢了"的观感，但它是
产品决策（想让人看到新版），不是性能缺陷 —— 优先级低，不改也不影响任何指标。

### B3. 数据瀑布合并 —— **LCP 的真凶（中期，最大）**

`load` 2.3 s 就结束了，图片却到 7.8 s 才完成 —— 中间 5.5 s 全花在「取数据 → 渲染 → 才发现图片」上。
上一轮已查出「我」页首访 31 个请求里约一半是重复查询（`user_follows` ×6、`posts id` ×4、
`profiles points` ×3、`get_my_user_space_summary` ×2），根因是同一页有两套统计实现。
首页同源同构，需一并收口。**这是唯一能把 LCP 从 6 s 级降到 3 s 级的改动**，但涉及数据口径，
要配对照探针，单独一轮。

### B4. 开场画不再随每次发版重播 —— **产品决策，非性能 bug**

`utils/home-gate-storage.js:23` 把 `buildId` 拼进 storage key，所以**每次发版所有人都要重看一遍
开场画**，而且是"等用户手势才收起"。频繁发版期间，这就是"怎么又变慢了"的直接来源。
如果这是有意为之（想让人看到新版），保持；如果只是顺手写的，把 buildId 从 key 里去掉、
只留 24h 时间窗即可。

### B5. 入口 JS 208 KB —— 暂不动

`supabase-vendor` 217 KB(55 gz) 是入口第二大块。要拆它得把 auth 会话恢复改成懒初始化，
触及登录态语义（`stores/auth.ts` 在 `main.js` 顶部被 `useAuthStore()` 同步使用）。
收益约 −55 KB gz，风险高，除非 B1~B3 做完还嫌慢，不建议现在动。

## 4. 建议执行顺序

按「真能省多少秒」排，不按「听起来多像性能优化」排：

1. **A1 + A2**（Cloudflare，今天就能做，零风险）—— 唯一不用发版、不碰代码、立刻见效的一项。
   冷边缘 TTFB 721→约 250 ms，并顺手消掉「发版后旧 HTML 引用已删 hash → 404 → 整页重载」
   那个窗口（这才是"偶尔特别慢"的来源）。
2. **B3 数据瀑布合并** —— 唯一能把 LCP 从 6.3 s 打到 3 s 级的改动，是「首次访问慢」的主体。
   根因上一轮已定位到「同一页两套统计实现」，接着做即可。
3. **B1 入口 CSS 非阻断** —— 值得做，但它**不是提速**：总等待时间不变（JS 完成 4525→4391 ms
   几乎不动），只是把开头 1 秒白屏换成骨架。作为"第一印象"修复排在 B3 之后。
4. **不做 B2**（已实测证伪）、**B5 暂不动**（改登录态语义，风险收益不匹配）。
5. A4（国内 CDN）视目标用户分布决定是否立项 —— 它比上面所有代码优化加起来都大。

> 一句话：**先让 Cloudflare 别把带 hash 的资源当 4 小时过期品，再去治数据瀑布。
> CSS 那条是"好看一点"，不是"快一点"。**
