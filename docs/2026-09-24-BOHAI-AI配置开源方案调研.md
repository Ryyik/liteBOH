# BOHAI AI 配置开源方案调研（2026-09-24）

> 背景：BOHAI 的 AI 调用链路是「前端 → EF `api-key-vault` → 上游」。用户**配置了多个平台各自的 API key**（siliconflow / zhipu / openrouter / custom 中转站等），每个 BOHAI 模式绑死一个平台+模型。调研 GitHub 上可直接引入的代码/方案。

## 〇、场景修正：多平台多 key（v2 更新）

初版误判为「单一别人的中转站 key」，实际是**多平台各一把 key**。这改变两个关键判断：

1. **自建 one-api/new-api 的核心卖点（key 池化分发）依然不对口**——key 是各平台官方 key，不是要二次分发的资源；但**跨平台渠道降级**正好是这类网关的本职，而 BOHAI 现在完全没有。
2. **EF 内候选链（原 P1）升为 P0**：它是唯一不部署新服务就能覆盖「siliconflow 挂了切 zhipu」这类**跨 provider** 降级的方案；OpenRouter `models` 数组只覆盖走 openrouter 的 mode，降为补充优化。

### key 解析现状（`api-key-vault/index.ts:864` resolveActiveSecret）
- `api_keys` 表 `onConflict: provider,purpose` → **每平台每用途只有一把 key**，无同平台 key 池。
- 解析顺序：DB active key → custom provider chat 缺失时回退 `default` purpose → `Deno.env` 环境变量兜底（`SILICON_CLOUD_API_KEY` / `ZHIPU_API_KEY` / `OPENROUTER_API_KEY` 等）。
- `runtimeChatCompletion`（`:936`）/ `runtimeChatCompletionStream`（`:978`）：单次 fetch，**无重试、无跨 provider 降级**；失败原样返回。
- per-provider 特判零散分布：zhipu 剥 `stream_options`（`:1007`）、gemini 参数清洗在手写 Worker、4 套 test 函数——**清洗知识不在一处，跨平台重试时必须按新 provider 重新清洗 payload**，这是实现候选链的前置重构点。

## 一、现状盘点

### 后端（EF 层）
- `supabase/functions/api-key-vault/index.ts`（2147 行）：key 管理 + 运行时代理 + 配额 + 模型发现一把梭。
- provider 白名单：siliconflow / zhipu / openrouter / tavily / cloudinary / turnstile / custom（`index.ts:31`）。
- per-provider 清洗全靠手工：`testSiliconFlow` / `testZhipu` / `testOpenRouter` / `testTavily` 各写一套；Gemini quirks 靠手写 `cloudflare/gemini-proxy` Worker 剥参数（frequency_penalty 400 / reasoning_effort 仅 low / max_tokens 兜底，见该 README 实测记录）。
- **无 provider 降级机制**：gemini-proxy README 第 91 行原话「vault 那边没有 provider 降级机制，429 就是直接失败给用户」。
- usage 精度：流式不带 usage 时 `normalizeTokenUsage`（`index.ts:1081`）退化为按字符估算。

### 前端（配置面）
- `src/views/DataManagement/components/ApiKeyConsole.vue`（1444 行）：**已有**「测试连接」按钮 + 「发现模型（/v1/models）」弹窗（带筛选/导入/URL 编辑/诊断信息），custom provider 提示「中转站的 chat completions 端点，模型发现时会自动推导出 /models 端点」。底子比预想好。
- `src/utils/api/bohai-model-config-api.js`：每模式可配 temperature / top_p / frequency_penalty / max_tokens，但默认值硬编码在前端 `normalizeBohaiModelConfigRow`（0.2 / 0.75 / 0.06 / 1800）。
- `src/utils/api/api-key-runtime-api.js`：SSE 解析手写（`choices[0].delta.content`），meta/error 事件分离。
- `src/views/DataManagement/components/LabAiModelConfig.vue`：Lab 五个功能从 BOH AI 现有模式中绑定模型 + temperature/max_tokens 数字输入，无连通性预检。

### 配置真相源
- `bohai_model_configs` 表：唯一生效字段 `api_url`，前端 `buildBohaiRuntimeModels` 生成 generationProfiles。

## 二、GitHub 可引入的方案（按接入成本排序）

### A. 零自建 —— OpenRouter `models` 数组 fallback（平台侧能力）
官方文档已确认（openrouter.ai/docs/guides/routing/model-fallbacks）：
- 请求体传 `models: ["model-a", "model-b"]`（按优先级排序），第一个模型 429 / 宕机 / 审核拒绝时自动试下一个；
- 只按实际使用的模型计费，响应 `model` 字段标明最终用了谁；
- 兼容 OpenAI SDK（`extra_body.models`）。

**前提**：上游中转站走的是 OpenRouter（或其兼容实现透传 `models` 字段）。
**落点**：
1. `bohai_model_configs` 加一列 `fallback_models`（text[] 或 jsonb，默认空数组）；
2. EF `buildRuntimePayload`：provider === 'openrouter' 且配置了 fallback 时，payload 附加 `models` 数组；
3. 前端 EditDrawer/tables.js 同步加列声明（列名漂移会 400 42703，见数据管理面板查错报告）。

### B. EF 内轻量重试链（不引服务，抄 LiteLLM 语义）
- 借鉴 LiteLLM（BerriAI/litellm，56k★）的 fallback 配置模型：同一 purpose 配多条 (provider, api_url, model_id) 候选，主候选收到 429/5xx/超时时按序重试一次再报错。
- 落点：`api-key-vault/index.ts` 的 `runtimeChatCompletion` / `runtimeChatCompletionStream` 外包一层 retry-when；候选列表从 `bohai_model_configs` 读（同 mode 多行或新增 fallback 字段）。
- 注意：流式场景重试要放在「拿到首个 chunk 之前」——已经往外吐过字节就不能换上游了（现有 `metaFlushed` 机制可复用判断）。

### C. 自建网关（要不要服务器是分水岭）
| 方案 | Stars | 栈 | 适配度 |
|---|---|---|---|
| Portkey AI Gateway（Portkey-AI/gateway） | ~12.7k | TS，**官方支持 Cloudflare Workers** | 高：与 gemini-proxy 同栈、免服务器；内置 200+ provider 参数清洗、重试、fallback 链、负载均衡 |
| new-api（one-api 活跃 fork） | ~45k | Go 单二进制，需 Docker | 中：Gemini 原生通道、计费、渠道自动禁用；但上游已是别人的中转站，自建=二道贩子，意义减半 |
| LiteLLM Proxy | ~56k | Python | 中：功能最全但栈陌生、需常驻服务 |

接入方式（C 类通用）：部署后把 `bohai_model_configs.api_url` 指向网关，EF/前端零改动，真相源不动。本质是把手写 gemini-proxy 工业化。

### D. 前端配置体验（借鉴对象）
- **LobeChat（lobehub/lobe-chat，~60k★）**：`src/config/modelProviders/<provider>.ts` 声明式配置——fetchModelList（动态拉模型列表）、checkModel（连通性测试）、vision/functionCall 能力标记、上下文窗口口径、CORS 声明、流式动画速度。BOHAI 的 ApiKeyConsole 已有测试+发现，缺的是**能力标记声明化**（哪些模型支持视觉/函数调用/上下文多大，现在全靠手填和踩坑）。
- **Open WebUI（open-webui/open-webui，~90k★）**：Connections = URL + Key → 自动探测模型列表下拉。与现有 discoverModels 思路一致，可参考其「连接级默认参数 + 模型级覆写」的两层参数模型。

### 不建议引入
- **Token.js**（token-js/token.js）：200+ provider 统一协议，零依赖 TS 可嵌 EF，但维护基本停滞，不适合做长期依赖。
- **Vercel AI SDK**：定位是「构造请求/结构化输出」，与现有「OpenAI 协议直发」架构重叠收益低，且 Deno EF 引入增加冷启动。
- **one-api 原版**：维护节奏不如 new-api；且「用别人的 key」场景下自建分发平台是重复建设。

## 三、修正后的推荐（v3：多平台多 key + 模型绑定商业化档位）

> v3 关键约束（2026-09-25 用户补充）：**不同平台的模型 = 不同订阅档位的 AI 体验**（`min_tier` + `quota_multiplier` 分层）。模型绑定是商业化承诺，降级不得跨越档位语义。

**档位感知降级原则**（取代 v2 的「无脑跨平台候选链」）：
1. **候选显式配置、逐档审查**：`fallback_chain` 里每个候选由管理员手工配置并标注语义，系统绝不自动跨档挑选。
2. **等价候选（tier_semantics = equivalent）**：同档位内换平台/换模型的同级备胎（如 premium 档 openrouter/Claude 挂 → 管理员预配的另一家同级旗舰），切换无感，商业承诺不变。
3. **临时候选（tier_semantics = temporary，可选）**：低档模型临时顶上时**UI 必须明示**「当前使用临时替代模型」，是否叠加补偿（送配额）由产品决策。
4. **计量按实际模型扣**：候选自带 `quota_multiplier`，`logTokenUsage` 本就按实际响应记 usage，降级后按实际使用的候选倍率扣，不按主模型的倍率。
5. **档位隔离**：premium 链里不允许出现 free/plus 模型，反之 free 用户永远不会被升档到高价模型（成本不可控）。

- **P0 — EF 内档位感知候选链**（吸收 LiteLLM fallback 语义，不引服务，降级语义遵循上述五条原则）：
  - `bohai_model_configs` 加一列 `fallback_chain`（jsonb，形如 `[{provider, model_id, api_url?, tier_semantics: 'equivalent'|'temporary', quota_multiplier}, ...]`，默认空 = 不降级，行为与现状完全一致）；
  - EF 新增「候选解析」：主候选失败（429 / 5xx / 超时 / 首个 chunk 前）→ 按 chain 取下一候选：换 provider + 换 key（`resolveActiveSecret` 已按 provider 独立）+ **按新 provider 重新清洗 payload** → 重试一次；等价候选静默切换，临时候选在响应 meta 事件带 `temporaryModel: true` 标记，前端聊天页显示「临时替代模型」提示；
  - 流式复用 `metaFlushed` 判断：已向客户端吐过字节就不再降级，报错收场；
  - 前置重构（建议同批做）：把 `buildRuntimePayload` 的 per-provider 清洗收敛成一张**声明式规则表**（哪些参数剥除/注入/改写，按 provider 查）——这样新增 provider 和跨平台重试都只改数据不改分支，也顺手消化掉 gemini-proxy 里的清洗知识。
- **P0.5 — OpenRouter `models` 数组**：对走 openrouter 的 mode 零成本补充降级（同上 v1 方案 A），与候选链叠加生效。
- **P1 — Portkey Workers**：多渠道路由/重试/清洗是它本职，与 gemini-proxy 同栈免服务器；等候选链验证过、或 provider 数量继续膨胀再上，避免一次引入两层新抽象。
- **P2 — 前端能力标记声明化**（LobeChat 思路）：`bohai_model_configs` 加 capability 细分（vision/tools/context_window），ApiKeyConsole 发现弹窗导入时标注；候选链配置 UI 也挂在这层。
- **不做**：自建 one-api/new-api（key 非分发场景）；Token.js（停滞）；Vercel AI SDK（收益不匹配）。

## 四、现状差劲的根因一句话

不是缺某段代码，而是「每 provider 的适配知识（清洗规则/能力/降级）散落在手写 Worker 和巨型 EF 里」且**每平台单点无降级**——开源方案（LiteLLM fallback / Portkey / LobeChat 声明式配置）的共同思路就是把这些知识变成**配置数据**而不是**代码分支**。多平台多 key 的现状下，第一步收益最大的就是把「降级」和「清洗」都数据化。
