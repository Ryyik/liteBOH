## 2. 新增问题

### P1-N1 🔴 匿名可枚举全站用户生日与最后活跃时间

> **2026-11-03 状态：已修并上线。** `2026110307_harden_birthday_profiles.sql` 保持 `SECURITY DEFINER`
> 与 `anon` 授权不变（首页生日墙依赖它），只做三件事：`last_active_at` 按 `hide_online_status` 脱敏、
> `p_limit` 夹到 1..50、过滤 `is_banned` / `login_banned`。上线后 `pg_get_functiondef` 已复核三项均生效。
> 「改 `SECURITY INVOKER` + 公开列视图」的方案仍保留为后续纵深方向（会牵连 `profiles` 列权限边界，需单独验证）。

**位置**：`public.get_recent_birthday_profiles(p_limit integer)`
**属性**：`SECURITY DEFINER`（绕过 RLS）、`has_function_privilege('anon', …, 'EXECUTE') = true`、函数体内**无 `auth.uid()`、无登录判断、无隐私过滤**

**实测（匿名，仅用 `.env` 里的 anon key）**

```bash
curl -s -X POST "$U/rest/v1/rpc/get_recent_birthday_profiles" \
  -H "apikey: $K" -H "Authorization: Bearer $K" \
  -H "Content-Type: application/json" -d '{"p_limit":3}'
# → HTTP 200
# 字段：id, username, avatar_url, bio, join_date,
#       birth_month, birth_day, last_active_at, hide_online_status, birthday_days_until
```

**影响面**：`profiles` 共 33 行，其中 **19 行**有出生月/日 ⇒ **19 个真实用户的生日 + 最后活跃时间，任何人无需登录即可拉取**（`p_limit` 可放大到全量）。

**两个次生问题**（同一函数内）
1. 返回了 `last_active_at`，但**没有按 `hide_online_status` 过滤** —— 用户明确选了「隐藏在线状态」，这里仍然原样吐出。前端在 `profile-api.js` 的粉丝/关注列表里是**有**消费这个开关的，说明口径不一致。
2. 返回 `id`（UUID）与 `bio`，可与论坛内容做跨表关联，构成「匿名 → 可识别」的链路。

**根因**：这是首页生日榜（`BirthdayHero`）的后端。为了「不登录也能看到谁过生日」，把 SECURITY DEFINER 当成了「绕过 RLS 的捷径」，但没有在函数内补上 RLS 本来会做的隐私判断。

**修复（按优先级）**
1. **最小改**：函数体 `where` 加 `and coalesce(p.hide_online_status, false) = false` 之外的隐私判断；并**不要返回 `last_active_at`**（生日榜不需要它），或按 `hide_online_status` 置 null。
2. **推荐**：改 `SECURITY INVOKER` + 给 `profiles` 建一个「公开列」视图（只含 `id/username/avatar_url/bio/birth_month/birth_day`），前端读视图；这样 RLS 重新生效，未来加隐私开关自动继承。
3. **必须**：加 `hide_birthday` 之类的显式开关，并在协议里披露「生日会公开展示」。现在用户填生日时没有任何提示。

**验收**：匿名调用该 RPC 后，返回体**不含** `last_active_at`；对 `hide_birthday = true` 的用户返回 0 行。

### P2-N1 🟡 下单无节流：库存锁争用 + 订单表增长 + 邮件成本

**位置**：`create_shop_order` / `place_shop_order_with_points`（均 `SECURITY DEFINER`，`anon_exec = true`）

**已做对的**（这次改版质量不错，别推翻）
- `v_user_id := auth.uid()`，为空直接返回 `NOT_AUTHENTICATED`；
- `contact_type` 白名单 `('qq','vx','profile')`；`contact_value` 长度 ≤ 64；
- `p_items` 校验必须是非空数组；
- 扣库存用了 `for update` 行锁。

**缺的**：`prosrc` 里 `check_rate_limit` **不存在**，也没有「同一用户未完成订单数上限」。
⇒ 一个刚注册的账号可以脚本化循环下单：反复占库存行锁、订单表无界增长、每次都可能触发一封结算邮件（`Shop/index.vue → sendMerchandiseSettlementEmail`）。

**修复**
1. 函数入口加 `check_rate_limit('shop_order:' || v_user_id, 5, 3600)`（5 单/小时）。
2. 加「同一用户 `status in ('pending','paid')` 的订单数 ≤ N」硬上限。
3. `anon_exec` 建议一并 revoke（函数本身已判 uid，属冗余授权；见 P2-2 的统一收口）。

### P3-N1 🟡 `user_impressions` 公开读不过滤审核状态

**策略**：`"Impressions are viewable by everyone"`，`cmd=SELECT`，`roles={public}`，`qual = true`
**表结构**：`author_id, target_id, content, category, moderation_status, moderation_reason`

**问题**：`qual = true` 意味着 `moderation_status = 'pending' / 'rejected'` 的行**也对外可读** —— 审核拦下的内容仍然公开。要么在策略里加 `and moderation_status = 'approved'`，要么确认该列从未被写入非 approved 值。

## 3. 功能缺陷（非安全，但会影响线上行为）

**`refund_lab_usage(p_user_id, p_device_id, p_flow_type)` 对所有人都被 RLS 拦死**

- 函数是 `SECURITY INVOKER`（`secdef = false`），做的是 `DELETE from lab_usage_records`；
- 而 `lab_usage_records` **只有 INSERT / SELECT 策略，没有任何 DELETE 策略** ⇒ RLS 默认拒绝；
- 结果：`DELETE` 永远删不到行，函数返回 `false`；`useLabQuota.js:242` 走「本地回退」分支。

⇒ 用户 AI 调用失败时**配额不会真的退回**，只是本地少扣了。数据侧会持续对不上。修法：要么给该函数改 `SECURITY DEFINER` 并在函数内判 `auth.uid() = p_user_id`，要么补一条 DELETE 策略。
