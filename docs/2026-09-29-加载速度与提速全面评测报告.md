## 0. 评测口径与环境（先读这段再看数字）

| 项 | 值 |
| --- | --- |
| 被测对象 | 线上 `https://www.blockofhome.cn`（GitHub Pages → Fastly → Cloudflare 三层）+ 本机 `dist/`（2026-09-29 08:41 构建）+ `src/` |
| 浏览器 | 系统 Chrome，headless，`--no-proxy-server --proxy-server=direct:// --proxy-bypass-list=*` |
| 视口 | 390×844（iPhone 尺寸，含 touch），**未做 CPU/网络节流** |
| 本机出口 | Cloudflare Dublin edge（`x-served-by: cache-dub4390-DUB`） |
| 登录态 | **匿名游客**（未登录，未写入任何数据） |

⚠️ 三条口径限制，直接影响结论怎么读：

1. **本机 RTT ≠ 中国大陆用户 RTT。** 本机 `node` 直连 `nplnlefdwfgtyimfkyih.supabase.co` 会 `ECONNRESET`，同一 URL 在 Chrome 里 200 —— 说明本机网络路径对该域名有选择性干扰。Supabase 项目在新加坡区，中国大陆真实延迟**只会比本报告测到的 444ms 更高（外推，未实测）**。
2. **未节流**，所以 TBT/long task 是桌面级 CPU 的值；低端手机要按 4× 折算（外推）。
3. `dist/` 与线上 chunk 哈希不同（线上 `app-DGwop3-V.js` / 本地 `app-BaVEGTcb.js`），**体积按同一口径实测过**（`ui-components` 线上 97KB gz / 本地 98KB gz），可对照。

## 1. 结论摘要：首访慢在这五处，按可省的时间排序

| # | 主因 | 实测代价 | 修好能省 |
| --- | --- | --- | --- |
| 1 | **头像原图直出**（17 个头像全在 Supabase Storage，无变换、无 CDN、无尺寸归一） | 单张 avg 315KB / max 508KB，而展示尺寸只有 32–48px；单次首页拉 2 张 = 603KB | ≈ **1.9s**（两张的下载尾延迟）；见 §4.1 |
| 2 | **头像框 PNG 未压缩且一次性全取**（`background-image` 加载，不吃 lazy） | 首屏 3 张 = 667KB；线上 5 张合计 1083KB | ≈ **3.5–5s**（`/user-space` 尾部 10840ms 的主因之一）；见 §4.2 |
| 3 | **首屏请求数过多 + 单请求 RTT 高** | 匿名首页 **15 个 Supabase 请求**，p50 RTT **444ms** | 砍掉冗余请求 ≈ **省 1.3–2.7s**（外推，按 444ms×串行段数）；见 §5。（**2026-09-29 晚更正**：可砍数从 6 修正为 **4** —— P1-5 经核短路已存在、P1-1 实测只有 unlocks 该跳，见 §10） |
| 4 | **受保护路由被 3s 会话守卫阻塞** + 登录链路串行 4–6 个请求 | `router/index.ts:115` `INIT_TIMEOUT_MS = 3000` | 最坏省 **3,000ms**（守卫本身），叠加请求收敛后累计可达 **5s 级**；见 §5.4 |
| 5 | **线上没有长缓存**（`_headers` 在 GitHub Pages 上不生效） | `/static/js/*` 实测只拿到 `max-age=14400` | 与回访体验相关；见 §6.3 |

反向结论（**做对了、别动**）：

- **二次访问已经极快**：SW 生效后 `/` 的 TTFB 11ms、DCL 147ms、整页传输 **1KB**、115 个资源里 114 个命中缓存，LCP 从 3188ms → 1864ms；`/forum` LCP **644ms**。判据见 §2。→ **问题全部集中在"首访"**，不要在缓存层继续加复杂度。
- **53 个路由组件全部 `() => import()`、0 个静态引入**；`nsfwjs`/`tfjs`（产物 3.6MB+1.09MB）**不在入口静态闭包里**。判据：附录 A-3 的闭包 BFS 脚本 + `grep -rn "from 'nsfwjs'\|from '@tensorflow" src`。→ 这是本项目最强的一项，历史报告反复提的"3.6MB 拖慢首屏"**不成立**。
- 论坛缩略图链路健康：`f_auto,q_auto:good,c_fill,w_360/h_270` + LQIP `q_1,w_32,h_24,e_blur:1500`，首页 16 张 Cloudinary 图**总共只有 53KB**。判据：附录 A-1 的资源分类输出。

## 4. 图片链路（最大的可修块）

### 4.1 头像：原图直出，且 100% 不走 CDN

- 结论：库内 **33 个 profiles，17 个有头像，17 个全部托管在 `nplnlefdwfgtyimfkyih.supabase.co/storage/v1/object/public/avatars/`，0 个在 Cloudinary**。
  判据：`profiles?select=avatar_url&limit=2000` 后按 host 统计（附录 A-5）。实测 2026-09-29。
- 结论：这 17 张的字节分布 = **avg 315KB / p50 385KB / max 508KB / 15÷17 超过 100KB**，合计 5352KB；自然尺寸最大 **800×800**（`avatar_1780216188621.png` 实测 800×800），而**展示尺寸只有 32–48px**（`src/utils/avatar.js:8-13` 的 `AVATAR_SIZES`：xs=32 / sm=48 / md=96 / lg=256）。
  判据：`sed -n '7,13p' src/utils/avatar.js`。实测 2026-09-29。
  判据：附录 A-5（逐张 `fetch` + `naturalWidth`）。对照值：同一张脸走 Cloudinary `w_96,h_96,c_thumb` ≈ **7KB**（用 `res.cloudinary.com/demo` 的公开样本实测）。→ **约 50× 冗余**。
- 结论：`getAvatarUrl()` 的变换**对 Supabase 头像完全无效** —— `src/utils/cloudinary-client.js` 的 `getCloudinaryTransformedUrl()` 只重写 Cloudinary URL，其它 host 原样返回。而它的**采用率极低**：全仓只有 **1 处定义 + 8 个调用行 / 5 个文件**（`OverviewCard.vue:123`、`ProfileImpressionsPanel.vue:33`、`ForumMain.vue:4547,4550`、`PostCard.vue:100,633`、`ProfileMain.vue:893,894`）。**主渲染组件 `src/views/user-center/UserSpace/components/FramedAvatar.vue:3` 是 `:src="src"` 直接用原 URL，完全不过这个函数**。全仓头像 **0 处 `srcset`**。
  判据：`grep -rn "getAvatarUrl(" src`（9 行=1 定义+8 调用）；`sed -n '1,5p' src/views/user-center/UserSpace/components/FramedAvatar.vue`；`grep -rn "srcset" src/utils/avatar.js src/views/user-center/UserSpace/components/FramedAvatar.vue`（空）。实测 2026-09-29。
- 结论：**不是漏压，是压缩上限本身就太宽**：头像上传参数写死 `maxSizeMB: 0.5, maxWidthOrHeight: 800`（`src/views/Join/index.vue:903-904`），且 `src/utils/api/avatar-storage.js:19,24` 强制 `content_type = 'image/png'`、路径硬写 `.png` —— 800px 的照片级内容用 PNG 就是 400–500KB。
  判据：`grep -rn "maxSizeMB\|maxWidthOrHeight" src/views/Join/index.vue src/utils/api/avatar-storage.js`；`grep -n "AVATAR_CONTENT_TYPE\|\.png" src/utils/api/avatar-storage.js`。实测 2026-09-29。

**方案（性价比最高的一条）**：头像改为「上传即产出 3 档 webp/jpg 到 Cloudinary 或 Storage 的 `avatar_256.webp` / `avatar_96.webp`」，读取端按显示尺寸选档。存量 17 张一次性批处理。**预期：首屏图片字节 667+603 → ~50KB，`/` 的尾部 8957ms 与 `/user-space` 的 10840ms 直接塌掉一截。**（收益是外推，基数=实测单张 385KB→7KB × 首屏 5 张）

### 4.2 头像框：5 张 PNG 共 1083KB，用 CSS 背景加载所以无法懒加载

- 结论：线上 `www.blockofhome.cn/avatars/frames/` 实测 5 张 = hamster **384KB**、cow 233KB、blue-dog 184KB、elf-flower 180KB、elf-grass 102KB。冷首访首页拿到其中 3 张 = **667KB**，`/user-space`、`/overview` 冷加载时同样是 667KB。
  判据：`for f in hamster-frame cow-frame blue-dog-frame elf-flower-frame elf-grass-frame; do curl -s https://www.blockofhome.cn/avatars/frames/$f.png -o /dev/null -w "$f %{size_download}\n"; done`；首页 3 张来自附录 A-1 的 `initiatorType=css` 分类。实测 2026-09-29。

## 5. 数据库与请求数（时间成本的主战场）

### 5.1 最重要的一个数：单请求 RTT = 444ms

- 结论：游客态对 `rest/v1/posts?select=id&limit=1` 连续 12 次串行请求，耗时 **416 / 433 / 437 / 439 / 441 / 443 / 444 / 446 / 450 / 458 / 665 / 701ms → p50 444ms、avg 481ms**。

- 结论：SW 的 runtimeCaching 覆盖了 route CSS / Supabase 公开对象 / Cloudinary（含 LQIP）/ tfjs-nsfw 共 6 条规则，**但 `/static/images/*` 一条都没有**（既不在 precache 也不在 runtimeCaching）。配合上一条，**10.36MB 本地图在生产上是"每次真下载、拿不到长缓存"**。
  判据：`grep -n "globPatterns\|runtimeCaching\|static/images" vite.config.js \| sed -n '1,40p'`。实测 2026-09-29。
- 结论：`vite.config.js` 里 `maximumFileSizeToCacheInBytes = 4MB` 恰好容得下 3.6MB 的 `nsfw-weights` —— 这个数值是"为了让它进 precache"还是"为了不误伤"，**我没有在文档里找到依据**；改动它之前要问清（附录 B）。
