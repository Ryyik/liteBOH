## 一、让 AI 更好参与开发（MCP / 上下文 / 工作流）

### 1.1 ⭐ Supabase MCP（官方）— `supabase/mcp`

- **是什么**：Supabase 官方 MCP Server，让 AI 助手直连项目，读 schema、跑 SQL、看日志、管理分支与 Edge Function。
- **直击本仓痛点**（都在 `.workbuddy-ai/memory/MEMORY.md` 与 `docs/未完成任务清单.md`）：
  - 线上库只读查询现在要 `supabase db dump --dry-run` 抠凭据 + node+pg + `set role postgres`，**每次都要重来一遍**；
  - 迁移漂移检查（`migration list --linked`）靠人肉；
  - `activity_campaigns` 的 RLS `using(true)` 泄漏 draft（§5，**已定性为安全问题**）这类问题只能靠人工 review 发现。
- **落点**：写进 `~/.workbuddy-ai/mcp.json`（**注意不是 `.mcp.json`**），配好后在连接器管理页右上角「信任」才生效。
- **⚠️ 必读安全约束**：官方文档明确写了连 MCP 有安全风险。**必须开 read-only 模式 + 只授权 `nplnlefdwfgtyimfkyih` 这一个项目**，绝不给写权限 —— 本仓有生产数据。
- **成本**：10 分钟配置。**收益/成本比最高的一条。**

### 1.2 ⭐ Chrome DevTools MCP（Chrome 官方）— `ChromeDevTools/chrome-devtools-mcp`

- **是什么**：把 Chrome DevTools 的能力（console、network、**Performance trace**、DOM/CSS 检查）暴露给 AI Agent。
- **直击本仓痛点**：`docs/未完成任务清单.md` §9 开头自己写着「**本节的结论全部来自代码阅读，没有真机实测数据**」，并列出「接手人先验什么」= 用 Performance 面板看选图→首帧缩略图的长任务归属。
  **这正是本仓探针体系的盲区**：200+ 个 Playwright 探针能验「布局/类名/断言」，但拿不到 trace、long task、内存快照。
- **落点**：与现有 `scripts/probes/*.mjs` 并存，用于 §9.4 的真机/桌面性能取证。
- **成本**：低（本地 MCP，不进产物）。

### 1.3 Playwright MCP（微软官方）— `microsoft/playwright-mcp`

- **是什么**：用可访问性树驱动浏览器，Agent 可以「点、填、看」而不是写脚本。
- **与现网关系**：本仓已用 `@playwright/test` 写探针，**同栈零迁移**。
- **价值**：临时验证（「这个按钮现在点得开吗」）不用再新写一个 `probe-xxx.mjs`；正式探针仍走仓库脚本。
- **成本**：低。

### 1.4 ⭐ Serena — `oraios/serena`（LSP 语义检索 MCP）

- **是什么**：基于 30+ 语言 LSP 的语义代码工具包：`find_symbol`、`find_referencing_symbols`、按符号改代码，而不是按文本。
- **直击本仓最贵的一条纪律**：`MEMORY.md` 第一条 —— **bash `grep "a\|b"` 在本环境恒返回 0 匹配（假阴性），否定性结论必须用 Grep 工具交叉验证**；已经据此写出过一次错进 `plans/022` §3.9 的结论。
  Serena 的「找引用」是**解析语义**而非文本匹配，天然没有 BRE/转义/`2>/dev/null` 这些坑。
- **另一处**：§6 明确写了「删正则前必须用 Grep 确认消费方」，且 `mergeAutoDecisionWithLocalGuardrails` 曾**只被单测引用**（测试在给死代码续命）——「谁在引用这个符号」正是 Serena 的核心能力。
- **成本**：中（要装语言服务器、首次索引）。

### 1.5 ast-grep — `ast-grep/ast-grep`（含 MCP 版）

- **是什么**：按 AST 做结构化搜索/替换，不是正则。
- **直击本仓痛点**：
  - `plans/023` 遗留「约 35 处死 CSS」，散在 4 个样式文件；
  - `landscape-rail.css` 的 `body.page-home` **选择器列表合并**（记忆里明确写「别复制色值，裸色棘轮会红」）；
  - 批量改 `.composer-panel` 系列类名时，正则容易误伤。
- **成本**：低-中（学一套 pattern 语法）。

## 二、清理既有债（性价比最高，且本仓文档已明确要求做）

### 2.1 ⭐⭐ Knip — `webpro-nl/knip`

- **是什么**：一次找出**未使用的文件、导出、依赖**，可自动修复。
- **为什么是本仓最该装的一条**：
  1. `AGENTS.md` 写明 lint 棘轮 **183 条 unused-vars**，且「**删 exported 符号不会让数字下降**」（`no-unused-vars` 只对未导出局部符号生效）—— 也就是 **ESLint 看不见导出级死代码**，Knip 正好补这个盲区；
  2. `plans/023` 已确认存在「零引用死导出」（`AsyncBOHAI`）；
  3. `未完成任务清单.md` §8 明确写「清理死代码后请**下调** `--max-warnings`」—— 下调的输入正是 Knip 的清单；
  4. 依赖侧也能查（`@vueuse/motion` 等是否真的在用）。
- **落点**：`npx knip` 先跑一次出报告（**先只读，不自动 fix**）；确认后分批清理，每批跑 `npm run verify`。
- **⚠️ 注意**：Vue SFC 支持需要在 `knip.json` 里配 `entry`/`project` 通配（含 `.vue`），否则会把 `views/**` 全报成未使用。**第一次跑一定会有大量误报**，要先调配置再信结论。
- **成本**：低。**建议第一个做。**

### 2.2 oxlint / Biome — `oxc-project/oxc` / `biomejs/biome`

- **用途**：Rust 实现的快速 linter，可在 CI 前置跑一遍常见规则（保留 ESLint 跑长尾插件规则）。
- **本仓注意**：`AGENTS.md` 规定**改门禁或加门禁后必须跑 `npm run check:gates-self-test`**，且新门禁要在 `scripts/lib/gate-fixtures.mjs` 里有 fixture。加 oxlint 必须走这套流程，否则就是「又一道永远绿的门禁」。

### 2.3 postgres_lsp（`supabase/postgres_lsp`）+ pgTAP + splinter

- **直击的三件事**：
  1. **`MEMORY.md` 记录的 2026-10-03 真事故**：`toggle_forum_comment_like` 的 `returns table (… like_count integer …)` 与裸列名 `like_count` 撞名 ⇒ **运行期** 42702 ambiguous（建函数时不报）。这是 plpgsql 静态检查的经典覆盖项 —— `postgres_lsp` 能对迁移 SQL 做语法+lint。
  2. **`supabase/splinter`**（Supabase 官方 Postgres linter）：把 RLS 缺策略、`using(true)` 这类问题静态查出来 → 直接服务 §5 的 `activity_campaigns` 安全问题。
  3. **`supabase test db`（pgTAP）**：给 RLS 写断言测试，把「draft 不该被 anon 看到」变成一条会红的测试，而不是靠人工 review。
- **⚠️ 前置**：本仓沙箱**没有 deno**，但 `supabase functions serve` 用的是 **CLI 自带的 Edge Runtime（不依赖系统 Deno）** ⇒ 「Edge Function 无法本地类型检查」这条旧限制，**可以靠 CLI 本地 serve 来部分解决**（值得实测确认）。

### 2.4 `supabase gen types typescript`

- **直击**：本仓有「列名漂移会 400 / 42703」的历史（数据管理面板查错报告），且 `boh_cloud_entries.source_post_id` 这类列**不在 `CLOUD_COLUMNS` 里，前端拿不到**。
- **价值**：从线上库生成 TS 类型，把列名/可空性变成编译期约束。本仓是 JS 为主，可先只对数据层（`src/utils/api/*`）用。

## 三、功能升级（按项目痛点排序）

### 3.1 ❌ 图片审核换 Transformers.js —— **实测后否决**（2026-10-04 更正）

> ⚠️ **本节初版推荐「换成 `@huggingface/transformers`（Transformers.js v3）」是错的**，理由是当时只有印象没有数字。
> 实测后结论反转：**不要换**。下面是证据。

#### 实测：现状的真实代价（`dist/` 产物，gzip 后）

| chunk | raw | gzip | 说明 |
| --- | --- | --- | --- |
| `tfjs-vendor-*.js` | 1066 KB | **263 KB** | TF.js 运行时 |
| `nsfw-vendor-*.js` | 38 KB | 11 KB | nsfwjs 包装 |
| **`nsfw-weights-*.js`** | **3516 KB** | **2477 KB** | ← **大头**。整个文件里**最长的一行有 3,600,156 字符** ⇒ 权重被内联成单个 JS 串，**要下载 + 当 JS 解析** |
| 合计 | ~4.6 MB | **~2.75 MB** | 且这三块已被 `manualChunks` 拆开、并有 workbox 运行时缓存（`cacheName: 'nsfw-model-vendor'`） |

#### 实测：候选 ONNX 模型的体积（HF API）

| 模型 | 参数量 | 文件 | 与现状比 |
| --- | --- | --- | --- |
| 现状 nsfwjs MobileNetV2 | ~3.5M | 3.5 MB | 基准 |
| `Falconsai/nsfw_image_detection`（最流行的 NSFW ONNX，187 万下载） | ViT-base **85.8M**（F32） | int8 ≈ **86 MB** | **≈ 25×** |
| `navodPeiris/deit-nsfw`（唯一 deit-tiny 候选，transformers.js 标签） | DeiT-tiny | `onnx/model.onnx` = **82.7 MB**（仓库内**无** q8/q4 变体） | **≈ 24×** |

⇒ 在 HF 上搜 `nsfw` + `onnx`，**绝大多数是 ViT-base / ViT-Large**（86–300 MB）。
「MobileNet 级别 + 已量化 + transformers.js 可直接用」的组合**目前不存在现成方案**。

#### 实测：网络可达性（决定性）

```
$ curl -s -o /dev/null -w "%{http_code}" https://huggingface.co/
000
$ curl -s -o /dev/null -w "%{http_code}" https://cdn-lfs.huggingface.co/
000
```

`huggingface.co` 在本沙箱被代理挡成 000 —— 这正解释了**本仓为什么把权重内联进 chunk 而不是从 CDN 拉**。
Transformers.js 默认从 HF Hub 取权重，接入即意味着要么依赖 `huggingface.co`（大陆用户不可达/极慢），
要么自建 ONNX 托管 —— 那就等于把现在这套自托管方案重做一遍。

#### 顺带更正两处过时描述

1. `useForumImageModerationPreload.js` **不是「无条件预载」**：它有 `hasUsableConnection()`
   （跳过 `saveData` / `slow-2g` / `2g`）与 `shouldPreload()`（仅桌面大屏：`deviceMemory > 4`、
   细指针、`shortScreenSide > 900`）；`schedulePreload({ immediate: true })` 的「意图预载」只绕过设备档位、
   **仍保留网络守卫**。原 `未完成任务清单.md` §9.1 与本文件初版的「无条件」说法都不准确。
2. `vite.config.js` 已经做了三件事，换库等于把它们全部作废：
   `nsfwjsTreeShakePlugin`（把 `inception_v3` / `mobilenet_v2_mid` 换成空实现，只留 MobileNetV2）、
   `manualChunks` 三拆、workbox 对这三个 chunk 的运行时缓存。

#### 那么真正该做的是什么（按收益排序）

| 优先 | 动作 | 收益 | 风险 |
| --- | --- | --- | --- |
| **P0** | **§9.3 P3：本地模型只在「云端不可达」时才加载** | 大多数用户**永远不下载那 2.4 MB** | 低（只是延后加载时机） |
| **P1** | **把权重从「内联 JS」改成「可 fetch 的静态资源」**（TF.js `loadGraphModel` 支持传 URL） | 去掉 **3.6M 字符的 JS 解析**（主线程大头），并让它进 HTTP 缓存 | 中（要保证自托管、不能指向 CDN） |
| P2 | 若驱动力是**识别准确率**（而非性能），再评估更大的模型 | 准确率 | 20–80 MB 对「上传前兜底」不可接受，尤其移动端 |

⇒ **结论：这条从「推荐引入」改为「不引入」。** 真要优化 §9 的卡顿，做 P0/P1，别换库。


### 3.2 搜索：MiniSearch / Orama（前端），而不是 Pagefind

- **现状**：`plans/020` 组 D 及增强项未做 —— 「结果关键词高亮 / 搜索历史 / 空态引导 / 意图识别」。
- **选型**：
  - **`lucaong/minisearch`**：体积小（~10KB 级）、支持前缀+模糊+自定义分词（中文可接 pinyin 或简单 bigram），**in-memory**，适合论坛/Cloud+ 的已加载数据集二次检索与高亮。
  - **`oramasearch/orama`**：能力更全（容错、拼音、可持久化），体积更大。
  - **Pagefind**：❌ 不推荐 —— 中文分词弱（这是它的已知短板），而本仓论坛是中文为主（已有 `2026092701_forum_search_cjk_fallback.sql`）。
- **数据库侧**：`pg_jieba` / `zhparser` / `PGroonga` 是 PG 中文全文检索的正解，**但 Supabase 托管库不支持自编译扩展**，装不上 ⇒ **别把方案押在这条上**，应用层分词更现实。
- **落点**：搜索结果的「关键词高亮」与「历史/热门词」在视图层做，不动 RPC。

### 3.3 图片 URL：`ascorbic/unpic`

- **现状**：Cloudinary 变换 URL **散在多处手写** —— `getCloudinaryTransformedUrl`、`resolveDbPointsCardImage`（`c_limit,w_1280`）、`utils/db-image-url.js`、`pointsCardPresetThumb`。`AGENTS.md` 还专门记了一条事故：只调 `getImageUrl` 时 Cloudinary 条目会指向大陆不可达域名而裂图。
- **unpic 是什么**：通用图片 CDN URL 翻译器（支持 **Cloudinary**、**Supabase Storage**、imgix 等），输入原始 URL + 目标宽高，输出正确变换 URL；配套 `@unpic/vue` 组件自动生成 `srcset`/`sizes`。
- **价值**：① 把散落的手写变换收口到一处；② 顺带解决响应式图（现在靠 `c_limit,w_1280` 一把梭）；③ 对「非 CDN 的 `@/assets/...` 别名」也能走 fallback 分支。
- **⚠️ 风险**：本仓 `check-project-structure` / `check-liquid-glass` 等门禁对**新增依赖与文件位置**敏感，引入前先确认目录规则。

### 3.4 流式 Markdown：借鉴 `streamdown`（Vercel / lobehub）

- **问题**：BOHAI 流式输出时，未闭合的代码块/表格/列表会让 marked 渲染出半截结构（闪烁、错行）。
- **streamdown 的做法**（可借鉴，**不要直接装**）：区块级缓存 + 只重渲尾部 + 未闭合块兜底。
- **⚠️**：streamdown 是 **React** 的，Vue 需自己实现；本仓 `markdown-vendor` 还承载着「代码块样式唯一来源」的硬约束（见加载性能审计报告），改动要小心。

### 3.5 Token 计数：`gpt-tokenizer` / `js-tiktoken`

- **现状**：`api-key-vault/index.ts` 的 `normalizeTokenUsage` 在流式不带 usage 时**退化为按字符估算**，额度口径不准。
- **价值**：JS 侧真正的 BPE 计数（`gpt-tokenizer` 是 tiktoken 的 TS 移植，支持 chat 编码）。
- **⚠️**：本仓上游是**多平台**（siliconflow / zhipu / openrouter / gemini），**各家 tokenizer 不同**，只能用最接近的近似 —— 定位是「比按字符估算准」，不是「精确」。

### 3.7 液态玻璃：只借鉴技术，不换库

- 候选：`dashersw/liquid-glass-js`（WebGL 折射）、`JUNGHERZ/GlassKit`（纯 CSS）。
- **⚠️ 强烈不建议整体替换**：本仓已有自研 `liquid-glass.css` + **专用门禁 `check:liquid-glass`** + `important-budget` / `dark-tokens` 两道棘轮。整体替换会当场炸掉三道门禁。
- **可借鉴的点**：WebGL 版的高光/折射位移算法；CSS 版的 `backdrop-filter` 组合写法。**只抄思路，不动现有类名体系。**

### 3.8 无障碍：`@axe-core/playwright`

- **价值**：本仓 200+ 探针目前只验布局/行为，**零无障碍断言**。axe 可以挂进现有 Playwright 流程，一次性扫出对比度、缺失 label、焦点顺序问题。
- **成本**：低（就是 `@playwright/test` 的一个插件）。
