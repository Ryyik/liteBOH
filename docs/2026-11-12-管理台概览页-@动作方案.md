# 管理台概览页 · @ 动作方案（v1，无 AI）

> 2026-11-12 决策记录。三条硬约束，后续实现不得绕过：
>
> 1. **动作只能通过 `@` 触发**。没有 `@` 的输入永远只做「找 / 看」，不做「改」。
> 2. **不接入 AI**。不调模型、不做意图分类、不做自然语言创建。所有判断都是规则。
> 3. **所有写入复用目标页已有的保存路径**。概览页不新增第二套写库逻辑。

---

## 1. 为什么把动作收进 `@`

上一版设计里，命令栏要判断「这句话是找功能还是建东西」。这个判断本身不可靠：
「抽奖 机械键盘 11/20」既像搜索也像创建，只能靠阈值和猜测。猜错的代价不对称 ——
猜成搜索只是多点一次，猜成创建会**凭空打开一个表单甚至写库**。

`@` 把意图从「语义问题」降级成「语法问题」：用户显式声明要做事，
系统不需要理解句子。代价是用户要多打一个字符，换来的是 100% 可预测。

## 2. 页面结构

```
┌──────────┬──────────────────────────────────────────────┐
│ 侧栏      │  今天，做点什么？                              │
│ 概览 ●    │  ┌────────────────────────────────────────┐  │
│ 订单·退款 │  │ 搜索功能、用户、订单…            ⌘K     │  │
│ 用户·积分 │  └────────────────────────────────────────┘  │
│ 内容审核  │  ┌────────┬────────┬────────┬────────┐       │
│ 抽奖·活动 │  │待发货 7│待审核12│待开奖 2│7日新增23│       │
│ 生日·邮件 │  └────────┴────────┴────────┴────────┘       │
│          │  待处理 6                        查看全部     │
│ 设置·退出 │  ● 交易  订单 #A1832 待发货   12 分钟前 去处理 │
│          │  ● 内容  帖子「周末联机」待审  28 分钟前 去处理 │
└──────────┴──────────────────────────────────────────────┘
```

三块各有单一职责：**侧栏负责去哪，命令栏负责做什么，下方两块负责现在该处理什么**。
下方两块全部可点击下钻，不做只读报表。

### 2.1 侧栏

- 按**工作流**分组，不按表名：交易（订单·退款）、用户（账号·积分·会员）、
  内容（帖子·评论·举报·资讯）、活动（抽奖·活动平台·报名）、生日·邮件、系统。
- 宽度 176px（≥1280）/ 208px（≥1600）；竖屏收成左滑抽屉。
- 直接复用 `src/views/DataManagement/components/AdminSidebar.vue` 与
  `config/function-index.js`（模块 + 页签 + 别名已是唯一真源）。
- 无权限项**置灰保留**并标 `denied`，与现有侧栏口径一致（可审计，不凭空消失）。

### 2.2 命令栏（本方案核心）

高度 52px，圆角 12，宽度撑满主区（主区 max-width 920 居中）。
占位文案随状态变化：

| 状态 | 占位文案 |
|---|---|
| 空 | 搜索功能、用户、订单，或输入 @ 执行动作 |
| 搜索中 | 继续输入…（↵ 打开第一条） |
| 动作模式 | 选择要填的参数，或继续输入 @ 换动作 |

**两种模式由首字符决定，只有一条规则**：

```js
const isActionMode = (raw) => /^[@＠]/.test(String(raw).trimStart());
```

- 全角 `＠` 一并识别（中文输入法容易打出全角）。
- `@` 只认**首个非空白字符**。句子中间的 `@` 不触发动作模式，按普通搜索词处理
  （避免「@某人」这类文本误触）。
- 输入框内一旦进入动作模式，`@` 与已选动作渲染成 chip，不可拆分删除；
  退格一次删除整个 chip 并回到搜索模式。

### 2.3 状态卡

4 个，一格一数，右下角无按钮（整卡可点，点击即下钻）。

| 卡 | 口径 | 点击落点 |
|---|---|---|
| 待发货 | `shop_points_orders.status = 'preparing'` | `?tab=shopOrders&status=preparing` |
| 待审核 | 待审帖/评论 + 待处理举报（两段合并计数） | 审核队列（分别带筛选） |
| 待开奖 | `lotteries` 中 `draw_at <= now()` 且未开奖 | `?tab=lotteries&draw=due` |
| 近 7 日新增 | `profiles.created_at >= now() - 7d` | `?tab=users&created=7d` |

规则：只放「需要你动手」的数字；为 0 时数字转灰、整卡降权，但不隐藏
（隐藏会让布局跳动，也不利于确认「真的没有」）。不放 PV/UV 类虚荣指标。

### 2.4 待处理收件箱

统一模型：一条待办 = `{ type, title, createdAt, severity, action }`。

| 类型 | 来源（P0） | 严重度 | 按钮 |
|---|---|---|---|
| 交易 | `shop_points_orders` 待发货，按最早下单排 | 红（>24h）/ 黄 | 去处理 |
| 内容 | 待审帖 / 待审评论 | 黄 | 去审核 |
| 内容 | `forum_post_reports` 未处理 | 红 | 去处理 |
| 活动 | `lotteries.draw_at` 已过且未开奖 | 红 | 去开奖 |

- 排序：`severity` 降序，同级按 `createdAt` 升序（越老越靠前，避免烂尾）。
- 首屏最多 5 条 + 「查看全部」；行高 52px，竖屏 56px。
- 行结构：左侧 5px 圆点（红/黄/灰）+ 类型（11px）+ 标题（13px，省略号）+ 相对时间（11px）+ 单动词按钮。
- 「稍后」写 `localStorage`（key `admin.pending.snooze`，24h），不做服务端状态。
- P0 只做单条操作，不做批量。

## 3. `@` 动作体系

### 3.1 语法

```
@<动作名> [参数槽...]
```

输入 `@` 立刻弹出动作清单（只列当前角色可用的），继续输入即前缀过滤，
支持别名与拼音首字母：`@cj` → 抽奖，`@hd` → 活动。↑↓ 选择，↵ 确认。

### 3.2 动作清单

P0 只做 6 个，够覆盖日常 80% 的操作；其余先不给入口，避免清单变长。

| 动作 | 别名 | 参数（* 必填） | 提交方式 |
|---|---|---|---|
| `@抽奖` | 摇奖、cj | *奖品、*开奖时间、份数、参与门槛 | 跳抽奖新建，参数预填 |
| `@活动` | 活动平台、hd | *标题、*报名截止、*活动时间、名额 | 跳活动平台新建，参数预填 |
| `@发货` | 发件、fh | *订单号（可多选） | 跳订单页并勾选 |
| `@开奖` | 抽奖开奖、kj | *抽奖（从待开奖列表选） | 二次确认 → 执行开奖 |
| `@发积分` | 补发、加分、ffjf | *用户、*积分、*原因 | 跳积分发放并预填 |
| `@封禁` | 禁言、拉黑 | *用户、*时长、*原因 | 二次确认 → 执行 |

「跳 × 新建，参数预填」= 概览页**不写库**，把参数带给目标页已有的保存逻辑。
这条是硬约束 3 的落地方式：写入永远只有一处。

### 3.3 动作定义

每个动作是一份声明式配置，不是一段 if：

```js
export const lotteryCreate = {
  id: 'lottery.create',
  label: '抽奖',
  aliases: ['摇奖'],
  keys: 'cj',
  type: 'create',
  to: { path: '/admin/data-management', query: { tab: 'lotteries', create: '1' } },
  params: [
    { key: 'prize_title', label: '奖品', type: 'text', required: true, maxLength: 120 },
    { key: 'draw_at', label: '开奖时间', type: 'datetime', required: true },
    { key: 'max_entries', label: '份数', type: 'number', min: 1 },
    { key: 'min_points', label: '参与门槛', type: 'enum', options: [...] },
  ],
  // 参数名与 tables.js 里 lotteries 的字段同名，目标页可直接消费
};
```

为什么这么写：参数 `key` 与 `tables.js` 字段同名，目标页拿 query 就能预填；
`required/min/max/options` 同时供参数条校验和单测使用，不写第二份校验。

### 3.4 参数区：主行 + 更多设置

```
输入 @  →  动作清单  →  参数区  →  预览确认  →  结果条
              ↑              ↓
              └── 换动作 ────┘
```

抽奖有 14 个可写字段，**一行塞不下，也不能只做 5 项**。参数区分两层：

| 层 | 内容 | 规则 |
|---|---|---|
| 主行 | 奖品、开奖时间、报名上限、报名截止 | 前两项必填；填完这四项就是一场可用草稿 |
| 更多设置 | 标题、保底规则、保底礼、奖品说明、抽奖说明、封面、三个开关、只读的中奖人数 | 默认收起，收起时显示「还有 N 项可选」 |

### 3.4.1 抽奖字段全集（与 `tables.js` / `SAVE_STRATEGIES.lotteries` 同名）

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `prize_title` | text | — | **必填**，与 `title` 同为空时保存策略会抛错 |
| `draw_at` | datetime | — | **必填**，必须晚于当前时间 |
| `entry_deadline_at` | datetime | 空 | 留空 = 报名到开奖前；不能晚于 `draw_at` |
| `max_entries` | number | 空 | 留空 = 不限人数 |
| `title` | text | 空 | 留空自动生成「{奖品} 抽奖」 |
| `pity_mode` | enum | `none` | `none` / `count_only` / `eligible` |
| `pity_reward_title` | text | 空 | 仅 `pity_mode='eligible'` 时出现且必填 |
| `prize_description` | textarea | 空 | 规格、数量、发放方式 |
| `description` | textarea | 空 | 抽奖页活动说明 |
| `cover_image_url` | url | 空 | 只收 http(s)；上传仍在详情页 |
| `is_community_visible` | switch | **true** | 社区抽奖页可见 |
| `is_home_visible` | switch | **false** | 首页轮播可见 |
| `enforce_account_age_check` | switch | **true** | 账号年龄门槛 |
| `winner_count` | 只读派生 | — | 不给输入框，见下 |

### 3.4.2 三个必须写死的默认（踩过就知道疼）

`SAVE_STRATEGIES.lotteries` 的归一化用的是**反向判断**：

```js
is_home_visible: editingItem.is_home_visible !== false   // 不传 → true
enforce_account_age_check: editingItem.enforce_account_age_check === true  // 不传 → false
```

所以 draft 初值必须显式铺开：

- `is_home_visible: false` —— 否则「建个草稿」直接推到首页轮播；
- `enforce_account_age_check: true` —— 否则账号年龄门槛被静默关掉；
- 由此 `initialDraft(action)` 是**唯一**入口，页面里不允许 `draft.value = {}`。

单测 `admin-overview-actions.test.js` 直接断言这两条，改默认值会立刻变红。

### 3.4.3 中奖人数为什么不能填

`pity_mode === 'eligible'` 时必须是 2（1 位普通 + 1 位保底），其余必须是 1，
填错会被保存策略抛「中奖人数只能为 1 或 2」。所以它做成**派生只读**：

```js
deriveLotteryWinnerCount(pityMode) // eligible → 2，其余 → 1
```

界面上显示为虚线只读框，下方写「由保底规则自动决定，不能手改」。

### 3.4.4 六条互锁校验（提交前就拦，不等保存策略报错）

| 条件 | 提示 |
|---|---|
| `draw_at` ≤ now | 开奖时间已经过去，保存后会立刻开奖 |
| `entry_deadline_at` > `draw_at` | 报名截止不能晚于开奖时间 |
| `max_entries` < `winner_count` | 中奖人数不能大于报名上限 |
| `pity_mode='eligible'` 且无保底礼 | 选了「兑现保底」就必须填保底礼 |
| `cover_image_url` 非 http(s) | 封面链接必须以 http(s):// 开头 |
| 空 `prize_title` / `draw_at` | 还缺：奖品、开奖时间 |

这些规则在 `validateLotteryDraft` 里，与 `SAVE_STRATEGIES` 的硬校验对齐但**更早**：
用户填完就能知道，而不是点了确认才看到报错。

### 3.4.5 预览分三段，不只列字段

确认卡必须回答三个问题：

| 段 | 回答 |
|---|---|
| 基本信息 | 写什么（标题、奖品、开奖、报名截止） |
| 中奖规则 | 抽几个人、有没有保底、上限多少、年龄门槛 |
| 前台影响 | 会不会出现在社区页 / 首页轮播 / 现在是草稿 |

加一段**体检提示**（不阻断提交）：报名不限、首页轮播开着但状态是草稿、
没有封面会用占位图。这三条是最容易「建完发现不对」的点。

状态恒为 `draft`：概览页不直接开报名，避免误发到前台。要开报名去抽奖列表点一下，
这是刻意的两步。

### 3.5 键盘与移动端

| 操作 | 语义 |
|---|---|
| `⌘K` / `/` | 聚焦命令栏，全选现有内容 |
| `@` | 进入动作模式（首字符） |
| ↑ ↓ | 清单内移动 / 参数槽间移动（无清单时） |
| ↵ | 打开选中项 / 提交（参数齐全时） |
| Tab | 下一个参数槽 |
| Esc | 撤销一层：参数条 → 动作清单 → 搜索词 → 失焦 |

移动端：`@` 在中文键盘要切符号，所以竖屏常驻一个 `＋` 按钮，点开同一个动作清单，
效果等价于打 `@`。命令栏吸顶（容器内 `position: sticky`，不用 fixed）。

### 3.6 权限

动作注册表按 `canViewModule` + 角色过滤，**解析前就过滤**，不给「点了才报无权」。
无权动作不进清单，也不出现在 `@` 搜索建议里。

## 4. 搜索模式（没有 `@` 时）

### 4.1 索引来源

| 分组 | 数据源 | 是否查库 |
|---|---|---|
| 功能 | `function-index.js`（模块 / 页签 / 独立控制台 / 系统子页 + 别名） | 否，本地 |
| 实体 | 用户名、订单号、抽奖标题、帖子标题 | 是，限 5 条 |
| 最近使用 | `localStorage` 最近 5 条落点 | 否 |

### 4.2 匹配与排序

精确命中（1.0）> 别名精确（0.9）> 前缀（0.8）> 包含（0.6）> 编辑距离 1（0.4）。
同分按「最近使用」加权。纯本地，防抖 120ms，不阻塞输入。

### 4.3 结果与空态

- 最多 8 条，按分组显示小标题；`↵` 打开第一条，↑↓ 移动，Tab 跳分组。
- 空结果：显示「没有找到「X」」，下面给 3 个最近功能 + 一行提示
  「要创建内容？输入 @」。
- 实体搜索有 loading 骨架，返回后追加到同一列表，不替换功能结果。

## 5. 反馈规范

| 场景 | 表现 |
|---|---|
| 提交中 | 按钮转 loading，参数条锁定，不弹全局遮罩 |
| 成功 | 输入框下方结果条：绿点 + 「已创建 抽奖「机械键盘」」+ 「去查看」；3s 后收成 chip 常驻，可点开 |
| 失败 | 参数条**不清空**；错误贴到对应槽；底部给「复制参数」，便于重试 |
| 需二次确认 | 弹窗（复用 `AdminConfirmModal`），标题写明动作，正文列参数，危险按钮右置 |
| 跳转类 | 不显示"成功"，直接进目标页并高亮预填字段（1.2s 高亮后恢复） |

错误文案必须是可行动的原因，不用「操作失败，请重试」这类话术：
`开奖时间必须晚于现在`、`份数需 ≥ 1`、`该订单已发货`。

## 6. 数据口径

- 所有计数走 `head: true` 的 `count` 查询或 `select count`，不拉全表再前端算。
- 时区统一 `Asia/Shanghai`（与生日邮件、抽奖开奖同口径）。
- 待办与状态卡共用一个 API 模块，避免两处各写一套筛选条件。
- 查询失败时卡片显示 `—` 而不是 0（0 会让人误以为"没有待办"）。

## 7. 视觉与响应式

| 元素 | 数值 |
|---|---|
| 侧栏 | 宽 176，导航项圆角 9 |
| 命令栏 | 高 54，圆角 14，`focus-within` 主色边框 + 3px 淡红光晕 |
| 状态卡 | 4 列，gap 12，内边距 15/16，数字 27px/600，hover 上浮 2px + 阴影 |
| 待办行 | 52px，hover 浅底，分隔线 1px |
| 表单输入 | 高 34，圆角 9，focus 主色边框 + 3px 光晕；textarea 行高 1.55 |
| 更多设置 | 浅底圆角 11，内边距 12（与主行形成两层） |
| 预览卡 | 圆角 14；三个分段各为浅底圆角 10，段间 8 |

三条**视觉规则**，改动时别破坏：

1. **表单不用整块红框**。红色只留给 `@` 动作 chip 和焦点环。整块红边会让人
   以为表单在报错，而它其实只是"正在输入"。
2. **必填描红要等用户碰过**。进入表单时输入框保持中性，失焦后才把空的必填项描红；
   一进来两个红框比不给提示更劝退。
3. **竖屏（≤620px）预览改单列**。两列会把「机械键盘」截成「机械键…」，
   而预览的唯一价值就是让人看清将要写什么。

- 全部用主题 CSS 变量，暗色不写死颜色（`--border` / `--card` / `--muted` / `--primary`）。
- 竖屏：侧栏隐藏、状态卡 2×2、命令栏 sticky；390×844 首屏必须同时看到
  命令栏 + 4 张卡 + 3 条待办。
- 动效只做 opacity / transform / box-shadow，`prefers-reduced-motion` 下全关。
