# BOH 网站性能全面审查报告（只读审查，未改动任何代码）

审查日期：2026-08-25
审查对象：BOHLITEBeta2.5（Vue 3 + Vite 7 + Pinia + Supabase + PWA）
审查方法：三重交叉验证 —— ① 源码静态勘察（路由/组件/数据层）② 构建产物分析（dist 实测 + stats.html）③ Playwright + vite preview 真实浏览器实测（移动端视口，未登录态，测试首页 / 与 /#/user-space）

---

## 一、总体结论

该项目的性能工程基础**明显优于一般同类站点**，以下机制经核实真实有效：

- 路由 100% 懒加载（5 个路由文件全部 `() => import()`）
- UserSpace 五个 tab（Forum/Community/Shows/AI/Messages）全部 `defineAsyncComponent` + KeepAlive + requestIdleCallback 空闲预载 + 弱网感知（saveData/2G 检测）
- UserSpaceMain 数据层有 TTL 内存缓存 + AbortController 取消 + fetch token 防竞态
- homeHeroes 有 localStorage SWR 缓存（先返缓存、后台刷新）
- supabase-vendor（42KB gz）为动态加载，不阻塞首屏 modulepreload 链
- 首屏关键链实测仅约 125KB gzip JS + 20KB gzip CSS，健康
- auth store 懒加载 supabase（`import type` + 动态 loadAuthApi），首屏零数据库 SDK 成本

**以下问题经"源码 + 产物 + 实测"三方交叉验证确认真实存在**，按优先级排列。

## 二、确认存在的问题

### P1：论坛帖子逐卡查询订阅等级 RPC（实测实锤）

**实测证据**（未登录访问 `/#/user-space`）：
```
/rest/v1/rpc/get_user_subscription_tier   ← 被调用 4 次（首屏 4 个帖子作者各一次）
```

**源码证据**：
- `src/views/Forum/components/PostCard.vue:133` — 每张帖子卡片挂载时各自调用 `fetchUserTier(authorId)`
- `src/composables/useUserTier.js:63-122` — **批量接口 `fetchUserTiersBatch()` 已存在**（单次 RPC 查多用户），但 PostCard 未使用
- `useUserTier.js:41-44` — RPC 失败/无数据时**不写缓存**，导致每次组件重渲染都重新发起请求

**影响**：帖子列表 limit=11，最坏 11 次串行 RPC；未登录时 RLS 限制下查询基本无效却每次重试；tier 只影响昵称颜色徽标（纯视觉增强）。

**建议**：
1. ForumMain 拿到帖子列表后一次性 `fetchUserTiersBatch(authorIds)`，PostCard 只读缓存
2. 未登录（无 uid）直接跳过 tier 查询，回退 free 样式
3. 对失败结果写 30-60 秒短 TTL 负缓存，避免无限重试

### P2：未登录打开 /user-space 默认加载论坛全套（意图与注释不一致）

**实测证据**：未登录打开 `/#/user-space` 与 `?tab=posts` 结果完全相同 —— 45 个 JS、11 个 Supabase 请求（posts 列表嵌套 count 查询 + 周报 + 广告）、DOM 732 节点、全部论坛 chunk（ForumMain 41KB gz JS + 49KB gz CSS + markdown-vendor 等）。

**源码证据**：
- `UserSpaceMain.vue:1736` `resolveAccessibleTab` 兜底返回 `'posts'`
- 但 `UserSpaceMain.vue:2534` watch 里的注释写"切换到默认标签（profile）"—— **代码与注释不一致，疑似实现漂移**

**影响**：「用户空间」语义上是个人中心，未登录用户进来即拉论坛动态列表（含广告位、周报查询），首字节成本高。

**建议**：
1. 先确认产品意图：未登录默认 tab 到底是 posts 还是 profile
2. 若保留 posts：把 weekly_reports / advertisements 请求延迟到对应模块进入视口（IntersectionObserver）再发
3. 修正注释，消除意图漂移

### P3：首页 LCP 三跳依赖 + hero 主图偏大

**实测证据**（首页加载瀑布）：
```
document → 35 个 JS → home_heroes RPC（Supabase 往返）→ hero 主图 146KB webp（eager）
```

**源码/产物证据**：
- 首页 hero 数据库驱动（`stores/homeHeroes.ts`），首次访问 FCP→LCP 必须等 JS 执行 + RPC 往返 + 图片下载三跳
- `dist/static/images/2024-1-fangkuai-*.webp` 146KB，移动端 390px 视口下 eager 加载
- 有 localStorage SWR 缓存，但**仅二次访问生效**，首次访问无降级

**建议**：
1. hero 主图加 `srcset/sizes` 响应式多档（390/768/1280），移动端预计可省 60%+ 字节
2. 首屏 hero 图在 index.html 或 chunk 内加 `<link rel="preload" as="image">`
3. 可选：构建时把 home_heroes 快照内联为静态兜底数据（首访秒开，RPC 校验后热替换）

### P4：巨型组件与巨型 CSS 的解析成本（网络无碍，运行时有碍）

**产物证据**（均为未压缩值，gzip 后网络成本可接受）：

| 文件 | 未压缩 | gzip | 说明 |
|---|---|---|---|
| DataAdmin CSS | 575KB | 77KB | 52 个 @media、规则基数大 |
| ForumMain CSS | 304KB | 49KB | 2377 条规则、42 个 keyframes |
| BOHAIMain JS | 662KB | 116KB | 仅 AI tab 使用，隔离良好 |
| ForumMain.vue | 3808 行 | — | 单文件组件 |
| AssetsHubPanel.vue | 3108 行 | — | 单文件组件 |
| UserSpaceMain.vue | 2686 行 | — | 单文件组件 |

**已排除的疑点（交叉验证否定）**：主题×UI风格组合选择器（`.forum-page[data-theme=dark][data-ui-style=flat] …`）经统计仅占 ForumMain CSS 的 2%、DataAdmin 的 3%，**不是**体积膨胀主因，无需为主题机制做手术。

**真实主因**：规则基数大 + 巨型单文件组件导致样式计算和响应式更新粒度粗。

**建议**：
1. 优先拆 ForumMain.vue / AssetsHubPanel.vue（目的不是网络，是渲染更新粒度与可维护性）
2. DataAdmin 的样式按面板子组件拆分 import
3. 42 个 keyframes 中重复定义的（同名动画在不同组件重复声明）可收敛到全局

### P5：PWA 预缓存全量 CSS（96 个文件约 2.5MB 未压缩）——⚠️ 已撤回，勿执行

**产物证据**：`vite.config.js` globPatterns 含 `static/css/*.css`，sw.js 实测预缓存全部 96 个 CSS（含 DataAdmin 575KB、ForumMain 304KB 等低频页面样式）+ 核心 vendor JS。

**影响**：首次访问 SW 安装期后台全量下载，弱网下占用带宽与存储。

**原建议（已作废）**：预缓存收缩为首屏 CSS + 其余走 runtimeCaching。

**撤回原因（2026-08-25 用户确认历史事故后复核）**：全量 CSS 预缓存是**故意防御设计**，不是疏漏。`vite.config.js:108-111` 注释明确记载："发布会替换旧 hash 文件；若旧 SW 仍提供旧 index.html/JS 而 CSS 未缓存，页面会退化为浏览器默认样式"。`index.html:91-96` 的 `bohAssetRecovery` 恢复脚本正是为该事故（页面缓存丢样式）设计的兜底。收缩预缓存清单会在"旧应用壳 + 新部署"窗口期重新打开 404 丢样式的失败模式；且 runtimeCaching SWR 会引入"新 HTML + 旧 CSS"的错配变体。2.5MB 首装成本是已验证可靠的保险费，不值得为省它冒险。**保持现状，不动。**

### P6：compress-images 未纳入默认构建流程

**产物证据**：
- `package.json`：`build:full` 才跑 `compress-images`；`build:ci` 与 `build` 均不跑
- 源图与 dist 产物字节完全一致（xnbag-1.webp 源 297KB = dist 297KB；main1.webp 208KB = dist 208KB）
- dist 中 >150KB 的 webp 有 11 张

**影响**：若日常发布用 `npm run build`，图片压缩完全跳过。大图集中在懒加载路由页（BOH8YearsJourney/Shows/Login），Login 是高频页面。

**建议**：把 compress-images 并入 `build` 主链（或 CI 强制 build:full），并对 Login 页图片单独加严阈值。

### P7（低优先级）：UserSpace 多 tab 全保活的内存驻留

**源码证据**：posts tab 用 `v-show` + KeepAlive，其余 tab v-if + KeepAlive；切走不销毁。配合全局 image-optimizer 把 35/35 张图全标 lazy（实测）。

**影响**：移动端切遍 5 个 tab 后 Forum/AI/Messages 组件与图片全部驻留内存。属于体验（切回秒开）与内存的权衡，非 bug。

**建议**：保持现状；若低端机内存告警，可对 AI tab（BOHAIMain 662KB 未压缩 JS + 聊天历史）加 LRU 驱逐。

## 六、缓存安全红线（后续任何性能优化必须遵守）

历史事故：发布后旧 SW 提供旧 index.html/JS，其引用的旧 hash CSS 已被新部署删除 → 404 → 页面丢样式。现有三层防御：
1. `vite.config.js` globPatterns **全量 CSS 预缓存**（保证 SW 控制的应用壳引用的 CSS 永远可得）
2. `index.html` 内联 `bohAssetRecovery` 脚本（监听 stylesheet/module 加载错误 → 强制清缓存刷新）
3. `skipWaiting + clientsClaim` + version-checker 独立版本指纹检测

任何涉及 SW/缓存的改动必须维持不变式：**SW 服务的任何版本 index.html，其引用的全部 CSS 必须同步可得（预缓存或同版本可取）**。禁止：收缩 CSS 预缓存清单、给 CSS 配 SWR 运行时缓存（会新 HTML 配旧 CSS）、给 sw.js 加长缓存 TTL。

以上全部为建议，未改动任何代码。
