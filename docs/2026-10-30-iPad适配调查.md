# iPad 适配调查（2026-10-30）

> 目标：查清「iPad mini 上不友好」到底出在哪一层。**本轮只调查，未改任何代码**
>（唯一一次临时改动是断点实验，已用 `git diff` 确认还原）。
>
> 证据：`debug-screenshots/ipad/`（8 档 × 3 路由截图 + `report.json`）、
> `debug-screenshots/ipad-pages/`（744 vs 834 × 5 个 tab）、
> `debug-screenshots/ipad-sim/`（三种底栏几何对照 + 744 桌面导航实验）。

---

## 1. 结论先行

**iPad mini 竖屏（744×1133）是唯一「宽屏设备吃手机档」的档位，只差 24px。**

- 底栏被拉到 **704px**（视口 94.6%），5 项各 **138px**，而图标仍是 **17×17**、标签 12px
  → 视觉上是「一台被拉开的 iPhone 底栏」，中间空出一大片。
- 再宽 24px（iPad 768）立刻变成 **336px 居中胶囊**、每项 64px。
- 顶部同理：744 是汉堡（`max-width:768`），820/834 是完整桌面导航。
- 内容单列全宽 744，正文行宽约 **690px**（手机 350 / 桌面主列 600）。

一句话：**iPad mini 本身没问题，是 `768` 这条断点把它判成了手机。**

## 3. 三条根因（带位置）

### 根因 1｜底栏手机档的边界卡在 767，mini 在 744（差 23px）

| 文件 | 行 | 档位 | 效果 |
|---|---|---|---|
| `views/user-center/UserSpace/components/bottom-nav.css` | 937 | `max-width: 767px` | `left:16 / right:16` **拉满**，item 52×44，图标 17 |
| 同上 | 961 | `max-width:767px` + 竖屏 | `left/right:20` **拉满**，item 56×48，标签 12 |
| 同上 | 921 | `768–1024` | item `min-width:64`，胶囊回到内容宽度（实测 336） |
| 同上 | 901 | `≥1025` | item 72，`nav-items max-width:800` |

744 命中 767 档 ⇒ 胶囊宽度 = 视口 − 40 = **704**，grid 五等分 ⇒ 每项 138。
768 命中 921 档 ⇒ 胶囊回到 336。

### 根因 2｜768 处三套判据互不同步

| 判据 | 值 | 位置 |
|---|---|---|
| 顶部导航切移动版 | `max-width: 768px` | `styles/vendor/unified-nav.css:1034`（另有 1571/1644/1658 三处竖屏手机微调） |
| 底栏切手机档 / 平板档 | `max-width: 767px` / `min-width: 768px` | `bottom-nav.css:937` / `:921` |
| 内容切「左栏 + 主列」 | `landscape and min-width:1024 and min-height:600` | `utils/forum-viewport.js:16` |

后果是 **768 一个宽度上出现混搭**：导航按手机（汉堡）、底栏按平板（336 胶囊）
——`ipad-97-portrait-userspace.png` 里就是「汉堡 + 小胶囊」。
744 则是「汉堡 + 拉满」。
而 767 与 768 之间没有任何过渡，旋转或分屏跨过 24px 就是一套完全不同的 UI。

### 根因 3｜竖屏平板没有多栏，内容列只靠 720 上界

- UserSpace：`.tab-page .page-content { max-width: 720px }`（`shell-community.css:154`）
  ⇒ 744 屏上 720 = 96.8%，等于全宽；正文 690，一行中文约 45 字。
- 首页论坛层：`.forum-container` 无上界，实测 728（比 720 还宽）。
- 对照：≥1024 横屏/桌面有「左 rail + 主列 ~600 + 右栏」，行宽回落到 600 左右。
- ⇒ 大屏只在「横屏」时提升信息密度，竖屏一律单列全宽，一屏仍只放得下 1–1.5 张帖子。

## 4. 外部依据（都指向同一件事）

1. **iPadOS 18 起，系统 tab bar 从底部搬到顶部。**
   WWDC24《Elevate your tab and sidebar experience in iPadOS》原文：
   >「The bar now sits at the top of the app, where it is closer to other navigation controls…
   > It also shares a space with the top bar, **allowing more of the app's content to be visible**.」
   >「a new compact look that **reduces the amount of unused vertical and horizontal space**」

   Apple 中国新闻稿同一句：「标签页栏经过重新设计，现悬浮于 app 内容上方……可为内容实现无边框设计。」
   ⇒ 在 iPad 上，**底部一条拉满的 tab bar 属于上一代 iOS 形态**，iPadOS 用户看到的系统 App 已经不是这样了。

2. **HIG 派生规则（iPad 不是大号 iPhone）**：regular width 应使用多栏/侧边栏，
   >「Avoid single-column full-width layouts on large screens.」
   >「In regular width, replace the iPhone tab bar with a sidebar.」

   iPad mini 744pt 属于 **regular width**（竖屏 regular 下界约 744）。

3. **mini 是家族里唯一的边缘机型**：744 是 iPad 全系最小逻辑宽度，且分屏/侧拉极常用
   （1/2 分屏 = 372 → 退回手机档，这是正常的；问题只在全屏竖屏）。

## 5. 关键实验：744 装得下完整导航

把 `unified-nav.css` 4 处 `max-width: 768px` 临时降到 700、`Home/style.scoped.css`
的槽位 `min-width:768` 降到 701，744×1133 渲染结果（`ipad-sim/744-desktopnav-experiment.png`）：

- 完整导航：🍎 + 首页/社区/探索/服务/关于 + 登录，**一行放下，无换行、无截断**
- 横向溢出：`scrollWidth = 744`（0 溢出）
- 首页底栏消失（槽位按 `min-width` 关闭），页面只剩顶部一套导航

⇒ 「744 太窄放不下桌面导航」不成立，它只是被 768 拦住了。

底栏几何三种方案实测（`ipad-sim/744-messages-*.png`）：

| 方案 | 胶囊 | 单项宽 | 备注 |
|---|---|---|---|
| 现状（767 档拉满） | 704×75 @x=20 | 138 | 图标 17 |
| 借用平板档（336 居中） | 336×80 @x=204 | 64 | 图标 20，选中态会被压成圆形 |
| 只收窄到 520 居中 | 520×75 @x=112 | 101 | 图标字号仍 12 |

## 6. 建议的判据象限（待决策）

现有判据只在「宽度」一个维度上切，所以横屏矮屏（折叠屏展开）与竖屏大屏（平板）会互相踩。
建议按 **方向 + 宽度** 分四象限：

| 象限 | 顶部导航 | 底部导航 | 内容 |
|---|---|---|---|
| 竖屏 且宽 ≥ 744（iPad 全系竖屏） | **桌面导航** | 不显示，或 336 居中 | 单列 + 上界（720 或更窄） |
| 横屏 且宽 ≤ 1023（折叠屏展开，**已做**） | 汉堡 | **右侧竖胶囊** | 600 锁宽 |
| 横屏 且宽 ≥ 1024（iPad 横 / 桌面） | 桌面 + 左 rail | 无 | 主列 + 右栏 |
| 竖屏 且宽 ≤ 743（手机 / 折叠屏合上） | 汉堡 | 贴底拉满 | 全宽 |

三档实现成本：

- **A｜只治拉伸**：给 767 档加 `max-width: min(100% - 32px, 520px)` + 居中。
  改 1 处，不动导航。744 从 704→520（item 101）。**治标**。
- **B｜把 mini 抬进平板侧（推荐）**：导航与底栏的手机档上限统一到 **700**，
  竖屏手机微调三处同步。改动 4+3+2 处边界，744/768 都变成「桌面导航 + 336 胶囊 /
  无底栏」，与 820/834 一致。风险面只有 700–768 这 68px（mini 744 + 少量 Android 平板）。
- **C｜B + 竖屏多栏**：再给竖屏平板加内容上界或「主列 + 侧栏」，
  让竖屏也能一屏两张卡。结构改动，需要产品确认（大屏留白 vs 密度）。

## 7. 附带发现（不是 iPad 特有，但在 iPad 上都能看到）

1. **「我」tab 未登录空态被顶部动态导航卡遮住**：「登录以查看我的」被卡片压掉一半，
   744 与 834 都复现 ⇒ 顶部 inset 少了卡片高度（预存 bug）。
2. **`/forum` 独立页两种壳**：≤768 显示底栏（704），>768 不显示 → 同一路由两套骨架。
3. **`/forum` 全档约 1% 横向溢出**：744→751、768→776、1024→1034、1133→1144
   （`/` 与 `/user-space` 都是 0）⇒ 论坛页自身布局问题，与 iPad 无关。
4. **768 竖屏帖子图片被裁成横条**：3 列 `object-fit:cover` 在 768 宽下每格 230 宽、
   高度不足，图片主体被切（`ipad-97-portrait-userspace.png`）。

## 9. 实施记录（B｜2026-10-30）

### 9.1 改了哪些判据

边界 **768 → 700**（手机档 `≤699`，平板档 `≥700`）。四处必须同源，漏一处就会再次出现
"顶部桌面导航 + 底部拉满"或"汉堡 + 居中胶囊"的错配：

| 文件 | 位置 | 原值 → 新值 |
|---|---|---|
| `src/styles/vendor/unified-nav.css` | 移动导航档 + 竖屏修正档 + dvh 降级档（共 4 处） | `max-width: 768px` → `699px` |
| `src/components/UnifiedNavbar/style.scoped.css` | 竖屏 mini 条 + 岛高度（2 处） | 同上 |
| `src/components/UnifiedNavbar/index.vue` | `portraitMiniQuery`（JS） | 同上 |
| `src/components/UnifiedNavbar/index.vue` | `handleResize` 的 `innerWidth > 768` | → `> 699` |
| `src/views/user-center/UserSpace/components/bottom-nav.css` | 平板块 `min-width: 768` | → `700` |
| 同上 | 手机档 `max-width: 767`（2 处） | → `699` |
| `src/views/Home/style.scoped.css` | 首页底栏槽位 `min-width: 768` | → `700` |
| `src/style.css` | AI 页 `--bohai-standalone-nav-height` 镜像档 | `768` → `699` |

### 9.2 实测（改前 → 改后）

| 档位 | 改前 | 改后 |
|---|---|---|
| 744 iPad mini 竖 | 汉堡 + 底栏 704px（94.6% 屏宽，item 138） | **完整导航 + 336 居中胶囊（item 64）**，与 820/834 完全一致 |
| 768 iPad 9.7 竖 | 汉堡 + 336 胶囊（半吊子混搭） | **完整导航 + 336 胶囊** |
| 700 边界 | — | **完整导航**（logo + 5 链接 + 搜索 + 登录，一行放下、零溢出） |
| 699 边界 | 手机形态 | 手机形态（不变） |
| 390 / 430 手机 | 汉堡 + 拉满底栏 | **不变** |
| 939 / 951 / 594 横屏展开 | 右竖胶囊 | **不变**（探针 42/42） |

首页底栏槽位边界同步到 700：700–1023 竖屏首页不再挂底栏（顶部完整导航足够），
避免"顶部完整导航 + 底部又一条"。

### 9.3 顺手修掉一个上一轮引入的真缺陷

`fold-nav-rail.css` 里"让顶部导航以内容区居中"原本只用 `left: -gutter/2`。
surface 宽度已接近满宽（769 下 745、794 下 770、939 下 860），左移 44 就**越出视口**：

- 实测 769 / 794 的 `.nav-logo` `left = -11px`（logo 被裁掉一截），900 下 -3px。
- 正解：同时给 `max-width` 加上限 `calc(100% - 24px - gutter)`，宽度先收进盒子，
  居中余量 ≥ 56 > 44，左移就不再越界。
- 改后 769/794/844/900 的 logo `left = 33`，939 起导航中心 = 内容列中心（426 vs 426）。

> 另一个被否掉的方案：给 `#unified-nav-container` 加 `padding-right`。
> 实测算出 `padding: 0px` —— 被 UnifiedNavbar scoped 的 `padding: 0 !important` 压掉
> （`landscape-rail.css` 里早有同样记录）。

### 9.4 探针与反证

新增 `scripts/probes/probe-responsive-tiers.mjs`（85 条断言）：12 个档位 × 形态身份，
锁「导航形态 / 底栏形态 / 首页槽位 / 链接集合一致 / 无横向溢出 / 699-700 边界互斥」。
已在 `scripts/lib/gate-map.json` 登记（unified-nav.css / bottom-nav.css / Home 样式 /
UnifiedNavbar 四个入口）。

反证（每次只撤一处，确认真的会红）：

| 撤掉什么 | 结果 |
|---|---|
| `bottom-nav.css` 手机档回 767 | E 红 ×3：700/720/744 的底栏变 668/688/**712** 拉满条 |
| `unified-nav.css` 移动档回 768 | A/B/D ×8 + H 全红：700–768 全部退回汉堡形态 |
| `Home/style.scoped.css` 回 768 | G 红 ×3：700/720/744 首页重新挂上底栏 |
