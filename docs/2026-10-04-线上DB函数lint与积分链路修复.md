## 1. ⭐ 最重要的一个：`reserve_ai_points` 每次都抛 42883

### 证据链

```
$ supabase db lint --linked --level warning
  "function": "public.reserve_ai_points",
  "level": "error",
  "message": "function hashtextext(text) does not exist",
  "query": "SELECT pg_advisory_xact_lock(hashtextext('boh-ai-points:' || p_user_id::text))",
  "sqlState": "42883"
```

线上直查（只读）确认：

| 表达式 | 结果 |
| --- | --- |
| `select hashtext('a')` | `1075015857` ✅ |
| `select hashtextext('a')` | `ERROR 42883: function hashtextext(unknown) does not exist` ❌ |

PostgreSQL 只有 `hashtext(text)` 与 `hashtextextended(text, int8)`，**没有 `hashtextext`**。

### 影响

- 函数体第 43 行 `perform pg_advisory_xact_lock(hashtextext(...))` ⇒ **该函数每次调用都失败**。
- 调用方 `supabase/functions/api-key-vault/index.ts:2119-2126`：
  ```ts
  const { data, error } = await client.rpc('reserve_ai_points', { ... });
  if (error) throw error;      // ← 直接抛
  ```
- ⇒ 积分预扣链路从未成功。这与 `docs/2026-10-02-BOHAI模型倍率与积分制度审查.md`
  的「**积分只发不收**」结论**互相印证** —— 之前把它归因为「制度设计」，实际有一半是**这个 bug**。

### 修复

迁移：`supabase/migrations/2026100401_fix_reserve_ai_points_hashtextext.sql`

- 只改一处：`hashtextext(` → `hashtext(`。
- 其余函数体**逐字节取自线上 `pg_get_functiondef`**（已验证：`diff` 输出只有第 43 行不同）。
- 已在事务内验证修复后的表达式可用（`begin; select pg_advisory_xact_lock(hashtext(...)); rollback;` → 无错）。
- 幂等：`create or replace`，签名 `(uuid, uuid, text, integer, numeric)` 与线上一致。

### ⚠️ 这是行为变更，不是纯技术修复

修好之后，**已登录的非游客用户**在 AI 调用时**会开始真正预扣/结算积分**（在此之前是静默不扣）。
也就是说：**修复会改变用户的积分余额曲线**。是否现在修、要不要先公告、要不要先给补偿，
属于产品/经济侧决策 —— **不要在没有明确同意的情况下 push**。

### ✅ 最终结果（2026-10-04 21:4x，**已 push 并验证**）

这个函数其实有**两个**串联的运行期错误 —— 修掉第一个才暴露第二个：

| # | 错误 | 迁移 | 发现方式 |
| --- | --- | --- | --- |
| 1 | `42883 function hashtextext(text) does not exist` | `2026100401` | `supabase db lint` |
| 2 | `42702 column reference "reason" is ambiguous`（OUT 参数 `reason` 撞 `points_transactions.reason`） | `2026100402` | **`db lint` 没报**，是「事务内真跑一次 + ROLLBACK」抓到的 |

> 第 2 条与 `MEMORY.md` 记录的 2026-10-03 `toggle_forum_comment_like` 是**同一类事故**
> （`RETURNS TABLE` 的 OUT 参数名与表列名同名 ⇒ plpgsql 体到首次执行才解析 ⇒ 运行期 42702）。
> 修法是给表加别名 `pt` 并把四个列名全部限定（不只改 `reason` 一处，避免将来再加 OUT 参数又踩）。

**两条独立路径验证**：

| 路径 | 结果 |
| --- | --- |
| ① 直读 DB `pg_get_functiondef` | `hashtextext` 出现 **0** 次、`hashtext(` **1** 次；与修复前逐行 diff **只有 1 行不同**；`migration list` 的 Remote 列已登记 `2026100401` / `2026100402` |
| ② 真跑一次（事务内 + `ROLLBACK`，不留痕） | `reserve_ai_points(...)` → `{"allowed": true, "points_estimate": "0.000002", "points_balance": 11, "reason": "OK"}` ✅<br>`settle_ai_points(...)` → `{"settled": "0"}`（不存在的预约，优雅返回）✅ |

**`supabase db lint` 的 error 总数：6 → 5**，`reserve_ai_points` 已从列表消失。

**回滚**：修复前的原始定义留在 `/tmp/ROLLBACK_reserve_ai_points.sql`，`create or replace` 可直接还原。

### ⚠️ 这是行为变更，不是纯技术修复

修好之后，**已登录的非游客用户**在 AI 调用时**会开始真正预扣/结算积分**（在此之前是静默不扣）。
也就是说：**修复会改变用户的积分余额曲线**。用户已确认「立刻 push」，但**建议同步观察积分流水**，
并考虑是否要给存量用户公告或补偿。

## 2. 已修复的第 3 条：`execute_lottery_draw`（抽奖开奖）

**报错**：`column "fulfillment_id" of relation "lottery_notification_jobs" does not exist`（42703）

**根因（已定位到具体行）**：函数往 `lottery_notification_jobs` 的 insert 列清单里写了 `fulfillment_id`，
但这一列**只存在于 `lottery_admin_audit_logs`**（`2026081406_lottery_operations_and_retention.sql:72`
加的 `fulfillment_id uuid null references lottery_winner_fulfillments(id)`）。
`lottery_notification_jobs` 建表于 `2026052001:50`，此后**所有迁移都没给它加过这一列**。
⇒ 疑似 `2026081904:491` 的 insert 列清单**从审计日志那条复制而来**。

**影响**：走「保底中奖」分支时整个 `execute_lottery_draw` 事务失败 ⇒ **开奖不可用**。

**修复**：`2026100403_fix_execute_lottery_draw_fulfillment_id.sql` —— 从该 insert 的列清单与
values 里去掉 `fulfillment_id`（**不动表结构**，纯函数体修复）。上面
`returning id into v_fulfillment_id` 那条写的是 `lottery_winner_fulfillments`（另一张表），本身没问题，保留。

**验证**：`supabase db lint` 的 error 总数 **5 → 4**。

## 3. 已排除的一条：「`p_visibility` 疑似隐私缺陷」→ **不是缺陷，是未实现的预留参数**

17 个 warning 里 `p_visibility` 出现 5 次，一度怀疑「分享可见性功能没接线」。**查到底后排除**：

| 证据 | 结论 |
| --- | --- |
| 表约束 `boh_cloud_share_channels_visibility_chk` = `CHECK (visibility = 'token')` | **表只允许 `'token'` 一个值** |
| 线上 6 行数据的 visibility 分布 | 全部是 `'token'` |
| `upsert_my_boh_cloud_share_channel` 三个分支 | 全部硬编码 `visibility = 'token'` —— 与约束**一致** |
| `set_my_boh_cloud_share_visibility(p_visibility)` | 忽略参数、直接传字面量 `'token'` |
| 前端 `src/utils/api/boh-cloud-api.js:741` | `const TOKEN_SHARE_VISIBILITY = 'token'`，4 处都传它；**没有可见性选择 UI** |

⇒ 这不是「用户选了 A 却写成 B」的泄漏，而是**「多档可见性」这个功能从未实现**：
`p_visibility` 是**预留参数**，表约束、后端、前端三处都统一在 `'token'` 上，**fail-closed**。

**结论：不需要修。** 若要真正支持多档可见性，那是一次**功能开发**（要同时改约束 + 三个函数 + 前端 UI），
不是 bug fix。建议把这几个 `p_visibility` 参数要么实现、要么删掉（现在是会误导人的死接口）。
