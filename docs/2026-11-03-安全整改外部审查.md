## 0. 总结论

今天已上线的一批整改中，profiles 敏感列、生日接口、`user_impressions`、CSP 上报、配额回滚越权、匿名触发器执行面、Vault 化 cron 令牌、推送 SSRF 白名单等措施，**在代码与线上目录层面均有可复核证据，主路径未发现新的可直接越权漏洞**。

但不能据此宣布“登录链路已收口”或“可直接进入 RC 安全放行”：

1. **通行密钥（passkey）仍直连 GoTrue，绕过了 `auth-login` EF 的服务端封禁/风控检查**；这正是本次 `auth-login` 注释中明确指出“客户端检查可被绕过”的那类路径。
2. `refund_lab_usage` 的 `p_device_id` 过滤丢失已确认，不越权但会造成跨设备退错账。
3. “18 张表在 `src` 零 `.from()` 引用”的入选标准不准确；这些表实际被管理后台动态表名引用。此次没有造成 anon 故障，只因为管理路由保留 authenticated SELECT 且路由强制 admin。
4. 表级 revoke 仍不能阻断 view / RPC 的间接出口；线上确有匿名可读的 `lottery_failure_stats` view 与匿名可执行抽奖 RPC 引用被收权表。若把这些视为产品公开口径则可接受，否则“匿名读不到”的结论不成立。
5. CSP 仍为 Report-Only 且 `script-src` 含 `'unsafe-inline'`，当前只能作为观测和未来收紧的基线，不能视为已生效的 XSS 边界。

**建议结论：继续整改，不阻断今天已上线的安全修复；但在修复 passkey 服务端封禁旁路、refund 设备过滤、明确间接公开口径前，不建议做 RC 安全终审通过。**

## 2. 主要发现

### F1｜高｜passkey 登录绕过新的服务端登录防线

**证据：**

- `src/utils/api/auth-api.js:430`：`signInWithPasskey = () => supabase.auth.signInWithPasskey()` 仍直连 GoTrue。
- `src/stores/auth.ts:898-918`：passkey 成功后只做客户端 `checkBanAfterSignIn()`。
- `supabase/functions/auth-login/index.ts:209-268`：服务端封禁校验只存在于密码 / `auth-login` EF 路径。

**影响：**

被封禁用户若已注册 passkey，可通过 GoTrue API 获取有效访问令牌。前端会把 UI 登出，但直接持有 token 的调用者不受该客户端检查约束；同时 passkey 也不经过登录失败计数、Altcha 与服务端封禁检查。OAuth 入口同样不在 `auth-login` 的唯一入口内，是否构成实际旁路取决于当前启用的第三方登录。

**建议：**

短期至少评估“封禁时立即撤销所有 session + RLS/服务端函数统一拒绝封禁用户”是否足够；更稳妥的方案是在签发会话的服务端边界统一执行封禁校验（例如可行的 Auth/session 层钩子或撤销机制），或在服务端防线覆盖前临时关闭 passkey 登录。不能只用前端 `signOut` 作为封禁边界。

---

### F2｜中高｜Altcha 当前更像低成本 PoW，不应表述为可靠“人机验证”

**证据：**

- `supabase/functions/altcha-challenge/index.ts:21-25` 直接下发挑战。
- `supabase/functions/_shared/altcha.ts:110-113` 只验证算法解与 HMAC，不验证真实用户交互。
- `ALTCHA_MAXNUMBER` 已单独配置，具体值未读；代码默认仅 75000。

**影响：**

被触发 `requireAltcha` 后，自动化攻击者同样可以请求挑战并程序化求解；它增加的是计算成本，不是“只有人才能完成”的边界。若威胁模型包含分布式撞库，不应把 Altcha 作为唯一人机证明。

**建议：**

把文案和威胁模型改成“PoW 限速因子”，并显著提高求解成本；或接入真实 CAPTCHA / Turnstile 类验证。保留账号、IP、设备维度失败计数仍是核心防线。

---

### F3｜中高｜`refund_lab_usage` 确认丢失设备过滤，且 `flow_type` 可选会退错账

**证据：**

- 线上函数体与 `supabase/migrations/2026110310_refund_lab_usage_definer.sql:66-75` 一致。
- 登录分支只按 `user_id = p_user_id` 匹配，完全忽略 `v_device_id`。
- `p_flow_type is null` 时取该用户“最新任意 flow”的一条。

**判权结论：**

未发现认证绕过：匿名用户传 `p_user_id` 会被拒，登录用户只能传自己的 UID，登录用户也不能借匿名 device 通道删除匿名记录；`search_path` 已固定且对象均 schema-qualified。

**影响：**

同一用户多设备时会删除另一台设备的最新记录；`flow_type` 为空时会退错流程。属于账目完整性回归，不是越权。

**建议：**

在 `p_user_id is not null` 分支补：

```sql
and (v_device_id is null or device_id = v_device_id)
```

同时建议把 `p_flow_type` 改必填，并为“原实现 device 过滤不能丢失”“flow 为空不能退任意 flow”补守卫测试。

---

### F4｜中｜匿名 device_id 仍是裸客户端字符串凭证

`refund_lab_usage` 的匿名分支只要求 `user_id is null and device_id = v_device_id`。`device_id` 可猜测、可伪造，且当前未见签名、HMAC、IP 绑定或服务端首次发放记录。Lab 当前无消费方，所以是潜在风险；等 BOHAI Work 接账后会变成实际账目凭证。

建议将来改为服务端发放不可伪造的设备令牌，或至少保存加盐 device hash 并绑定 IP / UA 指纹；同时明确 device_id 轮换和冲突策略。

---

### F5｜中｜anon 收权入选标准被动态调用推翻；表级 revoke 不等于关闭间接出口

**动态引用事实：**

18 张被收权表中的多张实际出现在管理后台动态表配置 / 嵌入查询中，例如：

- `src/views/DataManagement/config/tables.js`
- `src/views/DataManagement/query-config.js:226`
- `src/views/DataManagement/DataAdmin.vue`

因此“`src` 零 `.from()` 引用”不是事实。此次未炸，是因为 `/admin/data-management` 在 `src/router/routes/admin.ts:5-20` 声明 `requiresAdmin: true`，且迁移只撤 anon、保留 authenticated SELECT。

**间接出口事实：**

线上目录核查发现：

- `lottery_failure_stats` 是 anon SELECT view，返回 `user_id`、username、参与次数、胜负、失败率、最近参与时间，定义引用 `lottery_draw_logs` / `lottery_entries`。
- `get_community_lotteries`、`get_home_lottery` 是 anon EXECUTE 的 SECURITY DEFINER RPC，抽奖后返回 winner `user_id` / username。
- `get_my_boh_cloud_share_viewers` 虽 anon EXECUTE，但函数第一分支拒绝未登录，当前未见泄露。
- `get_active_post_reward`、`subscribe_with_points` 等也以 RPC 方式访问部分被收权表，但返回口径分别像公开活动信息 / 服务端定价校验。

**结论：**

本次 18 张表的直接 PostgREST 面确实收窄，但如果安全目标是“匿名无法读到这些表的数据”，当前并未达成；view / RPC 仍是独立出口。公开抽奖统计和获奖者可能是产品预期，需要产品/安全共同确认。

**建议：**

- 修正文档中的入选标准，从“零 `.from()`”改为“无匿名路由、匿名 RPC、公开 view 依赖”。
- 对 anon 可读的 view / RPC 建一份“公开数据出口清单”，逐条标注是否允许匿名可见。
- 后续收权前先跑“表 → 前端调用点 / view / RPC → 角色与返回列”的依赖图，不能只 grep 字面 `.from()`。

### F6｜低中｜触发器函数 anon 面已清零，但 authenticated 仍残留 14 个执行权

线上 53 个触发器函数中 anon EXECUTE=0；这 37 个匿名授权的回收符合 Postgres 触发器语义，且线上函数体 / cron 扫描未发现显式调用者。

但仍有 14 个触发器函数保留 authenticated EXECUTE，包括：

- `archive_boh_ai_*`
- `boh_enqueue_web_push`
- `enforce_forum_*`
- `sync_forum_*`
- `sync_lottery_winner_fulfillment_from_draw_log`
- `sync_official_forum_card`

本地未找到前端直接 RPC 调用，历史迁移中有显式 grant，像是遗留授权。触发器本身不依赖这些 EXECUTE 权限，建议下一轮在回归测试后从 anon、authenticated、PUBLIC 一并回收，只保留 service_role / postgres。

### F7｜中｜商城订单链路存在三个账目/兼容性残留

1. **混合支付模式计算错误**：`supabase/migrations/2026110312_shop_order_rate_limit.sql:140-171` 中，points-only 分支会把 `v_order_payment_mode` 重置为 `points_only`；points + rmb 混合购物车不会稳定得到 `combined`。当前线上无 `rmb_only` 在售商品，但商品上架后会变成订单口径错误。
2. **`total_points > 0` 与纯 RMB 订单冲突**：线上 `shop_points_orders` 约束仍要求 `total_points > 0`，与函数中的 `rmb_only` 分支不兼容；当前只是因为没有纯 RMB 商品而未触发。
3. **现有 `create_shop_order_with_points` 也是运行期死函数**：`supabase/migrations/2026090905_points_ledger_shop_checkin.sql:176-195` 插入 `status='pending'`，而线上 CHECK 只允许 `preparing/shipped/completed/cancelled`。交接文档中“不是死函数（能跑）”的说法不准确；它会走到插入并违反 CHECK。该函数 authenticated 可执行但前端零调用。

**建议：** 下一批迁移同时修 payment_mode 状态机、`total_points >= 0` / payment-mode 条件约束、drop 旧的 `create_shop_order_with_points(jsonb,text,text)`，并补“混合购物车必须 combined”“纯 RMB 订单可插入”的事务级测试。

### F8｜中｜Cloudflare 安全头注入失败会静默放行发布

`scripts/cloudflare-security-headers.mjs:8-13` 明确把 token 缺失、权限不足、网络失败设计成“告警 + exit 0”。当前线上头已实测正常，但未来 token 失效或 Cloudflare API 变更时，CI 仍可能全绿并发布一个失去 CSP/HSTS/XFO 的站点。

**建议：** 增加发布后只读探测门禁：对线上域名断言 CSP、`Reporting-Endpoints`、HSTS、`X-Frame-Options` 至少存在；失败时阻断发布。当前观察期可以只报警，RC/正式发布时应阻断。

---

### F9｜低中｜CSP 当前只是观测基线，尚不是可依赖的 XSS 防线

线上 CSP 为 Report-Only，且：

- `script-src 'self' 'unsafe-inline' https://static.cloudflareinsights.com`
- `frame-ancestors 'none'` 在 Report-Only 下不生效；当前实际点击劫持保护依赖 `X-Frame-Options: DENY`

这意味着即使未来转 enforce，只要 `'unsafe-inline'` 仍存在，CSP 对注入型 XSS 的约束也有限。今天的上报端点补全了观测闭环，这是正确方向，但不要把它描述为“CSP 防护已上线”。

**建议：** 先消除内联脚本依赖（nonce/hash 或移除内联），再按指令分批 enforce；当前 `object-src/base-uri/form-action` 可优先。

---

### F10｜低｜推送白名单方向正确，但存在两个运营性边界

- DB 侧拒绝任何带端口 authority，EF 侧允许显式 `:443`；真实浏览器端点通常不带端口，影响低，但两层的“同源名单/端口口径”应逐字一致。
- 当前名单覆盖主流 Chromium/FCM、Firefox Autopush、Safari Apple Push、WNS。公开资料中 Opera 主流实现走 FCM，个别资料仍提到 `push.opera.com`；若未来某浏览器新增域名，订阅会被 CHECK 约束明确拒绝，这是优于静默 SSRF 的失败模式。

建议保持“新增域名必须同时改 DB 函数与 EF 白名单”的测试，并统计订阅 host 分布 / 失败率，用于发现新域名。

---

### F11｜低｜`img-src` 通配符可接受，但建议拆分“CSP source pattern”和“精确 origin”

`https://*.supabase.co` 对 `img-src` 的风险低于脚本/连接通配符，且与现有 `connect-src` 口径一致；头像缺口是实测事实，放行必要。真正的问题是同一数组里混入 CSP pattern 与精确 origin，依赖注释提醒“不能传给 `isAllowedImageSrc()`”。

当前 `isAllowedImageSrc()` 只消费 `AI_ANSWER_IMAGE_ORIGINS`，通配符尚未造成实际误判；测试也已断言 Supabase 图片源存在于 CSP 清单。建议拆成 `CSP_IMAGE_SOURCES` 与 `EXACT_IMAGE_ORIGINS` 两类，避免未来调用方误用。

---

### F12｜低｜线上存在 3 个 ACTIVE 的 `mail-keepalive` 部署名（含 2 个 UUID slug）

只读部署清单显示：除正常 `mail-keepalive` 外，还有两个 UUID slug 的同名 ACTIVE 历史部署。当前没有证据说明其代码可滥用或暴露秘密，但它们不在仓库当前函数清单来源内，属于部署库存异常。

建议用 Management API 核对这两个 UUID 函数的入口、JWT 配置与最近调用日志；确认无人使用后下线。下线属于破坏性操作，应单独确认。

## 3. 对交接文档 6 个重点问题的直接回答

1. **`refund_lab_usage` 是否有绕过路径？**  
   未发现认证绕过；匿名越权已收窄。`p_device_id` 过滤丢失确认是本次引入的账目回归，应尽快修。

2. **触发器函数收权是否会断显式调用？**  
   仓库与线上目录未发现库内 / cron 显式调用；触发器本身也不依赖调用者 EXECUTE。anon 收权安全。剩余 14 个 authenticated 授权是卫生残留。

3. **删除 `place_shop_order_with_points` 的依据够不够？**  
   对仓库、线上函数体、cron、`pg_stat_statements` 的核查均未发现调用；原函数每次必抛 42P01，因此也不存在“外部依赖它成功执行”的现实路径。删除可接受。真正的未知面只可能是仓库外私有脚本，但它此前也必然失败。

4. **anon 表级收权标准是否遗漏间接路径？**  
   是。动态管理后台引用推翻“零 `.from()`”表述；view / RPC 也确实提供间接出口。功能未坏，但安全语义必须改成“只收直接表级授权”。

5. **推送域名白名单是否完整？**  
   主流域名当前足够，白名单优于黑名单的决策成立。新增域名会造成可见的订阅失败，这是正确取舍；需监控 host 分布，并修 DB/EF 显式 443 端口口径。

6. **CSP `img-src` 通配符是否过宽？**  
   风险低，且为修复真实头像缺口的必要项；建议未来收敛到项目 ref 或拆分 pattern / exact origin。当前 CSP 更大问题仍是 Report-Only + `script-src 'unsafe-inline'`。

8. 核实并下线两个 UUID slug 的历史 `mail-keepalive` 部署。
9. 重新评估 Altcha 的 threat model；若目标是防真人撞库，改用真正的人机验证。

### 8.1 F1 修复：封禁下沉到 GoTrue（不关闭 passkey）

**产品决定**：passkey 好用，保留。

**收口点**：不改登录方式，改**签发方**。迁移 `2026110321_mirror_ban_to_auth_users.sql` 让
`admin_ban_user` / `admin_unban_user` 在写 `profiles` 的同一个事务里，同步写
`auth.users.banned_until`。

**依据（GoTrue 源码，`internal/api/passkey_authentication.go`）**：passkey 断言校验通过后、
`issueRefreshToken` **之前**有一道

```go
if user.IsBanned() {
    return apierrors.NewForbiddenError(apierrors.ErrorCodeUserBanned, "User is banned")
}
```

`IsBanned()` 读的就是 `auth.users.banned_until`。因此写入这一列即可让 passkey 在服务端被
403 `user_banned` 拒绝；OAuth 与密码走 `/token` 的同款检查，一并覆盖。**不需要删除用户的
passkey 凭据**，解封后原凭据照常可用（解封同步清空 `banned_until`）。

**两个口径的分工**（避免「双真源」误解）：

| 口径 | 位置 | 谁在读 | 语义 |
| --- | --- | --- | --- |
| 业务 / 展示 | `profiles.is_banned`、`banned_until`、`ban_reason` | 管理后台列表、徽标、`checkBanAfterSignIn` | 为什么被封、封多久 |
| 执行 | `auth.users.banned_until` | GoTrue（所有签发路径） | 能不能拿到 token |

两者由同一函数、同一事务写入。永久封禁写 `now() + interval '100 years'`（不用 `'infinity'`，
Go 侧解析依驱动版本而异；100 年也是 GoTrue admin API 的 ban_duration 上限量级）。

**对账 SQL**（若有人绕过 RPC 直接改 `profiles`，两份状态会分叉 —— 表现为「后台显示已封禁但还能登录」）：

```sql
select p.id, p.username, p.is_banned, p.banned_until, u.banned_until as auth_banned_until
  from public.profiles p
  join auth.users u on u.id = p.id
 where p.is_banned = true
   and (u.banned_until is null or u.banned_until <= now());
```

**验收**：线上函数体实测含 `update auth.users` + 100 年兜底（ban）与 `set banned_until = null`（unban）；
`check:db-lint` 仍绿、`security:anon-check` 116/116 不变。

**残留（已知、可接受）**：

1. 已签发的 access token 在 JWT 有效期内仍可用 —— 由封禁流程里的 `admin-revoke-session`
   撤销 refresh token 兜住，窗口等于 access token 剩余寿命。
2. OAuth 被拒时 GoTrue 通过 URL 参数回传 `error_code=user_banned`，前端 OAuth 回调没有专门
   文案映射，用户可能看到英文描述。属体验问题，不影响拦截。
3. 前端文案已补：`toPasskeyLoginMessage` 把 `user_banned` 映射为「该账号已被封禁，无法登录」，
   且**优先于**「这台设备还没有通行密钥」的引导（否则用户会反复去加凭据）。
