## 二、P0：邮箱登录绕过了整个闸门

### 2.1 证据链

`src/utils/api/auth-api.js` 的 `signIn()` 按登录标识是否含 `@` 分流：

```js
// 修改前
if (!safeLoginId.includes('@')) {
  const edge = await invokeAuthLoginEdge(...);   // 方块 ID → EF（有闸门）
  ...
}
const { data, error } = await supabase.auth.signInWithPassword({  // 邮箱 → 直连 GoTrue
  email: resolvedEmail, password: safePassword
});
```

三处事实叠加，构成一条完整的旁路：

1. **登录框文案就是「请输入方块 ID 或邮箱地址」** —— 这条路径面向用户开放，不是死代码。
2. **直连 GoTrue ⇒ 不写 `auth_attempt_events`**，而 `should_require_login_altcha` 的全部判据
   都来自这张表 ⇒ 邮箱被撞库时，闸门**永远是哑的**（连被撞的事实都看不见）。
3. **GoTrue 侧也没有兜底**：`GET /config/auth` 实测 `security_captcha_enabled = false`
   （`provider=turnstile` 但未启用），`external_email_enabled = true`、`disable_signup = false`。

即：同一批修复里，方块 ID 登录被限制了失败次数并会触发 Altcha，而换成邮箱就能无限次试密码。

### 2.2 修法

两种标识都走同一个 `auth-login` EF 入口，删掉直连分支（`src/utils/api/auth-api.js`）。

三条前提都已在代码里核实过，不是假设：

- **EF 本来就支持邮箱**：`_shared/resolve-login-id.ts:61` 对含 `@` 的输入直接返回，
  **不做任何库查询** ⇒ 走 EF 不会引入新的枚举面。
- **EF 反而更严**：密码通过后还会在服务端查 `is_banned/ban_reason/banned_until`，
  命中就 `signOut` 并返回 403 —— 直连路径没有这一步（原先只有客户端检查，可被绕过）。
- **失败仍收敛为 `INVALID_CREDENTIALS`**，不区分「账号不存在」与「密码错误」。

顺带修掉一个文案缺陷：EF 对未验证邮箱返回的是中文文案「请先验证邮箱后再登录。」，
旧的友好提示只按 `'email not confirmed'` 匹配，永远命中不了；改为按 `code === 'EMAIL_NOT_CONFIRMED'` 判定。

### 2.3 反证

把邮箱分支临时改回直连后，新增用例**5 条立刻变红**（已实测），恢复后 27 条全绿：

```
× 输入是邮箱 → 走 EF，且前端绝不 signInWithPassword
× 邮箱登录失败 → 用 EF 的错误码，不回落直连
× 邮箱未验证：EF 给的是 EMAIL_NOT_CONFIRMED 码 + 中文文案 → 仍给可行动提示
× 风控要求验证码时，邮箱登录同样透传 requireCaptcha
× 源码守卫：signIn 函数体内已不存在 signInWithPassword 调用点
```

> 源码守卫第一版写的是 `not.toContain('signInWithPassword')`，被**自己写在函数里的注释**误伤。
> 已改为断言**调用点** `not.toMatch(/signInWithPassword\s*\(/)` —— 注释里保留删除原因是有价值的文档。

### 2.4 代价与残留

- **EF 成为登录的唯一路径**：EF 不可用时，邮箱用户也不再能登录（此前还有直连可用）。
  这是有意的取向——故障时明确报错，好过静默降级出一条没有风控的路。
- **旧 PWA 缓存**：仍调用 `signInWithPassword` 的老前端不受影响（不报错），
  但也**不受闸门约束**，直到用户更新到新版本。这点无法从服务端强制。
- 服务端旁路是否需要彻底堵死（例如关掉 email provider 或对 `/auth/v1/token` 加 WAF 规则），
  取决于是否还要支持邮箱密码登录 —— 本次按「保留功能、统一入口」处理。

## 三、P1：`_rate_limits` 保留策略

### 3.1 为什么不是「卫生问题」

- 全库 12 个 cron 任务，**没有一个是清扫这张表的**。
- `check_rate_limit()` 只在窗口过期时把 `count` 重置为 1，**行本身永久保留**。
  实测 37 行（2026-11-01 为 34 行）。
- 键由调用方决定，而 EF 侧用**客户端 IP** 做键；`csp-report` 是匿名可写端点，**每个 IP 一行**
  ⇒ **外部流量可以直接决定这张表的行数**，换 IP 刷上报就能无限堆键。

所以清理是上限约束，不是日志轮转。

### 3.2 口径

- 删除 `reset_at < now() - interval '1 hour'` 的行；
- **进行中的窗口（`reset_at > now()`）绝不删** —— 删了等于把攻击者的计数清零；
- 过期 1 小时内保留，便于排障时看到「刚刚被限流的是谁」（现有最长窗口 15 分钟，宽限充足）；
- 补 `_rate_limits_reset_at_idx`（原本只有 `key` 的主键索引，而清理谓词是 `reset_at`）；
- `7 * * * *` 每小时第 7 分钟执行，避开整点抽奖/队列任务。

### 3.3 上线后取证（Management API）

| 判据 | 结果 |
| --- | --- |
| 一次性清理 | **删除 35 / 37 行** —— 绝大多数是长期过期的垃圾，诊断成立 |
| 索引 | `_rate_limits_pkey, _rate_limits_reset_at_idx` |
| cron | `cleanup_rate_limits_hourly` / `7 * * * *` / `active=true` |
| 迁移登记 | `2026110309` 已在 `schema_migrations` |
| 口径自检 | 剩余 2 行均为「已过期但未满 1 小时」，`reset_at < now()-1h` 的行数 = **0** |

> 该表启用 RLS 且**没有任何策略**（刻意的 deny-all，只允许 service_role/postgres）。
> cron 以 postgres 执行，不受 RLS 影响；若将来有人改成 `force row level security`，
> 这个任务会静默失效 —— 届时需要给 postgres 加策略或改用 definer 函数。
