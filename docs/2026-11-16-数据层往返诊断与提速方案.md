# 数据层往返诊断与提速方案（2026-11-16 · 复核版）

> 触发：「总感觉等一会儿之后，所有数据才都有；数据库配置 / 页面读库的设置有没有能提速的？」
> 方法：线上站点实测（`probe-forum-feed-load.mjs`，冷缓存，4G/桌面两档，各跑 2 轮）+ 本机直连采样 + 只读查库 + 一次针对性的 CORS 预检实验。
> 与 `2026-11-16-首访性能诊断与解决方案.md` 的分工：那份治**入口字节与发现时机**，这份治**数据往返与到齐顺序**。
>
> ⚠️ **本版是复核版**：初版有 4 处判断经复测被推翻（含 2 处会导错方向），全部记在 §6，正文已按复核结果改写。

---

## 0. 一句话结论

**库不是瓶颈，往返次数是；而往返之前还压着 590 KB 的入口资源。**

- 数据量：`posts` 165 / `comments` 183 / `likes` 299 / `profiles` 33。热查询实测 **执行 24.6 ms + 规划 63.0 ms ≈ 88 ms**（165 行走 seq scan，是正确选择）。
- 项目在**新加坡**，本机到 `auth/v1/health` 的 TTFB 实测 **1.17–1.36 s**（4 次采样）；对照 Cloudflare 边缘同法 0.71 s ⇒ 跨境成本，调库没用。
- 首屏要在数据之前付掉 **58 个 JS（460 KB）+ 20 个 CSS（129 KB）**；1.6 Mbps 下光传这些就约 3 s。

所以能做的不是调数据库参数，而是：**合并往返、把请求提前发、本地先给一版**——且收益上限受带宽守恒约束（见 §6 更正 4）。

## 1. 实测时序：数据为什么"一点一点"才到

### 1.1 4G 档两轮（1.6 Mbps / RTT 150 ms / 390×844 / 冷缓存）

| | 第 1 轮 | 第 2 轮 |
|---|---|---|
| 首张卡片 | 5294 ms | 4944 ms |
| LCP | 6476 ms | 6184 ms |
| 数据链 | 2456 → 6653 ms | 2261 → 5822 ms |
| `posts` 请求 | 3835（+1067） | 3298（+1240） |
| `get_user_subscription_tiers` | 5130（+969） | 4569（+576） |
| 3 张头像（Storage） | 5136（+1318/1517/1490） | 4574（+1123/1200/1248） |
| `comments`（预览补拉） | 5138（+943） | 4576（+612） |
| 数据条数 | 11 条 + 8 次 OPTIONS | 11 条 + 8 次 OPTIONS |

两轮结构完全一致（绝对值差 ~10%，本机网络抖动）。**关键因果：`posts` 请求距 `ForumMain` chunk 下载完成只差 30–40 ms** ⇒ 它就是被组件挂载卡住的，不是被鉴权或别的什么。

### 1.2 桌面档（不限速，本机真实网络）

```
首帖 6310 ms | LCP 7772 ms | 数据链 2048 → 8265 ms | 串行波次 3
avatar_frames 2048 → posts 4648：中间 2.6 s 一条数据请求都没发
```

真实网下单跳 TTFB ≈ 0.9–1.4 s，所以每多一波 chunk 就是 1 秒级代价。
⚠️ 桌面档比 4G 档还慢不是反直觉 bug，是那一轮本机网络更差（TTFB 917 ms > 4G 档模拟的 150 ms）。

### 1.3 四条独立管道，而不是一条

| 管道 | 首卡之后多久到 | 为什么是第二波 |
|---|---|---|
| 卡片正文（含图、评论数、作者资料） | 0 | 一次 embed 查询给全 |
| 作者头像图 | **+0.6–1.3 s** | Storage 原图 21.9 KB（96 px 显示），无缩放、无边缘缓存 |
| 昵称等级 / 卡色 | **+0.6–0.9 s** | `get_user_subscription_tiers` 要等作者 id |
| 3 条回复预览 | **+0.6–0.9 s** | 列表 embed 拿不到「最新 3 条」，只能补拉 |

结论：**观感由最慢那条决定**。只优化其中一条，用户仍会觉得"还在转"。

## 2. 数据库侧核查：没有可调的"提速旋钮"

| 项 | 实测 | 判断 |
|---|---|---|
| 热查询成本 | keyset 主查询：执行 24.6 ms / 规划 63.0 ms | 88 ms，相对 0.5–1.4 s 的往返是小头 |
| 单次响应体积 | 线上真实 feed 查询 **29,934 B**（gzip 后 8.3 KB） | 带宽不是问题 |
| 索引 | posts 覆盖 `(status,created_at DESC,id DESC)` / `(author_id,…)` / trgm / search_vector / 影集部分索引 | 与查询形状对齐，**不要再加** |
| `profiles` seq_scan | 102 万次（RLS 与函数里的 `exists(select 1 from profiles …)`） | 表只有 33 行，**无害** |
| 库体积 | 118 MB，其中 `cron.job_run_details` 19,834 行 / 14 MB | 已从 9 月的 31 MB 清过，**别再动** |
| Realtime | publication 只剩 `notifications` | 9 月建议已落地，**已收窄到位** |
| CORS | `access-control-max-age: 3600`，**按 URL 记** | 8 次预检是首访专属；复访为 0（实测，见 §6 更正 3） |

> 别做的事：给 `lotteries` / `lottery_draw_logs`（5–12 行）加索引、给 `profiles` 补零命中索引 —— 都是负收益。见 `2026-09-20-数据库与加载性能审查报告.md`。

## 3. 页面读库侧：三处真实浪费

### 3.1 首页在播开场画，数据请求却还没发

`Home/index.vue` 的 `onMounted` 只做 `fetchGateConfig()` + `homeHeroesStore.fetchPublished()`；
论坛流的第一次请求发生在 `ForumMain` 挂载之后（3.3–3.8 s）。**开场画那 0–2 s 是纯空窗**。

### 3.2 等级徽标天生第二波

`tier` **不是 `profiles` 的列**，是从 `user_subscriptions`（`status='active' and expires_at>now()`）算出来的，
所以只能走 SECURITY DEFINER 的 `get_user_subscription_tiers`。作者 id 又要等列表返回 ⇒ 必然串行。
（想真正省掉这一次往返，得给 `profiles` 加物化的 `tier` 列 + 触发器同步——成本远高于收益，见 §4 P2。）

### 3.3 头像绕开了 CDN，而且没缩放

`profiles.avatar_url` 是 `…supabase.co/storage/v1/object/public/avatars/…`：
实测 **21,964 B**，TTFB **0.81 s**。同页面其他图片走 `cdn.blockofhome.cn`（Cloudinary），有 `f_auto,q_auto,w_`。

⚠️ **但"套一层 CDN"这条路当前走不通**：该 Cloudinary 账号的远程抓取是关的（`/image/fetch/` 实测 **401**），
CDN 域名下的 `image/fetch` 路径还直接 404。见 §6 更正 2 与 §4 的替代路径。

### 3.4 顺带的：默认列表路径丢了回复预览

`getPosts` 在 `cursorMode='keyset'` 时走**直连表查询**（`posts` + embed），而 `replies` 预览只有 RPC 分支才返回。
表路径从不设 `replies_preloaded` ⇒ `scheduleIdleReplyPrefetch` 对**每一张卡**都可能补拉一次。
这就是那条第 4 管道的来源，也是"每屏必然多一次往返"的原因。

## 4. 方案（按 收益 ÷ 风险 排序）

| # | 做法 | 预期收益 | 风险 | 动到哪 |
|---|---|---|---|---|
| **A1** | **开场画期间预发首屏 feed**：在 `Home.onMounted` 用与 `ForumMain` **完全一致**的 scope/params 预热一次，命中 `request-core` 的 in-flight 去重 | 首卡 **−1～1.5 s**（**不是** −2～3 s，见 §6 更正 4） | 中低 | `views/Home/index.vue`；建议把 feed 参数抽成 `buildForumFeedParams()` 单源，避免两处字面量漂移 |
| **A2** | **头像换源 + 缩放**：现成的 CDN fetch 不可用，三条备选：① 上传时同时落一份到 Cloudinary（改上传链，最干净）② Cloudflare Worker 缓存 Storage 响应（仓库已有 `cloudflare/` 链路）③ 开 Supabase Storage 图像转换插件（付费） | 视觉"补齐" **−0.6～1.2 s** | 中 | 上传链 / Worker / 存储配置 |
| **A3** | **非首屏数据延后**：`forum_weekly_reports` / `advertisements` 首屏看不见，改 idle 或进视口再拉 | 首屏少 2 条并发、少抢一轮带宽 | 低 | `ForumMain.onMounted` |
| **A4** | **首页聚合 RPC**（posts+news+activities+广告+周报 一次拿） | **−3～4 往返** ≈ 0.5–1.4 s | 中（新 RPC + 5 个消费方适配） | 后端 + 4 个区块组件 |
| **A5** | 快照扩容：把 tier / 头像 URL 一起存进 `forum-feed-cache` | 复访时"连徽标头像都先有" | 低 | `utils/forum-feed-cache.js` |
| **B1** | 首访免预检（`?apikey=` 替代 `Authorization` 头，把请求变成简单请求） | 首访省 **8 个 OPTIONS** ≈ 0.6–1.3 s | **中**（key 进 URL / 日志） | 请求层 |
| **P2** | `profiles.tier` 物化列 + 触发器，消掉第二波 RPC | −1 往返 | 中高（同步一致性） | 迁移 + 触发器 |
| **P3** | 首屏静态化 / SSG（`2026-11-16` 文档 §1.5 L5） | 唯一能进 1 s 级的方案 | 大改 | 架构 |

**建议先做 A1 + A3**（都不碰 SQL、不改数据模型，一天内可验），A2 需要先定"从哪取图"。

### 已撤回的建议（复核后不成立）

- ~~`author_tier` 并进 `list_forum_posts`~~ —— 热路径根本不走这个 RPC，且 tier 不是 profiles 列。见 §6 更正 1、2。
- ~~`request-core` 并发 6 → 8~~ —— 首屏同时最多 5 条数据 + 1 条 idle，**6 个槽刚好够，没有排队**。收益 ≈ 0。
- ~~预热一次 CORS 预检~~ —— 预检缓存按 URL 记，预热一个端点不会覆盖另外 7 个。见 §6 更正 3。

## 5. 复跑方式

```bash
# 首屏数据瀑布（4G / 桌面两档，冷缓存）
BASE=https://www.blockofhome.cn node scripts/probes/probe-forum-feed-load.mjs --only=4g
BASE=https://www.blockofhome.cn node scripts/probes/probe-forum-feed-load.mjs --only=desktop

# 预检缓存粒度（新增）
set -a && source .env && set +a && KEY="$VITE_SUPABASE_ANON_KEY" \
  node debug-screenshots/probe-preflight-cache.mjs

# 单跳往返采样
curl -s -o /dev/null -w "%{time_starttransfer}\n" \
  "https://nplnlefdwfgtyimfkyih.supabase.co/auth/v1/health"
```

⚠️ 读数纪律沿用探针文件头那四条：`dur` 含等预检；串行波次是启发式；
绝对值只在本机网络成立（到区域 1 RTT ≈170 ms、首次建连 +550 ms）；**看结构不看绝对值**。

## 6. 复核记录：初版 4 处判断被推翻

| # | 初版说法 | 复测结果 | 影响 |
|---|---|---|---|
| 1 | 首页论坛首屏走 `list_forum_posts` RPC | ❌ **一次都没调**。`ForumMain` 传 `cursorMode:'keyset'` ⇒ 走 `posts` 直连 + embed；两轮探针里 `rpc/list_forum_posts` 均为 0 条 | 原方案 A2「改 RPC」打错目标 |
| 2 | `author_tier` 并进 RPC 是零成本（已 join profiles） | ❌ 双错：① 热路径不走 RPC；② `tier` **不是 profiles 列**，由 `user_subscriptions` 计算（SECURITY DEFINER） | 该方案降级为 P2，需物化列 |
| 3 | 头像套 `cdn.blockofhome.cn` 做 Cloudinary fetch | ❌ `/image/fetch/` 404、`/dkqae7j1m/image/fetch/` **401**（远程抓取未开启） | 换源需另选路径（上传双写 / Worker / Storage 插件） |
| 4 | 「预热一次 CORS 预检」可省 4 个 OPTIONS | ❌ 预检缓存**按 URL** 记：同 URL 并发 ×2 → **2 个** OPTIONS；两个不同 URL → 2 个；同 URL 再打一次 → **0 个** | 该建议撤回；但"并发不去重"这句本身是正确的 |
| 5 | 预发数据可回收 2～3 s | ⚠️ 过于乐观。3.8 s 之前已发 58 JS（460 KB）+ 20 CSS（129 KB），1.6 Mbps 下约 3 s | 修正为 −1～1.5 s，且受带宽守恒约束 |

✅ **复核后仍然成立的**：
- `request-core` 并发上限 6（`new RequestQueue()` 默认值）；
- auth 持久化 `isLoggedIn` / `userInfo` 到 localStorage ⇒ A1 在 `Home.onMounted` 能同步拿到正确 `userId`，
  不必等 `initLoginState` 那一跳；
- 三条"后到管道"的时序在两轮复跑中完全复现；
- 库侧不是瓶颈（88 ms vs 0.5–1.4 s 往返），且 cron / realtime / 索引三处历史问题确已处理。
