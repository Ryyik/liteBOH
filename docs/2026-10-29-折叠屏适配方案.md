# 折叠屏 Web 适配方案（华为优先 + iPhone Duo）

> 2026-10-29 调研 + 实测。数据来源：华为开发者联盟《阔折叠/阔直板应用开发》、WebKit《Safari 27.1 Features》
> 官方视口表、W3C Media Queries L5 / Device Posture 规范；本项目读数由 Playwright 在本机 dev server 上实测。
>
> 结论先行：**这个项目不需要 "折叠屏专属适配"，需要的是补三个断点裂缝。**
> 真正的折叠屏 API（Device Posture / Viewport Segments）对两台目标机都**用不上**，见 §3。

## 1. 目标设备的真实 CSS 视口

CSS px ≠ 物理像素。适配要看的是 vp / CSS 逻辑像素，下表都是官方给的数，不是估算。

### 1.1 华为（官方 vp 值，华为开发者联盟）

| 机型 | 形态 | 视口 (vp) | 高宽比 | 华为断点 (横×纵) |
| --- | --- | --- | --- | --- |
| **Pura X Max** | 折叠态（竖） | **459 × 672** | 14:10 | sm × lg |
| **Pura X Max** | 展开态（横） | **939 × 664** | 10:14 | lg × sm |
| Pura X | 折叠态（横） | 326 × 326 | 1:1 | sm × md |
| Pura X | 展开态（竖） | 440 × 707 | 16:10 | sm × lg |
| Pura X View | 直板 | 440 × 744 | 16:9.5 | sm × lg |

物理分辨率 2584×1828（内屏）/ 1848×1264（外屏），DPR ≈ 2.75，所以内屏展开只有 **939×664 CSS px**——
不是"2400 多宽"，别拿物理像素去推断点。

### 1.2 iPhone Duo（WebKit 官方表，Safari 27.1）

| 姿态 | 宽度 | SVH | LVH |
| --- | --- | --- | --- |
| 外屏 竖屏 | 382 | 580 | 618 |

宽 382–951、高 368–902。**两个最危险的档**：外屏横屏只有 368 高（比任何直板机横屏都矮），
内屏横屏 951 宽但只有 585 高。

## 2. 行业方案盘点：三层，只有第一层是现在该做的

### L1 纯尺寸响应式（所有浏览器，官方推荐）

WebKit 原文：「你不需要操心这些数字，lean into Responsive Web Design… Avoid UA sniffing,
use feature detection instead.」华为文档同样是「以 Web 实际获得的视口尺寸为依据」。

做法就是三件事：合适的断点、`clamp()` 流式字号、内容区最大宽度。**这一层能拿到 90% 的收益**，
且零兼容风险。

### L2 形态感知（Device Posture API，实验性）

```css
@media (device-posture: folded) { /* 书本 / 桌面半折叠 */ }
@media (device-posture: continuous) { /* 完全展开 或 完全合上 */ }
```

```js
navigator.devicePosture?.addEventListener('change', (e) => { ... });
```

⚠️ **两个坑决定了它现在不能用**：

1. **`continuous` 同时代表"完全展开"和"完全合上"** —— 它区分不了你在大屏还是小屏，
   拿到 `continuous` 之后仍然要靠宽度媒体查询才知道自己在哪块屏上。**它不替代断点。**
2. **Safari 27.1 默认关闭**，要用户自己去「设置 → Safari → 高级 → 功能标志」手动开；
   Chrome 125–128 是 origin trial。**默认关闭 = 对线上用户等于不存在。**

### L3 折痕避让（Viewport Segments API）

```css
@media (horizontal-viewport-segments: 2) {
  grid-template-columns: env(viewport-segment-width 0 0) env(viewport-segment-width 1 0);
  column-gap: calc(env(viewport-segment-left 1 0) - env(viewport-segment-right 0 0));
}
```

⚠️ **对这两台机器几乎无用**：

- Pura X Max 是**单柔性屏**（seamless）。完全展开时 `horizontal-viewport-segments` = **1**，
  没有"两段"，只有**半折叠悬停态**才会变 2。
- iPhone Duo 同理，而且同样在 Safari 功能标志后面。
- 只有 Surface Duo 这种**物理双屏**才在展开态给 2。

**所以：Segments 是给"悬停态分屏"用的（上半看视频、下半看评论），不是给"展开态适配"用的。**
本项目目前在悬停态没有任何专门设计，属于可选增强，不进第一优先级。

### 结论

| 层 | 解决什么 | 本项目优先级 |
| --- | --- | --- |
| L1 尺寸响应式 | 展开/折叠后的**布局正确性** | **P0，全部收益在这** |
| L2 device-posture | 半折叠悬停态的**专属布局** | P2，可选 |
| L3 segments | 折痕/铰链**避让** | P2，可选（单柔性屏展开态为 1，用不上） |

### 3.2 三个肉眼可见的故障

**① 中宽档「桌面导航 + 手机内容」的割裂（939×664 / 951×585 / 794×716）**

截图 `06-puraxmax-unfolded-home.png`、`07-duo-inner-landscape-home.png`：
顶栏是桌面版（首页/社区/探索/服务/关于 + 搜索 + 登录），
下面却是**移动端单列** —— 一个 939px 宽的搜索框、一张横跨 939px 的帖子卡、两栏各 400px 的图片。

根因是一个**断点裂缝**：

| 判据 | 值 | 出现在 |
| --- | --- | --- |
| 导航栏切移动版 | `max-width: 768px` | `src/styles/vendor/unified-nav.css:1034` |
| 内容切横屏左栏版 | `landscape && min-width:1024 && min-height:600` | `src/utils/forum-viewport.js` `FORUM_LANDSCAPE_QUERY` |

⇒ **769–1023px 这段没有任何一档负责**：导航已经当桌面了，内容还当手机。
939（Pura X Max 展开）、951（Duo 内屏横）、794（Z Fold 7 展开）全掉进这个洞。

**② 极矮横屏首屏无内容（594×368）**

截图 `03-duo-outer-landscape-home.png`：顶栏（汉堡版，按钮巨大）78px + 标签栏 ≈50px + 搜索框 56px +
工具栏 padding 80px（实测 `forum-main-grid` 顶边 204，`forum-page` 顶边 124）= 首屏 368px 里
**只剩不到 100px 给内容**，帖子卡只露出作者名。同档横溢元素从 30 涨到 54（forum 95）。

**③ FAB 压住搜索框（594×368）**

同一个截图右侧：`+` 悬浮按钮直接盖在搜索框右端「问 BOHAI」上，两处可点区域重叠。

### 3.3 一条附带发现（非折叠屏引起）

`/forum` 路由在**每一档**（含 390×844 基线）都有约 1% 的横向溢出，表现为移动端浏览器自动缩小
（`innerWidth` 从 390 变 394）。折叠屏只是把它放大了，根因在论坛页布局本身，另开单子。

## 4. 方案：四步，按性价比排序

### S1｜内容区锁宽（改一处，收益最大）

移动形态下的主内容容器加最大宽度，让超宽视口"居中留白"而不是"拉伸铺满"：

```css
.forum-container,
.home-forum-stage > .forum-section-shell {
  max-width: min(100%, 720px);
  margin-inline: auto;
}
```

- 390 竖屏下 `min(100%, 720px)` = 100%，**行为零变化**；
- 939 / 951 下锁到 720 居中，行宽回到可读区间。

> ⚠️ 别用 `max-width: 720px` 裸写 —— 481–768px 的窄窗会被硬压。必须 `min()`。
> ⚠️ 这条会改变桌面左栏版的观感，所以要限定在「非横屏左栏」分支内。

### S2｜补"矮横屏"档（P0）

现有 `max-height` 档是 500 / 520 / 560 / 600，全部是"更矮"的散点。缺的是
**"宽度够、高度不够"** 这一档：

```css
@media (orientation: landscape) and (max-height: 700px) {
  /* 顶栏 64→52、标签栏 48→40、工具栏 padding-top 80→24、区块间距 ×0.7 */
}
```

命中 368 / 585 / 664 三个高度，不命中 844（竖屏）与 900（桌面）。

### S3｜断点裂缝（P0，**方向已定：A**）

769–1023 这段必须有人负责。两个方向对比：

| 方向 | 做法 | 收益 | 代价 |
| --- | --- | --- | --- |
| **A｜内容上移**（✅ 2026-10-29 定） | 桌面导航断点 768 → 1024，769–1023 走移动导航 + 底栏 | 形态一致（竖屏窄条）；判据收敛到一处 | 需核对 768 断点的影响面；平板竖屏（768/820）会变成移动导航 |
| B｜左栏下移 | `FORUM_LANDSCAPE_QUERY` 的 `min-width` 1024 → 768 | 改动只一处 | 664px 高时左栏很挤；iPad 竖屏 768 也会进左栏，风险更大 |

#### A 的实际影响面（别误读成"把 99 处 768 全改成 1024"）

`max-width: 768px` 在 `src/` 里共 **99 处、分布在 67 个文件**。但这 99 处里绝大多数是**页面内部的微调**
（字号、卡片间距、图片列数），它们跟"这是手机还是桌面"**无关**，改了只会引入无谓回归。

真正要动的是**决定整页形态**的那一层，共三类：

| 类别 | 位置 | 改法 |
| --- | --- | --- |
| 导航本体切移动版 | `src/styles/vendor/unified-nav.css`（4 处 `max-width:768`）、`src/components/UnifiedNavbar/index.vue:1096` 的 `portraitMiniQuery` | 768 → 1023 |
| 整页形态判据（底栏显隐 / 单列 vs 左栏 / 页面 padding） | 各页 shell 级 CSS | 768 → 1023 |
| 页面内部微调（字号 / 间距 / 卡片列数） | 其余 60 余个文件 | **不动** |

判定口径：一条规则如果只影响"元素多大、多密"，保留；如果影响"有没有这个元素、走哪套骨架"，跟着改。

> ⚠️ 改完必须跑 `npm run probe:rail-more-menu`、`probe-rail-landing`、`probe-home-forum-rail`、
> `probe-nav-mobile-menu` —— 这四条分别锁左栏浮层、左栏落点、首页论坛入口、竖屏菜单，
> 都是 768/1024 断点直接相关的事故记录点。

### S4｜形态感知（P2，可选）

只给"半折叠悬停态"做增强，且必须包 `@supports` + 特性检测，默认关闭：

```css
@supports (device-posture: folded) {
  @media (device-posture: folded) and (horizontal-viewport-segments: 2) {
    .post-detail__media { grid-column: 1; }
    .post-detail__comments { grid-column: 2; }
  }
}
```

## 5. 验证：新增探针 `probe-foldable-viewports.mjs`

六档 × 三条路由 = 18 组断言，纳入 `scripts/lib/gate-map.json`。

| 断言 | 判据 |
| --- | --- |
| 无横向溢出 | `documentElement.scrollWidth ≤ clientWidth + 1` |
| 首屏有内容 | 首张帖子卡的可见高度 ≥ 屏高 × 0.25 |
| FAB 不压输入框 | FAB rect 与任意 input/textarea rect 不相交 |
| 内容锁宽生效 | 中宽档下主容器 `clientWidth ≤ 721` |
| 导航/内容形态一致 | 桌面导航可见 ⇒ `isForumLandscape()` 为真 |
| 切换连续性 | 459×672 → 939×664 后 `--viewport-width` 在 400ms 内更新，且无浮层残留 |

最后一条是折叠屏特有的：**展开/折叠是"没有 orientationchange 事件的尺寸突变"**。
本项目 `src/main.js` 的 `scheduleViewportSync` 已经同时监听 `resize` + `visualViewport.resize`
+ 240ms 尾延迟，机制是够的，但**没有任何断言锁住它**。

## 6. 明确不做

- **不为折叠屏单独做一套布局**。L1 断点补齐后，六档自然落进已有形态，多一套布局 = 多一处漂移。
- **不用 UA 嗅探**。WebKit 与华为文档都点名反对；折叠屏 UA 还识别不准。
- **不把 device-posture 当主判据**。`continuous` 分不清大小屏，且默认关闭。
- **不引入 `postcss-px-to-viewport` 那类全局方案**。本项目是 `rem`/`px` + 断点体系，
  换全局转换单位会牵动全仓 570+ 文件，收益不如 S1+S2 两条。

## 8. 已实施（2026-10-29 第二轮）：底栏 → 右侧竖向导航胶囊

### 8.1 依据：Duo 官方规范（不是"把底栏竖起来"这么简单）

Apple《Design for iPhone Duo》原文（Tech Talk 111466）：

> When closed, the display is wider and shorter than a traditional iPhone. Buttons and
> controls that normally sit at the top and bottom **move to the right side** of the display
> in order to maximize vertical space… This new space on the side houses the app controls.
> This includes **the tab bar**, the app toolbars, and navigation controls… **creating an
> uninterrupted area for its content to its left, comparable to the area on an iPhone with
> more traditional display proportions.**

三条要点，代码都按它落：

1. 控制区在**右侧**（右拇指可达），不是左侧 —— 与本项目 ≥1024 已有的左栏是两套东西，
   靠断点互补不共存。
2. 内容留在左边并**保持手机比例**，不被拉宽。
3. 空间不够时控制区收进 overflow，而不是压小内容。

Web 侧的对应实现就是 Material 的 `NavigationRail` 思路（微软为 Surface Duo 做的
`NavigationRailView` 也明确了「折叠设备上主导航放在**侧面或下沿**」）。

### 8.2 生效区间与断点互补

| 区间 | 导航形态 | 由谁负责 |
| --- | --- | --- |
| 竖屏（任意宽度） | 贴底横胶囊 | `bottom-nav.css` 既有档 |
| 横屏 ≤1023px | **贴右竖胶囊**（本轮新增） | `bottom-nav.css` 末段 + `styles/fold-nav-rail.css` |
| 横屏 ≥1024 且 ≥600 高 | 左侧 `UserSpaceSideRail` | `side-rail.css` + `landscape-rail.css` |

939（Pura X Max 展开）/ 951（Duo 内屏横）/ 794（Z Fold 7）三档正好落进新增区间 ——
它们之前既不满足 ≥1024，又被 `max-width:768` 当成桌面，是 §3.2① 那个断点裂缝。

### 8.5 两条实测踩到的坑（都已写进代码注释）

1. **右缘 AI 热区不能左移避让**。第一版把 `.ai-edge-trigger.side-right` 的 `right` 从 0
   改到 88px，707×354 实测正好压住顶部汉堡按钮（`#nav-hamburger` 落进 603..619），
   `.ai-edge-zone` 拦截 pointer ⇒ `probe-nav-mobile-menu` 点击超时。
   正解：热区留右边缘、只降 `z-index` 到 900（低于胶囊 1000），**只左移教学条**。
2. **顶部导航居中只对桌面版成立**。`left: -gutter/2` 这条在 ≤768 会把满宽汉堡胶囊
   往左推出视口（707×354 实测二级菜单 `left = -31`）。必须单开
   `(min-width: 769px)` 一档。
