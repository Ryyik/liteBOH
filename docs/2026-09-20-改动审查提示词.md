## 一、推荐的 10 个审查角度（按优先级排序）

| # | 角度 | 看什么 | 典型落点 |
|---|---|---|---|
| P0 | **改动范围真实性** | `git status` 里未跟踪文件是不是本次产物；有没有调试残留（临时脚本、截图、`console.log`、`debugger`、写死的测试 URL）；`dist/` / `dist-check/` 是否被手改 | 全部 untracked 文件 |
| P0 | **正确性 / 竞态** | 异步时序、`watch` 缺 `immediate`、卸载未清理（`setInterval`、事件监听、AbortController）、缓存失效语义、乐观更新回滚 | `src/App.vue`、`UserSpaceMain.vue`、`async-loaders.js` |
| P0 | **单源真相** | 同一规则是否被写了第二处（判据、常量、URL 参数、模块说明符）；改一处是否要动四处 | 路由 `view`、SW 预缓存清单、`preloadSettingsSubPanels` 的 import 说明符 |
| P1 | **数据 / 迁移安全** | 迁移是否幂等、可回滚；索引增删依据是否被证伪；新表 revoke 后是否**分别** grant anon + authenticated；RLS 是否漏 `auth.uid()` | `supabase/migrations/2026092001~004` |
| P1 | **性能回归** | 首屏壳是否被撑大（9 JS + 2 CSS）；SW 预缓存「两半是一对」是否还成立；路由增量 chunk；后台轮询 | `vite.config.js`、`scripts/check-shell-precache.mjs` |
| P1 | **样式 / 暗色** | 新增 `!important` 是否同步 `important-budget.json`；scoped 覆盖父级变量；暗色容器白名单；sticky 是否被 `body{overflow-x:hidden}` 吃掉 | `style.scoped.css`、tokens.css |
| P1 | **测试是不是真守卫** | 断言撤掉修复会不会变红（反证）；是否只是断言了字符串/变量名而非语义；有没有用「固定 tick 数」放行事件循环 | `tests/unit/*.test.js` |
| P2 | **安全 / 隐私** | 密钥、VAPID、service_role、内网地址是否进仓；日志是否打用户信息；`debug-screenshots/` 是否含真实数据 | 全仓 grep |
| P2 | **文档与实现一致** | 今天产出的 4 份审计报告里的数字，是否和实现里真正生效的数字一致（尤其被标注为「测量污染」的数字有没有被引用成结论） | `docs/2026-09-20-*.md` |
| P2 | **可维护性 / 死代码** | 新加的导出是否有人调用；是否又造了一个已有的过渡/组件；命名是否跟既有约定冲突 | 新增脚本与导出 |

**本仓特有的三条硬约束（审查时必须带上）**
1. 构建验证走 `vite build --outDir dist-check`，**不许动 `dist/`**。
2. 门禁是链式的（views → structure → liquid-glass → important-budget → dark-tokens → first-paint → build → shell-precache → bundle），中途断了后面不会跑，本地要**全链跑**。
3. 探针数字有污染先例（「设置子档 291–313ms」实为论坛并发挤占，隔离后 34ms）——**不要把污染数字当结论引用**。

## 二、可复制提示词（通用主版本）

> 把下面代码块整段复制给 AI，末尾补上你的附加要求即可。

```text
你是本仓库的资深代码审查者。请审查「今天工作区里的全部改动」，输出一份可直接执行的审查报告。

【仓库背景】
- 项目：BOHLITE，Vue 3 + Vite + Supabase，hash 路由，PWA（有 Service Worker 预缓存）。
- 工作区：/Users/ryyik/Documents/BOHLITEForMacLatest/BOHLITEBeta2.5
- 本人最在意三件事：① 真相源单一（同一规则只应有一处定义，最反感「改一处要动四处」，以及宣传与实现两套数字）；
  ② 改完要有能真正变红的测试守卫（不接受只断言变量名/字符串的假守卫）；
  ③ 性能与视觉质感（首屏体积、SW 预缓存、暗色一致性）。

【第一步：建立改动清单（必须先做，不要跳过）】
1. 跑 `git status --porcelain` 和 `git diff --stat`，把「已修改」与「未跟踪」分开列。
2. 只针对源码改动做审查；`dist/`、`dist-check/`、`node_modules/` 跳过。
3. 对每个未跟踪文件判断：本次产物 / 调试残留 / 应当删除。把「建议删除」的单独列出来，不要混进问题清单。

【审查角度（按此顺序，逐项给结论）】
A. 范围真实性：有无调试残留（临时脚本、截图、console.log、debugger、写死的测试地址/端口）；有无手改 `dist/`。
B. 正确性 / 竞态：异步时序（watch 是否缺 immediate）、卸载是否清理（setInterval / 事件监听 / AbortController）、
   缓存失效语义、乐观更新是否回滚、错误态是否被静默吞掉。
C. 单源真相：本次改动是否引入了第二处定义（判据、常量、URL 参数、模块说明符、清单文件）。
   凡是「同一规则在两处各写一遍」的，一律报 P0，并指出应该保留哪一处分歧点。
D. 数据 / 迁移：SQL 是否幂等、可回滚；新表 revoke 后是否分别 grant anon 与 authenticated（漏 anon 会导致线上 42501，
   本地 mock 不会暴露）；索引增删依据是否成立；RLS 是否漏 auth.uid()。
E. 性能：首屏壳体积是否被撑大；SW 预缓存「壳样式进预缓存 + 其余路由 CSS 走 CacheFirst」这一对是否仍同时成立
   （删任一半会变成「有 HTML 无样式」）；路由 chunk 增量；是否新增后台轮询。
F. 样式 / 暗色：新增 !important 是否同步 scripts/important-budget.json；scoped 样式是否压了父级变量；
   sticky 是否被全局 body{overflow-x:hidden} 吃掉；暗色容器是否需要进白名单。
G. 测试守卫：本次新增/修改的断言，撤掉修复后会不会变红？有没有用「固定 tick 数放行事件循环」这类不可靠写法？
   有没有未 await 的 promise 会污染下一个用例？
H. 安全 / 隐私：密钥、token、内网地址是否进仓；日志是否打印用户信息；调试截图是否含真实数据。
I. 文档一致：docs/ 下今天新增的审计报告里的数字，是否与代码里真正生效的值一致；
   报告中标注为「测量污染」的数字有没有被引用成结论。
J. 死代码 / 重复造轮子：新增导出是否有人调用；是否重复实现了已有组件或过渡。

【输出格式（严格遵守）】
1. 先给「改动清单」（已修改 N 个 / 未跟踪 M 个，未跟踪里建议删除的 X 个）。
2. 再给问题清单，每条必须包含：
   - 等级：P0（必须改）/ P1（建议改）/ P2（可选）
   - 落点：文件:行 或 具体符号名（没有具体落点的结论不要写）
   - 现象：现在是什么行为
   - 影响：会坏在哪、谁会先发现
   - 建议改法：具体到怎么改，不要写「建议优化一下」
   - 验证方式：跑哪条命令 / 哪个脚本 / 加哪条断言能证明改好了
3. 最后给「通过项」一句话总结，以及一个「发布前必做清单」（可勾选）。

【行为约束】
- 不要只看 diff 字面下结论：涉及某个模块的语义时，必须去读该模块的完整上下文和调用方。
- 不确定的地方标「待确认」，并说明需要确认什么，不要编。
- ⚠️ 本仓库有一条硬性红线：构建验证只能跑 `vite build --outDir dist-check`，严禁改动或删除 `dist/`。
- 除非我明确要求，不要修改任何文件，只输出报告。
```

## 三、三个聚焦变体（可选，按需替换主提示词的「审查角度」段）

**① 只审正确性（适合改动集中在逻辑层）**
> 只做角度 B 与 G：逐条列出可能的竞态、未清理副作用、被静默吞掉的错误；并对本次每个新增断言回答「撤掉修复会不会变红」，不会变红的给出更强的断言写法。

**② 只审数据与性能（适合改动含 SQL / 构建配置）**
> 只做角度 D 与 E：SQL 逐条判幂等性与回滚方案、grant 是否双份、索引依据是否被证伪；
> 构建侧确认首屏壳与 SW 预缓存一对是否仍成立，并给出本地全链门禁命令（`build:ci` 的 9 个环节要跑完）与预期基线数字。

**③ 只审「能不能发」**
> 只做角度 A / H / E：列出所有必须清理的调试残留、隐私风险、体积回归，并输出一份发布前勾选清单（含本地全链门禁、关键探针脚本、需要人工确认的项）。
