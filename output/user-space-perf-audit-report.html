00结论速览

先说最重要的四条

1. 交叉复合问题真实存在，且集中在「挂载条件 + 清理条件」两个缺口上。BOH AI 因 v-if="currentTab === 'messages'" 在进入消息 tab 时被整体挂载（而非切到 AI 分区才挂载），又因 1 秒轮询仅在 onUnmounted 清理，形成「一次进入 = 全量加载 + 永久轮询」的复合放大。

2. posts tab 是请求浪费最重的区域。双重触发路径（switchTab 直调 + sync 路由 watcher 重复调用）+ 聚合 RPC 失败无负缓存，导致每次进入都重复请求并走重型兜底（含 500 条全量云盘条目查询）。

3. 好消息：缓存体系与列表渲染基础扎实。回访社区零 DB 请求、request-core 去重、共享懒加载 observer、消息虚拟列表均已生效，本报告不动这些。

4. 预期收益：P0 四项落地后，messages tab 首进网络量约 -70%、堆内存增量约 -12MB，posts tab 进入期 DB 往返约 -50%，印象面板渲染从全量 O(n) 降为分页 20 条。

03确认的交叉复合问题

每项均给出静态证据（文件:行号）与运行时证据；RT = 探针实测确认，ST = 静态确认

A · 加载速度 / 资源加载

P-01进入消息 tab 即整体挂载 BOH AI，拉满整个依赖图严重RTST

UserSpaceMain 中 AsyncBOHAI v-if="currentTab === 'messages' || leavingTab === 'messages'" ——挂载条件是 tab 而非 分区。用户只想看消息列表（inbox），AI 的全部依赖却已加载求值。

运行时证据
  • messages tab 单次进入：93 个请求，其中 69 个 JS 模块（marked、highlight.js core+8 语言、useChatEngine、bohai-auto-router、bohai-connectors、treehole-api…）
  • 堆内存单跳 +12.2 MB（30.8 → 43.0），后续阶段不再回落
  • 切到 AI 分区（ai-section 阶段）反而 0 新请求——该拉的早就拉完了
静态证据
  • UserSpaceMain.vue:129 — AsyncBOHAI v-if="currentTab === 'messages'…"
  • BOHAIMain.vue:514-530 — marked / DOMPurify / highlight.js/core + 8 语言 + github.css 顶层静态 import
修复：① 挂载条件改为 messagesSection === 'ai'（v-show 外壳保留，异步组件延迟到分区激活）；② marked/hljs 改动态 import——首条 AI 消息渲染前再载入，或拆到「消息含 markdown 时」按需加载。两项合计可将 messages tab 首进网络量砍约 70%、堆增量砍约 12MB。
P-02embedded 论坛仍发独立页才需要的请求中RTST

ForumMain 以 embedded 模式嵌入社区 tab，但 onMounted 仍执行整页逻辑：周报、签到状态、广告、NSFW 模型预载。

运行时证据
  • 社区冷加载期实测发出 get_weekly_checkin_status（签到）与周报请求
  • 这些数据在嵌入式视图中无对应 UI 承载
静态证据
  • ForumMain.vue:2182-2222 — onMounted 无条件调用 loadForumWeeklyReport / loadActiveAds / loadWeeklyCheckinStatus / scheduleForumImageModerationPreload（NSFW 模型体积大）
修复：embedded 时跳过周报/广告/签到，NSFW 预载仅在「发帖器打开」时触发。社区冷加载可减 3~4 个请求 + 一段模型下载。
P-03每次 feed 拉取附带 3 个类型探测查询（hydrate 三连查）中RTST
运行时证据
  • 社区冷加载：table posts ×2、news ×1、activities ×1，与 feed 拉取 1:1 伴随出现
静态证据
  • forum-api.js:520-547 — hydrateOfficialPostKinds 对每批帖子追加 posts/news/activities 三个 select=id 查询
  • ForumMain.vue:3064 — 每次列表响应后调用

C · 资源调度 / 请求并发

P-06posts tab 双重触发：sync 路由 watcher 与 switchTab 各跑一遍关键拉取严重RTST

这是「渲染层事件重复 + 网络层重复」的交叉复合问题：一次点击产生两套并发数据流，互相 abort、互相作废。

运行时证据
  • posts tab 进入期实测：get_my_user_space_summary ×2
  • 2 个 HEAD 计数查询被 abort（posts 计数 + profiles 排名，net::ERR_ABORTED）——第二套数据流启动时把第一套的 in-flight 查询掐掉
静态证据
  • UserSpaceMain.vue:1913 — switchTab('posts') 直调 runProfileCriticalFetches()
  • UserSpaceMain.vue:2659-2692 — watch(route.query.tab, …, { flush: 'sync' }) 在 syncUserSpaceTabRoute 的 router.replace 时同步再次调用 runProfileCriticalFetches()
  • fetchUserStats 无 in-flight 合并（仅 token 作废机制，后到者 abort 先到者）
修复（三选一或组合）：① 去掉 flush: 'sync'（改默认 pre，一次导航只触发一次）；② runProfileCriticalFetches 加 5s in-flight 合并窗口；③ watcher 内改为只做 preloadProfileStyles()，数据拉取统一收口到 switchTab。
P-07聚合 RPC 失败无负缓存 → 每次进 tab 重试并滑向 500 条全量兜底严重RTST

get_my_user_space_summary 失败（或旧库未部署）时没有负面结果缓存，每个 tab 的每次进入都会：再试一次 RPC → 失败 → 走重型 legacy 兜底。兜底链里最重的一环是云盘用量统计。

运行时证据
  • 实测 get_my_user_space_summary 在 community / posts / assets / settings 四个阶段各出现（共 5 次），从未写入成功缓存
  • posts tab 实测兜底链发出：user_subscriptions + boh_cloud_entries（500 条全量）
静态证据
  • UserSpaceMain.vue:1158-1199 — fetchAggregatedUserSpaceSummary 失败仅 logger.warn，summaryRpcUnavailable 只在「RPC 不存在」时置位；一般性失败（权限/网络）不置位 → 下次照试
  • UserSpaceMain.vue:1391 — 兜底 listMyCloudEntries({ userId, limit: 500 })，boh-cloud-api.js 返回 CLOUD_COLUMNS 全列（含 contentBlocks JSONB）
  • 前端只为数图片块：contentBlocks.filter(type==='image').length（UserSpaceMain.vue:1402-1407）——为计数拉全量正文
修复：① 失败时把负面结果也缓存 60s（summaryRpcUnavailable 扩展为带时间戳的软标记）；② 云盘用量兜底改窄查询：新建 count_cloud_image_blocks RPC 或 select('content_blocks') 仅当无法避免时限制 limit: 50 + 计数上不封顶提示；③ RPC 部署校验脚本纳入 CI（db push --dry-run 查占用已有先例）。
P-08社区冷加载小额重复请求低RT
运行时证据
  • forum_post_drafts ×2（草稿查询两路独立发起）
  • 同头像图 ×2（nci9byj…png、etvmr2u…jpg 各请求两次）
静态证据
  • 草稿：ForumMain 与内容区草稿逻辑各查一次（需合并收口）
  • 图片：SW 已对 Cloudinary 做 StaleWhileRevalidate，但同页面并发首刷时两请求都可落到网络
修复：drafts 查询收口到单一 composable + request-core in-flight；头像去重交给 SW（已在缓存名单内，预热后自然收敛），优先级低。

与 P-01 构成同一复合问题的两面：加载时整体挂载（P-01），挂载后 1 秒轮询只在组件卸载时清理——而组件几乎不会被卸载。

运行时证据

  • 切回 inbox、切到设置、回访社区、65 秒驻留后——该定时器全程活跃（最终存活定时器清单里始终在列）
静态证据
  • BOHAIMain.vue:1591 — setInterval(checkVisibility, 1000)，仅 onUnmounted 清理
  • GlobalAiGlassOverlay.vue — mountedOnce 首开后置 true 永不复位 → overlay 关闭也不卸载
  • messages tab 内 BOHAI 为 v-show 隐藏而非卸载
修复：① checkVisibility 改事件驱动：document.visibilitychange + IntersectionObserver（宿主可见性变化本来就有事件）；② 至少在 messagesSection !== 'ai' && !overlayOpen 时 clearInterval，回到 AI 时重建。
P-10堆内存平台化：+14.8MB 后全程不回落中RT
运行时证据
  • 28.7 → 30.4 → 30.8 → 43.0 → 43.5 → 42.8 → 42.8 MB：messages 一跳 +12.2MB，此后平台化。不是泄漏型增长（无持续攀升），是「加载即持有」型

  • Messages realtime 重连 setTimeout 未入可取消集合（Messages/index.vue:1171-1175）——重连窗口期卸载可致孤儿 channel，属低概率长尾
修复：P-01/P-09 落地后预期堆平台回到 ~31MB。重连定时器并入 realtimeTimers 集合，onUnmounted 统一 clear。
