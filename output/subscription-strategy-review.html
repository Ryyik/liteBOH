SUBSCRIPTION REVIEW

BOH 订阅体系诊断与优化方案

从代码与数据库实际生效口径出发，复盘现有五档订阅的定价结构、权益真相源与转化链路，给出分层可落地的优化建议。

00

先说结论

整体架构方向是对的（积分化 + 三态续费 + 试用转正），但存在 4 个会直接漏收入或伤害信任的硬问题，以及一个被忽略的定价结构缺陷。

服务端不校验价格，订阅可以 0 积分拿到 subscribe_with_points 完全信任前端传入的 p_points_cost 与 p_duration_months，只拒绝负数。任何登录用户可直连 RPC 以 0 积分开通 120 个月 Ultra。试用 RPC 同理可改档改期。这是收入侧第一优先级。
Plus → Pro 完全线性，主推档缺升级台阶 线上库（2026-09-11 核查）实际配置为 20/80/200/500/1000 万，与页面宣传一致——但迁移基线仍是 100/200/300/500/1000 万另一套数字，「靠人工改库对齐」正是缺单一真相源的实证。且 Plus → Pro 价格 ×2.5、Token ×2.5 完全线性，Token 上给不出升级激励。
签到就能白拿 Pro，积分经济闭环是断的 周签到 5 积分，一个月约 21.7 积分；Pro 月费 20 积分。也就是说「每周签到」这一条路径就能长期覆盖 Pro 的订阅成本，付费转化会被自身激励稀释。
付费墙一半建在前端，可绕过 实验室 PPT/Word 月度次数仅在 useLabQuota.js 前端判断，服务端 record_lab_usage 只插入记录、不做任何限额校验。同时试用期不发放 Cloud+ 权益（服务端只认 status='active'），与「完整体验 Pro」的承诺不符。
订阅的「身份理由」缺失，权益只能靠功能堆量 可见收益只有昵称颜色、抽奖保底次数、Cloud+ 张数。头像框方案（plans/avatar-frame-design-plan.md）已在规划，是补齐身份层最现成的抓手；而 Coding 附加包曾完整上线、却在 8/25 重构中被撤下——服务端至今仍在校验其门禁并发放额度加成，把入口补回来是最干净的新增收入来源。

F1 · 服务端不校验价格与时长，订阅可被 0 积分获取

证据
RPC 只做 p_points_cost < 0 与 p_duration_months > 120 两项范围校验，价格与档位均取自调用方传参，没有任何白名单或价格表比对。 2026090903_points_ledger_completion.sql:76-83 · :175 · 授予 authenticated 执行权见 2026082609_...:496-497
路径
前端调用是 supabase.rpc('subscribe_with_points', { p_points_cost: price, ... })，price 来自前端常量。src/utils/api/subscription-api.js:100-107
影响
任何已登录用户绕过 UI 直连即可传 p_plan_code='ultra'、p_points_cost=0、p_duration_months=120，以 0 积分获得 10 年 Ultra。同类问题存在于 start_subscription_trial：档位与天数同样是调用方传参，可申请 90 天 Ultra 而非 3 天 Pro。

建一张服务端价格表（subscription_plan_prices：plan_code × billing_cycle → points_cost、duration_months），RPC 内按 (plan_code, billing_cycle) 查表取价，忽略调用方传参；试用 RPC 把档位与天数硬编码为常量。这是纯服务端修复，不涉及前端改动。

P0 严重

F4 · 积分经济闭环断裂：签到即可覆盖 Pro 月费

证据
周签到固定奖励 5 积分，一个月约 4.33 周 ≈ 21.7 积分；Pro 月费 20 积分。 2026090905_points_ledger_shop_checkin.sql:263-266 · 价格见 SubscriptionPlans.vue:285
影响
「每周签到」这一条零门槛路径的月度收益足以长期覆盖 Pro。同时发帖有奖（points_per_post 由活动配置，日/月上限均可调）会进一步抬高免费积分水位。结果是订阅定价被自身激励体系稀释，付费转化率无法真实反映产品价值。
建议
关键不是砍签到，而是让「免费积分」与「订阅支出」保持明确水位差。建议把免费积分对单档的覆盖率控制在 30–40%（例如签到降为 2 积分/周，或把 Pro 提高到 50 积分档），并把积分的主要出口引导到「加油包 / 装饰 / 徽章」等消耗型商品上——积分能买东西，才叫货币；只能买订阅，就是折扣券。

03

定价方案建议

分两层：先修口径与结构（不动价格，风险最低），再按需要调整价格锚点与商品形态。

3.1 第一优先：统一计价口径

当前页面用 ￥ 展示、用 积分 扣费，充值还要人工核对。用户的心理账本是「我付了多少钱」，系统的账本是「扣了多少积分」，两者之间没有明确锚点，这会产生典型的「我的钱去哪了」困惑。

方案 A · 积分即主单位（推荐）

页面价格直接写「20 积分 / 月」，去掉 ￥ 符号，计价与扣费同源、零歧义，与积分体系天然一体。不强调积分与人民币的兑换关系，为后续定价调整保留灵活度。

方案 B · 双单位并排

主价显示 ￥，副标显示「= 20 积分」。用户知道要花多少积分，也知道折合多少钱。适合未来接入真实支付、需要保留货币锚点的路线。

无论选哪个，年付折扣的表述都要统一。当前 Tab 写「省 17%」，卡片写「省 40 积分」，两处单位不一致。建议统一为「年付 = 10 个月价格，多送 2 个月」——「送」比「省」的转化率通常更高。

3.2 第二优先：把单位价值阶梯修正为单调上升

价格保持不变（避免影响存量订阅），只修日 Token 梯度。「现日 Token」为 2026-09-11 线上库核查值（= 页面宣传口径）；下表为设计示例，具体数值需结合真实单 Token 成本复核。

04

内容与权益方案建议

核心思路：订阅要卖「身份 + 独占能力」，Token 数量只是支撑，不是主角。

4.1 权益单一源（对应 F2）

新增 plan-entitlements.js 或建配置表，把「档位 → 权益项 → 数值」集中一处。订阅页卡片、对比表、服务端配额校验全部从这里取。改权益只改一个地方，也不会再出现宣传与执行两套数字。

4.2 重排权益矩阵，给 Pro 一个独占理由

现状 Pro 与 Plus 的差异只有昵称色 + 150 张 Cloud+ + 5 次实验室。建议把 Agent & Plan 从 Max 下放到 Pro，并新增「导出免水印」「优先审核」两项零边际成本的独占权益。

4.3 用可交付的差异化替代功能堆量

真正能分层且已在服务端跑的锚点有两个现成的：单次输出上限（TIER_MAX_OUTPUT_TOKENS：Free 1200 / Plus 1800 / Pro 2400 / Max·Ultra 4096）和每日联网搜索次数（10/30/60/120/240），这两个是 Edge Function 里真实生效的阶梯，做权益单一源时应一并收编。可再扩展的锚点：模型档位（bohai_model_configs.min_tier 门禁机制真实存在，但需先把各模式的门禁值真正配置起来）、上下文长度、并发会话数、导出格式与去水印、Cloud+ 分享有效期、审核优先级。这些都比「Token 数字」更难被质疑。

4.4 身份层：与头像框方案合并推进

头像框是与订阅绑定性最好的身份物，且 avatar-frame-design-plan.md 已做完设计与素材路线。建议订阅支付成功弹层直接提供「一键佩戴」，到期置灰但保留「曾经拥有」记录——回收动作本身就是续费钩子。

4.5 年度会员要给到「年度感」

现有年付权益只记一个「年度会员纪念徽章」标记。建议扩展为年度限定头像框 + 年度个人数据报告（用量、创作、社区贡献）+ 次年续费专属折扣，年付才有独立于月付的存在价值。

4.6 服务端权威化清单

三件事必须从前端搬到服务端：订阅价格（F1）、实验室次数（F3）、试用档位与天数（F1）。前端只做展示与预校验，判定权归服务端——这也是让权益矩阵可信的前提。

06

需要拍板的三个方向

下面三个选择会决定上面方案具体怎么落，建议先定方向再写 migration。

决策一 · Pro 的定位是「走量主力」还是「分层第一档」？

这决定了是下调 Pro 价格还是上调 Pro 配额。

推荐走量主力：保持 20 积分不变，把日 Token 抬到 800 万并下放 Agent & Plan，让 Pro 在功能与配额上都值得「最受欢迎」这个标签。
备选分层第一档：降价至 12–15 积分，作为 Plus 到 Max 之间的过渡档，靠 Max / Ultra 承担收入。

决策二 · 页面价格以什么为主单位？

这决定订阅页的计价口径，以及未来真实收银台怎么设计。

推荐以积分为主单位（去掉 ￥ 展示），计价与扣费同源。不强调积分与人民币的兑换关系，保留后续定价策略的灵活度。
备选双单位并排（￥ 主、积分副），适合未来接入真实支付、需要货币锚点的路线。（此路线对应 3.1 方案 B）

决策三 · 签到与社区贡献该不该覆盖订阅成本？

这是增长与收入的直接取舍，也决定 F4 怎么修。

增长优先允许免费积分覆盖一档订阅，把订阅当留存工具、把附加包与加油包当收入来源。前提是 F8 两条通道必须先跑起来。
推荐收入优先：免费积分对单档覆盖率压到 30–40%，签到收益转向装饰 / 头像框 / 加油包等消耗型商品。订阅保持为「付费所得」的清晰属性。

调研对象：BOHLITEBeta2.5 工作区 2026-09-10 快照。所有结论均可在标注的代码或 migration 位置核对。

全部结论已于 2026-09-10 晚逐条复核：核查了 0903 之后的全部迁移（0907/0908 为主视觉数据、0910 为敏感字段 RPC，均不触及订阅函数）、Edge Function api-key-vault 的配额与门禁实现、以及 git 历史中 Coding 附加包的下架记录。
