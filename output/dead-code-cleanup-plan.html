本次沉淀的两条关键判据（纠正了方案第 3 节的执行假设）

  1. CSS 选择器是 AND 语义：只要选择器内存在一个"永不被任何元素使用"的类名，整条规则就永不匹配 → 可删。不是要求所有类名都死（作用域类通常活着）。
  2. :is() / :where() 是 OR 语义：必须先展开为所有组合、要求每个组合都含死类才可删，否则会误删含活分支的规则（本批实测：某文件原判删 452 行，正确值 195 行）。另 :not(...) 内容须剔除出判定。

残留（后续可选）：user-center-dark.css 仍有 30 个死类名，全部位于"保留规则的 :is() 列表内"（死分支）——整条规则含活分支不可删，摘除死分支属选择器重写，收益仅数 KB 而风险更高，本轮不动。

仍待处理：三套并存的死类数字（style-remnant-audit.mjs 报 1133 / 本方案编制时 1667 / 当前 1493）建议合并为单一脚本单一产物。

1. 扫描口径与可信度分级

死代码判定没有单一权威工具，不同口径的结论能差出几倍。本方案所有条目都标注了可信度，只有 A 级才允许进入自动删除流程。

等级判定口径可否直接删验证方式
A 级 从 src/main.js 出发的全库 import 图不可达，且文件名/导出名在全仓（含 tests、scripts、probe、配置文件）零字符串引用 可以，走批次流程 构建 + 单测 + 探针冒烟
B 级 文件可达（被 import），但内部导出/样式类/变量零外部引用 只能删「文件内片段」 文件级单测覆盖后再删
C 级 引用路径是动态的（import.meta.glob、数据库字段、字符串拼接、getImageUrl(name)） 禁止批量删 需运行时观测或后台数据核对

本次扫描范围与方法

① 可达性分析：解析 import / export from / import() / require() 与 <style src>，支持 @/ 别名与 /src/ 绝对路径，多入口 BFS（入口 = main.js + tests/ + scripts/ + probe-*.mjs + 根级配置与 HTML）。

② 引用计数：导出名、CSS 类名、CSS 变量、@keyframes、图片文件名的词边界匹配，语料剔除了 <style> 块自匹配与生成产物（stats.html、.compress-images-cache.json、审计 JSON）——这一点很关键，否则几乎每张图片都会因缓存清单而被误判为「被引用」。

③ 基线：eslint . 全量 + vitest run 全量，用于判断「删除前是否已有失败」。

  3. getImageUrl(name) 接受任意相对名并自动补 /src/assets/images/ 前缀，字符串拼接即可命中。

11. 工具链与长期防复发

11.1 为什么本次没直接用 knip / depcheck

仓库未安装任何现成死代码工具（knip、depcheck、madge、ts-prune、unimported 均不存在）。直接安装会改动 package.json，与「本次仅输出方案」冲突。同时现成工具在本仓库有两个已知水土不服：

  • 不理解本仓库的动态约定：import.meta.glob 的 eager 全量、数据库驱动的 hero 图片、主题 CSS 动态 import —— knip 会把它们判为未使用。
