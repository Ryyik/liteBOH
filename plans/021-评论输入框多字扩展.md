# 021 · 评论输入框「多字扩展」（竖屏论坛回复框不随内容长高）

> 目标：论坛 / 用户空间内嵌论坛的**回复输入框**在竖屏手机上写多行内容时自动长高，写到上限后框内滚动，
> 清空或切换回复对象后自动回缩；键盘弹起时输入框与「取消 / 发送」仍在可视区内。
>
> 提出：2026-09-30（用户报障：「论坛竖屏评论输入没有多字扩展，即输入框不会改变」）
> 状态：**阶段 1 已实施并自证**（2026-09-30，探针 5/5 绿 + 反证已做）；阶段 2 / 3 未做。实施记录见 §9

## 2. 需求翻译成可验收判据

「输入框不会改变」要落成 6 条硬判据（探针就按这 6 条写）：

| # | 判据 | 验收口径 |
|---|---|---|
| A | 初始高度 == `rows` 行 | 未输入时 `clientHeight` ≈ `rows × lineHeight + padding`（±1px） |
| B | 内容变多 → 长高 | 逐行输入 6 行，`clientHeight` **单调不减**，且全程 `scrollHeight ≤ clientHeight + 1`（无内部滚动） |
| C | 到上限 → 框内滚 | 继续输入，`clientHeight` 停在上限，`scrollHeight > clientHeight`，`overflow-y: auto`，光标可见 |
| D | 内容变少 / 清空 → 回缩 | 全选删除后 `clientHeight` 回到 A 的值 |
| E | **父组件改写内容 → 同步重算** | 切换回复对象时 `replyContent` 被 `buildReplyDraft()`（`ForumMain.vue:3508`）替换为更短草稿 → 高度必须跟着回落 |
| F | 竖屏键盘态不遮挡 | 模拟键盘 inset 后，textarea 与 `.reply-actions-v2` 的 `getBoundingClientRect().bottom` 均在可视区内 |

> **E 是本设计最容易漏的一条**。`PostCard` 用的是 `:value` + `@input` 受控写法，
> 父组件会**主动改写** `replyContent`（切换目标、发送成功清空、取消）。只绑 `@input` 的实现在这些路径上不会收缩。
>
> 实施结果：A–E 已由 `scripts/probes/probe-reply-autogrow.mjs` 钉住并全绿；**F 只测量、不断言**（理由见 §9.3）。

## 3. 方案选型

| 方案 | 结论 |
|---|---|
| **A. 纯 CSS `field-sizing: content`** | ❌ 不作为主路径。Chrome 123+ 支持；Safari 直到 **26.2（2025-12）** 才支持（[WebKit 发布说明](https://webkit.org/blog/17640/webkit-features-for-safari-26-2/)），iOS 存量设备大量低于此版本。更关键的是它与「JS 写 `height`」互相打架（`field-sizing` 生效时 `height` 被忽略），要么全 JS、要么 `@supports` 分叉两套行为，回归面反而更大。**留作未来可选**（等 iOS 覆盖率够了，删 JS 只留一行 CSS）。 |
| **B. 抽 composable `useAutoGrowTextarea`** | ✅ **推荐**。与 `useKeyboardInset.js` 同范式（模块级能力 + 组件级接线），侵入最小，4 处存量实现可逐步收敛，不改变现有 `:value` / `@input` / emit 契约。 |
| **C. 抽组件 `<AutoGrowTextarea>`** | ⚠️ 暂不采用。会改掉 `PostCard` 现有的 `emit('update:reply-content')` 事件契约，且要透传 `enterkeyhint` / 禁用态 / 插槽，收益不抵改动面。 |

## 4. 单一真源设计

### 4.1 新增 `src/composables/useAutoGrowTextarea.js`

```js
/**
 * 评论/回复类 textarea 的「多字扩展」—— 全站单一实现点。
 *
 * ## 为什么需要它
 * 原生 textarea 的高度由 rows 属性决定，与内容无关；`resize: none` 后又封掉了手动拖高。
 * 竖屏手机写超过初始行数的评论时，文字只能在框内滚动，看不到上下文。
 *
 * ## 两条必须遵守的规则
 * 1. 先 `height = 'auto'` 再读 `scrollHeight`，否则收缩路径测不出变小。
 * 2. 高度是**内容驱动**的，父组件改写 value 时也要重算 —— 不能只绑 @input。
 *    （PostCard 用 :value 受控写法，切换回复对象/发送成功都会由父组件改写内容。）
 *
 * ## 真源划分
 * - **最小行数**：`rows` 属性（模板里的 `rows="2"` 从「死属性」升级为最小行数真源）。
 * - **上限**：CSS 的 `max-height`（断点可调）。JS 读 `getComputedStyle(el).maxHeight` 取用，
 *   **不在 JS 里写第二份像素值**。
 * - **过渡**：增高逐帧跟随（不加过渡，否则打字时框会滞后）；回缩用 `--duration-fast`。
 */

export const AUTO_GROW_MIN_ROW_HEIGHT = 16; // 兜底行高（读不到 line-height 时）

export function useAutoGrowTextarea(options = {}) { … }
```

**导出签名**

```js
const { textareaRef, resize, resetHeight } = useAutoGrowTextarea({
  value,                 // Ref<string> | () => string，可选：内容变化时自动重算（判据 E）
  animateOnShrink = true,// 回缩是否走过渡
});
```

**核心算法**（与既有 4 份实现的差异点标了出来）

```js
const measure = () => {
  const el = unref(textareaRef);
  if (!el) return;
  const cs = getComputedStyle(el);
  const lineHeight = parseFloat(cs.lineHeight) || AUTO_GROW_MIN_ROW_HEIGHT;
  const padding = parseFloat(cs.paddingTop) + parseFloat(cs.paddingBottom);
  const minRows = Number(el.getAttribute('rows')) || 2;   // ← 最小行数真源 = rows
  const minHeight = Math.round(lineHeight * minRows + padding);
  const maxHeight = parseFloat(cs.maxHeight) || Infinity; // ← 上限真源 = CSS max-height

  el.style.height = 'auto';                                // 必须：否则收缩测不出
  const next = Math.min(Math.max(el.scrollHeight, minHeight), maxHeight);
  if (Math.abs(next - el.offsetHeight) < 1) return;        // 防 ResizeObserver 回环
  el.style.height = `${next}px`;
};
```

**接线**（4 个触发点，缺一不可）

| 触发 | 为什么 |
|---|---|
| `@input` | 打字 |
| `watch(value)` | 父组件改写内容（判据 E） |
| `onMounted` + `nextTick` | 展开回复框那一刻；卡片被虚拟列表回收重建时 `replyContent` 可能非空 |
| `ResizeObserver`（宽度变化） | 旋转、侧栏开合、`KeepAlive` 唤醒 → 换行点变了，行数跟着变 |

**IME 处理**：`compositionstart` 期间跳过（中文拼音候选阶段 `scrollHeight` 会抖动，不跳会让框在组字时抽动），
`compositionend` 后补算一次。

**rAF 合并**：`@input` 里每键读一次 `scrollHeight` 会强制 reflow。用 `requestAnimationFrame` 合并成每帧至多一次，
与 `useKeyboardInset.js:75-78` 的 `scheduleFlush` 同写法。

### 4.2 CSS 侧（以主症为例）

```css
.reply-textarea-v2 {
  /* 上限真源：竖屏约 5~6 行；宽屏给到 240px */
  max-height: 240px;
  overflow-y: auto;          /* 触到上限后框内滚，光标始终可见 */
  min-height: 0;             /* 高度完全交给 JS，避免和 rows 打架 */
  transition: height var(--duration-fast) var(--ease-out);
  overscroll-behavior: contain; /* 框内滚到底不要把页面一起带走 */
}

@media (max-width: 768px) {
  .reply-textarea-v2 {
    /* 竖屏：键盘约占 300px，框 + 操作行不应吃掉半个屏 */
    max-height: min(168px, 30dvh);
  }
}

@media (prefers-reduced-motion: reduce) {
  .reply-textarea-v2 { transition: none; }
}
```

> `30dvh` 是给「折叠屏 / 小屏竖屏」兜底；键盘弹起时 `dvh` 不变（iOS），所以**不能**指望它自动避让键盘 ——
> 避让靠判据 F 的 `scrollIntoView`，不是靠高度上限。

## 6. 风险与坑（都是这类改动真会踩的）

| 风险 | 应对 |
|---|---|
| **`height` 过渡与逐键增高打架** → 打字时框滞后于文字 | 增高**不加**过渡（逐帧跟随）；只有回缩走 `--duration-fast`。composable 用 `resize({ animate })` 区分 |
| **`ResizeObserver` 回环**（写 height → 触发 observer → 再写） | 写入前比较 `Math.abs(next - el.offsetHeight) < 1` 直接 return |
| **只绑 `@input` 会漏掉父组件改写**（判据 E） | 必须 `watch(value)`，并在 `onMounted` 补一次 |
| **`resize: none` 仍要保留** | 触屏上原生把手没意义，且与 JS 写 height 冲突；保留 `resize: none` |
| **`overflow-y` 误写成 `hidden`** | 超上限后光标会被裁掉。必须 `auto` |
| **竖屏行高口径**：CSS 写 15px，实际被 `style.css:354` 的 `!important` 抬到 16px | 行高一律从 `getComputedStyle` 读，不写常量 |
| **虚拟列表性能** | 同时只有 1 张卡渲染 textarea（`v-if="activeReplyTarget.postId === post.id"`），且 rAF 合并 → 每帧至多一次 reflow |
| **`scrollIntoView` 与虚拟列表滚动打架** | 只在**展开那一刻**触发一次（不是每次增高），且仅竖屏；增高过程中用 `block:'nearest'` 做最小校正 |
| **门禁冲突** | 不新增裸色值（不碰 `check:dark-tokens:strict`）、不用 `!important`（不碰 `check:important-budget`）、不写死时长（用 `--duration-fast`）、不直连数据层（不碰 `check:layering`） |

### 9.2 探针抓到的两个坑（都不是肉眼能看出来的）

**① `height='auto'` 之后写「相等就跳过」→ 元素永久留在 `auto`。**
第一版 `measureNow` 里留了 `if (next === 上次值) return`。内容已经顶在上限时，下一次测量
`next` 与上次同为 168 → 提前返回，而 `height` 刚被设成 `auto` 且没写回 →
渲染回 `rows` 的固有高度。实测曲线：`n=5 → 168`、`n=6 → 85`、`n=7 → 168`、`n=8 → 85`
（**偶发恢复**，所以更隐蔽）。已改为无条件写回，并把原因写进代码注释。
> 教训：`height: auto` 是一个**必须闭合的中间态**，任何提前返回路径都要先把值写回去。

**② `watch(() => unref(value))` 传 getter 时 watcher 永不触发。**
`unref` 只解 ref，**不会调用函数**；传 getter 时它原样返回那个函数本身 → 依赖恒为同一引用 →
回调不触发。断言 E 实测：切换回复对象把内容从 200 字改成 7 字，高度停在 168 不动。
已改为 `typeof value === 'function' ? value : () => unref(value)`。
> 这条正是 §2 判据 E 预判的「最容易漏」路径，**只绑 `@input` 的实现在这里不会收缩** ——
> 若没有 E 这条断言，这个 bug 会一路带到线上。

**③ 设计文档里的「同族输入框」有一条是误判：`.reply-textarea-x` 是死 UI。**
本计划 §1.2 把 `PostDetail/components/CommentThread.vue:201` 列为「同一缺陷」。实施时给它接上 composable 后，
探针场景 B 却始终 SKIP：聚焦详情页底部输入栏后 `.reply-textarea-x` 不出现。追下去发现
`CommentThread` **只被 `PostDetailMain.vue` 引用**，而两处（`:2464`、`:2840`）都硬编码了 `:hide-composer="true"`，
组件的内嵌评论框被彻底压制；详情页真正的评论输入是底部操作栏的单行
`<input class="pd-reply-input" type="text">`（单行框本来就不该长高，也不存在多字扩展问题）。

→ 该处改动**已撤销**；探针里把它改写成一条**绊线**（场景 B）：断言「详情页评论输入仍是单行 input 且
内嵌 `.reply-textarea-x` 不渲染」。一旦有人把内嵌评论框放出来，这条立刻变红，逼其接上 `useAutoGrowTextarea`
并补 A–D 断言 —— 而不是让一个休眠的输入框悄悄上线。
> 教训：设计阶段的「同族清单」是按类名和样式扫出来的，**必须用运行时可观测性复核一遍**。
> 一个组件被 `v-if` 压制、参数硬编码关掉，静态读代码是看不出来的。

### 9.3 判据 F（键盘遮挡）为什么只测不改

竖屏 390×844、输入框顶到上限（168px）时实测：

| 量 | 值 |
|---|---|
| textarea 底边 | 562 |
| 「取消 / 发送」操作行底边 | 630 |
| 可视底（`visualViewport`） | 844 |
| 是否遮挡 | **否** |

所以本轮**不引入** `scrollIntoView`，理由有两条：
① iOS 聚焦时自身会把元素滚进可视区，再叠一层自定义滚动有双滚风险；
② `scrollIntoView({ block:'center' })` 会与论坛虚拟列表的滚动锚定互相打架。

→ 待办：真机（iOS Safari + 真实键盘）复测后再决定。探针已把这项测量固化进 `report.info.keyboardOcclusion`，
后续改动可直接前后对照，不必重新设计测法。
