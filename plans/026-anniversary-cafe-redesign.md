# plans/026 — 云上咖啡店（`/anniversary-cafe`）玩法与界面重构方案

> 2026-10-08 · 基于 1318 行 `index.vue` + 291 行 `style.scoped.css` 的实测审计
> 方法：Playwright跑真页面取几何 + 节点脚本核算数值，不是看代码猜的。

---

## 0. 一句话结论

这个页面的问题不是「美术没做好」，而是**它把所有玩法都压成了同一条规则**：
`processProgress` 从0 涨到 100，停在金色区就算成功，越界就失败。
11 个制作步骤（研磨/萃取/注水/打奶泡/糖浆/冰块/果汁/可可/生椰/气泡/拉花）
**全部退化成这一个机制**，只是换了图标、换了 rate、换了 target 区间。

界面拥挤是这个机制的必然结果：既然每个步骤都是「一个进度条 + 一个按钮」，
那多几个步骤就得多几个面板，于是 844px 的竖屏里塞了 9 块绝对定位浮层。

---

## 1. 实测证据

### 1.1 界面占位（Playwright `getBoundingClientRect`，非估算）

**竖屏 390×844**

| 区域 | y 范围 | 高度 | 占屏 |
| --- | --- | --- | --- |
| 顶栏 `.game-bar` | 7–54 | 47 | 5.6% |
| HUD 三格 | 99–161 | 62 | 7.3% |
| `.order-queue` | 159–252 | 93 | 11.0% |
| `.equipment-status` | 253–311 | 58 | 6.9% |
| **面板合计** | **7–311** | **504** | **59.7%** |
| 顾客 + 猫（唯一「画面」） | 311–502 | 191 | 22.6% |
| `.workbench` | 507–837 | 330 | 39.1% |

- 竖屏下**没有任何元素重叠或溢出**（`overlaps: []`, `overflow: []`）——
  所以拥挤不是 bug，是设计一开始就按「塞得下就行」算的。
- 但机器占位被压到 `grid-template-columns: 128px 1fr`，
  咖啡机主体只剩 128px 宽，视觉上退化成一根彩色竖条。
- `.order-queue` 每张卡要显示 头像/名字/饮品/当前步骤/耐心条 = 5 行信息，
  塞进 93px 高的三列 = 每列 123px，`.queue-order img { display: none }` 已经被迫隐藏头像。

**桌面 1440×900**

- 无重叠，但中部（`y 300`–`600`，约 300px 高 × 全宽）是纯背景图，
  没有内容也没有引导 —— 这就是「空」和「挤」同时存在的原因。
- 17 个可交互元素（按钮）分布在 5 个互相竞争的面板里。

### 1.2 玩法机制冗余

| 输入范式 | 步骤 | 判定 |
| --- | --- | --- |
| `hold` | 研磨 | 松手时`processProgress` 是否落在 `[62,78]` |
| `toggle` | 萃取 | 再次点击时同上，区间 `[58,72]` |
| `gesture:water` | 热水 / 生椰 / 气泡 | 拖动改rate，松手同上 |
| `gesture:steam` | 蒸汽 | 拖动改位置 + 松手同上 |
| `gesture:pour` | 拉花 | 拖动累计距离 + 往复次数 ≥3 |
| `tap` | 糖浆 / 冰块 / 果汁 / 可可 | 点够固定次数 → `completeStep(96,...)` |

11 步里只有 `pour` 有独立判定（往复次数），`tap` 类**完全没有技巧空间**（点够数就 96 分）。

### 1.3 数值实测（`node -e`核算）

**操作窗口过窄**

| 步骤 | 到达窗口耗时 | 窗口停留 | 含 ±8容错 |
| --- | --- | --- | --- |
| 研磨 | 2.14s | **552ms** | 1103ms |
| 萃取 | 2.64s | 636ms | 1364ms |
| 注水 | 1.94s | **455ms** | 939ms |
| 打奶泡 | 2.32s | 560ms | 1200ms |
| 生椰 | 2.03s | 533ms | 1067ms |
| 气泡 | 1.67s | **472ms** | 917ms |
| 拉花 | 2.23s | 484ms | 1000ms |

455–636ms 意味着「反应时间预算」，但这个游戏**同时还在跑 3 个订单的耐心条**。
对照：主流动作游戏的判定窗口通常给到 150–300ms 的**宽松档**，
这里的 16 点区间（≈500ms）已经是相对宽松的那一档，但**没有分级**——
`gradeStep` 只有「完美 / 稍偏差 / 失败」三档，且「稍偏差」还只扣 8 点耐心。

**猫的救场是最优解，不是彩蛋**

```
摸猫：320ms 冷却，+1 亲密度；逗猫：+2；救场消耗 8 点
攒满 8 点最快 1.28s（连点逗猫 4 次）→ 救场 0.35s
⇒ 每杯总耗时 ≈ 2.9s，150s 内可刷 51 杯（品质锁定 82）

认真做一杯：4–5 步 × 3–4s ≈ 17s
⇒ 150s 内可做 7–9 杯（品质可达 96）
```

这是**奖励结构反了**：认真做是劣势策略。
更糟的是 `resolveSuccess` 里 `catAssist` 走的品质硬编码 82，
比认真做的满分 96 低，但**时间成本只有 1/6**。

**升级让游戏变简单，而不是变难**

```
targetBounds = [start + shrink - bonus, end - shrink + bonus]
  shrink  = min(5, served × 0.65)   ← 越做越难（上限 -10 总宽度）
  bonus   = grinder 等级 × 1.4   ← 满级 +4.2/侧（总 +8.4）

served=8 时 shrink = 5.0（窗口 16 → 6）
磨豆机满级 → 窗口 16 + 8.4 - 10 = 14.4 ⇒ 反而比开局宽 1.5倍
```

即「**越熟练越难，但升级能把难度买回来**」——可预期的正反馈爬坡，
没有转折、没有天花板、没有「后期挑战」的内容。

**耐心系统在实际时长内几乎不构成压力**

```
基础衰减 0.62%/s，served=8 时 1.06%/s
served=0 时 150s 只掉到 1%（几乎刚好不超时）
served=8 时 94s 归零（此时早已过中段）
```
衰减太慢，且 `arrivalTimer` 每 10.5s 才尝试补一单（满了就静默失败），
所以「漏单」几乎只能来自玩家真的手慢，而不是节奏压力。

## 2. 重构方案

### 原则：不引入游戏引擎，先把机制和布局做对

理由：这是一个**嵌在社区站点里的小游戏**，不是一个独立游戏产品。
引入 Phaser 会带来 ~345KB(gzip) 依赖、独立的场景/输入体系、
和站点其余部分的样式体系打架，而且**上面的问题一个都不是引擎能解决的**——
它们是设计问题不是渲染问题。

所以分两步：**P0 改玩法内核 + 布局**（纯 Vue，零新依赖），
**P1 视效果再决定是否上canvas 渲染层**。

---

### P0-1 拆分 1318 行单文件（结构，不改行为）

现在 `index.vue` 里塞了：数据表、游戏循环、状态机、音频、存档、10 种手势 handler、
4 个 phase 的模板。落点：

```
src/games/cafe/
├── data/drinks.js          # 8 款饮品 + 步骤定义（从 stepDefinitions 搬出）
├── data/customers.js       # 12 位顾客 + 皮肤图
├── data/memories.js        # 5 段回忆
├── core/roundState.js      # 纯函数：createRound / tick / settleOrder
├── core/recipes.js         # 饮品 → 步骤序列的解析
├── core/scoring.js         # 评分公式（现在散在 resolveSuccess 里）
├── systems/equipment.js    # 锅炉/蒸汽/台面 三条degrade 曲线
├── systems/cat.js           # 亲密度与救场
├── systems/persistence.js  # localStorage 读写（3 个 key 收口）
├── audio/sfx.js            # playTone 换成真实音效资源
└── components/             # OrderCard / Workbench / CustomerStage / CatZone / HudBar
```

判据：`index.vue` 降到 **< 300 行**，且 `core/` 与 `systems/` 全部是
**无 Vue 依赖的纯模块**（能直接 vitest）。
这条对齐项目已有的 `plans/025` 模块拆分做法。

---

### P0-2 给每个步骤一个**不同的核心动作**（玩法本体）

这是最关键的一条。现在的 `mode: hold/toggle/gesture/tap` 是**输入方式**的区分，
不是**玩法**的区分。要改成玩法区分：

| 步骤 | 现在的机制 | 改后的机制 | 玩家要判断什么 |
| --- | --- | --- | --- |
| **研磨** | 进度条进金区 | **转速振荡**：按住越久转速越高，超过刻度线会过热回落；要在正确的转速区间**稳定保持** 1 秒 | 什么时候松手 vs 再等等 |
| **萃取** | 进度条进金区 | **分段萃取**：前段 18s 稳定萃取，中段必须**点一次排气**（漏了扣品质），后段 30s 内结束 | 要不要为了排气打断节奏 |
| **注水** | 拖动改 rate | **画圆注水**：绕着杯心画圈，圈要闭合才连成一体；画歪了断水重连| 手速稳定性 |
| **打奶泡** | 拖动改位置 | **引入空气的时机**：乳泡量从 0涨，太早进气太粗、太晚没气泡，要在**旋涡稳定后**某个时刻停 | 时机取舍 |
| **糖浆/冰块** | 点够次数 | **冰块要抢在冰化前下**（化完这单作废）；糖浆有先后顺序（先可可后糖浆才对） | 顺序 |
| **生椰 / 气泡** | 拖动改 rate | **分层不能混**：注入时液面必须高于已有液面，同层则分层失败 | 节奏与高度管理 |
| **拉花** | 往复次数 ≥3 | **画心形**：跟随一条引导轨迹，抖动惩罚；终点要落在杯心偏心 6px 内 | 轨迹控制 |

改完后的关键差别：**每一步都在要求玩家判断不同的东西**，
而不是「同一条进度条换rate」。

---

### P0-3 判定分级 + 真实的失误惩罚

现在 `gradeStep` 只有完美/偏差/失败三档，且偏差只扣 8 点耐心（≈12s）。

改成四档，每档影响**不同的东西**（这样才有决策）：

| 档 | 条件 | 品质 | 额外 |
| --- | --- | --- | --- |
| Perfect | 落在金区内 30% | 100 | +连杯×2、combo 不清零 |
| Good | 落在金区其余 | 88 | — |
| Fair | 落在外侧 8 点内 | 70 | **连杯清零** |
| Fail | 越界 | — | **该步骤整体重做 + 耐心 -15** |

关键改动：**Fail 的成本从「重做一步（3s）」提高到「连杯清零 + 耐心 -15（≈14s）」**。
让「稳一点别fail」变成有意义的策略。

同时把 `targetBounds` 的**金区宽度**做成玩家可见且可学习的
（现在金区宽度只有 16 点，且`shrink` 随 served 缩窄但**从不告知玩家**）。

---

### P0-4 修掉「猫救场是最优解」

三条一起改，缺一条都还会有人刷猫：

1. **亲密度获取变慢**：摸猫 320ms 冷却 → 1.5s；逗猫 +2 → +1；
   且**只在无订单在制作时**才能逗猫（不能在别人等待时白嫖）。
2. **救场有真实代价**：`resolveSuccess({catAssist:true})` 的品质 82 → **68**
   （低于认真做的中位档），且**不计入 `totalQuality` 的连杯加成**
   （`comboTip = 0`），连击清零。
3. **救场次数有上限**：每局 `maxRescues = 2`（HUD 上明示）。

算一下改完的账：
```
认真做：4-5 步 × 3s ≈ 15s/ 杯，品质 88~100，连杯可持续累积
救场：攒 8 点至少 6s（1.5s 冷却）+ 0.35s，且断连击、品质 68、每局 2 次
⇒ 150s 内认真做≈9 杯 / 全救场≈2 杯 + 2 次额度
```
认真做重新变成优势策略。

### P0-5 布局：竖屏改为「单列 + 折叠」，桌面改为「三栏真布局」

现在的 5 个 `@media` 各自为政，每个都在**同样的绝对定位上加 `scale()`**
（`.customer-zone { transform: scale(.59) }`）——缩放是省事，但会让文字小到不可读
（`font-size: 7px` 的 `.upgrade-row > span small`）。

改成**布局重构，不是缩放**：

**竖屏（≤768px）—— 四行网格，用 CSS Grid 不用 absolute**

```
┌─────────────────────────┐
│ 顶栏：店名 + 倒计时 + ⏸  │ 44px  ← 单一顶栏，不再三段
├─────────────────────────┤
│ 订单条（横向滚动的胶囊） │ 64px  ← 一行，不是三列卡
├─────────────────────────┤
│                │        │
│   舞台（顾客+猫）│ HUD    │ 1fr   ← 顾客在这里，猫在脚下
│                │ 2 列    │
├─────────────────────────┤
│ 设备条（3 个小图标）     │ 40px
├─────────────────────────┤
│ 操作台：步骤 + 装置 + CTA│ 260px
└─────────────────────────┘
```

具体改动：
- `.order-queue`：三列卡 → `display: flex; overflow-x: auto` 的**单行胶囊**，
  每张只显示 `名字 + 饮品名 + 耐心环`，隐藏当前步骤文字（步骤在操作台里显示）。
- `.equipment-status`：竖屏从 58px 三格改成 **40px 图标条**，
  只在数值进危险区时才展开显示文字（`danger` 类已有，接到这个上面）。
- `.customer-zone` / `.cat-zone`：从 `bottom: 47%` + `scale(.72)` 改成
  grid 单元内的 `width: 100%`，猫固定在舞台右下角，`--cat-spot` 的随机位移在竖屏下关掉。
- 竖屏的`.hud`、`.day-progress`、`.game-bar` 三者合并成一条顶栏。
- **删掉 `.queue-order img { display: none }`** —— 缩放不再需要，图片放得下。

**桌面（>900px）—— 三栏 grid，填掉中部空洞**

```
┌────────────┬─────────────────────┬──────────────┐
│ 订单队列    │      舞台            │  HUD + 设备   │
│ 280px      │      1fr             │  280px       │
│ (3 张竖排) │  顾客 + 咖啡机 + 猫   │ (竖排)        │
├────────────┴─────────────────────┴──────────────┤
│ 操作台（横贯全宽，装置在左、控制区在右）          │
└───────────────────────────────────────────────────┘
```

把现在的 `top: 70px` / `left: 16px` / `right: 16px` / `bottom: 39%`
这些绝对定位**全部删掉**，改成一个 `grid-template`。
中部空洞会被舞台填满，顾客形象可以直接放大到 240px（现在是 210×0.78）。

### P0-6 视觉：像素风做成真像素风

现在的背景是**写实渲染的 Minecraft 截图**，前景装置是**CSS 画的方块**，
两者画风打架（截图里能明显看到）。而且 `26coffee4.webp` 是整页背景图，
在窄屏被 `background-size: cover` 裁得只剩一片木头纹理。

改法（按成本排序）：
1. **背景分层**：桌面前景 / 店内中景 / 远景天空，做成 3 层视差（`translateY` + 鼠标视差），
   用同一套像素化滤镜（`image-rendering: pixelated` + 低分辨率缩放）。
2. **装置改用 sprite**：现在 `.bean-hopper` / `.voxel-kettle` 等是纯 div拼的，
   在 128px 宽里必然糊。换 32×32 或 64×64 的 PNG sprite，
   帧动画（研磨时豆子落下、水流、气泡）用 CSS `steps()` 驱动（项目已有 `steps(2,end)` 用法）。
3. **统一色调**：走项目已有的 `tokens.css`（MEMORY 里记着「动效/玻璃单源 tokens.css」），
   别再在这一个文件里硬编码 14 个色值。

### P1（效果达标后再评估）是否上 canvas 渲染层

如果 P0-2 做完粒子/水花/蒸汽还是不出彩，再考虑：
用 **PixiJS v8**（gzip ~50KB，只做渲染层，不换掉 Vue 的 UI）
画舞台里的粒子和装置，DOM 继续负责 HUD 和订单卡。
**不要上 Phaser**：345KB 且要接管输入和场景，
会和站点的路由/无障碍/焦点管理全面冲突，收益不抵成本。

## 4. 我建议的取舍

如果只能做一件事：**做 P0-2（给每步一个不同动作）+ P0-4（修猫的最优解）**。

理由：界面拥挤是表象，玩法塌陷才是根因。
现在这个游戏**认真玩不如薅猫**，玩家一旦发现这条最优路径就不会再回来——
这不是美术能救的。反过来，如果每一步都要求不同的判断、
且认真做有明确收益，玩家的注意力自然会被吸回界面上，拥挤感也随之下降。

界面部分建议先只做 P0-5 的竖屏（因为手机是主要场景），桌面三栏可以第二轮。
