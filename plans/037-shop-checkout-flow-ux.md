# 037 · 周边商城下单流程：UX 重构方案

> 状态：**方案待确认（2026-11-03）**，只有诊断与规格，**代码未动**
> 目标：把「购物袋 → 提交」这条链从"表单弹窗"升级成主流电商的四段式下单（购物袋 → 确认订单 → 提交 → 结果），并补上下单前后缺失的三样东西：**商品清单、总额明细、下单之后的去处**
> 关联：`src/views/Shop/{index,BagPanel,ProductDetailSheet,OrderPanel,OrderDetailSheet,ShopPaymentSuccessModal}.vue`、`stores/bag.ts`、`utils/api/{shop-orders,profile,address}-api.js`、`plans/points-redeem-plan.md`
> 证据截图：`docs/shop-ux-audit-2026-11-03/`（2026-11-03 实测，390×844 / 1440×900）

---

## 1. 一句话

现在的结算**不是下单流程，是一个收货地址表单**：点「去结算」直接弹出 420px 的「确认收货信息」卡片，用户在整个过程中**看不到自己买了什么、总共付多少、提交后会发生什么**；提交成功又立刻说「支付成功」，而现金部分其实是线下收的 —— 信息缺三块、话术错一处，这就是"不像成熟购物平台"的来源。

## 2. 现状诊断（读码 + 实拍）

### 2.1 流程骨架

| 环节 | 实现 | 评价 |
|---|---|---|
| 商品列表 | `index.vue` 两列/三列网格，卡内只有图 + 名 + 价 | 勉强够用，缺状态信息（见 2.2） |
| 商品详情 | `ProductDetailSheet.vue`，竖屏全屏 / 横屏居中弹窗 + clip-path 形变 | **这是全站最成熟的形态，应被结算页复用** |
| 购物袋 | `BagPanel.vue`，列表 + 合计 + 「去结算」，全部 in-flow | 总价会随内容滚走；缺选择/失效处理 |
| 结算 | `index.vue` 的 `.modal-scrim` + `.contact-card`，标题「确认收货信息」 | **核心问题所在**：没有商品清单 |
| 结果 | `ShopPaymentSuccessModal.vue`，积分卡翻转 + 「支付成功」 | 品牌感够，信息与话术不够 |
| 订单 | `OrderPanel.vue` 列表 OK；`OrderDetailSheet.vue` 只有号/时间/金额/商品 | 看不到寄给谁、到哪一步 |

### 2.2 逐条问题（都可在截图里看到）

**A. 商品列表**
1. 价格是 12px 次要灰（`.p-price` 用 `--boh-text-secondary`）—— 主流电商价格是卡内最强视觉，这里被做成了注脚。
2. **无售罄/缺货/库存紧张角标**：`stock <= 0` 的卡与可买卡长得一模一样，只有点进详情才看到按钮变「暂不可兑换」。
3. 卡片高度随标题行数变化，同一行底边不齐（截图 01 可见第一行两张卡不等高）。
4. 桌面端实测 `cols=3 / cardW=373 / pageW=1440`（截图 05）：一屏只看得到两行，图片被放大到失真；横屏 844 只有 2 列。缺容器 `max-width` 与列宽档位。

**B. 商品详情**
5. 只有「加入购物袋」，**没有「立即购买」**，也没有数量选择 —— 想买 2 件必须先加购、再去购物袋按加号。
6. 组合支付呈现为「积分价 45 积分 / 现金价 ¥6.90」两行并列，**没有"到手要付多少"的合计表达**。
7. 无多图、无配送说明（包邮？到付？几天发？）。

**C. 购物袋**
8. 无单选/全选、无编辑批量删除。
9. 合计与「去结算」跟着内容走：商品一多就被推到屏幕外，用户滑到底才知道能结算。主流是**底部固定结算条**。
10. 🔴 每行价格是**加购时的 localStorage 快照**（`bag.ts` 只做 `normalizeBagItems`，进袋/进结算都不刷新）。服务端 `create_shop_order` 会按 `products` 表重算金额（`2026081102_multi_payment_support.sql:117-167`）⇒ **显示价与实扣价可能不一致，且全程没有任何提示**。
11. 🔴 数量可以加到 99；服务端只校验 `1..99`（同文件 `:113`），**既不校验库存、也不扣库存** —— `products.stock` 目前是装饰字段，"库存 100 件"这句在详情页是假承诺。
12. 无积分余额对照（"你有 1200，本单 55"），积分不足要等提交后才由 `resolveOrderErrorMessage` 兜出来。

**D. 结算弹窗（最要紧）**
13. **没有商品清单** —— 确认一次购买却看不到买了什么，只有底部两行「积分支付 55 积分 / 现金支付 ¥11.90」。
14. 地址是**一组手填字段**（省份 select + 城市 input + 详细地址 textarea + 粘贴识别框），不是"选地址"。主流是地址卡 + 更换 + 新增。
15. 点「管理地址」会 `closeContactModal()` 后跳到「地址」Tab（`index.vue:678-681`）⇒ **辛苦填的表单被关掉**，回来要重开、重填。
16. 「邮箱（账号）」整行只读，多数时候显示「未绑定邮箱」—— 对下单零帮助，纯噪音。
17. 金额只有两行，没有「商品金额 / 运费 / 优惠 / 应付」的明细口径，积分与现金也没有一个"合计"的说法。
18. 按钮写「确认提交」，**不写金额、不写后果**（主流是「提交订单 ¥11.90」）。
19. 竖屏是居中 420px 卡片 + 内部滚动：地址区一展开就变成"弹窗里的表单"，与商品详情那种全屏页的成熟感差一档。
20. 无备注、无发票、无配送方式、无预计发货时间。

**E. 结果页**
21. 🔴 标题「支付成功」，但现金是**线下**收的（`shop_points_orders` 只记 `rmb_total`，无支付网关）⇒ 事实性误导。
22. 只有「完成」，没有「查看订单」「继续逛逛」；没有"谁联系我、几天发货"的后续说明。
23. 订单号被截断成 `BOH20261103214...`（`.payment-success-details dd` 是 `text-overflow: ellipsis`），且不可复制。
24. 成功页不显示买了什么、寄给谁 —— 用户截图分享/事后核对都靠记忆。

**F. 订单**
25. 状态时间线（`od-steps`）**已经做过了**（2026-11-02，四态 + 当前步骤高亮）—— 这块是成熟的，**不要重做**。真正缺的是另外两块：**收货信息**（收件人 / 电话 / 地址）与**物流单号**，时间线只能回答"到哪一步"，回答不了"寄给谁、单号多少"。
26. 🔴 `shop_points_orders` **没有地址快照列**（表结构见 `2026033104_shop_points_order_hardening.sql:6-17`）⇒ 用户改了默认地址后，历史订单永远说不清当时寄给谁；结算邮件也是按 order_id 回读 `profiles.shipping_*`。
27. 时间线只有 `created_at` / `updated_at` 两个可信时间戳（代码注释明确"不编时间"）⇒「已发货」这一步显示不出发货时间。要补得靠 P2 的状态事件表，**不要在 UI 层编造**。

### 2.3 一句话归因

不是视觉不够"高级"，是**信息结构缺了一层**：主流电商把「确认订单」当成一页独立的信息核对页，BOH 把它压缩成了一个地址表单的弹窗标题。

## 3. 外部调研（只取对 BOH 有用的）

| 来源 | 关键结论 | 对 BOH 的用法 |
|---|---|---|
| Baymard 2025 Checkout UX | 平均弃购 70%；可修复原因里「看不到总价/额外费用」40%、「流程太长太复杂」17%、「支付方式不足」9%；平均结算 23.48 个表单元素，理想 12–14 | 结算**不能加字段**，只能重排 + 给默认值。现在的地址手填（4 个控件 + 识别框）正好踩在"太多"那一侧 |
| Stripe《结账流程设计》 | 五段式：购物车 → 配送信息 → 支付 → **订单复核**（商品明细/金额/地址与配送方式/预计送达/优惠税费）→ 确认页（成功状态 + 订单号 + 商品汇总 + 后续流程 + 联系方式） | 复核页与确认页这两段，BOH **两段都缺**；确认页的"后续流程 + 联系方式"正好对应"管理员会联系你"这件事 |
| 国内电商（淘宝/京东/拼多多） | 确认订单页 = 地址卡（可切换）+ 商品清单（图/名/规格/单价×数量）+ 金额明细（右对齐、含运费优惠）+ 备注 + **底部固定**「合计 + 提交订单（带金额）」；提交后进支付 → 结果页（订单号/查看订单/继续逛） | 直接照抄这个骨架，把"优惠券/发票/多商户"砍掉即可 |

**必须裁剪的三处**（照搬会出问题）：
1. **没有在线收款** → 结果页不能说「支付成功」，应说「订单已提交」；现金部分的去向必须写清楚。
2. **没有实时物流** → 不做物流地图/快递轨迹，只做四态时间线 + 单号（有则显示）。
3. **SKU 只有个位数** → 不做分类、筛选、凑单满减、凑单推荐；不做购物车分页。

## 4. 目标流程

```
商品列表 ─→ 商品详情（加购 / 立即购买） ─→ 购物袋（底部固定结算条）
                                              │
                                              ▼
                                    确认订单（全屏 sheet）
                              地址卡 / 商品清单 / 金额明细 / 备注
                                              │  提交订单（按钮带金额）
                                              ▼
                                    结果（订单已提交）
                          已扣积分 · 现金去向 · 后续三步 · 查看订单 / 继续逛
```

### 4.1 确认订单页规格（P0 主体）

**形态**：复用 `ProductDetailSheet` 的容器逻辑 —— 竖屏全屏、横屏居中弹窗（`z-index: 2147482400`）、`captureOrigin` + clip-path 形变进场、`Escape` 关闭、`body.style.overflow` 收口。理由：这是仓库里唯一已经过三档视口验证的弹层形态，另起一套必然要重踩定位/裁剪/滚动的坑。

**分区顺序（自上而下，不可乱）**

| # | 区块 | 内容 | 为什么在这一格 |
|---|---|---|---|
| 1 | 地址卡 | 收件人 + 脱敏电话 + 完整地址 + 「更换 ›」；无地址时是虚线"添加收货地址" | 主流第一格都是地址：它是"能不能收到"的前提 |
| 2 | 商品清单 | 缩略图 + 标题 + 规格 + `单价 × 数量` + 小计；失效商品置灰并标红字 | 用户核对的第一诉求 |
| 3 | 金额明细 | 商品积分 / 现金 / 运费（包邮） / 分隔线 / **应付合计**（右对齐、最大字号） / 「当前余额 X，本单后剩 Y」 | 一次把"付多少"说死，杜绝事后争议 |
| 4 | 备注 | 一行「订单备注（选填）」，未填时是折叠态 | 需要 DB 列，P2 才落地 |
| 5 | 预期说明 | 一行浅色说明："提交后 1 个工作日内管理员会电话联系确认现金部分" | 替代现在藏在商品详情里的那句小字 |
| 6 | 底部固定条 | 左「合计 55 积分 + ¥11.90」／右主按钮「提交订单」 | 滚动不消失；按钮不再叫"确认提交" |

**地址交互（关键改动）**：地址不再是一组输入框，而是「一张卡 + 更换」。点「更换」在**当前 sheet 内**开一个地址选择层（列表单选 + 新增），不再跳到「地址」Tab。地址簿维护仍只在「地址」分区一处，这里只做选择。

**提交前预检（P0 的核心价值）**：进入确认页时立即做四项检查，把失败前置到"看得见"的地方，而不是提交后弹 toast：
1. 积分余额是否够 → 不够：合计条上方红字 +「去赚积分」；
2. 商品是否仍在售 / 可购 → 失效行标红 +「移除失效商品」；
3. 数量是否超库存（若 P2 补了库存校验）；
4. 价格是否与快照一致 → 不一致：「价格已更新，以新价为准」并就地刷新合计。

### 4.2 结果页规格

- 标题从「支付成功」改为 **「订单已提交」**；副标题写明构成：`已扣 55 积分 · 现金 ¥11.90 待确认`。
- 保留现有积分卡翻转动画（它是这个页面最好的部分），但把它降为视觉背景，信息层放在卡下方。
- 必含：订单号（**完整显示 + 点击复制**）、商品摘要（2 件）、收货人一行、**后续三步**（管理员联系 → 确认现金 → 发货，可查订单）、两个出口「查看订单 / 继续逛逛」。
- 邮件发送失败仍就地提示（现有 `emailState` 机制保留）。

### 4.3 购物袋规格

- 底部固定结算条：`合计 + 去结算`，`bottom` 走 `--messages-sab-offset` 同族的安全区与底栏高度（周边页底栏是 `UserSpaceBottomNav`，隐藏时条要跟着让位）。
- 每个行内改为「单价 × 数量 = 小计」，而不是只显示单价。
- 顶部若存在失效商品，出现一条警示条：「2 件商品已下架 · 一键移除」。

## 7. 已知会踩的坑（动工前必读）

1. **不要新建 `/shop/checkout` 路由**。结算必须能中途关掉回到购物袋，路由化会把"返回即丢状态"变成系统性问题，还要接 `probe:route-switch`。用 sheet。
2. **`ProductDetailSheet` 的形态里有两条不能省的实现**：进场 `focus({ preventScroll: true })`（否则键盘/读屏滚动会漏到背后页面）、退场 `keepFinal`（否则 clip 动画在节点移除瞬间弹回全屏）。
3. **`.contact-card` 现在是 `overflow-y: auto` 的一整块**。改成"固定头 + 滚动体 + 固定底"时必须拆成三段 flex，否则底部条会跟着滚。
4. **结算页的 z-index 与灵动岛**：`2147482400` 是既有共识（`ShopPaymentSuccessModal` 文件头有 2026-11-02 踩坑记录），新组件必须同档，低了会被导航岛压住。
5. **地址同步不要顺手改**：现在关闭结算时会 `syncDefaultAddress` 把结算里改的地址写回地址簿默认（`index.vue:685-693`）。换成"选地址"后，**选了什么就是什么，不要反写默认地址** —— 否则用户只是这一单选了另一个地址，默认地址就被悄悄改了。
6. **价格快照问题不能只在 UI 修**：确认页刷新成实时价之后，购物袋列表仍显示旧价，两处必须同一口径（建议进购物袋/进确认页各刷一次 `products`，用 id 对齐）。
7. **库存字段当前是装饰**（服务器不校验不扣减）。UI 上如果开始显示"仅剩 N 件"，必须先落 P2-⑩，否则是自己埋假承诺。
8. ⚠️ **开工前先看工作区**：写这份方案时（2026-11-03）已有并行改动落在周边链路上 —— `OrderDetailSheet.vue` 的取消通知邮件、`supabase/migrations/2026110322_shop_order_progress_notification.sql`、`2026110323_shop_order_progress_mail.sql`（订单进度通知 + 进度邮件）。动结算/订单详情前先 `git diff` 一遍，别把在途改动卷进提交（见 `docs/AI-ENV.md` 并行会话纪律）。
